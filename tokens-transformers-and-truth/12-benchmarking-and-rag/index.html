Benchmarking LLMs & Retrieval-Augmented Generation

How we measure language model quality, why benchmarks break, and how retrieval-augmented generation extends LLMs with external knowledge and tools.

Evaluation and retrieval are two pillars of modern LLM systems: how benchmarks work, why they fail (contamination, saturation, LLM judges), and how RAG and tool use extend models with external data and APIs.

00

Why Evaluation Matters

After pre-training, post-training, and deployment, we need to know: how good is our model? Users have diverse needs — translation, coding, reasoning, creative writing — and we must measure whether the model handles them appropriately.

A benchmark generally consists of three components: data (prompts to feed the model), a metric (how to score responses), and a protocol (decoding settings, pass@K vs pass@1, tool use allowed or not).

Static vs Dynamic Benchmarks

Static benchmarks use a fixed set of prompts. Whenever a new model is released, you generate responses for each prompt and evaluate them with the same metric. Dynamic benchmarks evolve over time — the most prominent example is the Chatbot Arena (now LM Arena), where models are ranked by user preferences on prompts that users submit in real time.

Single Task vs Broad Task Distribution

Single-task benchmarks focus on one capability (translation, summarization) with specialized metrics. Broad task distribution benchmarks collect diverse tasks — like a random sample of real user prompts — to measure general-purpose chatbot quality across many domains.

Key insight: The easier a task is to evaluate automatically, the more attractive it is to benchmark designers. Multiple-choice exams are trivial to score; story generation is subjective and hard. That's why you see far more work on multiple-choice evals than on creative writing evals.

For any new task, a practical workflow is to collect human judgments first, then search for an automatic metric whose scores agree with those labels. As metrics grow more elaborate and tasks more open-ended, the metric itself may need evaluation—often by correlating it again with human ratings. For the most subjective outputs (for example, short-story quality), even careful human protocols struggle: incoherence and grammar errors are easy to agree on, but “creativity” or “enjoyment” rarely yield high inter-annotator agreement.

Human evaluation

High cost in time and money; rubrics for open-ended work are hard to design; agreement can be low on aesthetic or narrative qualities. Still the reference when you need to know whether an automatic scorer is meaningful.

Automatic metrics

Fast and cheap at scale. The goal is correlation with human judgments on the task you care about—not intrinsic “correctness” of the number the script prints.

Reward models as evaluators: Reusing a reward model trained on preference data to rank benchmark outputs is tempting because it mirrors post-training. In practice, scores are hard to interpret (what does a 0.5-point gap mean?), and the same failure modes as training appear at test time—reward hacking and mismatch between the latent objective and the construct you wanted to measure. Goodhart’s Law applies in force once the reward becomes both training target and leaderboard score. Benchmarks still favor agreement-heavy, task-specific signals—exact match, unit tests, or validated rubrics—over a single monolithic reward.

01

Types of Benchmarks

Benchmarks span a spectrum from easy to evaluate (multiple choice, code with unit tests) to hard to evaluate (long-form writing, story generation). They also vary in how automatable the evaluation is.

Benchmarks cluster by how answers are scored: multiple-choice suites (MMLU, GPQA), executable code with pass@1 vs pass@K (HumanEval), numeric or exact-match math (GSM8K), reference-based text metrics (BLEU, ROUGE for translation and summarization), and open-ended chat judged by humans or LLMs (MT-Bench, Chatbot Arena). Frontier models have largely saturated many static MCQ and code suites; static prompts also face contamination risk once they circulate widely.

Two Axes: Task Open-Endedness vs. Automatability

A useful mental model plots how open-ended the output is against how easily evaluation can be automated. In one corner sit multiple-choice suites like MMLU and many GPQA-style items: constrained outputs, crisp correctness. Nearby, machine translation with BLEU is still relatively automatable even though the linguistic task is richer than picking A–D.

Toward the middle, benchmarks like MT-Bench and EQ-Bench ask for paragraphs of reasoning or fiction; automation usually means an LLM judge or pairwise preference model, with all the biases that come with it. In another corner, Chatbot Arena is dynamic and human-driven—slow, expensive, but not reducible to a single closed-form score. Agentic and tool-heavy tasks push even farther: evaluation may require long horizons, environment interaction, or subjective review of entire workflows.

High automatability, constrained output

MMLU-style MCQ, many code benchmarks with unit tests, reference-based MT metrics when references exist.

Lower automatability, open generation

Creative writing rubrics (EQ-Bench), pairwise chat judging (MT-Bench), arena Elo from humans, emerging agent evals.

Protocol Considerations

Benchmark designers must specify: decoding hyperparameters (temperature, top-p), reasoning budget (how many tokens the model can use for chain-of-thought), system prompt (standardized or minimal to avoid prompt tuning), and tool use (allowed or forbidden). Comparing a model with 20K reasoning tokens to one with zero is unfair.

Protocols increasingly spell out whether models may call search, code execution, calculators, or corporate knowledge bases. A “closed book” leaderboard entry is not comparable to a stack that shells out to compilers and browsers. As products blend retrieval, tools, and memory, the benchmark’s environment contract matters as much as the raw prompts.

02

Contamination and Data Leakage

Data contamination occurs when a model is trained on benchmark data — directly or indirectly. If the test set appears in the pre-training corpus, SFT data, or RL data, scores become inflated. The benchmark no longer measures capability; it measures memorization.

Closed-source models have no transparency. Developers have every incentive to train on as many benchmarks as possible to juice numbers. One analysis took popular benchmarks, created new test examples with the same format and difficulty, and re-evaluated saturated models. Some dropped from 90% on the public benchmark to 30% on the fresh set — strong evidence of contamination.

Mitigation Strategies

Benchmark authors use canary strings — unique identifiers embedded in the data so training corpora can filter them out. They request that examples not be published in plain text. But with static benchmarks, the prompts and answers are eventually exposed. The robust solution is dynamic or interactive benchmarks where prompts change every time — like the Chatbot Arena.

GPQA’s authors explicitly asked teams not to redistribute items verbatim and embedded canary text to make leakage easier to detect. Partial mitigations—publishing prompts without answers behind a submission API—still leak over time through reverse engineering and distillation. Closed training stacks make external auditing nearly impossible, which is why held-out isomorphs of public benchmarks (same format and difficulty distribution, new items) have become a blunt instrument for spotting memorization.

Goodhart's Law: "When a measure becomes a target, it ceases to be a good measure." If we train models to maximize benchmark scores, those scores no longer reflect true capability. This is why using reward models for evaluation is risky — they're the same targets we optimized during RL.

03

LLM-as-Judge Evaluation

For open-ended tasks — creative writing, essays, multi-turn dialogue — there's no reference output. LLM-as-judge uses another LLM to score or compare responses. EQ-Bench grades stories on rubrics (instruction adherence, emotional complexity, etc.); MT-Bench uses pairwise comparisons: "Which response is better, A or B?"

Problems with LLM Judges

LLM judges share biases with reward models: they prefer longer responses, and they often prefer responses from their own model family. GPT-5 may rate GPT-5 stories higher than Gemini's. Judges may not be deterministic — sampling can yield different scores. And there's no guarantee the judge correlates with human preferences; many benchmarks don't validate against human judgments at all.

Rubric-heavy setups like EQ-Bench ask a judge model to narrate strengths and weaknesses, then assign sub-scores (for example, instruction following versus emotional depth). Some implementations re-sample the judge several times per item and average—stability of the number does not imply the number is right, only that the judge is self-consistent. Auxiliary “slop” diagnostics (repeated phrases across generations) highlight stylistic tics but are still heuristic.

MT-Bench-style tasks often pair a multiple-choice or short stem with a follow-up that demands paragraphs; a strong model judges pairwise which assistant answer is better. The same length and vendor biases appear, so leaderboard shifts can track judge upgrades as much as true quality gains.

Judge churn: When the state of the art moves, teams face an expensive choice: re-score everything with a new judge or leave historical numbers incomparable. Ensemble judges from multiple families reduce self-preference but raise cost and complexity—and still do not replace human calibration on the task you care about.

Human Evaluation Challenges

Human eval is expensive and slow. For highly subjective tasks (e.g., "how enjoyable is this story?"), even humans disagree. It's hard to design a rubric that yields high inter-annotator agreement. Automatic metrics are fast and cheap but must be validated against human judgments when possible.

Reality check: Many researchers at frontier labs say they don't rely on these metrics during development. They use "vibes" — reading a few responses and deciding if the model feels better. Benchmarking is in a rough state: contamination, LLM judges no one can verify, and tasks that don't reflect real usage.

Aggregator analyses plot how long a median human would need to solve tasks drawn from many public suites — from minutes for standard math items to hours for competition-style problems. Similar tracks order software-engineering tasks from quick lookups to multi-hour projects. These views help visualize how scattered leaderboard points compose into capability over time; they are not substitutes for careful task validation.

04

Retrieval-Augmented Generation (RAG)

RAG (retrieval-augmented generation) augments a frozen LLM with external information. The term crystallized in industry research circles (Meta/Facebook-era work; later popularized broadly) for the pattern: keep a strong general model fixed, and change what it reads at inference time. Given a prompt, you retrieve the top-K most relevant documents from a data store, concatenate them to the prompt, and generate. By default the base weights are untouched; the knowledge arrives through context.

In practice, teams often still add supervised fine-tuning examples where the input includes retrieved passages and the target shows faithful use of those passages—so the model learns formatting, citation habits, and refusal behavior when evidence is missing. That hybrid is still “RAG” at deployment if retrieval supplies the live facts.

Given prompt X → Retrieve top-K docs (z₁, z₂, ..., zₖ) → Generate Y from P_θ(Y | X, z₁, ..., zₖ)

Why Use RAG?

Knowledge cutoff: Models are trained on data up to some date. RAG lets you inject fresh information — news, quarterly reports, new documentation. Proprietary data: Your internal documents aren't in the training set. RAG lets the model operate over them. Attribution: You can encourage the model to cite retrieved documents, linking generated text to sources. Reduce hallucinations: Grounding in retrieved docs can help, though it's not guaranteed — the model can still misinterpret or ignore them.

Knowledge Conflicts

If retrieved documents conflict with what the model memorized during pre-training, behavior is unpredictable. Sometimes the model overrides its parameters with the document; sometimes it ignores the document. There's no reliable schema for handling this. Knowledge editing and model unlearning are active research areas.

Real deployments hit this when world facts change—leadership titles, product names, scientific consensus—and the model’s parametric prior is “sticky.” Retrieval can nudge answers, but strong memorized associations may not disappear without retraining. Unlearning remains unreliable: models may suppress one phrasing of a fact while retaining paraphrases, and there is no clean map from parameters to individual assertions.

Inference cost: Concatenating dozens of long chunks blows up prompt tokens, latency, and spend. The defense is task-dependent: if the answer truly is not in weights, you pay for context or you fail silently. When the corpus is small enough to fit entirely in-window, brute-force “no retrieval” can beat a brittle retriever—bad retrieval often hurts more than it helps.

Web search as retrieval

Issuing the user query to a search API and stuffing top results into the prompt is a strong baseline for public information: ranking is outsourced to the search engine. You pay per query and inherit policy constraints.

Private vector store

Required when documents are proprietary or offline. You own indexing, embedding refresh, and security—but must fund approximate nearest-neighbor infrastructure yourself.

05

Dense vs Sparse Retrieval

Retrieval means measuring similarity between the prompt and documents. Two main approaches: sparse (string matching) and dense (vector embeddings).

Sparse Retrieval: BM25

BM25 is a phrase-matching algorithm that upweights important words and downweights frequent ones. It's cheap and effective when texts are long and share keywords. Cons: No semantic similarity — "car" and "automobile" don't match. Paraphrases fail. It assumes relevance requires string overlap, which isn't always true.

Dense Retrieval: Vector Database

Use a pre-trained encoder (Transformer encoder blocks with bidirectional attention) to map text to a fixed vector—often the final-layer [CLS] state or a mean pool over tokens. Embed the prompt and every chunk in the corpus. Score candidates with dot product or cosine similarity; retrieve the K nearest neighbors. Exact brute-force search over billions of vectors is usually intractable, so production systems rely on approximate nearest neighbors; Faiss is the de facto library family for GPU/CPU ANN at scale.

A plain BERT-style encoder trained only for masked-language modeling yields embeddings that reflect similarity more than query relevance. Retrieval pipelines therefore fine-tune on query–document pairs—often contrastive objectives that push matching pairs together and negatives apart—so inner products align with human judgments about whether a passage answers a question.

Store: one embedding per chunk (typ. 1024–2048 dims) × corpus size → TB-scale indices that live on disk/CPU tiers, not entirely in GPU HBM

Empirically, if cost were ignored, stuffing more retrieved text often helps up to the point where at least one chunk contains the answer—attention over long contexts can surface a needle—but noise, contradictions, and context limits eventually bite.

Chunking

Long documents exceed the encoder's max length. Chunking splits documents into smaller pieces, each embedded separately. Chunking loses context — a chunk in isolation may be ambiguous. Chunk size and overlap are hyperparameters.

RAG Failure Modes

Poor retrieval: If none of the top-K docs is relevant, RAG can perform worse than no retrieval — irrelevant text may overwrite correct parametric knowledge. Information loss: Squeezing a document into one vector loses detail. Inference cost: More retrieved chunks mean longer prompts and higher cost. We don't know what the model has memorized, so we don't know when retrieval helps versus hurts. For open-web facts, search-engine ranking plus snippet injection is often strong; proprietary corpora require your own index — and hybrid stacks may query both.

06

Tool Use and Function Calling

Tool use generalizes RAG. Instead of retrieval happening once before generation, the model can call tools during generation. The model produces special tokens indicating a tool call (name + arguments); the tool runs; the result is fed back; the model continues generating.

Toolformer was an early paper showing that a fine-tuned LLM could autonomously decide when to call APIs — a QA system, calculator, Wikipedia search, machine translation. The model generates <tool>calculator(400/400)</tool>; the calculator returns "1.0"; that replaces the tool call; the model continues with "out of 400 participants..."

Training used a bootstrap: sample model completions, execute candidate tool spans, and keep trajectories where tool use lowered perplexity on the ground-truth continuation versus a no-tool baseline. Fine-tuning on those successes teaches when invoking an API helps—an empirical substitute for hand-writing thousands of rules.

At decode time a streaming parser watches partial text. As soon as a tool call is syntactically complete, the runtime executes it, splices the observation back into the token stream, and lets the LM continue—execution is interleaved with generation rather than deferred to the end of the passage.

RAG vs Tool Use

In vanilla RAG, retrieval happens once, before generation. The LLM doesn't control when to retrieve. In tool use, the model decides when to call a tool — including retrieval — and can do so multiple times. Tool use is a step toward agents: LLMs with dynamic control flow, multiple tool calls, and state that evolves over many steps.

Parametric vs non-parametric knowledge: Parametric knowledge is encoded in the model's parameters (from pre-training and post-training). Non-parametric knowledge lives in external documents. The challenge: we don't know what's in parametric memory, so we don't know when the model needs to retrieve.

From Tool Loops to Agents

Tool-augmented decoding still imagines a mostly linear path: one forward pass (with tool insertions) yields the user-visible answer. Agents add dynamic control flow: multiple LLM calls, branching on observations, mutable environment state, and no fixed cap on steps until a halting condition triggers. Informally, some researchers describe agents as “LLMs in a for-loop” with a planner/controller deciding which tool fires next; others stress that any coupling between a model and the outside world counts, making even one-shot RAG a minimal agent under the broadest definition.

Evaluation cliff: Once systems write code, browse, file tickets, or draft papers end-to-end, benchmarks inherit all the pathologies of LLM scoring plus environment non-stationarity, tool latency, and ethical cost (for example, flooding human reviewers with synthetic submissions). The measurement problem scales with the system’s freedom.

Vanilla RAG pipeline

Retrieve once, prepend chunks, generate once. The model does not choose retrieval timing; orchestration is external.

Tool use & agents

The LM emits tool calls mid-stream (search, calculators, SQL, browsers) and may loop: observe → replan → act until done.

RAG vs Fine-Tuning: When to Use Which

Both RAG and fine-tuning extend an LLM with new knowledge. The choice depends on your constraints and goals.

RAG vs Fine-tuning Decision Tree

Use RAG when

  • ✓ Data changes frequently (news, docs)
  • ✓ Proprietary or internal documents
  • ✓ You need attribution to sources
  • ✓ You can't retrain (cost, time)
  • ✓ Knowledge is large and external

Use Fine-tuning when

  • ● Data is stable and well-curated
  • ● You need consistent behavior
  • ● Retrieval would be unreliable
  • ● You have compute for training
  • ● Knowledge fits in parameters
