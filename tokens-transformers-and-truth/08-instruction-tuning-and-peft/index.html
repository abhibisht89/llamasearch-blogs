Instruction Tuning & Parameter-Efficient Fine-Tuning

From pre-trained next-word predictors to instruction-following models — and how to fine-tune them efficiently without billions of parameters.

Pre-trained language models excel at predicting the next token — but they often fail to follow explicit instructions. This chapter covers supervised fine-tuning (SFT) for instruction following, chat templates and special tokens, and parameter-efficient methods like LoRA and QLoRA that let you adapt large models on consumer hardware.

00

From Pre-Training to Instruction Following

Pre-training produces a model optimized for next-word prediction on massive text corpora. The result is a strong language model — but not one that reliably follows instructions. Sometimes it ignores prompts entirely; other times it follows them but adds unwanted behavior. The pre-training data rarely contains explicit instruction–response pairs, so the model has never learned that format.

The goal of post-training is to bridge this gap: take a pre-trained model and make it follow user instructions better. A sub-goal is alignment — making the model behave in ways consistent with human values, including safety. Alignment is not a solved engineering problem: there is an inherent trade-off between helpfulness (answering usefully) and harmlessness (refusing harmful requests). Over-censoring can cause false refusals on benign queries; under-censoring risks harmful outputs.

What pre-training optimizes

Pre-training pushes training loss down on huge web-scale corpora. Scaling laws tell us that larger models and more data tend to predict held-out text better. The artifact is a strong next-token predictor that has absorbed grammar, some reasoning, and factual associations — but not a supervised mapping from arbitrary natural-language instructions to user-intended completions.

What post-training adds

Post-training reshapes behavior on smaller, curated data: instruction–response pairs, preference rankings, safety policies, and task mixtures. The objective is no longer “predict the next token of Wikipedia” but “produce outputs that match how humans want the system to respond,” including refusals, tone, and format — while reusing the linguistic competence frozen into the base weights.

01

The Post-Training Pipeline

As sketched above and in prior chapters, post-training runs pre-training → instruction tuning (SFT) → RL alignment on the same architecture. The pipeline visualizer walks through those stages; the sections below focus on instruction tuning and parameter-efficient adaptation.

Steps 2 and 3 are often repeated in production. If a model underperforms on a specific task, teams collect targeted data and re-run SFT or RL. The risk is catastrophic forgetting — improving one capability can degrade others — so broad evaluation is essential.

Regression is task-local but evaluation must be global. Extra SFT on one skill may improve that slice while unrelated capabilities slip — the optimizer only optimizes what you measure. Production teams run broad eval suites after every targeted fix: coding, reasoning, safety, multilingual quality, and long-context behavior, not only the skill that triggered the patch.

Instruction-formatted data is expensive to obtain at quality. Leading labs spend on the order of hundreds of millions of dollars on annotation, contractor workflows, and tooling. They also use their own models to synthesize new instruction–response pairs and filter or revise them — scaling coverage while introducing new risks (bias amplification, “model teaching model” loops). Data strategy for step 2 is as active a research and engineering area as algorithm design.

How industrial post-training teams actually spend time: Much of the work is diagnosing failure modes on internal and public benchmarks, commissioning data for the worst buckets, re-running SFT or preference-based RL, and proving via regression testing that the rest of the surface did not collapse. The three-step diagram is a conceptual spine; the operational reality is a long tail of iterations merged, split, or interleaved per product.

02

Supervised Fine-Tuning (SFT)

Task-Specific Fine-Tuning

In the simplest case, you take a pre-trained model and collect a dataset of input–output pairs for a single task. For example: "127 + 13" → "140". You train the model to minimize negative log likelihood on the output tokens only. The input tokens are visible (prefix LM mask) but you do not compute loss on them.

Task-only pairs (narrow SFT)

The string on the left is whatever the task defines — digits for addition, a French sentence for translation, a review for sentiment. There need not be a natural-language instruction; the model is not learning “when I say add, sum the numbers,” only the input–output mapping you supervise. That differs from chat-style usage, where the user expresses intent in free text.

Same mechanics as pre-training

Optimization is still next-token prediction with a causal backbone, but the data are paired demonstrations and the mask skips loss on the conditioning prefix. Weights start from a capable base model rather than random initialization — hence fine-tuning: you expect small updates to specialize behavior, not to learn language from scratch.

During pre-training we use a diagonal (causal) mask because we predict every token. During SFT we assume the prompt is given — we are not generating it. So we use a prefix LM mask: prompt tokens can attend to all other prompt tokens (no masking among them), but we only predict and compute loss on the response tokens. The setup is the same as pre-training except: (1) different data, (2) prefix LM mask so the model sees the full prompt, and (3) parameters are initialized from the pre-trained model, not randomly.

If you omit the prefix-style treatment of the prompt, the model may still be trained to predict the next token of the prompt itself. For many short prompts the effect is minor. But when the prompt is enormous (e.g., “Is this claim true?” followed by a full book), the token count of the prefix dominates the loss — gradients emphasize next-token prediction over the document instead of the single-token or short answer you care about. Prefix masking and loss masking on the response are how we keep supervision aligned with deployment, where the user supplies the prefix and the model only generates the completion.

Usually no. Standard supervised fine-tuning trains only on the new paired data. You are not interleaving trillions of web tokens unless you explicitly design a hybrid stage. An important exception is continual pre-training — for example, to extend context length by training on longer documents — which is distinct from instruction SFT but sometimes stacked in a long production recipe.

Pre-training corpora include textbooks, tutorials, and parallel text, so base models often show some skill on patterns like arithmetic or translation without task-specific SFT. Fine-tuning still matters when you need reliability, a particular output format, or behavior that is rare in raw crawl data. Empirically, specialized data moves the distribution of outputs far more than prompting alone for many products.

Why SFT Is Needed

Pre-trained models predict the next word. They are not optimized to interpret "add these two numbers" as an instruction and produce the sum. Instruction tuning teaches the model to map instructions to desired outputs. Without it, you get a next-word predictor that may or may not follow what you asked.

Instruction Tuning: General-Purpose Chatbots

For a general-purpose chatbot, you need instruction tuning — SFT with a diverse set of tasks. The data format is: instruction + optional input context + output. The instruction differentiates tasks: "add these numbers" vs. "summarize this book" vs. "write Python code for homework 2." Datasets like Tulu 3 contain millions of such examples.

Tulu 3 (Allen Institute for AI) is one public example at scale on Hugging Face: on the order of a million instruction-following examples spanning summarization, coding, multilingual prompts, and multi-turn threads. Rows often pair a user message with an assistant reply under a fixed template — the same structural idea as production chat APIs, so the model learns both what to say and how turns are delimited in tokens.

At the architecture level, instruction and optional context are concatenated (with role tags) into one token sequence the transformer processes like any other input. The tripartite split is a dataset convention for collectors and trainers; the network does not need a special head that detects which span is “instruction” versus “payload.” Everything left of the assistant’s completion is conditioning; loss is typically on the assistant’s tokens only.

SFT Data: Human vs. AI-Generated

Instruction–response pairs can be human-written or AI-generated (e.g., from a stronger model). Both are used. Human labeling is expensive; synthetic data scales but can inherit model biases.

Quality vs. Quantity: The LIMA Finding

The LIMA paper showed that "less is more" — a small, high-quality dataset can outperform a large, noisy one. Quality of instruction-tuning data matters more than raw quantity. Curating clean, diverse, well-formatted examples often beats scaling up indiscriminately.

Loss = −(1/T) · Σᵢ log P(wᵢ | prompt, w₁, ..., wᵢ₋₁)    (output tokens only)

Catastrophic forgetting: Fine-tuning heavily on one task can erase abilities learned during pre-training. For single-task optimization this may be acceptable. For general-purpose models, use diverse instruction data and monitor performance across tasks.

Reinforcement-learning stages (covered later in a full curriculum) often ingest human preference data: annotators compare two or more model completions for the same prompt and mark which better matches policy — helpfulness, safety, verbosity, or brand tone. Those rankings train a reward model or feed policy-gradient updates so the system moves toward preferred outputs without explicit gold text for every comparison. SFT still matters because RL alone on weak bases is unstable; a strong instruction-tuned policy is the usual starting point.

03

Chat Templates and Special Tokens

Instruction-tuning data is often formatted with roles: system, user, and assistant. These are encoded via special tokens — e.g., <user>, </user>, <assistant>, </assistant>. Different models use different chat templates. Using the wrong template can cause strange behavior — this is a common source of SFT errors.

Chat templates also teach the model the format of responses. Stylistic quirks (e.g., "Certainly!" or em-dashes) often come from patterns in the instruction-tuning data. Whatever is in the data has a large impact on behavior.

Replicating style is feature, not noise. If many gold responses in SFT begin with enthusiastic acknowledgements or favor em-dashes because annotators or upstream models wrote that way, the tuned model will imitate those tics at inference. This is one reason harmonizing labeling guidelines across vendors matters: unconscious stylistic drift in training data becomes user-visible personality.

Parameter-Efficient Fine-Tuning (PEFT)

Full fine-tuning updates all parameters. For a 40B model, that means loading billions of parameters, computing gradients for all of them, and storing the updated weights. Memory and compute costs are prohibitive for most users. PEFT reduces the number of parameters adjusted during fine-tuning.

Scale makes the pain universal. At hundreds of billions of parameters, even a “small” instruction dataset does not help if you cannot fit activations and optimizer states for full updates in GPU memory. Frontier labs face the same arithmetic as hobbyists — only their cluster sizes differ. PEFT and quantization are parallel levers: the former shrinks the set of trainable scalars; the latter shrinks the footprint of the frozen base.

Prompting (Zero Parameters)

The simplest approach: no training. Control behavior by modifying the prompt — e.g., adding few-shot examples. This works for simple tasks but fails for complex ones and typically requires very large pre-trained models. Users must craft prompts carefully; there is no single "best" prompt that generalizes.

Deployment friction. If only a brittle, hand-tuned prompt makes addition work, every end user would need to paste that exact scaffold — an unacceptable product experience. The business goal is natural task descriptions without secret prefixes. Prompt engineering on a frozen base is a diagnostic and prototyping tool; instruction tuning exists so ordinary prompts suffice after adaptation.

Prompt Tuning / Prefix Tuning

Freeze the entire pre-trained model. Add a small number of learnable soft tokens (embeddings not in the vocabulary) prepended to every input. Only these embeddings are updated. The intuition: instead of searching for the optimal prompt in natural language, let the model learn it. Surprisingly, this works — and works better with larger pre-trained models. Common choices: 1, 5, or 10 soft tokens. The model still needs to run full forward and backward passes (no compute savings), but you only store and share the tiny set of new embeddings.

Prefix tuning (Li & Liang, 2021) names a closely related family of methods that also prepends trainable activations, but it is not identical line-for-line to the prompt tuning setup emphasized here (learned input embeddings with a frozen transformer, as in Lester et al.). Vendor codebases may label hooks differently; the implementation details matter when reproducing numbers.

Einew = Eiold − η · ∂L/∂Ei    (only for soft-prompt parameters E; transformer blocks frozen)

The loss is summed over all supervised output tokens, and back-propagation flows through the entire depth of the frozen network. By the chain rule you still materialize intermediate gradients in the stack; what changes is the optimizer step: it applies updates only to the soft prompt vectors (and optionally a small head), not to attention or MLP weights. Savings are in checkpoint size and versioning — you email megabytes of embeddings, not gigabytes of altered layers — not in wall-clock FLOPs per step.

Prompt tuning (soft prefixes)

Trainable vectors sit at the bottom of the stack and influence every layer through depth. Empirically, that global routing can beat freezing everything except the topmost layer on some benchmarks, because shallow readouts cannot remix lower representations as flexibly. The price is a full backward pass through all blocks each iteration.

Last-layer fine-tuning

Updating only the final linear layer (or a thin head) allows gradients to stop early during back-propagation, which can reduce activation memory and engineering complexity. It is more destructive to the generality of the base model than prompt tuning because you are directly rewriting the logits interface — but for narrow classification heads it remains a baseline worth measuring.

Because backbone weights stay fixed, prompt tuning tends to preserve most pre-training skills relative to full fine-tuning, which can overwrite weights and damage unrelated tasks. The soft embeddings are not interpretable tokens; researchers sometimes nearest-neighbor them into vocabulary space and find directions correlated with the target task, but the optimization remains a black box in partial derivatives of a high-dimensional loss.

Hyperparameter: The count of soft tokens is not fixed at two — that was only a schematic example. Papers often sweep 1, 5, or 10 vectors; gains tend to saturate (beyond roughly ten on many tasks) because a small basis already spans a useful subspace for the adaptation.

Adapters

Small trainable modules inserted into transformer blocks. The base model stays frozen; only the adapter parameters are updated. Adapters add parameters but are more expressive than prompt tuning.

LoRA (Low-Rank Adaptation)

The most popular PEFT method. Instead of updating a full weight matrix W, LoRA learns a low-rank update: ΔW = B·A, where A is m×r and B is r×n, with r ≪ m, n. Only A and B are trained; W is frozen. At inference, you can merge W + B·A into a single matrix — no extra latency. LoRA is applied to projection matrices (e.g., WQ, WK, WV, WO) in attention; feed-forward and embeddings are often left frozen. Performance is close to full fine-tuning with a fraction of the parameters.

LoRA Deep Dive

Consider a linear layer: h = f(W·x), where W is m×n. Full fine-tuning updates W. For LoRA, we keep W frozen and add:

h = f((W + B·A) · x)    where A ∈ ℝ^{n×r}, B ∈ ℝ^{m×r}, r ≪ m, n

Full fine-tuning stores and differentiates a dense update of the same shape as W. Writing η for the learning rate,

Wnew = Wold − η · ∂L/∂W    with ∂L/∂W ∈ ℝ^{m×n} (optimizer states add further memory on top)

LoRA instead accumulates changes in low-rank factors. Only ∂L/∂A and ∂L/∂B are formed for the adaptation parameters; Wpretrained stays constant in the update rule. The matrices A and B are far smaller than W when r ≪ min(m, n), so optimizer memory for the trainable subset drops accordingly.

The forward pass still forms an m×n contribution from the low-rank product (or an equivalent sequence of two small matrix multiplies). The win is in how many independent trainable scalars you keep and differentiate — storing and checkpointing A and B instead of a full dense ΔW. You pay the fused multiply at inference once after merging into a single weight matrix.

The product B·A is m×n — same shape as W — but we only store A and B, which have m·r + n·r parameters. For r = 8 and m = n = 1024, that's 16,384 vs. 1,048,576 — a 64× reduction. The rank r is a hyperparameter (typically 4, 8, or 12). We apply LoRA to each target weight matrix (e.g., WQ, WK, WV) and learn separate A and B per layer.

At training time: compute gradients for A and B only; W stays frozen. At inference time: compute W_final = W + B·A and use it as a single matrix. No extra compute or latency. To share a fine-tuned model, send only the A and B matrices; recipients merge them with their copy of the base model.

QLoRA: Quantized LoRA

LoRA reduces trainable parameters, but you still need to load the full base model W in memory. QLoRA combines LoRA with quantization: store the base weights in 4-bit (or 8-bit) integers instead of floating point. This reduces memory footprint significantly, allowing fine-tuning of larger models on consumer GPUs.

Quantization Intuition

Model weights are typically float32 or float16. Quantization maps them to a smaller set of discrete values (e.g., 4-bit → 16 possible values per parameter). A simple approach: compute min and max over the weights, divide the range into bins, and round each weight to the nearest bin. Dequantization: multiply by a scale factor and add a zero-point to recover approximate float values. Some precision is lost, but storage drops by 4–8×.

For 4-bit quantization: scale s = (max − min) / 15, zero-point z = round(−min / s). To quantize: q = round(x / s) + z. To dequantize: x ≈ (q − z) · s. Recovered values will have some error compared to the original floats — the trade-off is smaller memory footprint for slightly degraded precision.

Outliers break naive min–max buckets. Real weight tensors contain extreme values that stretch the scale s and waste most of the 16 4-bit codes on empty range. Production quantizers (GPTQ, AWQ, NF4, and others) use per-channel scales, outlier clipping, or learned codebooks. The affine walkthrough below is for intuition only.

Worked example (symmetric-ish affine 4-bit). Take a tiny “layer slice” vector x = (−1.0, 0.5, 2.0). Then min = −1, max = 2, and with 16 distinct unsigned codes 0…15 the bin width is

s = (xmax − xmin) / 15 = 3 / 15 = 0.2

Choose an integer zero-point z = round(−xmin / s) = round(5) = 5 so that values near zero map near the middle of the code range. Quantize each entry with q = round(x / s + z), clamped to [0, 15]:

(−1.0, 0.5, 2.0) → (0, 8, 15)    after rounding

Dequantize with x̂ = (q − z) · s: you recover −1.0 and 2.0 exactly in this toy case, while 0.5 becomes 0.6 because the grid step is 0.2. That single-step error is the precision cost you accept for an 8× narrower storage footprint versus float32 (and larger savings when kernels pack sub-byte).

Larger models tend to tolerate quantization better than smaller ones. Many downloadable models today are offered in 4-bit or 8-bit quantized form and work well in practice.

Quantize: q = round(x / s) + z    |    Dequantize: x ≈ (q - z) · s

LoRA + quantization (QLoRA): Even after adapters train in low precision, the base weights must still reside in device memory during adaptation unless the implementation streams layers. Quantization attacks that bottleneck; LoRA attacks the count of changing parameters. Together they are what make single-GPU adaptation of multi-billion-parameter bases practical in many notebooks.

07

Full Fine-Tuning vs. PEFT: When to Use Which

Full fine-tuning is best when you have ample compute, want maximum performance, and can afford to store and distribute full model checkpoints. Prompt tuning is cheapest (few parameters, no training of base model) but weakest for complex tasks. LoRA is the practical default: near full fine-tuning performance, minimal storage for updates, and easy to merge at inference. QLoRA extends LoRA when memory is the bottleneck — quantize the base model, train LoRA adapters, and fine-tune on a single GPU.

Full SFT

Updates every weight; best ceiling when data and compute allow. Checkpoint size equals the base model; multi-tenant serving needs separate full copies per specialization unless you externalize adapters anyway.

LoRA / QLoRA

Trains low-rank residuals on selected projections (commonly WQ, WK, WV, sometimes WO); FFN and embeddings often frozen in default configs. Ships as small adapter files merged at load time. QLoRA quantizes the frozen base to shrink VRAM.

Prompt tuning only

Tiny trainable footprint and strong retention of base capabilities, but limited expressivity on hard tasks. Backward still traverses the full depth; savings are about what you save and share, not FLOPs.
