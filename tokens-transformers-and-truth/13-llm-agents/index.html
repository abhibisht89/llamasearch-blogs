LLM Agents: From Tool Use to Autonomous Systems

How large language models break complex tasks into subtasks, use tools, and iterate until goals are met — from coding assistants to research agents and beyond.

An LLM agent is a multi-turn system that observes its environment, reasons about what to do next, takes actions via tool calls or worker models, and repeats until the task is complete. This tutorial covers the agent loop, ReAct, tool use, agent architectures, memory systems, coding and research agents, benchmarks, and how to train agents with reinforcement learning.

00

What is an LLM Agent?

An LLM agent is a system that uses a large language model to accomplish tasks by breaking them into smaller subtasks, executing those subtasks through tool calls or calls to other LLMs, and iterating until a goal condition is satisfied.

An agent is multi-turn, decomposes tasks, executes via tools or workers, and loops until done.

Key Properties

Agents differ from simple one-shot LLM calls in several ways. They are multi-turn: the model engages in many back-and-forth interactions with the environment. They decompose the input task into smaller subtasks, each of which may be executed by a tool call (e.g., calculator, search API) or by another LLM worker (e.g., "summarize this document"). The agent runs in a loop until some goal condition is hit — for example, "I have all the information to craft the final response" or "all unit tests pass." The loop can also be terminated by a budget (e.g., maximum cost or token limit).

Agents are typically implemented using reasoning models. The model receives a prompt, does some internal reasoning (often chain-of-thought style), formulates a plan, and then farms off subtasks to workers or tools. Critically, the plan can be revised based on intermediate results — if a search returns nothing useful, the agent might decide to try a different query or approach.

Key insight: The agent-environment interface is central. The agent observes the current state (e.g., search results, file contents, screenshots), decides what action to take, and the environment updates in response. This feedback loop is what makes agents adaptive and powerful.

Termination (typical): goal_satisfied ∨ budget_exhausted — the controller judges sufficiency (information gathered, tests passed, deliverable ready) unless a user cap on cost, tokens, or wall-clock time ends the run first.

The controller model typically judges whether the goal is satisfied — using prompt criteria and accumulated evidence (tool outputs, file diffs, test logs, screenshots). An orchestration layer enforces hard stops (max steps, disallowed tools, sandbox timeouts). Soft judgment and hard safety rails work together.

RAG vs. Tool Use: The Foundation

Retrieval Augmented Generation (RAG) — see Chapter 12 — follows a fixed retrieve-then-generate pipeline with no feedback loop. Agents generalize beyond that pattern.

Tool use lets the model call a diverse set of tools — calculator, search API, code executor, or any API — at any point during generation, not only at the start. Valid tool calls are detected via special tokens, executed immediately, and their outputs are appended to context. The Tool Former paper established this pattern; modern agents refine it with richer orchestration.

Many production systems evolved from static RAG toward research-style agents that retrieve dynamically: read a page, notice a gap, issue a new query, branch to a related entity, then synthesize. Deep research products signal many retrieval and summarization hops — often tens of minutes of wall-clock time — rather than a single retrieve-then-answer pass.

Design takeaway: Tool definitions belong in the prompt (system or user): natural-language descriptions of each tool’s purpose, arguments, and return shape. Tool Former additionally trained models to emit valid calls; many shipping systems today rely on strong prompting plus inference-time parsing, but the pattern — expose capabilities in text, stream generations, detect a complete call, execute, append results — is the same.

RAG

Fixed one-turn: retrieve → generate. No feedback loop. The model cannot decide when to retrieve or try alternative strategies.

Tool Use / Agents

Dynamic multi-turn: the model can call tools at any point, observe results, and iterate. Enables iterative search, summarization, and complex workflows.

Production agents typically hide intermediate tool calls — the user sees only the synthesized answer. Research setups and some UIs (including the Tool Former paper) may show calls and results inline. When the model emits a complete, valid tool invocation, a runtime supervisor executes it and appends the observation (stdout, JSON, page text) to context; whether the raw call string stays visible is a product choice.

02

The Agent Loop: Observe → Think → Act

The core loop of any agent follows a simple pattern: observe the current state, think about what to do next, act (issue a tool call or delegate to a worker), then observe the result and repeat. This continues until the agent decides the goal is satisfied or a budget is exhausted.

Observe → Think → Act → Observe → Think → Act → ... → Done

At each step, the controller LLM receives the full context: the original prompt, any previous tool outputs, and the current environment state. It reasons (often using "thinking" tokens that are hidden from the user), produces an action (e.g., run a terminal command, search the web, call a summarization worker), and the action is executed. The result is fed back into the context, and the loop continues.

Cost and depth: When “tools” are themselves full LLM calls (summarize this PDF, extract a schema, draft a patch), each hop is a billed forward pass. Deep trees of controller → workers → sub-workers can consume millions of tokens on a single user task (e.g., building or refactoring a whole site). Latency grows with depth because steps are often sequential.

03

ReAct: Reasoning + Acting

ReAct is a framework that interleaves reasoning (chain-of-thought) with acting (tool use). Instead of reasoning in isolation and then acting, the model alternates between thinking out loud and taking actions. Each action produces an observation from the environment, which informs the next thought.

The trace looks like: Thought → Action → Observation → Thought → Action → Observation → ... → Final Answer. This interleaving helps the model ground its reasoning in real observations and avoid hallucinating facts.

04

Tool Use and Tool Definitions

The starting point for any agent is defining the tools it can use. Tools are typically specified in natural language in the prompt: "You are an expert researcher. You have access to these tools: search — pick a search engine, query string, and number of results; summarize — summarize a document; ..." The model learns to produce valid tool calls from these descriptions.

In the Tool Former paper, the model is further trained to use tools — not just prompted. But in many modern agents, tool use is driven primarily by prompting: the model sees tool specifications and generates appropriate calls. Tool calls are executed as soon as they are produced (when a valid, fully formed call is detected in the stream), and the output is appended to the generation.

Complex Tools: LLMs as Tools

Tools can be more than simple APIs. A tool might be a prompt to another LLM: "Summarize this document" — one LLM calls another with a document and summarization prompt, waits for the result, and uses it. In practice, many agent tools are implemented via LLMs: a master controller calls worker LLMs for summarization, code generation, or information extraction. Each call burns tokens and adds latency, so agent trajectories can become expensive.

Agent Architectures: Controller and Workers

Most agents follow a controller-worker pattern. A controller LLM (sometimes called the "agent" or "manager") receives the user's task, makes a plan, and delegates subtasks to worker LLMs or tools. Workers execute specific tasks (e.g., "generate this HTML file," "search for this query") and return results. The controller then decides: do I have enough information to finish, or do I need to issue more calls?

Workers are typically the same model called with different prompts — not separate fine-tuned models. Each worker has a prompt like "You are an expert summarizer" or "You are an expert front-end designer." Breaking the task into smaller, focused prompts often performs better than giving one model the full responsibility. In production stacks, those calls are usually routed to a shared frontier API (same weights, different system strings) rather than a separate fine-tuned miniature model per subskill: the latter is hard to maintain when the set of tasks is open-ended, though specialized small models remain an active research and product direction.

Fixed vs. Proactive Planning

Early agents made a plan once and never changed it: decide on three subgoals, execute all three, then synthesize. Proactive planning allows the controller to revise the plan based on intermediate results. If the first worker's output reveals that a different search is needed, the controller can add a new goal or skip planned ones. Modern agents increasingly use this adaptive approach.

The open-source Agent S2 project illustrates this pattern for computer-use agents: a prompt library for multimodal models, with diagrams that contrast a manager dispatching subgoals to role-specific workers (front-end, graph search, filesystem navigation) under either a frozen plan or continuous replanning after partial observations.

Frozen plan

The manager commits to goals G1…G3 upfront, runs them to completion, then synthesizes — even when G1 already made G2–G3 redundant.

Proactive replanning

After worker outputs return, the manager can insert G4, cancel G2, or rewrite queries. This is the dominant design in recent systems because it wastes fewer steps when the environment behaves unexpectedly.

06

Multi-Step Reasoning and Planning

Agents break complicated tasks into multiple conversational turns. Instead of "generate an entire code repository in one shot," the agent might: look up information, write a file, run it, check for errors, fix them, run tests, and so on. This fine-grained decomposition is more reliable than monolithic generation.

Many coding agents use a to-do list: the controller formulates an initial plan (e.g., "create directory structure, write index.html, write CSS, create images, run verification") and presents it to the user. As each task completes, it is crossed off, and the controller moves to the next. The user can intervene at any step to redirect or correct the plan.

Controllers typically update asynchronously as worker results arrive — revising the plan as soon as one call returns enough information (e.g., skipping remaining searches). Parallel worker batches that wait for all results before replanning are less common.

What you see in a coding-agent UI: Many products now open with a visible to-do list derived from initial reasoning. Between items you often get thinking or reasoning traces (sometimes grayed out): the controller’s private chain-of-thought or a summary of it. Each substantive step — scaffold directories, write index.html, run a terminal command — is commonly a separate model call where the model re-reads the plan, the filesystem state, and prior outputs. For terminal tools, the runtime typically runs the generated command, captures stdout/stderr, and only then advances the plan once success or failure is known. Some runs end by deleting scratch artifacts the user never needed to keep, which is convenient until a bad rm -rf slips past safeguards.

Commercial agents expose stop or interrupt controls: you freeze the loop before the next worker step, inspect partial edits, and send a corrective message. That pattern is essential because planning errors and destructive commands do occur in the wild.

07

Memory Systems

Where does the agent's memory live? In most setups, memory is natural language. Worker outputs, tool results, and intermediate state are all appended to the context as text. The controller sees this context and decides what to do next. Some agents use context compression: instead of passing raw outputs, another LLM call summarizes "the most important things to know" to avoid exceeding context limits.

Companies typically cache conversation history so that recomputation is not needed for previous turns. For workers called with different context, each call may start a fresh "conversation" — the worker does not necessarily receive everything the controller has seen. Design choices vary: raw output vs. summarization, what to include in each worker's prompt, and how to manage long trajectories.

Context compression: When context grows too large, an LLM can be asked to summarize the key information. This is how some coding assistants save tokens during long, multi-file tasks — compress the history, then continue.

Compression pass: full_trajectory_text → [LLM: “What must the controller remember?”] → compressed_bullets → append to context; repeat as the session grows.

Hosted products cache prior turns and KV state so the full transcript is not re-forwarded on every new token. Workers spun up in fresh chats may deliberately not receive the controller’s full private history — only the slices the orchestrator passes through are visible to that sub-call.

08

Coding Agents

Coding agents are among the most impactful agents today. Given a high-level specification (e.g., "make a better version of this website with liquid glass design"), the agent implements the full solution: creates directories, writes HTML/CSS/JS, generates images, runs terminal commands, and verifies the result. Tools include: file read/write, terminal execution, directory search, and sometimes browser use.

OpenHands is an open-source example. It defines many tools (e.g., grep, glob, terminal, browser) each with its own prompt. Before executing a command, a security analyzer may check whether it would delete critical files. The agent loops until the model signals "done" or a budget is hit.

A common concern is safety: how do we prevent the agent from deleting files it shouldn't? In practice, agents do sometimes make mistakes (e.g., deleting a working directory). Implementations may allow specifying allowed paths or using a security layer to block dangerous commands. Users can also interrupt the agent at any time and provide corrective feedback.

OpenHands-style loop (simplified):
user_instruction → agent (plan / next action) → worker generates concrete command or file patch → security analyzer (optional: block destructive ops) → execute → event stream (success, stderr, new files) → append to context → optional compression → repeat until “done”.

Mature coding stacks also advertise skills or tool packs: each capability (grep, glob, browser automation, Jupyter, etc.) ships with its own instruction block the controller can cite when emitting calls. Proprietary assistants rarely publish those inner prompts, but open repositories show the pattern clearly: long markdown per tool describing when to use it, argument conventions, and failure handling.

High-visibility trace

To-do checklists, per-step thinking summaries, and streamed terminal output help users audit behavior and intervene before irreversible edits.

Opaque trace

Some products collapse intermediate tool chatter; you see a final artifact only. That reduces noise but makes forensic debugging harder when something goes wrong.

Destructive commands are real: Even with analyzers, agents occasionally issue broad deletes or overwrite trees. Treat shell access as production-risky: version control, backups, sandboxes, and least-privilege working directories are not optional extras — they are part of the safety story alongside automated checks.

09

Computer Use Agents

Computer use agents control the computer via screenshots and actions. The model is multimodal: it receives images (screenshots of the screen) and text, and outputs actions like "move mouse to (x, y)," "click," "type this string." It can browse the web, fill forms, use Excel, or run terminal commands — all by "seeing" the screen and issuing actions.

At a high level, multimodal models process images via a visual vocabulary: image patches are mapped to tokens, and the model processes them alongside text. The agent takes a screenshot at some frequency, sends it to the controller, gets an action, executes it, and repeats. For fast, continuous tasks (e.g., 3D games), latency is a major challenge — the loop may be too slow for real-time control.

These agents are expensive: each screenshot and each decision burns tokens. A single complex task (e.g., playing a game, building a website) can consume millions of tokens from start to finish.

Stress tests from research benchmarks highlight brittle behavior: a task might require loading a 3D browser game, following non-obvious navigation rules, and counting objects in the world. Agents often stall on loading screens, lose focus of the game canvas, or pivot to web search for a walkthrough when direct play fails — reasonable human troubleshooting, but it changes the evaluation contract. End-to-end runs for messy GUI missions can stretch to 30–40 minutes of wall-clock time, with a fresh multimodal forward pass after each screenshot.

Pricing reality: Subscription products (e.g., bundled coding or agent modes) sometimes mask per-step token burns behind a monthly cap, but the underlying cost is still superlinear in screenshots × reasoning depth. Expect continued investment in faster perception encoders, action abstractions beyond raw pixels, and cached UI representations to close the gap for interactive software — including richer mouse paths (drag gestures already appear in vendor updates).

10

Research Agents (Deep Research)

Research agents (often called "deep research") perform iterative search and synthesis. Given a topic or question, they search the web, read sources, decide what else to search for based on what they find, and repeat until they have enough information to produce a report. They may also run simple scripts (e.g., Python for data analysis or plotting).

The flow: user input → plan (possibly with clarification questions) → retrieval and search → summarization → more retrieval if needed → final synthesis. Tools are typically search and retrieval based. A key feature is attribution: the report cites sources, so users can verify claims. This addresses the trust problem — we don't trust raw LLM output, but we can trust it more when it points to readable sources.

Deep research jobs are deliberately slow: twenty to thirty minutes is normal when the controller is fanning out dozens of searches, rereading course sites, cross-checking older syllabi, and only then locking a structured answer. Along the way you may see coarse status chips (“scanning emerging trends”) rather than every HTTP URL — some vendors intentionally hide exact fetches, which aids UX but frustrates auditability.

User query → (clarify?) → plan → [search / browse / summarize / light code]* → citation-backed report — loop until information gain falls below a threshold or a time budget fires.

Why citations matter: A strong research agent ends with a table of claims, recommended additions, and a bibliography tying sentences to pages you can open yourself. That combination — fluent synthesis plus pointers to human-verifiable evidence — is what makes the artifact useful in classrooms and enterprises, not just rhetorically convincing.

Ethics horizon: The same loop is migrating into autonomous scientific assistants that ideate, run experiments, draft papers, and even submit to peer review. The failure mode is not only incorrect science but reviewer load and spam at scale. Any curriculum on agents should reserve space for institutional norms, disclosure, and human gatekeeping — not only capability demos.

Multi-Agent Systems

The term multi-agent is ill-defined: a controller calling multiple workers already qualifies, yet many tasks need only that single pipeline. Distinct agents that specialize and pass messages to each other remain an active research area — but most production wins still come from one controller with disciplined tools.

Naming vs. mechanics: If “multi-agent” only means one orchestrator and several prompted workers, most shipping systems already qualify — which makes the buzzword easy to inflate. Before adopting a multi-agent diagram, ask what additional autonomy, state, or communication protocol you gain over a well-structured single pipeline. Many production wins still come from one controller with disciplined tools rather than a crowd of loosely coupled personas.

Agent Benchmarks and Evaluation

Evaluating agents is hard because we care about the final outcome — did the agent fulfill the instruction? — not each individual step. OS World is a popular benchmark for general-purpose agents: it challenges agents to solve real computer-use tasks (e.g., "Make Bing the default search engine in Chrome") by taking screenshots and issuing actions. Ground truth trajectories show the correct sequence of clicks and key presses.

Outcome-first mindset: In many benchmarks, a trajectory that wanders or retries is still acceptable if the terminal state matches the spec — you mainly want reliability on real chores (settings dialogs, spreadsheets, file dialogs), not a unique golden path. Diagnostics that log action quality remain valuable for training and safety even when the headline metric is pass/fail.

Agents are evaluated on both task success (did they achieve the goal?) and trajectory similarity (how close were their actions to the ideal path?). Benchmarks like OS World include Chrome tasks, Excel tasks, and other real-world scenarios. The goal is to push agents toward practical usefulness for everyday tasks.

Primary metrics emphasize outcome correctness — if Bing becomes the default search engine, the task counts as solved even if the path meandered. Secondary metrics (click alignment, distance to expert demonstrations) diagnose efficiency and safety: an agent that succeeds only after random clicking may still be undesirable for deployment.

  • Chrome: “Make Bing the default search engine” — requires navigating settings, search engine panels, and confirming the change.
  • Excel: Spreadsheet chores such as filling sequence numbers down a column after selecting the right range.
  • Other desktop apps: Tasks that mirror small office workflows rather than toy grid worlds.

Challenges: Hallucination, Error Propagation, Safety

Agents face several challenges. Hallucination: the model may invent facts or tools. Error propagation: one bad step (e.g., a wrong search result, a buggy code edit) can compound — subsequent steps build on the error, and the final output is wrong even if later steps were correct. Safety: agents with file system or terminal access can delete files, run malicious code, or exceed intended permissions.

Error Propagation Demo

See how one incorrect step compounds. Step 2 uses the wrong result from Step 1, and Step 3 builds on that. The final answer is wrong even though Step 3's logic was correct.

Training agents to avoid these failures is an active area. Stepwise reward models can judge each action; outcome-level rewards judge only the final result. Using only outcome rewards to train intermediate steps is tricky — you don't want to penalize a correct step that was undermined by an earlier error.

14

Training Agents with RL

How do you train an agent to improve? Unlike pre-training (where we have massive text corpora), we lack large-scale ground truth interaction trajectories. Humans don't routinely screen-record themselves solving every kind of task. So training often relies on synthetic data: run the agent on many tasks, collect successful trajectories, and train via imitation learning on those. Failed trajectories can be analyzed to avoid repeating mistakes.

Reinforcement learning is another approach. If you have a reward model that scores the quality of each intermediate step (e.g., "searching for Tom Cruise's age when the question is about Glenn Hughes and Ross Lynch is bad"), you can use RL to upweight good actions and downweight bad ones. Outcome-level rewards (e.g., "was the final answer correct?") are harder to use for stepwise training — you risk unfairly penalizing correct intermediate steps when a later error caused failure.

The Swirl paper (synthetic data generation and multi-step RL) explores these ideas. This is a very new area; most production agents today are still primarily prompt-based, with training playing a growing role in closed-source systems.

Stepwise RL sketch: fix all tokens before actionk, treat the model’s fresh completion at step k as the decision variable, score it with a process reward model (e.g., “first search should mention entities from the question”), update policy; repeat for k+1…T.

Outcome RL: only the final answer (or task bit) receives reward — credit assignment across many tool calls is noisy because an early correct retrieval can be undone by a late bug.

Process / stepwise rewards

Can reject nonsense immediately — searching for Tom Cruise’s age when the question names Glenn Hughes and Ross Lynch should score poorly even if the final guess accidentally lands right.

Outcome-only rewards

Cheaper to collect when you have checkers for final answers, but unfairly punishes good intermediate work whenever a late step fails — the Swirl discussion highlights exactly this tension.

Synthetic curricula: Give an agent hundreds of coding or research tasks, let it roll out, log successes versus failures, then imitate winning trajectories or pair them with reward models. That sidesteps the scarcity of human screen recordings for every niche task — at the cost of trusting automated verifiers.

The Agent-Environment Interface

The agent interacts with an environment that exposes tools. You can run your own server with custom APIs (e.g., MCP — Model Context Protocol) to expose proprietary tools. For example, a search engine over a private dataset: you describe the tools ("nearest neighbor search with query, retrieve top-k results") and the agent calls them. The environment executes actions, returns observations, and the agent decides the next action.

The interface is: state (what the agent sees) → action (what the agent does) → observation (what comes back). This loop is the same whether the environment is a file system, a browser, a search API, or a suite of LLM workers.

Private data, public models: When Google Search is inappropriate, an MCP server can wrap embeddings + vector search, SQL, or ticket systems. The prompt enumerates callable methods (“nearest_neighbor with query string and k”) exactly like any other tool; the LLM never needs raw database credentials in-context if the server enforces auth. The same abstraction lets enterprises swap retrieval backends without retraining the chat model.
