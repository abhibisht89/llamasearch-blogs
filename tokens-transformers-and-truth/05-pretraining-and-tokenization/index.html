01

Decoder-Only Transformers

The dominant configuration in today's language models is the decoder-only transformer: L stacked layers of masked multi-head self-attention with a causal mask so position i attends only to positions 1 through i. Block structure, Q/K/V projections, residuals, and the vocabulary softmax head are laid out in Chapter 04.

Encoder stacks produce bidirectional Z vectors at every position — useful for classification, but unsuitable for naive next-token training because each position would already encode future tokens. Decoder-only models avoid that leakage by construction.

GPT-style models — GPT-2, GPT-3, GPT-4, Llama, Mistral, and most modern chat models — are all decoder-only. They excel at continuation, completion, and instruction-following because the training objective (next-token prediction) directly matches the generation task.

Pure decoder training: In a standard decoder-only language model, the training loss is applied at every non-padding position in the sequence, because nothing is treated as a privileged “prompt” region. Prefix-style masking is what later carves out a segment where no loss is needed.

Key insight: Decoder-only transformers are the dominant configuration today because they are simple, scalable, and flexible. Any task that can be framed as "given input, generate output" works naturally with this architecture.

02

Encoder Transformers

The encoder transformer differs from the decoder in one crucial way: it uses completely unmasked multi-head self-attention. Every position can attend to every other position — past, present, and future.

This creates a problem for next-word prediction. If the model can see the entire sequence, predicting the next token becomes trivial — it can simply "cheat" by looking at what comes next. The representations at each position already include information from the future, so there is no meaningful learning signal for autoregressive generation.

Instead, encoder models are designed for computing representations of full text sequences. They are excellent for tasks where you need a single vector (or per-position vectors) summarizing the whole input: sentiment analysis, named entity recognition, text classification, and similar tasks where the answer depends on the entire context.

Examples include BERT, RoBERTa, and ELECTRA. These models are not trained to generate text autoregressively; they use different objectives (like masked language modeling, which we cover later) that are compatible with bidirectional attention.

Encoder stacks are a natural fit when the task is “read this fixed string and emit a label (or a label at each position).” A pedagogical instance is counting: given a sequence of characters, predict at each timestep how many times the current character appeared strictly before and strictly after that position in the string (outputs in {0, 1, 2}). The answer at every location depends on the entire sequence, so bidirectional attention is appropriate; masking would throw away information you are explicitly asked to use.

Encoder use case: f(text) → vector(s) for classification, tagging, or scoring — not autoregressive completion of unseen future tokens.

Connection to diffusion: Some recent work explores diffusion-based language models that operate on continuous representations. The encoder's bidirectional view has conceptual parallels to how diffusion models can "see" the full sequence during denoising, though the mechanics differ.

03

Prefix LM (Prefix Language Model)

The prefix LM architecture sits between decoder-only and encoder-decoder. It has two conceptually distinct parts: a prompt (or prefix) and a completion (or response). The attention mask is partially masked.

The Mask Structure

Imagine a sequence split into prompt tokens and completion tokens. The attention matrix can be thought of as four blocks:

  • Prompt × Prompt (top-left): Fully unmasked. All prompt tokens attend to all other prompt tokens.
  • Completion × Prompt (bottom-left): Fully unmasked. Completion tokens can attend to the entire prompt.
  • Completion × Completion (bottom-right): Causal mask. Each completion token attends only to previous completion tokens (and all prompt tokens). Future completion tokens are masked to −∞.
  • Prompt × Completion (top-right): Masked to −∞. Prompt tokens cannot attend to completion tokens (which do not exist at "prompt time").

In practice, the system prompt and user prompt are concatenated into one prompt block. The model then generates the completion autoregressively, with each new completion token attending to the full prompt and all previous completion tokens.

Why Unmask the Prompt?

Because we do not compute loss on prompt tokens — we only compute loss on completion/response tokens. The prompt is given; we are not trying to predict it. Allowing bidirectional attention within the prompt gives richer representations for each prompt position, since each token can use full context from the rest of the prompt. There is no prediction needed there, so there is no risk of "cheating."

You could, in principle, run a single long causal mask over prompt plus completion. That is not wrong, but it is unnecessarily restrictive for the prompt segment: early prompt tokens would be blocked from attending to later prompt tokens even though you never ask the model to predict those later prompt tokens anyway. Unmasking within the prompt is a free way to give the completion side a better-conditioned view of the instruction.

Read attention matrices as rows = query positions, columns = key positions. The decoder-only causal mask (same idea as the “diagonal” mask in many papers) zeros out all entries above the main diagonal before softmax. Prefix LM keeps that causal structure only inside the completion block, while the prompt–prompt block is fully visible.

During training, implementations still materialize hidden states for prompt positions under the hood: completion queries need a stable, well-informed prompt representation. The mask shapes what may attend where; it does not mean the prompt is skipped in the forward pass.

Prefix LM (one stack)

One set of weights; change the mask so prompt tokens are bidirectional among themselves and invisible to future completion keys, while completion tokens stay causal among themselves but see the whole prompt.

Encoder–decoder (two stacks)

Separate parameter pools for encoding the source and generating the target. Historically motivated for translation when source and target are different languages; adds hyperparameters (relative depth/width of each stack) but can specialize each half.

Comparison: Prefix LM is simpler than full encoder-decoder — it's a single transformer with a custom mask, rather than two separate networks. Many instruction-tuned models use prefix LM or a variant of it.

04

Encoder-Decoder (Sequence-to-Sequence)

The encoder-decoder architecture uses two separate transformer networks: an encoder and a decoder. The original "Attention Is All You Need" paper used this for machine translation — French sentence in, English sentence out.

Encoder

The encoder applies unmasked self-attention over the input sequence (e.g., the source sentence). It produces a set of Z vectors — one per input position — that encode the full input.

Decoder

The decoder has two attention mechanisms per block:

  1. Masked self-attention over the output (decoder) sequence. Same causal mask as decoder-only — each output position attends only to previous output positions.
  2. Cross-attention: Q comes from the decoder, K and V come from the encoder's final Z vectors. The decoder "queries" the encoder's representation. Cross-attention is unmasked — the decoder can see all encoder positions.

Residual connections combine the decoder self-attention output with the cross-attention output. A decoder block = masked self-attention + cross-attention + feed-forward + residual connections, stacked L times.

Cross-attention is worth dissecting carefully. The attention weights are formed from decoder queries, but the value vectors being mixed are entirely a function of the encoder memory. Those values, by themselves, carry no information about which English (decoder) tokens have already been generated. The masked self-attention branch supplies that autoregressive context. The residual pathway is what fuses “what I have already produced in the target language” with “what the source sentence contributes,” so neither pathway is redundant.

Where do encoder K and V come from? In standard implementations, keys and values are linear projections of the encoder’s final-layer hidden states (the top-level Z vectors). Every cross-attention head reads from that same frozen encoder memory until the encoder is run again on a new source string.

Training examples are paired sequences: a source string and a target string that align as supervision (translation, summarization with target text, etc.). Even though the correct target is available on disk, the decoder is still trained with a causal mask so that position t only depends on target positions < t and on the encoder. At the first step the decoder might see only a start-of-sequence symbol plus the full source; it must predict the first real target token without peeking at later target tokens that appear in the label string.

Large decoder-only models on multilingual data can handle many tasks that once required a separate encoder, but the two-stack pattern remains essential wherever a generator must condition on another modality or external memory — images, retrieved documents, tool outputs — via cross-attention (queries from the generating side, keys and values from the external encoder).

Inference

At inference time, the encoder is run once on the input. Its K and V are cached. The decoder then generates the output token by token; each new token attends to the cached encoder K/V via cross-attention, and to previous decoder tokens via self-attention.

This architecture has more hyperparameters (encoder size vs decoder size) and was historically dominant until GPT-3 demonstrated that prefix LM could achieve similar or better results for many tasks. Model sharding across GPUs (e.g., with DeepSpeed) is often used for large encoder-decoder models.

Engineering note: Distributed training must decide whether to shard by data, by layers, or both. Encoder–decoder stacks add extra communication patterns around cross-attention compared with a single-tower decoder, so the tooling and performance trade-offs are not identical even when the math is familiar.

The Training Pipeline

Modern language models are built in stages. The pipeline is a form of transfer learning: first learn general language understanding, then adapt to specific behaviors.

Randomly initialized transformer decoder
↓ Pre-training
Pre-trained transformer (base model)
↓ Post-training
Fine-tuned / aligned model
↓ Deployment
Final deployed model

Pre-training trains on a giant dataset of text — trillions of tokens — to produce a model that understands language broadly. Post-training takes that pre-trained model and adapts it on smaller, task-specific or instruction-following data to produce the final model you deploy.

The same transformer skeleton—embedding layer, attention blocks, feed-forward layers, output projection—persists across the whole journey. What changes is the numerical setting of the parameters: random at initialization, optimized for next-token (or encoder) objectives after pre-training, then nudged again during alignment. This entire two-stage recipe is the dominant modern instance of transfer learning in NLP: expensive broad learning once, cheaper adaptation many times.

Architecture fixed; parameters reweighted: θrandom → θpretrain → θpost-train.

Production systems often complicate the cartoon diagram: routing layers may send different prompts to different specialist models, and agentic stacks add tools and policies around the core transformer. Nevertheless, the large language model at the center is still usually trained with the pre-train / post-train split described here.

06

Pre-training Deep Dive

Pre-training starts with a randomly initialized transformer and trains it on a massive dataset. Data typically comes from internet crawls (e.g., Common Crawl), books, textbooks, code repositories, and other text sources. Scale is measured in trillions of tokens.

Data and Filtering

Raw crawls are filtered for quality: duplicates are removed, low-quality or toxic content is filtered out, and language/domain balance may be adjusted. Loss spikes during training often correlate with bad data — malformed text, encoding errors, or adversarial content.

Duplicates and gibberish are not just hygiene problems. Seeing the same memorizable passage many times increases the chance the model can regurgitate it verbatim from a short prefix; extremely noisy pages can inject gradients that produce sudden loss explosions when a bad minibatch appears. Operational logs from large training runs sometimes show mysterious upward spikes that can be traced, after investigation, to a handful of pathological documents.

Copyrighted data (books, textbooks) is commonly used. The legal and ethical status of this is debated — fair use arguments exist, but the question is far from settled.

Memorization vs utility: High-frequency passages (famous documents, boilerplate licenses) are often memorized in a narrow sense: given a prefix, the continuation matches training text. Whether that is harmful depends on deployment and rights. Litigation around generative models frequently turns on empirical demonstrations of verbatim reproduction from copyrighted sources, not on abstract perplexity scores.

Scale and Goals

The prevailing strategy has been to train the biggest model affordable. There are signs we may be hitting limits — scaling laws suggest diminishing returns — but for now, scale remains a key lever.

The goal of pre-training is not to solve specific tasks. It is to produce a model that understands many linguistic properties: grammar across languages, world knowledge (e.g., "the president of France is ___"), and broad semantic relationships. Emergent properties — capabilities that appear suddenly at scale — include in-context learning (famously demonstrated by GPT-3) and chain-of-thought reasoning.

In-context learning is the phenomenon where a sufficiently large model, given several input–output demonstrations in the prompt, can infer a pattern and apply it to a new instance without weight updates. Chain-of-thought behavior is another example where asking the model to externalize intermediate reasoning steps can improve performance on structured tasks like math, even though those behaviors were not hand-engineered token-by-token at pre-training time. Both illustrate why “just predicting the next token” at scale can yield surprisingly task-general internal algorithms.

Pre-training objective

Self-supervised prediction on web-scale text (next token for decoders, masked tokens for encoders). Optimizes broad competence, not chat politeness.

What users want

Models that follow instructions, refuse unsafe requests, and answer in the requested format. That mismatch is exactly why post-training exists.

Key insight: Pre-training is about general language understanding. The model learns to predict the next token, which implicitly requires understanding syntax, semantics, and factual knowledge. Task-specific behavior comes later, in post-training.

07

Post-training Overview

Post-training takes the pre-trained (base) model and adapts it to follow instructions, align with human values, and behave safely. It uses less data than pre-training, though the compute gap is closing as post-training methods become more sophisticated.

Methods include Supervised Fine-Tuning (SFT) — training on human-written instruction–response pairs — and Reinforcement Learning (e.g., RLHF, DPO) to refine behavior based on preferences.

Reinforcement-style phases differ from SFT because the training signal is often a scalar score or preference over a free-form completion rather than a single correct string. The model may produce a long chain of thought; only the final boxed answer might enter into the reward. That makes credit assignment harder but allows optimization for outcomes that are easy to verify (unit tests, answer keys) even when human demonstrations are scarce.

Qualitative sanity check: Compare a base checkpoint and an instruction-tuned checkpoint from the same family on a constrained creative prompt (for example, ten sentences on a theme with numbered lines and a rare word required in sentence five). The base model often continues the rubric, invents extra constraints, or analyzes the task; the aligned model typically executes the instructions. Both behaviors are “reasonable” under next-token prediction—the difference is whose intent wins.

Given "Translate to French: Hello world", it might continue the instruction as if it were more text to complete, e.g. "Translate to French: Hello world and goodbye universe."

Instruct Model (Post-trained)

BERT — Masked Language Modeling

BERT (Bidirectional Encoder Representations from Transformers) is an encoder transformer with a different training objective. Because the encoder has no causal mask, next-word prediction would be trivial — the model could see the answer. So BERT uses Masked Language Modeling (MLM).

How MLM Works

During training, a random subset of tokens (typically ~15–30%) is replaced with a special [MASK] token. The model must predict the original token at each masked position. It can use context from both left and right — hence "bidirectional."

Trade-off: A low mask rate gives rich context but few training signals per example. A high mask rate gives more signals but less context per masked token. BERT uses around 15% masking.

The masking percentage is a true hyperparameter: papers explore roughly 15–30%. At one extreme, masking almost everything leaves too little evidence for each prediction; at the other, masking a single token in a long sequence means paying for a full forward pass of bidirectional attention while receiving gradient signal from only one softmax. Decoder language models sidestep that tension by supervising every position (subject to padding rules).

In standard random MLM, masks are drawn without regard to contiguity—runs of adjacent [MASK] tokens can appear, and whether a span corresponds to one word or several depends entirely on the tokenizer. The model never sees the exact identity of what was removed at masked sites, but abundant surrounding context can make the task easier in a different way: if a rare word also appears unmasked elsewhere in the paragraph, the model may learn shallow copying shortcuts instead of deeper reasoning. Designing masking strategies that force harder predictions remains an active research theme.

Compared to next-word prediction: MLM computes loss only at masked positions, whereas decoder-only models compute loss at every position. So MLM can be less sample-efficient in terms of tokens used per training signal.

Causal LM (decoder)

Supervise each step with left context only; natural for generation; no trivial leakage from future tokens because they are masked out.

Masked LM (encoder)

Use both sides of each mask; incompatible with naive next-token loss; excellent for sentence-level understanding and token-level classification.

BERT is not good for text generation — it was trained with context before and after each token, so it is not set up for autoregressive generation. It excels at classification and representation tasks.

Diffusion-flavored language models revisit encoder-like training dynamics: they build on bidirectional or mask-based denoising ideas that rhyme with BERT, even though consumer-facing chat models are still overwhelmingly decoder stacks.

Fine-tuning BERT

For tasks like sentiment analysis, you replace the MLM head with a task-specific classifier. A special [CLS] token is prepended to the input; its final representation is often used as the sequence embedding for classification. BERT dominated NLP from roughly 2019–2020 before the GPT-era shift.

The classifier head is not the only option: practitioners also pool mean final-layer representations over real tokens, or use the first or last subword piece of a span, depending on the toolkit. The [CLS] convention is the most cited because the original BERT paper standardized it, but the underlying principle is always “compress token-level encoder outputs into a fixed vector, then add a small softmax for K classes.”

Embeddings before the first transformer layer are not contextual: the same type has the same vector regardless of neighbors. Each subsequent layer mixes information from the whole sequence, so the final vector at position i entangles token identity with sentence-level context.

The Tokenization Problem

Tokenization is the process of mapping raw strings to sequences of discrete tokens — indices into a vocabulary. The model never sees raw text; it sees token IDs. The choice of tokenizer profoundly affects model behavior.

Recall the types vs tokens distinction: a type is a unique vocabulary entry; a token is an instance of that type in the sequence. "The" appearing three times is three tokens but one type.

Tokenization is not just a list of IDs. A complete recipe specifies (1) a vocabulary of types and (2) a deterministic procedure that maps any raw string to a sequence of those types. Once indices are chosen, the embedding layer simply looks up a row per index; everything interesting about spelling, punctuation, multilingual text, or code happens upstream of that lookup.

Raw string → tokenizer → [id1, id2, …, idT] → embedding matrix lookup → sequence of vectors fed to the transformer.

Punctuation and whitespace policy matters in detail: commas, periods, colons, and apostrophes are usually standalone types in modern subword vocabularies rather than being silently stripped. That is why two prompts that look similar to humans can produce different activations if the tokenizer splits them differently.

Word-Level Tokenization

The simplest approach: split on whitespace and punctuation. "Hello world" → ["Hello", "world"]. But edge cases abound: "O'Neal" vs "aren't" — do we split on the apostrophe? "New York" — one token or two? Rule-based tokenizers need specialized rules, syntactic parsers, or NER (e.g., SpaCy) to handle these, and they do not scale well to multiple languages, code, or mixed content.

A morphological shortcut—“store stems and suffixes explicitly”—can reduce redundant types for inflected words, but high-quality analyzers exist for only a handful of languages and degrade on informal text and source code. That fragility helped motivate data-driven subword methods that learn splits from corpus statistics instead of linguistic handcraft.

Languages without whitespace — Thai, Chinese, Japanese — break this approach entirely. Word boundaries are not clearly defined.

Vocabulary churn: Even if you freeze English “words” today, neologisms, typos, and product names appear tomorrow. A static word-level table either grows without bound or maps growing swaths of text to a single fallback symbol.

10

The Unknown Word Problem

With a fixed vocabulary, any word not in the vocab must be replaced with a special [UNK] (unknown) token. This causes information loss: you lose the identity of the word. "GPT-6" and "xyz123" might both become [UNK], and the model cannot distinguish them.

All unknown words share the same representation. The model must be trained to handle [UNK] during training, but contextually important words that fall out of vocabulary can severely hurt performance.

You cannot fix a missing type at test time by casually appending a new row to the embedding matrix: the model has no experience running forward passes with that row. Practical pipelines therefore inject during training as well—often by randomly replacing rare words—so the network learns a statistical story for "something unknown lives here." That remedy preserves shape but still discards surface form, and documents littered with unknowns bleed information at every occurrence.

A masked infilling model might guess the word behind , but the guess can be confidently wrong — especially for rare named entities or consecutive misses. Downstream modules would then condition on hallucinated specifics. Subword or byte-level tokenization preserves partial identity (for example the shared "GPT" prefix in a novel product name) instead of collapsing to one symbol.

Key insight: The [UNK] problem motivates subword tokenization. If we can decompose rare words into known subword pieces, we avoid [UNK] entirely for most text.

11

Character-Level Tokenization

At the other extreme, use individual characters as tokens. Vocabulary is tiny (~100–200 for most scripts), and there is virtually no [UNK] problem — any character can be represented.

Unicode reminds us that "character" is not trivially small: the standard assigns on the order of 100k+ code points. If you truly support all of them as atomic types, the embedding table is no longer minute. In practice, ASCII-centric alphabets keep the table compact, while full Unicode coverage pushes you toward byte-level decompositions instead.

The downside: very long sequences. A 100-word sentence might become 500+ character tokens. Self-attention has quadratic complexity in sequence length — N² dot products. Doubling the sequence length quadruples compute. Long sequences are expensive.

Full self-attention over length N: each query attends to N keys → Θ(N²) pairwise score interactions (ignoring constant factors and head dimension).

Individual characters also carry little meaning on their own. Learning to compose them into words and phrases adds significant burden. For large-scale training, character-level tokenization has generally been a deal-breaker.

Byte Pair Encoding (BPE)

BPE strikes a balance between word-level and character-level tokenization. It starts with characters (or bytes) and iteratively merges the most frequent adjacent pairs into new tokens.

Algorithm (Step by Step)

  1. Pre-tokenize (optional in modern tools): Split on whitespace or apply a light rule-based split. Libraries like SentencePiece can learn segmentation directly from raw text with a weaker dependence on this step.
  2. Initialize vocab: Add all individual characters (or bytes).
  3. Tokenize corpus: Represent the corpus using the current vocab.
  4. Count pairs: Count all adjacent token pairs in the tokenized corpus.
  5. Merge: Merge the most frequent pair; add the new token to the vocab.
  6. Re-tokenize: Update the corpus representation with the new merge.
  7. Repeat: Go to step 4. Stop after S merges (S is often 32k–100k+).

At inference time, always prefer the shortest tokenization using available merges. Base characters are always in the vocab, so there is no [UNK] problem. Common words eventually become single tokens; rare words are split into subword pieces.

Example: with words hug(10), pug(5), pun(12), bun(4), hugs(5), the first merge might be "ug" (appears in hug, pug, pun, bun). Then "hu" or "pu", etc. The vocab grows with each merge.

Counting makes the first merge concrete. After splitting into characters, adjacent pair u+g appears across hug, pug, pun, bun, and hugs with frequencies that sum to 20 occurrences in this toy corpus—higher than competing pairs such as h+u (15 from hug and hugs alone). BPE therefore merges ug first, retokenizes, and repeats. After each merge, when multiple segmentations are possible, implementations prefer the shortest encoding under the current merge table so frequent words collapse into single types as soon as the merges exist.

Why BPE kills most unknowns: The initial alphabet (characters or bytes) already covers every symbol. Merges only add shortcuts; they never remove the ability to fall back to atomic pieces. Worst case, an unseen string becomes a longer sequence of known roots, not a dead .

Beyond Basic BPE

BPE over bytes (instead of characters) was introduced by GPT-2. UTF-8 encoding means: ASCII = 1 byte per character; many non-Latin scripts = 2–4 bytes; emojis = 4 bytes. A single vocabulary can handle any Unicode text without pre-defined character sets.

The disadvantage: non-Latin languages often produce longer sequences (more bytes per character). There are ~160k Unicode characters, so byte-level BPE can be less efficient for some languages.

Dynamic Tokenization

Newer approaches like MegaByte (Meta) and Byte Latent Transformer (BLT) use a local encoder to compress byte subsequences into single vectors. The main transformer operates on this shorter "latent" sequence; prediction happens at the byte level at the end. Entropy-based splitting (in the BLT paper) decides how to segment. These methods are promising but not yet standard in state-of-the-art models.

MegaByte illustrates the pattern with fixed-width patches: non-overlapping groups of four raw bytes feed a tiny local encoder that emits one latent vector each, shrinking the sequence length seen by the massive transformer core. BLT refines the idea by letting a local model propose variable-length byte groups—high-entropy segments may stay granular while redundant stretches collapse—so the latent sequence length tracks information content more tightly than uniform patching.

Even when weights are proprietary, organizations publish tokenizers because billing, capacity planning, and benchmarking all require knowing how a string becomes tokens. Vocabulary sizes in the wild commonly land in the tens of thousands to 100k+ merge types; tokenizer choice materially changes sequence length for lower-resource languages and therefore fairness metrics—not just engineering trivia.

Research frontier: Dynamic or latent tokenization introduces new bookkeeping: variable group boundaries interact awkwardly with causal masking compared with a fixed subword lattice. That is part of why BPE-style static vocabularies still dominate production systems despite the intellectual appeal of fully learned segmentation.
