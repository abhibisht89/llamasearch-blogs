01 — BEYOND PROMPTING

Search Against Verifiers

Inference-time compute scaling has two families. Chapter 02 covered the first: modifying the proposal distribution — few-shot chain-of-thought, zero-shot CoT ("Let's think step by step"), and related prompting tricks that nudge the model toward longer reasoning traces without changing weights.

This chapter covers the second family: search against verifiers. Instead of trusting the first chain the model emits, you sample multiple answers (or multiple reasoning paths), score them with a verification layer, and return the best. The base LLM stays frozen; you pay extra compute at test time for higher accuracy.

Proposal Distribution

Change what the model is likely to generate — via prompts, temperature, or decoding tweaks.

Examples: CoT, zero-shot CoT, Tree-of-Thought (next chapter).

Verifiers

Keep generation as-is but add a layer that grades candidates and selects the winner.

Examples: self-consistency, best-of-N, beam search + PRM.

Question ──► Reasoning LLM ──► A₁, A₂, A₃, A₄ (multiple samples) │ ▼ Verification Layer (human or reward model) │ ▼ Best Answer

Crop-field analogy: Finding the best crop in a huge field. You could stop at the first good one — or pluck five or six samples and pick the best among them. Sampling more candidates raises the probability of finding the true optimum. Verifiers do the same for LLM outputs.

The verification layer increases wall-clock inference time and token count. That is exactly why these techniques fall under inference-time compute scaling: pre-training and fine-tuning stay fixed; the inference phase grows because you generate and evaluate multiple candidates before showing the user a single answer.

The ML Lifecycle with Verification

PRE-TRAINING ──► billions of tokens, base capabilities FINE-TUNING ──► instruction following, optional SFT on CoT INFERENCE ──► question in → ×N samples + verifier → answer out

Without verification, inference is a single forward pass. With verification, inference expands horizontally: the same frozen weights run N times (or branch into a search tree), and a separate verifier model may run N additional forward passes. Total test-time FLOPs can exceed training-time FLOPs for a single query — that is intentional.

02 — THE VERIFICATION PIPELINE

How Verification Works

Verification means: generate different answers, then select the best among them. The verifier can be a human (expensive, accurate) or a model trained to mimic human judgment — a reward model.

A canonical example on Hugging Face is OpenAssistant/reward-model-deberta-v3-large-v2. It is trained to predict which generated answer a human would prefer, given a question. Uses include RLHF reward scoring, model evaluation, and ranking toxic responses. The training data consists of human preference labels; the model learns to assign a scalar score so that better answers receive higher rewards.

ComponentRoleWhen it runs
Reasoning LLMGenerates CoT + final answer(s)Every sample
Verifier / reward modelScores each candidateAfter each sample (ORM or PRM)
Selection ruleMajority vote, argmax score, or beam pruneOnce all candidates scored

Production insight: Systems like OpenAI o1 and DeepSeek-R1 likely attach a verification layer before surfacing an answer — often a process reward model that evaluates reasoning steps and returns the path with the strongest chain, not merely the first fluent completion.

The key advantage of verifier-based methods: you do not need to fine-tune or retrain the base reasoning LLM. You wrap it with search and scoring. That makes verifiers the fastest path from a generic model to better reasoning on hard benchmarks.

03 — REWARD MODELS

Outcome vs Process Reward Models

Reward models that power verifiers come in two flavors. The names describe exactly what each one scores.

ORM Outcome Reward Model

Scores only the final answer. The chain-of-thought is ignored — the model does not care how the model arrived there.

score = ORM(question, final_answer)

Example: Question → reasoning trace → answer "42" → ORM returns 0.85.

Best for tasks where only correctness of the endpoint matters (e.g., multiple-choice extraction, numeric answers).

PRM Process Reward Model

Scores each reasoning step individually. The final answer may not be scored directly — correct steps imply a correct conclusion.

score = mean(PRM(q, step₁), …, PRM(q, stepₙ))

Assumption: If every step is sound, the final answer will be sound.

Preferred for math and logic where a wrong intermediate step dooms the solution even if the final number looks plausible.

PRM in Action: Roger's Tennis Balls

Consider the GSM8K-style problem: Roger has 5 tennis balls. He buys 2 cans of 3 tennis balls each. How many does he have now?

Step 1 ✓ 0.92 Roger started with 5 balls.

Step 2 ✗ 0.31 Two cans of three tennis balls each is five tennis balls. (Wrong — should be 6.)

Step 3 ✓ 0.88 Total is 5 + 6 = 11.

A PRM penalizes Step 2 even though Step 3 reaches the correct answer 11 via lucky arithmetic. An ORM might score the final "11" highly and miss the flawed reasoning.

Let's Verify Step by Step (Lightman et al., 2023)

The landmark paper "Let's Verify Step by Step" (Lightman et al., 2023) introduced PRM800K — 800,000 step-level human labels on MATH problem solutions. The authors showed that process supervision (PRMs) substantially outperforms outcome supervision (ORMs) on challenging math benchmarks, because ORMs cannot distinguish lucky guesses from valid derivations.

PRM800K labels each intermediate step as positive, negative, or neutral. A PRM trained on this data learns fine-grained supervision: wrong reasoning gets a lower reward even when the final boxed answer matches. Modern inference stacks — including best-of-N and beam search over reasoning steps — frequently employ PRMs built on this line of work.

Paper tie-in: Snell et al. (2024), Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters, organizes test-time methods into verifiers (this chapter) vs. proposal-distribution modifiers (Chapter 02). The lecture recommends reading it after these three chapters — the theory formalizes when extra inference compute beats training a larger model.

A fully correct chain (Step 2 = 6) would score ~0.90+. PRM ranks the flawed chain lower despite the right final answer.

04 — MAJORITY VOTING

Self-Consistency Decoding

Self-consistency (Wang et al., 2022/2023) is the simplest verifier: sample the LLM many times with stochastic decoding, extract each final answer, and take a majority vote. No separate reward model is required — the verifier is the vote count itself.

â = argmaxa |{ i : extract_answer(y(i)) = a }|

Intuition: diverse reasoning paths that independently reach the same conclusion are more likely correct than a single greedy decode. Temperature > 0 is essential — without diversity in samples, every path may return the same (possibly wrong) answer.

Limitation: Self-consistency has no ground-truth check. If the model systematically biases toward a wrong answer, majority vote amplifies that error. The next method — best-of-N with a trained verifier — addresses this by scoring quality, not just frequency.

Wang et al. report large gains on arithmetic and commonsense reasoning when combining CoT prompting with self-consistency over greedy decoding — often matching or beating much larger models, purely by spending more samples at inference time.

Self-Consistency Algorithm

Pseudocode # Input: question q, LLM, sample count N, temperature T > 0 answers = [] for i in 1..N: chain = LLM.sample(q, temperature=T) # diverse CoT paths answers.append(extract_final(chain)) return mode(answers) # majority vote

The critical hyperparameters are N (how many samples) and temperature (how diverse they are). Too few samples or temperature ≈ 0 collapses self-consistency to ordinary greedy decoding — all paths identical, vote meaningless.

Lecture Example: Prime Numbers (Vote Breakdown)

Six CoT paths on "Are the number of prime numbers finite?" — only final answers counted:

No × 4   Yes × 2

Majority selects No — mathematically correct (Euclid's theorem). If the model were biased toward "Yes" on 4/6 paths, self-consistency would confidently return the wrong answer with no way to detect the error.

05 — BEST-OF-N SAMPLING

Scoring N Candidates with a Verifier

Best-of-N keeps the multi-sample idea but replaces voting with a learned verifier. Sample N complete solutions from the LLM, score each with an ORM or PRM, and return the highest-scoring candidate.

â = argmaxi ∈ {1…N} R(x, y(i))

Where R is either an outcome reward (final answer only) or an aggregate of per-step process rewards.

Self-Consistency

Verifier = vote count. Free, no extra model. Fails when wrong answers dominate.

Best-of-N

Verifier = ORM or PRM. Costs N forward passes + N verifier calls. Catches quality, not just consensus.

06 — STRUCTURED SEARCH

Beam Search Over Reasoning Steps

Beam search is the third verifier strategy — and the most structured. Instead of scoring full chains after the fact, you grow a tree of partial reasoning steps, pruning weak branches at each layer using a PRM. The algorithm dates to speech recognition (HARPY system, 1976): search strategy described as keeping "a few best paths in parallel."

Classic NLP used beam search for translation: at each step, keep the top-k continuations by model probability. For reasoning LLMs, beam width m becomes how many partial chains survive each PRM scoring step; number of beams n is how many new thoughts the LLM generates per active branch per layer.

Parameters

SymbolNameMeaning
nNumber of beamsCandidate thoughts generated at each layer (e.g., 4)
mBeam widthHow many top-scoring paths survive pruning (e.g., 2)
LMax steps / layersDepth of reasoning tree before final answer
At layer ℓ: keep top-m of n (or n×m) scored partial chains → expand each into n children at layer ℓ+1

Unlike best-of-N — which scores entire chains independently — beam search commits early to promising prefixes and abandons dead ends. That makes it more compute-efficient on long reasoning problems when a good PRM is available, but wrong early pruning can be irreversible.

Implementation note: Reference Colab notebooks use notation n = total beams, m = beam width, and max_steps = number of layers. Raising temperature (e.g., 0.9) increases answer diversity across beams — critical when the base model otherwise collapses to identical chains.

Classic Beam Search: Translation Intuition

Before applying beam search to reasoning, the lecture walks through word-by-word translation. A Hindi sentence meaning "I am going to Delhi" is decoded into English one word at a time from a fixed vocabulary (~50,000 words).

Step 0: Vocabulary = 50,000 English words. Model scores each as the first translated word.

Step 1: Top-3 first words by probability: I, Delhi, zoo (beam width = 3).

Step 2: For each surviving prefix, score all 50,000 next words → 150,000 pairs → keep top-3 two-word phrases: I am, I love, zoo ….

Step 3+: Repeat until EOS. Paths like zoo … eventually score poorly and get pruned; I am going to Delhi wins.

The name beam search evokes shining a flashlight (beam) into a vast library — illuminating only a few books (candidates) at each shelf (layer) instead of reading everything.

For reasoning LLMs, "words" become reasoning steps or token spans, and probabilities become PRM scores. The search topology is identical; only the scoring function changes from log-probability to learned step quality.

Layer Expansion with n=4, m=2

Layer 1: LLM generates 4 thoughts → PRM scores → keep top 2 Layer 2: Each survivor branches into 2 children → 4 thoughts → keep top 2 Layer 3: repeat … Layer L: single complete solution (filled node = final answer)

Intermediate nodes are hollow (partial chains); the complete solution node is filled. Unlike best-of-N averaging over full chains, beam search discards low-scoring prefixes permanently — no second chance for a path that starts poorly.

Beam + PRM pseudocode beams = [empty_chain] for step in 1..max_steps: candidates = [] for b in beams: for i in 1..n: thought = LLM.continue(b, temperature=T) score = PRM(question, thought) candidates.append((b + thought, score)) beams = top_m(candidates, key=score) # beam width m return best_complete(beams)
07 — COMPUTE-OPTIMAL INFERENCE

Spending Compute at Test Time

Every technique in this chapter trades more inference compute for better accuracy. The compute budget can be spent on:

  • N samples — linear cost in N for self-consistency or best-of-N
  • Verifier forward passes — one ORM call per sample, or one PRM call per step per sample
  • Beam width × depth — structured search cost grows with n, m, and layers L

Snell et al. (2024) ask: given a fixed FLOP budget at test time, should you sample more chains, use a stronger verifier, or widen the beam? Their analysis shows that optimally allocating test-time compute can outperform simply training a larger model — echoing the lecture's pre-training → fine-tuning → inference diagram where the inference bar grows when verification is enabled.

Without verification Question ──► LLM ──► Answer (1× inference) With verification Question ──► LLM × N samples ──► Verifier ──► Best Answer (N×+ inference)
MethodVerifier typeCompute scalingWhen to use
Self-consistencyMajority voteO(N) generationsQuick win, verifiable extractable answers
Best-of-N + ORMOutcome RMO(N) gen + O(N) ORMFinal-answer tasks, cheap verifier
Best-of-N + PRMProcess RMO(N×L) PRM callsMath, logic — step errors matter
Beam search + PRMProcess RMO(L×n×m) structuredLong chains, early pruning helps

Practical takeaway: Verifiers let you improve a frozen model without gradient updates. The right method depends on your verifier quality, answer format, and latency budget. Production reasoning systems often combine high temperature sampling with PRM-guided beam search — the pattern likely used in o1-class models before answers are shown to users.

08 — BEYOND BEAM SEARCH

Tree Search Strategies for Reasoning

Beam search keeps a fixed-width frontier — greedy at the tree level. Richer tree search strategies explore reasoning more flexibly:

Tree-of-Thought

Deliberately branch on high-level "thoughts," backtrack when a branch looks unpromising, and use LLM self-evaluation or external verifiers to guide expansion. Modifies proposal distribution and uses search.

MCTS

Monte Carlo Tree Search balances exploration and exploitation — simulate rollouts from partial reasoning states, update value estimates, select promising nodes. Used when the search space is too large for fixed beams.

The lecture previews Tree-of-Thought and MCTS briefly before pivoting to reinforcement learning in Chapter 04. Beam search with PRMs sits between simple best-of-N and full game-tree search: structured enough to prune bad prefixes, lightweight enough to run at LLM inference latencies.

10 — PRACTICAL NOTES

Temperature, Diversity, and Colab Experiments

The lecture's beam-search Colab scores Roger's tennis-ball steps with a PRM and plots a search tree. When every beam returns answer 11, the demo shows insufficient diversity — search cannot help if all paths are identical.

Increase temperature (e.g., T=0.9) to diversify samples. The test-time compute paper recommends temperature tuning so best-of-N and beam search actually explore distinct reasoning trajectories. Small models at T≈0 may collapse all beams to one chain.
