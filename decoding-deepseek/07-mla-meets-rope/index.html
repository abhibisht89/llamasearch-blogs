00

Two Innovations That Must Coexist

DeepSeek-V3 and DeepSeek-R1 are built on multi-head latent attention (MLA) — a compression mechanism that stores a low-rank latent representation in the KV cache instead of full keys and values. They also use rotary positional embeddings (RoPE), the dominant positional encoding in modern LLMs because it injects position information without contaminating token embeddings.

These two ideas solve different problems. MLA solves the memory problem: how to cache attention state without storing N×H-dimensional keys and values for every token. RoPE solves the position problem: how to tell the model where each token sits in the sequence. Both are essential. Combining them is not obvious — and naively combining them breaks MLA entirely.

The DeepSeek-V2 paper documents this journey in two sections. Section 2.1.2 describes low-rank key-value joint compression — the basic MLA schematic where only a latent matrix is cached. Section 2.1.3 introduces decoupled rotary position embedding — the fix that makes RoPE and MLA work together. DeepSeek-V3 presents only the advanced version (MLA + RoPE combined) in its architecture section, with equations 1–19 packed into a single dense page. Many blog posts start there and leave readers lost among symbols: D, DC, DC′, DH, DHR, NH, and more.

This chapter unpacks every symbol. By the end, the DeepSeek architecture diagram — with its shaded "cache during inference" regions — will read as clearly as a whiteboard derivation.

01

Why Latent Attention Works — The Absorption Trick

As derived in Chapter 5, the absorption trick folds WUK into WQ (or WDQ·WUQ in DeepSeek-V3), so inference caches only the latent matrix CKV = X·WDKV. Attention scores become a dot product between an absorbed query and cached latents — no full keys stored.

Scores = (X · WDKVT) · (X · Wabsorbed)T   where   Wabsorbed = WQ · WUKT

During inference, only CKV is appended per token. When a new query arrives, it multiplies with the absorbed weights and dots against cached latent vectors.

Key constraint for this chapter: For absorption to work, WQ and WUKT must be directly adjacent in the matrix product chain — with nothing position-dependent between them.

What Gets Cached

In basic MLA, the cache holds CKV with shape (num_tokens × DC), where DC is the latent compression dimension — typically much smaller than NH × DH. Values are recovered on-the-fly by multiplying the cache with WUV. Keys are never stored explicitly; they are absorbed into the query projection.

02

The RoPE Incompatibility Problem

Rotary positional embedding (RoPE), introduced in the RoFormer paper and adopted by LLaMA, Mistral, and DeepSeek, operates on query and key vectors — not on token embeddings. Given a vector at position m, RoPE divides it into pairs (x1, x2), (x3, x4), … and rotates each pair by an angle that depends on position m:

Rm(x1, x2, x3, x4) → (x′1, x′2, x′3, x′4)

If the original vector was [x1, x2, x3, x4], after RoPE it becomes [x′1, x′2, x′3, x′4]. The rotation angle for pair (x1, x2) at position 0 differs from the rotation for the same pair at position 5. Rm is position-dependent. That is exactly what makes RoPE work — and exactly what breaks absorption.

What Happens When You Naively Add RoPE

Suppose we apply RoPE to both queries and keys in MLA:

Q = Rm(X · WQ)     K = Rm(X · WUK · WDKV)

The attention product becomes:

Rm_q(X · WQ) · [Rm_k(X · WUK · WDKV)]T

Now Rm sits between WQ and WUKT. Because Rm changes with position m, we cannot fold WQ · WUKT into a single constant matrix. Absorption is impossible.

The DeepSeek-V2 paper states this precisely: "Rotary positional encoding is incompatible with key-value compression. To be specific, rotary positional encoding is position-sensitive for both keys and queries. If we apply rotary positional encodings, WUK cannot be absorbed into WQ anymore during inference."

The Consequences

If absorption fails, two disasters follow:

  • Keys must be recomputed for every token during inference. The whole point of caching the latent CKV was to avoid recomputing keys. With RoPE in the middle, you must apply Rm to reconstruct full keys at every decode step.
  • MLA's memory advantage vanishes. You are back to storing or recomputing position-sensitive key representations — the exact problem MLA was invented to solve.

Why bother with RoPE at all, then? Because RoPE has decisive advantages over sinusoidal positional encodings: it does not add anything to token embeddings (preserving semantic purity), it operates at the Q/K level where relative position matters most, and empirically it delivers better length generalization and benchmark performance. DeepSeek wanted both — MLA's cache compression and RoPE's positional quality.

Why not use learned positional embeddings with MLA?

Learned absolute embeddings could be added to X before projection, but they contaminate the semantic representation and do not provide the same relative-position inductive bias that RoPE gives through its rotation structure. DeepSeek's own benchmark results show MLA + RoPE outperforming basic MLA on MMLU, CMMLU, and other evaluations — the positional quality matters for capability, not just for correctness.

Why RoPE Is Position-Dependent — A Concrete Example

Consider a single key vector with four dimensions: [x1, x2, x3, x4]. RoPE treats (x1, x2) as one 2D vector and (x3, x4) as another. At position 0, pair 1 might rotate by 0°. At position 3, the same pair rotates by a different angle θ3. The output [x′1, x′2] depends on both the input values and the position index. This is why Rpos cannot be treated as a constant matrix multiplier that commutes with WQ and WUK — it is a function R(pos) that varies row-by-row across the sequence.

03

Decoupled RoPE — The Core Insight

DeepSeek's solution is called decoupled RoPE (Section 2.1.3 in DeepSeek-V2). The name tells you the strategy: decouple the part of attention that needs RoPE from the part that must remain RoPE-free for absorption to work.

Split Queries and Keys in Two

Instead of one query matrix Q and one key matrix K, DeepSeek constructs two query matrices and two key matrices:

Content Path (No RoPE)

QC — queries without RoPE
KC — keys without RoPE
Absorption works here

Position Path (With RoPE)

QR — queries with RoPE applied
KR — keys with RoPE applied
Extra compute, but small

The full query and key are formed by concatenation along the feature dimension:

Q = [QC ; QR]     K = [KC ; KR]

Attention scores decompose by the bilinearity of the dot product:

Q · KT = QC · KCT + QR · KRT

The first term QC · KCT involves no RoPE at all — the absorption trick applies fully. The second term QR · KRT carries all positional information. We accept extra computation for this smaller RoPE-specific subspace, but retain MLA's cache compression for the content subspace.

It sounds like a cheat — solve the hard problem by splitting it in two. But the split is principled: content similarity and positional alignment are different signals, and DeepSeek allocates separate capacity to each. The content path uses the full latent compression machinery; the position path uses a deliberately small DHR dimensional subspace.

The Trade-Off Stated Clearly

DeepSeek increases computation slightly by adding QR and KR matrices and their RoPE operations. In exchange, it retains the old magic of MLA on the QC/KC path. The RoPE path is small (DHR × NH dimensions, with KR shared across heads — more on that later), so the extra cost is bounded. The content path still caches only CKV.

Part One — The No-RoPE Path (Left Side)

Input embedding matrix X has shape (4 × 8): four tokens, eight features each.

Step 1 — Latent Compression (CKV)

Project X into latent space via WDKV with shape (8 × 4):

CKV = X · WDKV   →   (4 × 8) · (8 × 4) = (4 × 4)

This CKV matrix is the only latent cache on the content path. Its column count DC = 4 determines KV cache size per token. The dotted-box notation in the DeepSeek diagram marks CKV as "cache during inference."

Step 2 — Keys and Values from Latent

Up-project CKV into key and value spaces. WUK and WUV each have shape (4 × 8) — that is (DC × D):

KC = CKV · WUK   →   (4 × 4) · (4 × 8) = (4 × 8)
VC = CKV · WUV   →   (4 × 4) · (4 × 8) = (4 × 8)

WUK is different per head (not shared). KC and VC have full model dimension D = 8. No RoPE is applied anywhere on this path.

Step 3 — Queries via Down-Projection and Up-Projection

DeepSeek-V3 adds a change from basic MLA: queries are not computed as X · WQ directly. Instead:

CQ = X · WDQ   (4×8)·(8×4) → (4×4)
↓
QC = CQ · WUQ   (4×4)·(4×8) → (4×8)

WDQ down-projects queries into DC′ = 4 dimensions. WUQ up-projects back to D = 8. The DeepSeek paper notes this saves activation memory during training and empirically improves performance — two extra matrices (WDQ, WUQ) replace the single WQ from basic MLA.

At inference, absorption uses WDQ · WUQ · WUKT as the absorbed query-side matrix (replacing WQ · WUKT from basic MLA).

Left-side summary: Three matrices produced — KC (4×8), VC (4×8), QC (4×8). Zero RoPE. Absorption fully valid. Cache: CKV only (4×4).

Part Two — The RoPE Path (Right Side)

The right side of the decoupled schematic constructs new query and key matrices whose sole purpose is carrying positional information via RoPE. These are QR and KR.

Building KR — Shared Key Across Heads

Start from the same input X (4×8). Multiply by WKR with shape (8 × DHR) = (8 × 4):

KR,base = X · WKR   →   (4 × 8) · (8 × 4) = (4 × 4)

Apply RoPE position-by-position. RoPE preserves dimension, so output remains (4 × 4). Now expand across NH = 2 heads by replicating the same rotated key for each head:

KR = expand_heads(RoPE(KR,base))   →   (4 × 8)

Critical design choice from the DeepSeek paper: "We use a shared key across all heads which carry the rotary positional embedding component." WKR has DHR columns, not NH × DHR. If each head had its own WKR, the weight matrix would be (8 × 8) for two heads — and the cache would need NH × DHR per token instead of just DHR.

Building QR — Per-Head Queries (Not Shared)

Queries on the RoPE path reuse the down-projected CQ from the left side — the same (4×4) matrix. Multiply by WQR with shape (DC′ × NH × DHR) = (4 × 8):

QR,pre = CQ · WQR   →   (4 × 4) · (4 × 8) = (4 × 8)

Apply RoPE to get the final QR (4×8). Unlike KR, WQR already spans all heads — its column dimension is NH × DHR = 8. Queries are not shared across heads; only the RoPE key is shared. This preserves head diversity in the positional query subspace while minimizing KR cache size.

KR (shared)

WKR: (8 × DHR). Same rotated key replicated across heads. Cache: DHR per token.

QR (per-head)

WQR: (DC′ × NH·DHR). Different query per head. Not cached — computed fresh for new token only.

Mapping to Paper Equations 14–15

Equation 14: QR = RoPE(CQ · WQR). Start from down-projected queries, up-project into RoPE subspace, apply rotation.

Equation 15: KR = expand(RoPE(X · WKR)). Project input directly, rotate, replicate across heads.

Both QR and KR end up as (4 × 8) = (tokens × NH·DHR) matrices, but they arrive there differently — KR via sharing and expansion, QR via per-head WQR.

06

Concatenation, Attention Scores, and Output

With QC, QR, KC, KR, and VC computed, we assemble full queries and keys by concatenation along the feature axis (Equations 16–17):

Q = [QC ; QR]    (4 × 16)     K = [KC ; KR]    (4 × 16)

In our toy example each half is (4×8), so the concatenated dimension is 8 + 8 = 16 per token. The attention score matrix (Equation 18) decomposes:

S = Q · KT = QC·KCT + QR·KRT    each term (4 × 4)

First term: no RoPE → absorption applies. Second term: pure positional dot-product in the DHR subspace. Add the two (4×4) score matrices element-wise to get the final pre-softmax scores.

Scaling, Softmax, and Context

Scale by √(DH + DHR) — in our example √(4 + 4) = √8. This keeps dot-product variance near 1 when query and key each have DH + DHR total dimensions split across content and RoPE parts:

Weights = softmax(S / √(DH + DHR))   →   (4 × 4)

Multiply weights by VC (4×8) — values come only from the content path; the RoPE path contributes to where to attend, not what to retrieve:

O = Weights · VC   →   (4 × 4) · (4 × 8) = (4 × 8)

Output O passes through the output projection WO to produce logits (Equation 19, denoted uT in the paper).

Inference — When "bright" Arrives

During autoregressive inference, prefix "The next day is" is already processed. The model predicts "bright" as the next token. Trace exactly what happens when "bright" enters the MLA + RoPE pipeline.

Path 1 — Content (Absorption, No RoPE)

For the new token x = embed("bright") with shape (1 × 8):

qabsorbed = x · WDQ · WUQ · WUKT   →   (1 × 4)

Compute new latent row and append to cache:

cnew = x · WDKV   →   (1 × 4) appended to CKV: (4×4) → (5×4)

Attention scores via absorption:

s1 = qabsorbed · CKVT   →   (1 × 5)

Five positions: The, next, day, is, bright. No key recomputation for old tokens — only one new latent row added.

Path 2 — RoPE

Compute and cache new KR row:

kR,new = expand(RoPE(x · WKR))   →   (1 × 8), append to KR cache: (4×8) → (5×8)

Compute QR for the new token (not cached — query is always fresh):

qR = RoPE(x · WDQ · WQR)   →   (1 × 8)

RoPE path scores:

s2 = qR · KRT   →   (1 × 5)

Combine and Predict

s = s1 + s2   →   softmax(s / √8) · VC   →   context (1 × 8)

Only the last token's context vector (1×8) feeds the output head for next-token prediction. Values VC recovered by VC = CKV · WUV on the updated (5×4) cache.

What Gets Cached — Reading the Diagram

The DeepSeek architecture diagram marks two regions with dashed boxes labeled "cache during inference":

  • CKV — the latent KV matrix from the content path (same as basic MLA)
  • KR — the RoPE key matrix, stored at DHR per token (one head's worth, replicated at attention time)

What is not cached: QC, QR, KC, VC in full. Q vectors are computed fresh for the current token. KC and VC are derived from CKV via WUK and WUV — the up-projection weights are fixed and applied on-the-fly or partially absorbed.

Why KR Must Be Cached

Unlike the content path, the RoPE path cannot absorb WQR and WKRT because RoPE(Rm(·)) depends on position m. Each cached KR row stores the already-rotated key for that position. When a new query at position 5 arrives, it dots against all five cached rotated keys — no recomputation of old keys needed.

Head Sharing and Memory

If KR were not shared across heads, cache per token would be DC + NH × DHR. By sharing WKR and replicating at compute time, DeepSeek reduces the RoPE cache to DHR only. Queries remain per-head (WQR has NH · DHR columns) so model quality is preserved — only the positional key side shares across heads, not the content path.

Does sharing KR across heads hurt performance?

DeepSeek's benchmarks show MLA + RoPE matching or beating standard MHA — the shared RoPE key carries positional alignment signal that all heads can use, while head-specific diversity lives in QC, QR, and WUK. The content path (the bulk of representational capacity) shares nothing across heads.

Memory Comparison — MHA vs MQA vs GQA vs MLA vs MLA+RoPE

The entire motivation chain begins with KV cache memory. Here are the formulas for cache size (16-bit / 2 bytes per element), batch B, context length S, layers L:

MHA:   2 × 2 × L × B × S × N × DH

The leading 2×2: one factor for K vs V, one for 2 bytes (fp16). N = number of heads, DH = head dimension.

MQA:   2 × 2 × L × B × S × DH   (N removed — one shared K/V set)
GQA:   2 × 2 × L × B × S × G × DH   (G groups instead of N heads)
MLA (basic):   2 × L × B × S × DL   (one 2 gone — joint latent, no separate K/V)
MLA + RoPE:   2 × L × B × S × (DL + DHR)

DeepSeek's chosen dimensions: DL = 4 × DH and DHR = DH / 2. Substituting:

DL + DHR = 4DH + DH/2 = 4.5 DH
MHA / MLA+RoPE = (2 × N × DH) / (DL + DHR) = 2N DH / (4.5 DH) = 4N / 9

With N = 128 heads (DeepSeek-V3):

4 × 128 / 9 ≈ 56.9 ≈ 57× memory reduction vs MHA

DeepSeek's own reported numbers: KV cache per token ~860 KB (MHA) vs ~34.6 KB (MLA) — roughly 25× in one comparison, 6–7× in another configuration. The formula gives the asymptotic ratio; constants depend on layer count, batch, and whether MOE layers are included.

RoPE Mathematics — Rotation by Position

Rotary positional embedding treats consecutive dimension pairs as coordinates in 2D planes and rotates each plane by an angle proportional to token position. For dimension pair (2i, 2i+1) at position m:

Rm(x2i, x2i+1) = (x2i cos(mθi) − x2i+1 sin(mθi),   x2i sin(mθi) + x2i+1 cos(mθi))

Base frequencies θi = 10000−2i/d (standard RoPE schedule). Position m enters through mθi — that is why Rm is not a single constant matrix: row m of the sequence uses rotation angle mθ, row n uses nθ.

Concrete Four-Dimensional Example

Vector at position 0: [x1, x2, x3, x4]. Two pairs: (x1, x2) and (x3, x4). At position 0, rotation angle is 0 for both pairs (cos 0 = 1, sin 0 = 0), so the vector is unchanged: [x′1, x′2, x′3, x′4] = [x1, x2, x3, x4].

Same vector at position 3: pair (x1, x2) rotates by 3θ0, pair (x3, x4) rotates by 3θ1 where θ1 ≠ θ0. Output [x′1, x′2, x′3, x′4] differs from the position-0 output even with identical input values. Position is baked into the rotated vector.

Attention dot-products between RoPE-transformed Q and K depend on relative position (m − n) — the elegant property that makes RoPE work for autoregressive models. But this same property means Rm cannot commute with fixed weight matrices WQ and WUK in a way that allows absorption across positions.

Why Not Apply RoPE Only to Queries?

If keys cause the caching problem, why not apply RoPE only to queries? Attention scores Q·KT must encode relative position symmetrically — both Q and K need compatible positional transformations for the dot product to measure positional alignment. Applying RoPE to only one side breaks the relative-position property that makes RoPE effective. DeepSeek applies RoPE to both QR and KR in the position subspace while keeping QC and KC free of RoPE in the content subspace.

Applying RoPE to the full Q and K in MLA forces per-position key reconstruction: for each cached token at position m, you need Rm(x·WUK·WDKV) — the rotation depends on m, so the absorbed form X·WDKV alone is insufficient.

B

Absorption Trick — Inference Algebra

Chapter 5 derives the full absorption identity. At inference, scores reduce to (x · Wabs) · CKVT where Wabs = WDQ · WUQ · WUKT in DeepSeek-V3. Only x · WDKV is appended to CKV for each new token.

Naive RoPE breaks this: score = Rm(x · WQ) · (Rk(ck · WUK))T. Rotation matrices Rm and Rk differ per position and cannot fold into a fixed Wabs.

Values Recovery

Values are not absorbed into queries. After softmax weights w (1×S):

output = w · VC = w · CKV · WUV

WUV is applied to the full cached CKV (S × DC) to get VC (S × D), then weighted by attention. The cache itself remains CKV, never full V.

class MLAAttention(nn.Module): def __init__(self, d_model, n_heads, d_c, d_hr): self.w_dkv = nn.Linear(d_model, d_c, bias=False) self.w_uk = nn.Linear(d_c, d_model, bias=False) # per-head in full impl self.w_uv = nn.Linear(d_c, d_model, bias=False) self.w_dq = nn.Linear(d_model, d_c, bias=False) self.w_uq = nn.Linear(d_c, d_model, bias=False) self.w_kr = nn.Linear(d_model, d_hr, bias=False) # shared across heads self.w_qr = nn.Linear(d_c, n_heads * d_hr, bias=False) self.rope = RotaryEmbedding(d_hr) self.scale = (d_model // n_heads + d_hr) ** -0.5 def forward(self, x, c_kv_cache=None, kr_cache=None): c_kv = self.w_dkv(x) k_c = self.w_uk(c_kv) v_c = self.w_uv(c_kv) c_q = self.w_dq(x) q_c = self.w_uq(c_q) k_r_base = self.w_kr(x) k_r = self.rope(k_r_base).repeat_interleave(n_heads, dim=-1) # expand q_r = self.rope(self.w_qr(c_q)) q = torch.cat([q_c, q_r], dim=-1) k = torch.cat([k_c, k_r], dim=-1) scores = (q @ k.transpose(-2,-1)) * self.scale out = F.softmax(scores, dim=-1) @ v_c return out, c_kv, k_r # return caches for inference

Production DeepSeek code splits WUK, WUV per head and fuses operations — but the dataflow matches this skeleton. Inference passes c_kv_cache and kr_cache from prior steps, appending new rows for each generated token.

Design Rationale — Why Each Choice Was Made

Why Decouple Instead of Dropping RoPE?

Basic MLA without RoPE works and compresses well, but DeepSeek's benchmark table shows MLA + RoPE outperforming basic MLA on knowledge and reasoning tasks. RoPE provides relative positional inductive bias that absolute or learned embeddings do not match. The decoupling trick adds minimal cache overhead (DHR per token, with DHR = DH/2) while unlocking RoPE's quality benefits.

Why Share KR But Not QR?

Positional keys answer "where is this token?" — a scalar location signal shared across heads is sufficient for aligning positions. Positional queries answer "what relative position am I looking for?" — different heads attend at different syntactic/semantic granularities and need distinct positional query patterns. Sharing KR saves NH× in RoPE cache; not sharing QR preserves head expressivity.

Why Query Down-Projection?

Training activations for QC path: storing full (batch × seq × D) query activations is expensive. Down-projecting to DC′ first reduces memory during backpropagation. DeepSeek reports this also improves final model quality — possibly by acting as a bottleneck regularizer on query representations.

Why Values Only from Content Path?

VC carries semantic content retrieved by attention. The RoPE subspace encodes position, not lexical semantics. Adding a VR would mix positional artifacts into the retrieved content. Keeping values on the content path ensures attention weights (informed by both content and position scores) select semantic information from VC only.

Does decoupling increase compute cost?

Yes, modestly: extra QR, KR projections and RoPE ops per token. But inference is memory-bandwidth bound — reducing cache size (57×) improves throughput more than the extra FLOPs hurt. The RoPE subspace is small (DHR = DH/2 per head slice, shared on K side).

The Warehouse Analogy — Why Decoupling Works

Imagine a warehouse matching customer orders (queries) to packages (keys). Each package carries a content barcode and a shelf location code. MLA stores compressed SKU codes (CKV) instead of full labels; absorption lets orders match against SKUs via a fixed template.

The Absorption Trick — Why It Is Lossless

Absorption is not an approximation. Matrix multiplication is associative: (X WQ)(WUKT CKVT) = X (WQ WUKT) CKVT. What changes at inference is order of operations, not result.

RoPE(Rm(·)) is position-dependent and prevents constant folding of WQ and WUKT across the sequence — the core conflict this chapter resolves via decoupling.

◆

RoPE on Queries and Keys — Pairwise Rotation

RoPE operates on the last dimension of Q and K, treating consecutive pairs as 2D coordinates. For a vector [x_1, x_2, x_3, x_4, ..., x_{d-1}, x_d], pairs (x_1,x_2), (x_3,x_4), etc. each rotate independently.

The rotation angle for pair i at position m is m * theta_i where theta_i = 10000^{-2i/d}. Low-index pairs rotate slowly (capture long-range position). High-index pairs rotate quickly (capture fine local position). This frequency spectrum is what gives RoPE its extrapolation behavior.

When DeepSeek applies RoPE in the decoupled path, it applies only to the D_HR-dimensional subspace — not the full D-dimensional Q and K. With D_HR = D_H/2 = 64 per head slice and N_H = 128 heads, the RoPE subspace is 8192 dimensions total in Q_R and K_R concatenation — but K_R cache stores only D_HR = 64 per token due to head sharing on the key side.

Preserving dimension through RoPE is critical: ||RoPE(v)|| = ||v||. The rotation is orthonormal. Scaling attention by sqrt(d_h + d_h^R) accounts for the increased total dimension after concatenating content and RoPE subspaces.

◆

Decoupled RoPE — The Concatenation Identity

Why does Q K^T = Q_C K_C^T + Q_R K_R^T work without cross terms? Because Q_C and Q_R live in disjoint subspaces produced by different projection matrices, and K_C and K_R similarly. The full Q vector is [Q_C; Q_R] and full K is [K_C; K_R].

Computing [Q_C; Q_R] [K_C; K_R]^T expands to Q_C K_C^T + Q_R K_R^T when cross blocks Q_C K_R^T and Q_R K_C^T are zero — which holds when the projection matrices are constructed so content and RoPE subspaces do not overlap in the naive concatenation layout.

In implementation, W_UQ projects to content dims and W_QR projects to RoPE dims from the same c_Q — the network learns during training to keep semantic and positional information factored across these branches.

This is mathematically equivalent to a single attention with structured Q/K, but algorithmically it allows the content block to use absorption while the RoPE block uses explicit caching of k_R.

Inference Efficiency — Two Paths, Two Caches

Each decode step appends one row to C_KV and one row to K_R. No O(S) key recomputation for prior tokens on either path. Path 1 uses absorption: O(D_C) dot product against full cache. Path 2 uses Q_R K_R^T: O(N_H D_HR) — smaller than content path when D_HR is small.

Compare to naive MLA+RoPE without decoupling: would need O(S * D) key recomputation per step as RoPE rotates all historical keys. At S=100K, that is catastrophic for latency.

Values V_C are derived from C_KV via W_UV at each step — O(S * D_C * D) but can be optimized by not materializing full V_C when only weighted sum is needed. FlashAttention-style fused kernels combine these operations.

DeepSeek's inference stack (custom CUDA kernels, expert parallelism) builds on this cache structure. The 57× memory reduction translates directly to more tokens served per GPU hour.

The 57× Formula — Full Derivation

Start with bytes per token per layer (fp16, batch=1):

MHA: 2 (K+V) × 2 (bytes) × N × D_H = 4 N D_H
MLA+RoPE: 2 (bytes) × (D_L + D_HR) = 2 (4 D_H + D_H/2) = 2 × 4.5 D_H = 9 D_H
Ratio = 4 N D_H / (9 D_H) = 4N/9

For N=128: 512/9 ≈ 56.89. Rounding gives ~57×.

The factor 9 in the denominator is (D_L + D_HR) / D_H = 4.5, times 2 bytes. The factor 4N in the numerator is 2 (K+V) × 2 (bytes) × N / (2 bytes) simplified — or equivalently 2×2×N/2 = 4N when comparing element counts.

Reported 25× in DeepSeek charts includes all layers (some MoE without full attention), implementation overhead, and possibly different precision. The 57× is the pure attention-cache theoretical ratio — both numbers are correct in context.

Shared K_R vs Per-Head Q_R — Design Deep Dive

The asymmetry between shared RoPE keys and per-head RoPE queries is one of the most subtle details in the DeepSeek implementation. Many readers assume both Q_R and K_R are treated identically — they are not.

W_KR has shape (D × D_HR). Multiplying X (S × D) gives (S × D_HR). After RoPE and head expansion, K_R appears as (S × N_H × D_HR) but only D_HR values per row are unique — the rest are copies. Cache stores the (S × D_HR) unique values.

W_QR has shape (D_C′ × N_H × D_HR). Multiplying C_Q (S × D_C′) gives (S × N_H × D_HR) directly — each head slice of Q_R is different because W_QR columns partition across heads. No expansion step needed; diversity is built into the weight matrix.

Intuition: all heads need to know where each token is (shared K_R), but each head asks different positional questions (distinct Q_R). Head 1 might attend locally; head 2 might attend to sentence boundaries — different Q_R patterns enable this while K_R provides common positional landmarks.

If W_KR were per-head (D × N_H × D_HR), cache would grow to D_C + N_H × D_HR — erasing much of the RoPE-side savings. DeepSeek explicitly chose sharing to keep cache at D_C + D_HR.

◆

Values Only from V_C — Why No V_R

Attention output is softmax(scores) · V. In MLA+RoPE, V comes exclusively from the content path: V_C = C_KV W_UV. There is no V_R.

The RoPE subspace influences where the model looks (attention weights) but not what information is retrieved. Retrieved content is always from the semantic latent cache, up-projected through W_UV.

If values also split into content and RoPE parts, the output would mix positional artifacts into the residual stream — potentially destabilizing layer normalization and FFN inputs downstream.

Scores combine content and position: w = softmax(Q_C K_C^T + Q_R K_R^T). Then output = w V_C. Position modulates the weighting; semantics flow through V_C alone. Clean separation of concerns.

Reading Equations 16–18 as One Operation

Equation 16 concatenates q_C and q_R. Equation 17 concatenates k_C and k_R. Equation 18 performs scaled dot-product attention and multiplies by v. Visually in the paper diagram, these three steps appear as one attention block after the branching converges.

The scale factor sqrt(d_h + d^R_h) is essential. Without it, concatenating two subspaces of dimensions d_h and d^R_h would increase dot-product variance by factor (d_h + d^R_h)/d_h — softmax would sharpen excessively. DeepSeek generalizes the standard 1/sqrt(d_h) scaling to account for both subspaces contributing to the dot product.

In our toy example: d_h = 4, d^R_h = 4, scale = 1/sqrt(8) ≈ 0.354. Standard MHA with d_h = 8 would use 1/sqrt(8) as well — same total Q/K width, consistent scaling philosophy.

Common Pitfalls When Implementing MLA+RoPE

Pitfall 1: Applying RoPE to C_KV or K_C. RoPE belongs only on the RoPE subspace (Q_R, K_R), never on latent cache or content keys.

Pitfall 2: Caching full K_R with N_H duplication. Store D_HR per token; expand at matmul time.

Pitfall 3: Using single W_Q instead of W_DQ · W_UQ. Breaks training memory optimization and changes absorption to W_DQ · W_UQ · W_UK^T.

Pitfall 4: Forgetting to add score paths before softmax. Must compute S = S_C + S_R, not separate softmaxes.

Pitfall 5: Scaling by sqrt(d_h) only. Concatenated Q/K have effective dimension d_h + d_h^R — scale must match.

Pitfall 6: Materializing full K_C during inference. Use absorption — never store or recompute full content keys.

Pitfall 7: Adding V_R. Values come from V_C only. RoPE path has no value projection.

Prefill vs Decode — Cache Behavior

During prefill, the entire prompt is processed in parallel. C_KV and K_R are computed for all S tokens simultaneously and stored. Absorption can still be used for Q_C K_C^T during prefill, or full Q_C and K_C computed directly — both are equivalent.

During decode, one token arrives per step. Only the new row is appended to caches. Absorption is critical here — without it, each decode step would require O(S) work scaling linearly with context, negating MLA benefits when combined with RoPE.

DeepSeek serving systems optimize both phases: prefill is compute-bound (parallel matmuls), decode is memory-bandwidth-bound (cache reads). MLA+RoPE shrinks the decode bottleneck by 57× — the primary economic win.

What breaks if you apply RoPE to C_KV directly?

C_KV is position-agnostic latent storage. Applying RoPE to it would entangle position into the compressed representation, forcing position-specific latent caches — defeating compression.

Can D_HR be zero?

Then Q_R and K_R are empty — you recover basic MLA without RoPE. DeepSeek finds D_HR = D_H/2 optimal for quality.

Is concatenation along features equivalent to separate attentions?

No — single softmax over combined scores. The decomposition Q_C K_C^T + Q_R K_R^T works because cross terms Q_C K_R^T and Q_R K_C^T are zero when subspaces are orthogonal by construction (different projection matrices).

How are subspaces kept separate?

W_UK and W_QR project from different latent paths into orthogonal-ish learned subspaces. Training learns to factor content vs position.

Does this work with multi-head?

Yes — N_H heads. Content path: per-head W_UK slices. RoPE path: per-head Q_R, shared K_R expanded.

RoPE on KR — Position-by-Position Example

For each token in the whiteboard sequence, KR applies RoPE at that token's position m. Pair (x1, x2) rotates by angle m·θ0; pair (x3, x4) rotates by m·θ1 (with θ1 ≠ θ0). At m=0 ("The"), all angles are zero and RoPE is the identity. At m=1, 2, 3 ("next", "day", "is"), rotations accumulate — the same pre-RoPE projection yields different rotated vectors per position.

Each rotated (DHR=4) vector is replicated across NH=2 heads and stored as one row of the KR cache (4 floats stored, 8 displayed after expansion). Attention scores between query position q and key position j depend on relative offset (q − j) through the RoPE dot product.

Production DeepSeek code fuses WDKV projection with cache append operations to minimize memory bandwidth. The explicit matrix forms in this chapter are for clarity; deployed systems apply these optimizations:

  • Fuse WDQ and WUQ into the absorbed query path at inference time.

Step-by-Step Score Computation — Numeric Template

For tokens indexed 0..3 at positions m=0..3, the score matrix S[i,j] = score from query token i to key token j.

Content component: S_C = Q_C @ K_C.T. Q_C[i] from C_Q[i] @ W_UQ. K_C[j] from C_KV[j] @ W_UK. Absorption form: S_C[i,j] = (X[i] @ W_abs) @ C_KV[j].

RoPE component: S_R = Q_R @ K_R.T. Q_R[i] = RoPE_m(i)(C_Q[i] @ W_QR). K_R[j] = expand(RoPE_m(j)(X[j] @ W_KR)). Relative position (i-j) encoded in dot product.

Combined: S = S_C + S_R. Apply causal mask: S[i,j] = -inf if j > i. Scale: S /= sqrt(8). Weights: W = softmax(S, dim=-1). Output[i] = W[i] @ V_C.

For inference token 4 ("bright"): only row i=4 computed. S[4,:] shape (1×5). Caches provide C_KV (5×4) and K_R (5×8 effective 5×4 unique).

This completes the numeric picture: theoretical 57× from 4N/9, empirical 25× from reported KB/token, both confirming MLA+RoPE as the production attention mechanism for DeepSeek-V3 and R1.

Inference Deep Dive — Token "bright" Step by Step

Prefix after four tokens: The next day is. Caches: CKV is (4×4), KR is (4×8). New token "bright" arrives as the fifth token at position index 4 (0-based). Every operation below uses our toy dimensions D=8, DC=4, DHR=4, NH=2.

Step A — Embed the New Token

xbright = Embedding("bright") + positional component if using learned pos (RoPE applied later in attention, not here). Shape: (1×8).

Step B — Path 1: Content Attention Scores

B1. Compute absorbed query: qabs = x · WDQ · WUQ · WUKT. Shapes: (1×8)·(8×4)·(4×8)·(8×4) — wait, WUKT maps from D to DC, so absorbed path is (1×8)·(8×4)·(4×8) for WDQ·WUQ giving (1×8), then · WUKT (8×4) → (1×4). Correct final: (1×4).

B2. Compute new latent row: cnew = x · WDKV → (1×4).

B3. Append to cache: CKV goes from (4×4) to (5×4).

B4. Scores path 1: s1 = qabs · CKVT → (1×4)·(4×5) = (1×5). Entry s1[0,4] is "bright attends to bright"; s1[0,0] is "bright attends to The", etc.

Step C — Path 2: RoPE Attention Scores

C1. kr,base = x · WKR → (1×8)·(8×4) = (1×4).

C2. Apply RoPE at position 4: rotate pairs in the (1×4) vector using angle 4θi for each pair i.

C3. Expand across heads: replicate the (1×4) vector twice → (1×8). This is kr,new.

C4. Append to KR cache: (4×8) → (5×8).

C5. Compute QR: cq = x · WDQ → (1×4). qr,pre = cq · WQR → (1×8). qR = RoPE(qr,pre) at position 4 → (1×8).

C6. s2 = qR · KRT → (1×8)·(8×5) = (1×5).

Step D — Combine, Softmax, Output

D1. s = s1 + s2 element-wise → (1×5).

D2. Apply causal mask if any future positions existed (none here — all five are past/current).

D3. w = softmax(s / √8) → (1×5).

D4. VC = CKV · WUV → (5×4)·(4×8) = (5×8).

D5. context = w · VC → (1×5)·(5×8) = (1×8). This is the context vector for "bright".

D6. Feed context through FFN, output head → logits → argmax → next token prediction.

Notice: we never stored full KC or VC in cache. We stored CKV (4 floats per token) and KR (4 effective floats per token due to head sharing). Total 8 floats/tok/layer vs MHA's 2×N×DH = 2×2×4 = 16 floats/tok/layer in toy dims — or 2×128×128 = 32768 in production.

Can you use YaRN or other RoPE extensions with MLA+RoPE?

Yes — RoPE extensions modify the θ schedule or apply scaling to the RoPE subspace. They apply to Q_R and K_R the same as standard RoPE. The content path Q_C/K_C is unaffected.

Does MLA+RoPE work with FlashAttention?

Yes. Concatenated Q and K can be passed to fused attention kernels. Cache stores compressed c_KV and k_R separately; kernels reconstruct or use decomposed scores depending on implementation.

Why not use ALiBi instead of RoPE with MLA?

ALiBi adds position bias to attention scores without rotating Q/K. It might avoid the absorption conflict — but DeepSeek chose RoPE for empirical performance. ALiBi+MLA is unexplored in their papers.

Is W_UK different per head?

Yes on the content path. Each head has its own slice of W_UK and W_UV. Only W_KR is shared on the RoPE key path.

What happens at context lengths beyond training?

RoPE subspace handles length extrapolation (especially with YaRN in R1). Content path behaves like standard MLA — cache grows linearly with D_C + D_HR per token regardless of length.

How does batching affect cache?

Cache shape includes batch dimension B. Each sequence in batch has independent C_KV and K_R caches. Memory formula: 2 × L × B × S × (D_L + D_HR).

Is the absorption trick used at training time?

Yes — training computes gradients through W_DQ, W_UQ, W_UK normally. Absorption is an inference optimization that precomputes W_DQ·W_UQ·W_UK^T for faster decode.

Why 4× head dim for D_L?

Empirical choice in DeepSeek-V2/V3. Provides enough latent capacity to preserve MHA-level quality while staying much smaller than N×D_H. Ablation in paper shows performance sensitive to D_C rank.

Does DeepSeek-R1 use the same MLA+RoPE?

Yes. R1 builds on V3 architecture with reinforcement learning — the attention mechanism including decoupled RoPE is inherited from V3.

What's the FLOPs overhead of the RoPE path?

Two extra projections (W_QR, W_KR) and RoPE rotations on D_HR dims — O(S·D·D_HR) vs content path O(S·D·D_C). D_HR << D, so overhead is small relative to FFN and MoE layers.

Numeric Walkthrough — 57× Memory Ratio

Let D_H = 128, N = 128. MHA cache per token per layer (K and V, fp16):

2 matrices × 2 bytes × 128 heads × 128 dims = 65,536 bytes = 64 KB per token per layer.

MLA+RoPE with D_L = 4×128 = 512, D_HR = 64:

2 bytes × (512 + 64) = 1,152 bytes ≈ 1.1 KB per token per layer.

Ratio: 65536 / 1152 = 56.89 ≈ 57×.

Over 61 layers and 100K context (ignoring batch): MHA ≈ 64KB × 61 × 100K ≈ 390 GB. MLA+RoPE ≈ 1.1KB × 61 × 100K ≈ 6.7 GB. Same ratio.

DeepSeek reports ~860 KB vs ~34.6 KB per token aggregate — includes all layers, MoE routing, and implementation details. The 25× figure is an end-to-end measured ratio; 57× is the attention-theoretic ratio. Both validate massive savings.

Summary — The Complete Picture

Multi-head latent attention compresses the KV cache via the absorption trick: WQ·WUKT merges at train time, leaving only CKV = X·WDKV to cache. Rotary positional embeddings are position-dependent and sit between those matrices if applied naively — destroying absorption and forcing full key recomputation.

DeepSeek's decoupled RoPE solves this by splitting attention into two parallel paths:

  1. Content path (QC, KC, VC): No RoPE. Full MLA compression. Cache CKV.
  2. Position path (QR, KR): RoPE injected. Small DHR subspace. Cache KR (shared across heads).

Scores add: S = QCKCT + QRKRT. Scale by √(DH+DHR). Softmax. Multiply VC. The result: ~57× smaller cache than MHA with equivalent or superior benchmark performance — the architectural foundation that makes DeepSeek-V3 and R1 inference-efficient at frontier quality.
