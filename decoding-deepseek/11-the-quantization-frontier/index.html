00 · THE FINAL PILLAR

From Architecture to Infrastructure

DeepSeek-V3's technical report splits into architecture (Multi-Head Latent Attention, Mixture of Experts, Multi-Token Prediction) and infrastructure. Section 3.3, FP8 Training, describes how DeepSeek trains and stores model parameters at dramatically reduced precision without collapsing model quality — the fourth pillar of the stack, engineered with the same care as the attention mechanism and expert router.

DeepSeek implements five distinct quantization innovations:

  • Mixed precision framework — different tensors stored and computed at different bit widths
  • Fine-grained quantization — per-block scaling factors instead of one scale per entire tensor
  • Increasing accumulation precision — periodic promotion of partial sums from tensor cores to CUDA cores
  • Mantissa over exponents — choosing E4M3 uniformly instead of mixing E4M3/E5M2
  • Online quantization — computing scale factors from the current tensor, not historical maxima

The five innovations at a glance

1. Mixed Precision Framework Section 3.3.1

Not all tensors deserve the same bit width. Master weights and weight gradients live in FP32. Activations store as BF16. Bulk matrix multiplications compute in FP8 on Tensor Cores. Sensitive modules — embeddings, attention, gating, normalization, output head — stay at BF16 or FP32. The "mixed" in mixed precision refers to this deliberate heterogeneity.

2. Fine-Grained Quantization Section 3.3.2

Instead of one scale factor per tensor, DeepSeek computes one scale factor per 128-element block of activations and per 128×128 block of weight matrices. This isolates outliers: a spike in one block cannot corrupt quantization in adjacent blocks. The block size NC = 128 aligns with NVIDIA Tensor Core tile dimensions.

3. Increasing Accumulation Precision Section 3.3.2

Tensor Cores accumulate GEMM partial sums at ~14-bit precision — insufficient for K=4096 inner dimensions. DeepSeek promotes partial sums to FP32 CUDA Core registers every 128 elements. This "promotion to CUDA cores" keeps accumulation error near zero while retaining Tensor Core FP8 throughput for the multiply step.

4. Mantissa Over Exponents Section 3.3.3

FP8 E4M3 (4 exponent, 3 mantissa bits) provides higher precision; E5M2 (5 exponent, 2 mantissa) provides wider range. Prior practice: E4M3 for forward, E5M2 for backward. DeepSeek uses E4M3 uniformly because fine-grained scaling eliminates the need for E5M2's extra range.

5. Online Quantization Section 3.3.3

Scale factors are computed from the current tensor's maximum absolute value — not from historical maxima stored from previous iterations. This prevents overflow when activation distributions shift during training. Online quantization adds O(block_size) overhead per block, fused with the quantization kernel.

Quantization is not an afterthought bolted onto a finished model. DeepSeek trains natively in FP8. The precision decisions are woven into every forward pass, every backward pass, and every weight update from the first training step.

01 · THE PROBLEM

Why Quantization Matters for Large Language Models

Every parameter in a large language model occupies memory. Token embeddings, positional embeddings, query/key/value projection matrices, feed-forward weights, layer normalization scale and shift parameters, the output projection head — each individual scalar is stored as a number in memory, and the bit width of that representation determines how much RAM or VRAM it consumes.

Think of it like building a house: the house takes up area on a plot of land. Similarly, every parameter takes up bytes in memory. A 70-billion-parameter model where each weight is stored as a 64-bit floating-point number requires:

Memory (bytes) = Nparams × (bits per param) ÷ 8

For 70B parameters at 64 bits: 70 × 109 × 64 ÷ 8 = 560 GB. At FP32 (32 bits): 280 GB. At FP16 (16 bits): 140 GB. Halving the bit width halves the memory — and that is exactly what quantization aims to do.

Without Quantization

A 70B model at FP32 needs ~280 GB just for weights. No consumer GPU can hold that. Even datacenter clusters strain under the memory bandwidth required to move full-precision weights during every matrix multiplication.

With Quantization

Representing the same 70B parameters at FP8 (8 bits) cuts weight memory to ~70 GB — a 4× reduction. Inference becomes feasible on fewer, cheaper GPUs. Training throughput increases because tensor cores process 8-bit operands faster than 16-bit ones.

The basic building block of every LLM layer is a matrix multiplication: y = W × x, where x is the input activation vector, W is the weight matrix, and y is the output. In multi-head attention alone, queries multiply keys, attention scores multiply values, and output projections multiply context vectors. In the feed-forward network, two large linear layers multiply activations by weight matrices. Every one of these operations touches millions of parameters — and every parameter's bit width matters.

The trade-off is precision. Lower bit widths mean fewer bits in the mantissa (the fractional part), so each stored number is a coarser approximation of the true value. Performance degrades slightly — but in practice, for most LLM operations, the accuracy loss is small enough that the memory and speed gains dominate.

Quantization is like reducing a high-resolution photograph to an 8-color palette: from a distance the image still reads clearly, but zoom in and banding appears. Model weights follow the same trade-off — coarser values, far less memory, usually acceptable quality.

Where parameters live in an LLM

Every parameter-bearing component in a standard transformer LLM contributes to total memory:

  • Token embedding matrix — (vocab_size × hidden_dim), e.g., 129280 × 7168 for DeepSeek-V3
  • Positional embeddings — if learned (often replaced by RoPE in modern models)
  • Per-layer attention projections — W_Q, W_K, W_V, W_O each (hidden_dim × hidden_dim) or factored variants
  • Per-layer feed-forward weights — two matrices, often (hidden_dim × ffn_dim) and (ffn_dim × hidden_dim)
  • MoE expert weights — multiplied by num_experts (256 experts in DeepSeek-V3)
  • Router/gating weights — (hidden_dim × num_experts)
  • Layer normalization parameters — scale γ and shift β per layer (small but non-zero)
  • Output head — (hidden_dim × vocab_size), often tied to token embeddings

Every scalar in every one of these matrices consumes bits. At 671B total parameters and 32 bits each, you need 2.6 TB before activations, gradients, or optimizer state. Quantization is not optional at this scale — it is a prerequisite for training to be physically possible.

Operations beyond storage: compute precision

Memory is half the story. The other half is compute throughput. Modern GPUs are compute-bound for large GEMMs but memory-bandwidth-bound for element-wise operations. Tensor Cores on an H100 deliver roughly 989 TFLOPS at FP8 versus 495 TFLOPS at BF16 — a 2× throughput advantage. When training a model for months on thousands of GPUs, 2× throughput halves training time or halves the cluster size. That is why DeepSeek converts to FP8 for computation even when weights could technically be computed at BF16.

If we lose precision, why not just use FP32 everywhere?

Because we don't need full precision everywhere. Many intermediate computations in a neural network are tolerant of small numerical noise. Matrix multiplications in feed-forward layers, in particular, accumulate thousands of small products — and the law of large numbers means small per-element errors often cancel out. The key insight is selective precision: keep master weights and sensitive operations in FP32, compute bulk GEMM operations in FP8.

02 · IEEE 754

Floating-Point Anatomy: Sign, Exponent, Mantissa

Floating-point numbers are stored in memory according to the IEEE 754 standard, which defines the bit layout for every format used below.

Take the number 3.14159. In FP32, it occupies exactly 32 bits, partitioned into three fields:

  • 1 sign bit — 0 means positive, 1 means negative. The value is multiplied by (−1)sign.
  • 8 exponent bits — stored in biased form. Controls the dynamic range: how large or small a magnitude the format can represent.
  • 23 mantissa bits — also called the significand. Controls precision: the spacing between representable values at a given magnitude.
value = (−1)sign × 2(exponent − bias) × (1 + mantissa)

For FP32, the bias is 127. If sign = 0, exponent field = 128 (biased), and mantissa = 0.5703125, then: (−1)0 × 2(128−127) × (1 + 0.5703125) = 1 × 2 × 1.5703125 = 3.140625. Close to π — the remaining error comes from mantissa truncation.

Full walkthrough: decoding 3.140625 from bits

Start with the 32-bit pattern for approximately π. The first bit is the sign: 0 means positive, so we multiply by (−1)0 = 1. The next 8 bits are the exponent field, stored in biased form — you subtract the bias (127 for FP32) to get the actual exponent. The remaining 23 bits are the mantissa, but IEEE 754 inserts an implicit leading 1, so the significand is (1 + mantissa_fraction).

Decoding step by step:

  • Sign bit = 0 → positive
  • Exponent bits decode to biased value 128 → actual exponent = 128 − 127 = 1
  • Mantissa fraction = 0.5703125 → significand = 1 + 0.5703125 = 1.5703125
  • Final value = 1 × 21 × 1.5703125 = 3.140625

Compare to the true π = 3.14159265… The error is 0.00096765 — invisible for most ML purposes but visible if you chain millions of operations. That is why master weights stay in FP32: the error must not compound across training steps.

FP32 — the default

32 bits total: 1 sign + 8 exponent + 23 mantissa. Range approximately ±3.4 × 1038. This is PyTorch's default float32 dtype and the precision used for master weights in DeepSeek's training pipeline.

FP16 — half precision

When the same parameter 3.14159 is represented as FP16 instead of FP32, it occupies only 16 bits — half the memory. But the trade-off is immediate and visible:

  • Range shrinks: FP32 covers ±3.4 × 1038. FP16 covers only ±65,504. A weight or activation above 65,504 overflows to infinity in FP16.
  • Precision shrinks: FP32 has 23 mantissa bits; FP16 has 10. The value 3.14159 becomes 3.140625 — a visible rounding error that grows with each operation.
  • Memory halves: 70B parameters at FP16 = 140 GB versus 280 GB at FP32. This 2× savings motivated the first wave of mixed precision training.

16 bits: 1 sign + 5 exponent + 10 mantissa. Range approximately ±65,504. Same number of total bits as BF16, but with a much smaller dynamic range — the exponent field shrinks from 8 bits to 5, so very large and very small values overflow or underflow easily. Precision is also reduced: 3.14159 becomes something like 3.140625 with visible rounding.

BF16 — Brain Float 16

16 bits: 1 sign + 8 exponent + 7 mantissa. The exponent field matches FP32 exactly, so BF16 covers the same dynamic range as FP32 (±3.4 × 1038). You sacrifice mantissa precision (7 bits vs 23) but retain range. DeepSeek stores activations and most intermediate results in BF16 because range matters more than fine-grained precision for activations that can spike during training.

The FP32 → BF16 migration path preserves range while halving memory. Compare the minimum and maximum representable values:

  • FP32 → FP16: Range shrinks from ±3.4×1038 to ±65,504. Large activations overflow.
  • FP32 → BF16: Range stays at ±3.4×1038. Only mantissa precision is lost.

This is why BF16 replaced FP16 as the default activation storage format in large-scale training. DeepSeek-V3 stores activations as BF16 between layers and converts to FP8 only at the Tensor Core boundary for GEMM computation.

INT8 — integer quantization

INT8 is the most aggressive common quantization format: 8 bits, no exponent, no fractional part. Every stored value is an integer in [−127, 127]. To convert FP32 tensor [2, 3, 4, −7.59, 10.8] to INT8:

  1. Find α = max(|x|) = 10.8
  2. Scale: x / α × 127 → [23.5, 35.3, 47.1, −89.3, 127.0]
  3. Round: [24, 35, 47, −89, 127]

Dequantize: q / 127 × α. For q=24: 24/127 × 10.8 = 2.04 ≈ 2. The integer constraint means all fractional information is lost — but for many weight distributions, the resulting model still performs well at inference time.

8 bits, no fractional part. Range: −127 to +127. Every stored value is an integer. To represent a floating-point tensor in INT8, you scale all values into [−127, 127], round to the nearest integer, and store the scale factor separately for dequantization.

FP8 — the frontier

04 · QUANTIZATION MATH

Scaling, Clipping, and Round-to-Nearest

Quantization is not magic — it is a deterministic mapping from high-precision floats to low-precision representations, governed by a scale factor α (alpha).

Given a tensor of FP32 values {x₁, x₂, …, xₙ}, the standard symmetric INT8 quantization procedure:

  1. Find the maximum absolute value: α = max(|xᵢ|)
  2. Scale each value into the target range: qᵢ = round(xᵢ / α × 127)
  3. Store the quantized integers {qᵢ} and the scale α
q = round( clip(x / α, −1, 1) × 127 )   ·   x̂ = q / 127 × α

Dequantization reverses the process: multiply each stored integer by α/127 to recover an approximation x̂ of the original x. The error |x − x̂| depends on how many distinct values the target format can represent between −127 and +127.

Worked example

Suppose we have FP32 values: [2, 3, 4, −7.59, 10.8]. The maximum absolute value is α = 10.8.

Quantizing to INT8 range [−127, 127]:

  • 2 → round(2/10.8 × 127) = round(23.52) = 24
  • 3 → round(3/10.8 × 127) = round(35.28) = 35
  • 4 → round(4/10.8 × 127) = round(47.04) = 47
  • −7.59 → round(−7.59/10.8 × 127) = round(−89.25) = −89
  • 10.8 → round(10.8/10.8 × 127) = 127

Dequantize: x̂ = q/127 × 10.8. For q=24: x̂ = 24/127 × 10.8 = 2.039 — close to 2. No outlier, so precision is preserved across the tensor.

The outlier problem: If the tensor is [2, 3, 4, 500], then α = 500. After scaling: 2/500 × 127 = 0.508, which rounds to 1 (or 0 in coarse FP8). Values 2, 3, 4 become nearly zero after dequantization. A single outlier destroys precision for the entire tensor. This is the core motivation for fine-grained quantization in Section 06.

Complete outlier walkthrough (exact numbers)

Start with the clean tensor [2, 3, 4] and α = 4:

  • 2 → 2/4 × 127 = 63.5 → rounds to 64 → dequantize: 64/127 × 4 = 2.0157
  • 3 → 3/4 × 127 = 95.25 → rounds to 95 → dequantize: 95/127 × 4 = 2.9921
  • 4 → 4/4 × 127 = 127 → dequantize: 127/127 × 4 = 4.0 (exact)

Now insert outlier 500: tensor becomes [2, 3, 4, 500], α = 500:

  • 2 → 2/500 × 127 = 0.508 → FP8 snaps to 0.5 → dequantize: 0.5/127 × 500 = 1.97 (should be 2)
  • 3 → 3/500 × 127 = 0.762 → FP8 snaps to 0.75 → dequantize: 0.75/127 × 500 = 2.95 (should be 3)
  • 4 → 4/500 × 127 = 1.016 → FP8 snaps to 1.0 → dequantize: 1.0/127 × 500 = 3.94 (should be 4)

Every small value is crushed. The dequantized tensor no longer resembles the original. During training, this corruption propagates through every subsequent layer. One rogue activation — perhaps from a difficult batch — can silently degrade the entire forward pass.

Clipping and round-to-nearest

Before rounding, values are typically clipped to [−1, 1] after dividing by α. This prevents values slightly above the maximum from wrapping or producing undefined behavior. Round-to-nearest-even (banker's rounding) is the IEEE default; for quantization, simple round-to-nearest-integer suffices:

q = round( clip(x / α, −1, 1) × 127 )

The scale factor α is sometimes called the scaling factor or scale tensor. In DeepSeek's fine-grained scheme, there is one α per 128-element block — not one α per entire activation tensor. Storing these scales adds overhead: one FP32 per block. For a 256-element vector split into two blocks, that is 8 extra bytes — negligible compared to the 256 bytes saved by using FP8 instead of FP32.

Why multiply by 127 and not 128 for INT8?

Symmetric INT8 quantization typically uses the range [−127, 127] rather than [−128, 127] to keep zero exactly representable and maintain symmetry around zero. Some implementations use −128 to 127 (asymmetric); DeepSeek's FP8 formats have their own defined maxima (240 for E4M3). The principle is identical: map the tensor's dynamic range onto the format's representable range via α.

05 · MIXED PRECISION

DeepSeek's Mixed Precision Framework

DeepSeek-V3 Section 3.3.1 describes a mixed precision framework: not every tensor lives at the same bit width. Different variables are stored, computed, and updated at the precision level appropriate to their numerical sensitivity. This is the central insight behind "mixed" — FP8 for bulk computation, FP32 for stability-critical state.

Forward pass: y = W × x

Consider a single linear layer. DeepSeek's forward propagation (F-prop) pipeline:

Input x stored as BF16, converted on-the-fly to FP8 for computation
↓
Weight W master copy in BF16/FP32, converted on-the-fly to FP8
↓
GEMM FP8 × FP8 multiplication on Tensor Core
↓
Output y computed initially in FP32, stored as BF16

Why compute the output in FP32 first? Because FP8 × FP8 produces a product with higher dynamic range than either operand — intermediate results need headroom. The output is then cast down to BF16 for memory efficiency. BF16 retains FP32's exponent range, so subsequent layers won't overflow.

Backward pass: gradients

Two gradients must be computed per layer:

Input gradient (dgrad): ∂L/∂x = (∂L/∂y) × WT

  • ∂L/∂y stored as BF16, converted to FP8 for computation
  • W converted on-the-fly to FP8
  • Product computed in FP32, stored as BF16

Weight gradient (wgrad): ∂L/∂W = xT × (∂L/∂y)

  • x converted to FP8, ∂L/∂y converted to FP8
  • Product computed and stored as FP32 — never downcast

Weight gradients drive the optimizer update. Any precision loss here accumulates across millions of training steps. DeepSeek keeps wgrad and master weights in FP32 throughout.

Weight update and master weights

Wnew = Wmaster − η × (∂L/∂W)   [all FP32]

After the update, master weights are cast to BF16 for storage. When the next forward pass needs them, they are converted to FP8 on-the-fly. The FP32 master copy is the source of truth; BF16 and FP8 are ephemeral views optimized for memory and compute.

Sensitive modules kept at higher precision

DeepSeek's paper explicitly states that the following components are retained at BF16 or FP32 — never forced through FP8:

  • Embedding modules — token and positional embeddings
  • Output head — final projection to vocabulary size
  • MoE gating modules — router decisions must be precise
  • Normalization operators — LayerNorm/RMSNorm scale and shift
  • Attention operators — softmax and attention score computations

Everything else — the bulk GEMM operations in feed-forward layers and linear projections — runs in FP8. This selective approach delivers memory reduction, computational speedup, and numerical stability simultaneously.

Why FP8 for GEMM?

NVIDIA Tensor Cores achieve peak throughput at 8-bit operands. Converting inputs and weights to FP8 on-the-fly unlocks ~2× speedup over BF16 GEMM on H100-class hardware, with minimal accuracy impact when combined with fine-grained scaling.

Why FP32 for wgrad?

Gradient accumulation over billions of tokens means even tiny per-step errors compound. Keeping weight gradients in FP32 ensures the optimizer sees the true descent direction, not a noisy approximation.

Optimizer state stays at FP32

Adam and AdamW maintain two running averages per parameter: the first moment (momentum) and the second moment (variance estimate). These are updated every step using the FP32 weight gradient. Storing optimizer state at FP32 for 671B parameters would be prohibitive — in practice, DeepSeek shards optimizer state across the training cluster, with each GPU holding state only for its assigned parameter shard. The mixed precision principle applies locally: compute in FP8, accumulate critical state in FP32.

Why convert master weights to BF16 after update but compute in FP8?

BF16 is the storage format — it halves memory versus FP32 while retaining range. FP8 is the compute format — it maximizes Tensor Core throughput. The conversion BF16 → FP8 happens on-the-fly at the Tensor Core boundary, fused with the quantization kernel. There is no persistent FP8 copy of the full weight matrix; it is materialized per-GEMM, per-block, with fresh online scale factors.

06 · FINE-GRAINED QUANTIZATION

Per-Block Scaling vs Per-Tensor Scaling

Section 3.3.2 of the DeepSeek-V3 report introduces fine-grained quantization. The problem it solves is the outlier problem from Section 04: a single large value in a tensor forces all other values to shrink toward zero during per-tensor scaling.

Per-tensor scaling (coarse)

The naive approach: one scale factor α for the entire tensor. For a 256-dimensional activation vector, find max(|xᵢ|) across all 256 elements, divide everything by that maximum, multiply by 127. Simple — but fragile. If element x₅ = 500 and the rest are in [0, 4], then 2/500 × 127 ≈ 0.5, which FP8 cannot represent finely. After dequantization, 2 becomes ~0.5, 3 becomes ~0.75, 4 becomes ~1.0. The entire vector is corrupted.

Per-block scaling (fine-grained)

DeepSeek's solution: divide the tensor into blocks and compute a separate scale factor for each block.

For a 256-dimensional activation vector, split into two blocks of 128 elements each:

  • Block 1 (elements 0–127): max = 20 → scale by 20
  • Block 2 (elements 128–255): max = 0.1 → scale by 0.1

Block 2 is no longer poisoned by Block 1's outlier. Each block uses the dynamic range of FP8 efficiently. The cost: storing one scale factor per block (typically a single FP32 per 128 elements — negligible overhead).

Weight matrices: 128×128 blocks

For a 256×256 weight matrix W, DeepSeek divides it into four 128×128 blocks: W₁₁, W₁₂, W₂₁, W₂₂. Each block gets its own scale factor. If W₁₁ contains an outlier, only W₁₁'s quantization suffers. W₁₂, W₂₁, W₂₂ remain precise.

Block size NC = 128  ·  αblock = max(|x|) within block  ·  q = round(x / αblock × 127)

The DeepSeek-V3 Figure 7 schematic has four distinct regions:

  1. Activation scaling (green shades) — per-128-element blocks of input activations, each with its own scale
  2. Weight scaling (purple shades) — per-128×128 blocks of weight matrices, each with its own scale
  3. Tensor Core GEMM — FP8 × FP8 matrix multiply on NVIDIA Tensor Cores
  4. CUDA Core upscaling — dequantize the FP8 result using block scale factors, accumulate in FP32 on CUDA cores

Why block size NC = 128?

128 is a hardware-aligned choice. NVIDIA Tensor Cores operate on tiles whose dimensions are multiples of 16 or 128 depending on the operation. WGMMA on Hopper uses 128-element K-dimension tiles. Choosing NC = 128 means the quantization block boundaries align with the hardware tile boundaries — no partial tiles, no wasted computation. Smaller blocks (e.g., 32) would give finer scaling but more scale-factor overhead and misalignment with tensor tiles. Larger blocks (e.g., 512) would reintroduce the outlier problem within each block.

Dequantization on CUDA cores

After FP8 GEMM on Tensor Core produces a low-precision result, the output must be rescaled to the original magnitude. Each block's contribution is multiplied by its scale factors: output += (FP8_result × α_W × α_X). This element-wise upscaling happens on CUDA cores in FP32, then the final value is stored as BF16. The dark blue dots in Figure 7B represent these dequantization multiplications.

07 · ACCUMULATION PRECISION

Why FP8 Multiply but FP32 Accumulate

Figure 7B in the DeepSeek-V3 report covers increasing accumulation precision — the right-hand side of the fine-grained quantization schematic. This addresses a hardware limitation, not a software preference.

The problem: limited tensor core accumulation

General matrix multiplication (GEMM) computes Y = W × X by multiplying rows of W with columns of X and summing the products. For a matrix with inner dimension K = 4096, each output element is the sum of 4096 FP8 products.

NVIDIA Tensor Cores perform these multiply-accumulate operations internally at a precision far below FP32 — approximately 14 bits of accumulation precision. When K is large, thousands of small FP8 products are summed in this low-precision accumulator. Rounding errors compound, and the final result can deviate from the true FP32 sum by as much as 2% for K = 4096. At LLM scale, a systematic 2% error in every matrix multiplication is catastrophic.

Accumulation = summation

The term "accumulation precision" refers specifically to the precision at which partial sums are stored during a GEMM. Each multiply produces a product; products are added to a running total. That running total's bit width is the accumulation precision. Tensor cores use ~14 bits. CUDA cores use full FP32.

DeepSeek's solution: promotion to CUDA cores

Two-step process:

  1. Low-precision MMA on Tensor Core — WGMMA (Warp Group Matrix Multiply Accumulate) performs FP8 × FP8 multiply-accumulate. Partial sums accumulate at ~14-bit precision internally.
  2. Promotion to CUDA Core — after every NC = 128 elements, partial accumulations are copied from the Tensor Core's low-precision registers to CUDA Core registers running at full FP32. Subsequent accumulation continues in FP32.

The periodic promotion ensures that no partial sum ever drifts more than 128 FP8 products away from a FP32 checkpoint. The dark purple dots in Figure 7B represent these promotion points — low-precision light purple accumulations transferred to high-precision dark purple CUDA accumulators.

After the full GEMM completes, the FP32 result on CUDA cores is dequantized using the per-block scale factors (the dark blue dots in the schematic) to recover the true magnitude, then stored as BF16 or FP32 depending on the operation.

Why not do the entire GEMM on CUDA cores in FP32?

Because Tensor Cores are ~10× faster for FP8 GEMM than CUDA cores for FP32 GEMM. The promotion strategy gets the best of both worlds: Tensor Core speed for the bulk multiply, CUDA Core precision for the accumulation. You pay a small synchronization cost every 128 elements — far cheaper than running the entire operation at FP32 throughput.

Numerical example: error at K = 4096

Suppose each of 4096 FP8 multiply pairs produces a product of approximately 0.001 × 0.001 = 10−6. The true sum is 4096 × 10−6 = 0.004096.

With 14-bit accumulation (~4 decimal digits of precision), the accumulator rounds after every addition. By element 4096, the running sum may read 0.004008 — an error of 0.000088, or roughly 2.1%. This matches the error bound cited in the DeepSeek-V3 paper for large-K GEMMs without promotion.

With promotion every 128 elements to FP32, the partial sum is refreshed at full precision 32 times during the accumulation. Each refresh resets the rounding error. Final error drops to near machine epsilon — effectively zero for training purposes.

Underflow: the dual problem

Overflow is not the only risk. When two small FP8 numbers multiply, the product can fall below the minimum representable FP8 value — this is underflow. The product becomes zero, and that zero propagates through the accumulation. Fine-grained scaling mitigates underflow by ensuring values are normalized to the center of FP8's representable range before multiplication. Online quantization ensures the scale factor reflects the current magnitude, not a stale smaller value that would leave current values too large (overflow) or a stale larger value that would crush current values toward zero (underflow).

08 · MANTISSA OVER EXPONENTS

E4M3 vs E5M2 — DeepSeek's Uniform Choice

FP8 comes in two primary flavors, trading range for precision:

E4M3

4 exponent bits, 3 mantissa bits. Higher precision, smaller dynamic range. Maximum representable ≈ 240. Best for values that stay within a moderate range after per-block scaling.

E5M2

5 exponent bits, 2 mantissa bits. Larger dynamic range, lower precision. Maximum representable ≈ 57,600. Best for gradients that can span many orders of magnitude.

Before DeepSeek, the conventional wisdom was:

  • Forward pass → E4M3 (precision matters for activations)
  • Backward pass → E5M2 (range matters for gradients)

DeepSeek broke this convention. They use E4M3 uniformly for both forward and backward passes. Their reasoning: fine-grained quantization eliminates the need for extra exponent bits.

Why E4M3 works with fine-grained scaling

Without per-block scaling, a tensor with an outlier forces small values toward zero. In E4M3 with only 3 mantissa bits, values like 0.508 become unrepresentable — they snap to 0.5 or 0.0. Precision is destroyed.

With per-block scaling, each block's values are normalized to fill the E4M3 range efficiently. No value becomes extremely small. Three mantissa bits are sufficient because the scale factor absorbs the magnitude difference. DeepSeek's paper notes that each element effectively shares the group's exponent bits through the block scale factor, expanding effective precision without needing five exponent bits.

This is a minor innovation compared to mixed precision and fine-grained quantization, but it simplifies the training pipeline: one FP8 format everywhere, no dtype switching between forward and backward passes, no risk of mismatch when casting between E4M3 and E5M2.

Effective precision with shared exponents

DeepSeek's paper makes a subtle point: with fine-grained quantization, each block's scale factor α acts like a shared exponent for all elements in that block. If α = 20 for a block, every element is normalized to [−1, 1] before FP8 encoding. The FP8 exponent bits then describe the relative positions within that normalized range, while α carries the absolute magnitude information separately.

This is analogous to how decimal notation works: 2.5 × 103 and 2.5 × 10−2 share the same mantissa digits (2.5) but differ in exponent. Fine-grained α is the external exponent; E4M3's 4 exponent bits are the internal exponent. Together, they provide more effective precision than E4M3 alone — without needing E5M2's fifth exponent bit.

When E5M2 would still matter (without fine-grained scaling)

Consider backward pass gradients that span six orders of magnitude within a single tensor — common in early training when gradients are large and heterogeneous. E4M3's max of 240 cannot represent values above 240 without scaling. Per-tensor scaling with a large α crushes small gradients. E5M2's wider range was the traditional fix: accept lower mantissa precision in exchange for not needing as aggressive scaling. DeepSeek's response: do not accept lower mantissa precision; instead, fix the scaling with per-block α so E4M3's range suffices.

09 · ONLINE QUANTIZATION

Real-Time Scale Factors vs Historical Maxima

Every quantization scheme needs a scale factor α. The question is: when do you compute it?

Delayed quantization (traditional)

In delayed quantization, the scale factor for the current tensor is derived from past iterations — a historical maximum stored from previous forward passes. If the current tensor's range has shifted significantly since that historical maximum was recorded, the stale scale factor causes overflow or underflow.

Example: suppose FP8 E4M3 has effective range ±240. A previous iteration had max = 100, so α = 100. This iteration, a value reaches 480. Using the stale scale: 480 / 100 × 127 = 611 — far beyond the representable range. Overflow. The value clips to maximum, information is lost, training diverges.

Online quantization (DeepSeek's approach)

DeepSeek computes the scale factor on the fly from the current tensor's data. Before quantizing, scan the current activation or weight block, find max(|x|) right now, use that as α. No historical state. No stale scales.

Same example: current max = 480, α = 480. Value 480 → 480/480 × 127 = 127. Perfectly in range. No overflow.

09B · HARDWARE CONTEXT

Tensor Cores, CUDA Cores, and WGMMA

DeepSeek's Figure 7 schematic references hardware components that deserve explicit explanation. Understanding where computation happens clarifies why accumulation precision is a separate concern from multiply precision.

General Matrix Multiplication (GEMM)

Every linear layer in a transformer is a GEMM: Y = W × X. For a batch of tokens, X might be (batch×seq_len, hidden_dim) and W is (hidden_dim, out_dim). The inner dimension — the K dimension in GEMM notation — equals hidden_dim. For DeepSeek-V3-scale models, K can be 4096 or larger. Each output element requires K multiply-accumulate operations.

Tensor Cores (NVIDIA)

Introduced with Volta (V100), Tensor Cores are specialized units that perform small matrix operations (e.g., 16×16×16) in a single cycle at reduced precision. Hopper (H100) adds native FP8 Tensor Core support. When DeepSeek says "FP8 GEMM on Tensor Core," it means the hardware natively multiplies 8-bit operands and accumulates internally — but the internal accumulator is NOT full FP32. It is approximately 14 bits.

CUDA Cores

Standard GPU arithmetic units. They run at full FP32 (or FP64) precision but at lower throughput than Tensor Cores for matrix operations. DeepSeek uses CUDA cores for: (1) promoting partial sums from Tensor Core accumulation, (2) applying dequantization scale factors, (3) storing final results in FP32/BF16.

WGMMA — Warp Group Matrix Multiply Accumulate

WGMMA is NVIDIA's Hopper-era API for warp-group-level matrix operations. A "warp" is 32 threads; a "warp group" is multiple warps cooperating on one matrix tile. WGMMA feeds FP8 tiles into Tensor Cores and reads back accumulated partial results. You do not need to program WGMMA directly to understand DeepSeek's approach — it is the mechanism by which step 1 (low-precision MMA) happens in the accumulation precision pipeline.

Step 1: WGMMA loads FP8 tiles of W and X into Tensor Core
↓
Step 2: Tensor Core accumulates ~128 products at ~14-bit precision
↓
Step 3: Partial sum promoted to CUDA Core FP32 register
↓
Step 4: Repeat until full K dimension processed
↓
Step 5: Dequantize with per-block α on CUDA Core → store BF16/FP32

The split between Tensor Core (fast, low accumulation precision) and CUDA Core (slower, full FP32) is not unique to DeepSeek. It is a fundamental constraint of modern GPU architecture. DeepSeek's contribution is recognizing that promotion every NC = 128 elements keeps error below 2% even at K = 4096 — and integrating that promotion into a production FP8 training stack.

# Online fine-grained FP8 quantization (conceptual)
def quantize_block(x_block, num_levels=127):
    alpha = max(abs(x_block))          # online: computed from CURRENT data
    q = round(x_block / alpha * num_levels)
    q = clip(q, -num_levels, num_levels)
    return q, alpha

def dequantize_block(q, alpha, num_levels=127):
    return q / num_levels * alpha

# GEMM with promotion every NC=128
def fp8_gemm(W, X, NC=128):
    acc = 0.0                          # FP32 accumulator on CUDA core
    for k in range(0, K, NC):
        w_tile = W[k:k+NC]               # FP8 on tensor core
        x_tile = X[k:k+NC]               # FP8 on tensor core
        partial = tensor_core_mma(w_tile, x_tile)  # ~14-bit internal
        acc = fp32_add(acc, promote(partial))       # promotion to CUDA core
    return acc * scale_W * scale_X       # dequantize with block scales

Glossary

  • Quantization — mapping high-precision values to lower bit-width representations
  • Dequantization — reversing quantization using stored scale factors
  • Scale factor (α) — max absolute value in a block/tensor, used to normalize before rounding
  • Per-tensor scaling — one α for the entire tensor (coarse, outlier-sensitive)
  • Per-block scaling — one α per NC elements (fine-grained, outlier-resistant)
  • Mixed precision — using multiple bit widths within one training run
  • Master weights — FP32 copy of weights used for optimizer updates
  • Accumulation precision — bit width of the running sum during GEMM
  • Promotion — copying partial sums from Tensor Core to CUDA Core at higher precision
  • Online quantization — computing α from current tensor data, not history
  • Delayed quantization — using stale α from previous iterations
  • E4M3 / E5M2 — FP8 format variants (4 or 5 exponent bits, 3 or 2 mantissa bits)
  • GEMM — General Matrix Multiply, the core operation in linear layers
  • WGMMA — Warp Group Matrix Multiply Accumulate (Hopper Tensor Core API)
09E · Q&A

Common Questions About DeepSeek Quantization

Does FP8 training mean the deployed model is also FP8?

Not necessarily. DeepSeek trains in FP8 for speed and memory efficiency during pre-training. The released model weights can be stored at BF16 or FP8 for inference. Inference frameworks (vLLM, SGLang) support FP8 and INT8 weight formats. The quantization techniques learned during FP8 training often produce models that quantize well for deployment — a property called quantization-aware robustness.

Why not quantize attention softmax to FP8?

Softmax involves exponentiation and division — operations that amplify small input errors into large output errors. A tiny perturbation in logits before softmax can change which token receives maximum probability mass. DeepSeek explicitly keeps attention operators at BF16/FP32. The memory cost is acceptable because attention is not the dominant GEMM in MoE architectures — the feed-forward expert layers are.

How does fine-grained quantization interact with MoE?

Each expert has its own weight matrices, each quantized with independent per-block scales. When a token is routed to experts 3 and 7, only those experts' weights are loaded and computed. Fine-grained scaling within each expert's weights is independent — an outlier in expert 3's W₁₁ block does not affect expert 7's weights at all. This composes naturally with MoE's sparse activation pattern.

Is 2% accumulation error really that bad?

Yes, at scale. A single GEMM with 2% error might seem tolerable, but a 60-layer transformer performs 60+ GEMMs per forward pass, plus an equal number in backward. Errors do not simply average out — they can accumulate coherently if the bias is systematic (always too low or always too high). Over millions of training steps, a systematic 2% per-GEMM bias shifts weight updates in a consistent wrong direction. Promotion every 128 elements keeps per-GEMM error near machine epsilon in FP32.

Could you use INT8 instead of FP8 for training?

INT8 lacks floating-point semantics — no exponent, no graceful handling of values spanning multiple orders of magnitude within one block. FP8 retains exponent bits, making it far more suitable for neural network weights and activations that vary over many magnitudes. INT8 remains popular for post-training inference quantization where calibration datasets establish fixed scales. FP8 is the right tool for training; INT8 is often sufficient for deployment.

10 · THE COMPLETE PICTURE

Five Innovations Working Together

None of DeepSeek's quantization techniques stands alone. They form a pipeline where each innovation enables the next:

1. Mixed Precision Framework

Store master weights in FP32. Compute bulk GEMM in FP8. Keep sensitive modules (embeddings, attention, gating, normalization, output head) at BF16/FP32. Convert on-the-fly between precisions at layer boundaries.

2. Fine-Grained Quantization

Split activations into 128-element blocks and weight matrices into 128×128 blocks. Each block gets its own scale factor. Outliers in one block cannot corrupt another. Enables accurate representation even in 8-bit formats.

3. Increasing Accumulation Precision

Perform FP8 GEMM on Tensor Cores for speed. Every 128 elements, promote partial sums to FP32 on CUDA Cores. Prevents the ~2% systematic error that low-precision accumulation would introduce at K=4096.

4. Mantissa Over Exponents

Use E4M3 uniformly for forward and backward passes. Fine-grained scaling makes the extra exponent bits of E5M2 unnecessary. Simplifies the dtype pipeline and avoids forward/backward format mismatches.

5. Online Quantization

Compute scale factors from the current tensor's data, not historical maxima. Eliminates overflow/underflow from distribution shift between training iterations. Fuses cleanly with the per-block scaling kernel.

What DeepSeek did not invent

FP8 formats, mixed precision training, and per-tensor quantization all existed before DeepSeek-V3. NVIDIA introduced FP8 Tensor Core support with Hopper (H100). Prior work explored INT8 and FP16 training.

What DeepSeek did invent

The specific combination: fine-grained per-block scaling + periodic FP32 promotion + uniform E4M3 + online scale computation + selective high-precision modules. Each piece existed separately; DeepSeek integrated them into a production training pipeline for a 671B-parameter model.

End-to-end worked example: one linear layer forward pass

Trace a single GEMM through the full DeepSeek FP8 pipeline. Let x be a 256-dimensional activation vector, W a 256×512 weight matrix, computing y = Wx (512-dimensional output).

  1. Load x from memory — stored as BF16 from previous layer. Shape (256,).
  2. Split x into 2 blocks — x₁ (elements 0–127), x₂ (elements 128–255). Compute α_x1 = max(|x₁|), α_x2 = max(|x₂|) online.
  3. Quantize x blocks to FP8 E4M3 — q_x1 = round(x₁/α_x1 × 127), same for x₂.
  4. Load W from memory — master copy BF16. Split into four 128×128 blocks: W₁₁, W₁₂, W₂₁, W₂₂. Compute α_W11, α_W12, α_W21, α_W22 online.
  5. Quantize W blocks to FP8 — each 128×128 block independently scaled.
  6. Tensor Core GEMM — multiply FP8 tiles. For output element y_j, accumulate over K=256 inner products in ~14-bit precision, promoting to FP32 every 128 products.
  7. Dequantize on CUDA Core — y_j += FP8_partial × α_W_block × α_x_block for each tile contribution.
  8. Store y as BF16 — cast FP32 result to BF16 for next layer.

Total scale factors stored: 2 for x + 4 for W = 6 FP32 values (24 bytes). Total FP8 compute: 256×512 = 131,072 multiply-accumulates at 8-bit precision with FP32 promotion checkpoints. Total memory for this layer's weights at BF16: 256×512×2 = 262 KB (versus 524 KB at FP32).

How the five innovations depend on each other

Remove any one innovation and the pipeline breaks:

  • Without mixed precision → either all-FP8 (unstable training) or all-FP32 (2× slower, 4× more memory)
  • Without fine-grained scaling → outliers destroy FP8 precision; E4M3 cannot be used uniformly
  • Without accumulation promotion → 2% GEMM error at K=4096 compounds across 60+ layers
  • Without E4M3 uniformity → must switch formats between forward/backward, adding conversion overhead and dtype mismatch risk
  • Without online quantization → stale scale factors cause overflow during training distribution shifts

11B · HISTORICAL CONTEXT

The Evolution of Neural Network Precision

FP32 — the original default

Early neural network training in the 2010s used FP32 everywhere. GPUs like the K20 and V100 were optimized for single-precision arithmetic. At the time, models had millions — not billions — of parameters. A 100M-parameter model at FP32 needs only 400 MB. Memory was not the bottleneck; compute was. FP32 provided ample precision for gradient descent on relatively shallow networks.

FP16 mixed precision — the first compression wave

NVIDIA's introduction of Tensor Cores with Volta (2017) enabled FP16 matrix operations at 2× the FP32 throughput. Mixed precision training (Micikevicius et al., 2018) kept master weights in FP32 while computing forward/backward passes in FP16, with loss scaling to prevent gradient underflow. This became standard for models up to ~100B parameters. FP16's limited dynamic range (±65,504) required careful loss scaling — multiply the loss by a large factor before backward pass so gradients stay representable in FP16, then unscale before the weight update.

BF16 — Google's range fix

Brain Float 16 (BF16), introduced by Google for TPU training, solved FP16's range problem by matching FP32's 8-bit exponent while accepting reduced mantissa precision (7 bits). BF16 eliminated the need for loss scaling in many workloads because activations rarely exceed ±3.4×1038}. BF16 became the default storage format for activations in large-scale training. DeepSeek stores activations in BF16 for exactly this reason.

INT8 — inference quantization

Integer quantization to 8 bits became the standard for deploying models on edge devices and CPUs. Post-training quantization (PTQ) calibrates scale factors on a representative dataset, then freezes them for inference. Quantization-aware training (QAT) simulates INT8 rounding during training so the model adapts. INT8 inference delivers 4× memory reduction versus FP32 and enables CPU inference via libraries like ONNX Runtime and llama.cpp. However, INT8 lacks floating-point semantics — no exponent bits — making it unsuitable for training where gradients span many orders of magnitude.

FP8 — the training frontier

NVIDIA Hopper (H100, 2022) introduced native FP8 Tensor Core support with E4M3 and E5M2 formats. FP8 retains floating-point semantics (sign, exponent, mantissa) in only 8 bits — the best of both worlds for training. Early adopters used E4M3 for forward and E5M2 for backward. DeepSeek-V3 (2024) demonstrated that five coordinated innovations make uniform E4M3 training viable at 671B scale.

12 · SUMMARY

Key Takeaways

  • Quantization reduces parameter precision from higher bit widths (FP32) to lower ones (FP8), cutting memory and accelerating compute with acceptable accuracy loss.
  • IEEE 754 defines floating-point layout: 1 sign bit + exponent bits (range) + mantissa bits (precision). FP32 = 32 bits, FP16 = 16 bits, BF16 = 16 bits with FP32 range, FP8 = 8 bits in E4M3 or E5M2 variants.
  • Memory scales linearly with bit width: a 70B model needs 280 GB at FP32, 140 GB at FP16, 70 GB at FP8.
  • Quantization math uses a scale factor α = max(|x|), then q = round(x/α × 127). Outliers destroy per-tensor precision.
  • Mixed precision keeps master weights and wgrad in FP32, computes GEMM in FP8, stores activations in BF16. Sensitive modules stay at higher precision.
  • Fine-grained quantization splits tensors into 128-element (activations) or 128×128 (weights) blocks, each with its own scale factor.
  • Accumulation precision promotes partial sums from ~14-bit Tensor Core accumulators to FP32 CUDA Core registers every 128 elements.
  • E4M3 everywhere works because per-block scaling eliminates the need for E5M2's extra range.
  • Online quantization computes scale factors from current data, avoiding overflow from stale historical maxima.

Precision hierarchy — the complete picture

Think of DeepSeek's precision stack as four tiers, from highest to lowest fidelity:

Tier 1 — FP32: Master weights, weight gradients, optimizer moments, GEMM accumulation after promotion
↓
Tier 2 — BF16: Activation storage, weight storage, dgrad storage, sensitive module compute
↓
Tier 3 — FP8 E4M3: Bulk GEMM operand compute on Tensor Cores (forward + backward)
↓
Tier 4 — Scale factors (FP32): One α per 128-element block, stored alongside FP8 data for dequantization

Data flows down the tiers during computation (BF16 → FP8 for GEMM) and up the tiers for storage (FP32 accumulation → BF16 storage). The tiers are not a one-way street — they form a cycle synchronized with the training loop.

FP8 training completes the four pillars of DeepSeek-V3 — Multi-Head Latent Attention, Mixture of Experts, Multi-Token Prediction, and quantization — which together enabled pre-training a 671B-parameter model at a fraction of the cost of comparable dense models.

The DeepSeek philosophy: efficiency through integration

DeepSeek's approach across all four pillars follows a consistent pattern: take established techniques (multi-head attention, MoE, speculative decoding, mixed precision), identify the specific bottleneck (KV cache memory, load balancing, inference latency, FP8 accumulation error), and engineer a targeted fix (latent attention, aux-loss-free routing, multi-token prediction, fine-grained online FP8). Quantization is no exception. FP8 training existed as a concept; DeepSeek made it work at 671B scale by solving the outlier, accumulation, and scale-staleness problems simultaneously.

Implementation summary

A DeepSeek-style FP8 training stack applies the following policy:

  • Use BF16/FP32 for embeddings, attention softmax, normalization, gating, and output head
  • Implement per-128-element block scaling with online α computation
  • Route FP8 GEMM through Tensor Cores with FP32 promotion every 128 accumulations
  • Keep master weights and weight gradients in FP32 throughout training
  • Use E4M3 uniformly — do not mix E4M3 forward with E5M2 backward

Section 3.3 of the DeepSeek-V3 paper maps directly to the sections above: Figure 6 (mixed precision) and Figure 7 (fine-grained scaling + accumulation) decode as precision labels on the y = Wx pipeline.

Can these techniques be used for inference-only quantization?

Yes — post-training quantization (PTQ) and quantization-aware training (QAT) apply the same scaling principles. DeepSeek's online per-block scaling is particularly useful for dynamic activation ranges during inference. The mixed precision decisions (which layers stay at BF16) transfer directly to deployment. Tools like llama.cpp, vLLM, and TensorRT-LLM implement similar per-block INT8/FP8 quantization for inference.

CONNECTIONS · DEEPSEEK ARCHITECTURE

How Quantization Connects to the Other DeepSeek Pillars

Quantization interacts with every other major DeepSeek-V3 innovation — MLA, MoE, and MTP.

Quantization + Multi-Head Latent Attention (MLA)

MLA compresses the KV cache by projecting keys and values into a lower-dimensional latent space before caching. This reduces memory bandwidth during inference — the primary bottleneck for long-context generation. FP8 quantization of the projection matrices (W_DK, W_DV, W_UK, W_UV) further halves the memory and compute cost of these projections. However, the attention softmax and the final attention output computation remain at BF16/FP32 — listed explicitly as sensitive modules. The combination: MLA reduces what you cache, FP8 reduces the cost of computing what you do not cache.

Quantization + Mixture of Experts (MoE)

DeepSeek-V3 has 256 experts per MoE layer, with 671B total parameters but only ~37B active per token. FP8 quantization is applied to expert feed-forward weights — the dominant GEMM in MoE layers. Each expert's 256×7168 weight matrices are quantized with independent per-block scales. Router/gating weights stay at BF16 because routing decisions are discrete and noise-sensitive. The result: you store 256 experts at FP8 (~1 byte/param) instead of BF16 (~2 bytes/param), halving expert memory while keeping routing precise.

Quantization + Multi-Token Prediction (MTP)

MTP adds auxiliary prediction heads that forecast multiple future tokens during training. These additional heads involve extra GEMM operations — matrix multiplications that benefit directly from FP8 compute. The MTP module weights are subject to the same mixed precision policy as the main model: FP8 GEMM, BF16 storage, FP32 for any gradient that feeds into the main model's weight update. MTP is training-only in DeepSeek-V3 (not used at inference), so the FP8 speedup during MTP training reduces pre-training cost without affecting deployment.

IMPLEMENTATION NOTES

Building FP8 Training in Practice

The following notes describe what a DeepSeek-style FP8 training stack requires in PyTorch or JAX.

Transformer Engine and torch.float8

NVIDIA's Transformer Engine library provides FP8 linear layers with automatic scaling. PyTorch 2.1+ exposes torch.float8_e4m3fn and torch.float8_e5m2 dtypes. DeepSeek's innovations go beyond what these libraries provide out of the box — specifically fine-grained per-block scaling and periodic accumulation promotion require custom CUDA kernels or Transformer Engine configuration.

Implementation checklist

  1. Dtype policy module. Define a policy mapping each module type to storage dtype, compute dtype, and gradient dtype. Embedding → BF16 storage. Linear → FP8 compute, BF16 storage, FP32 wgrad. LayerNorm → BF16 throughout.
  2. Block-wise quantizer. Implement quantize_block(x, block_size=128) returning (q, alpha). Must run online — no caching alpha across steps. Fuse with the GEMM launch to avoid extra memory pass.
  3. FP8 GEMM wrapper. Wrap cuBLAS or Transformer Engine GEMM. Accept FP8 inputs with scale tensors. Return FP32 output before dequantization.
  4. Promotion kernel. Every 128 accumulations in the GEMM inner loop, copy partial sum to FP32 register. This may require a custom CUTLASS kernel or Transformer Engine configuration.
  5. Dequantization. Element-wise multiply FP32 GEMM output by alpha_W * alpha_X per block. Done on CUDA cores.
  6. Master weight copy. Maintain FP32 master weights in optimizer. After step, cast to BF16 for checkpointing.

PyTorch pseudocode for a quantized linear layer

class FP8Linear(nn.Module):
    def __init__(self, in_features, out_features):
        super().__init__()
        self.weight = nn.Parameter(torch.empty(out_features, in_features, dtype=torch.bfloat16))
        self.master_weight = None  # FP32 copy managed by optimizer

    def forward(self, x_bf16):
        # Online per-block quantization
        x_fp8, scale_x = quantize_fine_grained(x_bf16, block_size=128, fmt='e4m3')
        w_fp8, scale_w = quantize_fine_grained(self.weight, block_size=128, fmt='e4m3')
        # FP8 GEMM with FP32 promotion every 128
        y_fp32 = fp8_gemm_with_promotion(w_fp8, x_fp8, promote_every=128)
        # Dequantize
        y_fp32 = y_fp32 * scale_w * scale_x
        return y_fp32.to(torch.bfloat16)

    def backward_wgrad(self, x_bf16, grad_out_bf16):
        x_fp8, sx = quantize_fine_grained(x_bf16, block_size=128)
        go_fp8, sgo = quantize_fine_grained(grad_out_bf16, block_size=128)
        wgrad_fp32 = fp8_gemm_with_promotion(x_fp8.T, go_fp8, promote_every=128)
        wgrad_fp32 = wgrad_fp32 * sx * sgo
        return wgrad_fp32  # stays FP32 — never downcast

Testing your FP8 implementation

Before scaling to full model training, verify:

  • Quantization round-trip error: quantize → dequantize should recover values within 1–2% for typical activation distributions without outliers
  • Outlier isolation: inject a single 500× outlier in one 128-block; verify other blocks have <0.1% error
  • Accumulation error: compare FP8 GEMM with promotion vs FP32 reference GEMM at K=4096; error should be <0.01%
  • Online vs delayed: simulate distribution shift; verify online α prevents overflow where delayed α fails
  • Loss curve parity: train a small model (125M params) in FP32 vs FP8; loss curves should match within noise

Common pitfalls

Pitfall: per-tensor scaling

Using one α for the entire weight matrix instead of per-128×128 block. Symptom: model trains but converges to worse loss than BF16 baseline. Fix: implement block-wise scaling with NC=128.

Pitfall: downcasting wgrad

Storing weight gradients as BF16 or FP8 to save memory. Symptom: training instability after ~1000 steps, loss spikes. Fix: keep wgrad in FP32 always.

Pitfall: stale scale cache

Caching α across training steps for speed. Symptom: sudden NaN losses when data distribution shifts. Fix: compute α online every forward pass.

Pitfall: no accumulation promotion

Using default Tensor Core accumulation without FP32 promotion. Symptom: 1–2% systematic bias in layer outputs, compounds over depth. Fix: promote every 128 elements.

Hardware requirements

Native FP8 Tensor Core training requires NVIDIA Hopper (H100) or newer. Ampere (A100) supports INT8 Tensor Cores but not FP8. AMD MI300 supports FP8 via ROCm. For inference deployment of FP8-trained models, H100, L40S, and RTX 4090 (with appropriate kernels) support FP8 inference.

WALKTHROUGH · STEP BY STEP

Complete Forward-and-Backward Pass with All Five Innovations

The following trace applies mixed precision, fine-grained scaling, accumulation promotion, E4M3, and online quantization to a single training step on one transformer layer.

Setup

Layer: feed-forward linear (not in the sensitive-module list). Hidden dimension: 256. Output dimension: 512. Batch: 1 token. Master weight W stored as BF16 from previous iteration. Master weight FP32 copy in optimizer. Input activation x stored as BF16 from previous layer.

Forward pass — step by step

Step F1: Load x (BF16). x is a 256-vector stored in BF16 from the previous layer's output. BF16 preserves range; no precision concern at load time.

Step F2: Online per-block scale for x. Split x into x₁ (indices 0–127) and x₂ (indices 128–255). Scan x₁: suppose values are [0.5, −1.2, 0.8, …], max absolute = 1.2. α_x1 = 1.2 (computed now, not from history). Scan x₂: max absolute = 0.05. α_x2 = 0.05.

Step F3: Quantize x to FP8 E4M3. q_x1 = round(x₁ / 1.2 × 127). Each element now in [−127, 127] integer range, representable in E4M3.

Step F4: Load W (BF16), split into 4 blocks. W is 256×512. Blocks: W₁₁ (128×128), W₁₂ (128×384 — note: DeepSeek uses 128×128 tiles; edge blocks may differ). Compute α for each block online.

Step F5: Quantize W blocks to FP8 E4M3. Independent scaling per block. W₁₁ might have α_W11 = 0.3; W₂₂ might have α_W22 = 2.1.

Step F6: Tensor Core GEMM. Compute y = W × x in FP8. For each output element y_j, accumulate 256 products. Products 0–127: accumulate in ~14-bit on Tensor Core. At product 128: promote partial sum to FP32 CUDA Core register. Products 128–255: continue accumulating in FP32 on CUDA Core.

Step F7: Dequantize. Multiply accumulated FP32 partial by α_W_block × α_x_block for the tile. Sum tile contributions. Result: y_j in FP32.

Step F8: Store y as BF16. Cast FP32 y to BF16. Pass to next layer.

Backward pass — step by step

Step B1: Receive ∂L/∂y (BF16). Upstream gradient from next layer, stored as BF16.

Step B2: Compute dgrad ∂L/∂x = (∂L/∂y) × Wᵀ. Convert ∂L/∂y and W to FP8 with online per-block scaling. GEMM on Tensor Core with FP32 promotion every 128. Dequantize. Store ∂L/∂x as BF16 — pass to previous layer.

Step B3: Compute wgrad ∂L/∂W = xᵀ × (∂L/∂y). Convert x and ∂L/∂y to FP8 with online per-block scaling. GEMM on Tensor Core with FP32 promotion. Dequantize. Store ∂L/∂W as FP32 — do not downcast.

Weight update

Step U1: Optimizer step. W_master (FP32) = W_master − η × ∂L/∂W (FP32). Adam may also update m and v moments in FP32.

Step U2: Cast for storage. W_master (FP32) → W_stored (BF16). FP32 master retained in optimizer state.

Step U3: Next iteration. When next forward pass loads W, it loads BF16, converts to FP8 on-the-fly with fresh online α. No persistent FP8 weight tensor exists.

Sensitive module contrast: attention softmax

For comparison, consider the attention softmax in the same forward pass — listed as a sensitive module:

  • Attention scores computed in BF16 or FP32 — not FP8
  • Softmax exponentiation requires precision; small score differences become large probability differences
  • Output probabilities stored as BF16 for the value weighted sum
  • No FP8 quantization applied to softmax inputs or outputs

This contrast illustrates the mixed precision principle: FP8 where throughput matters and precision loss is tolerable; BF16/FP32 where precision is critical.

MoE gating contrast

The MoE router computes logits = x · W_gate, then applies softmax to select top-K experts. W_gate and the router softmax are sensitive modules:

  • Router weights stored and computed at BF16/FP32
  • Expert selection is a discrete decision — small logit noise changes which experts activate
  • Once experts are selected, the expert feed-forward GEMMs run in FP8

The router is ~0.1% of total parameters but has disproportionate impact on model behavior. Keeping it at high precision is cheap insurance.

A.1 IEEE 754 Format Specifications

This appendix consolidates every numeric detail from the chapter for quick reference during implementation.

FP32 (IEEE 754 Single Precision)

  • Total bits: 32 (1 sign + 8 exponent + 23 mantissa)
  • Exponent bias: 127
  • Minimum positive normal: ~1.18 × 10−38
  • Maximum: ~3.4 × 1038
  • Machine epsilon: ~1.19 × 10−7
  • Bytes per value: 4
  • DeepSeek role: Master weights, wgrad storage, optimizer state, accumulation

FP16 (IEEE 754 Half Precision)

  • Total bits: 16 (1 sign + 5 exponent + 10 mantissa)
  • Exponent bias: 15
  • Maximum: 65,504
  • Minimum positive normal: ~6.1 × 10−5
  • Bytes per value: 2
  • DeepSeek role: Legacy reference; largely replaced by BF16 in DeepSeek-V3

BF16 (Brain Float 16)

  • Total bits: 16 (1 sign + 8 exponent + 7 mantissa)
  • Exponent bias: 127 (same as FP32)
  • Maximum: ~3.4 × 1038 (same range as FP32)
  • Bytes per value: 2
  • DeepSeek role: Activation storage, weight storage between iterations, dgrad storage

FP8 E4M3 (DeepSeek's uniform format)

  • Total bits: 8 (1 sign + 4 exponent + 3 mantissa)
  • Maximum: ~240
  • Bytes per value: 1
  • DeepSeek role: All GEMM computation (forward and backward)

A.2 Quantization Formulas

Symmetric quantization:   q = round( clip(x / α, −1, 1) × S )
Dequantization:   x̂ = (q / S) × α
Scale factor (per-block, online):   α = max(|xblock|)
S = 127 for INT8; S = 127 for FP8 E4M3 (implementation-dependent)

A.3 DeepSeek-V3 Section 3.3 Checklist

Use this checklist when reading the paper or implementing FP8 training:

  • ☐ Mixed precision: FP8 compute, BF16 activation storage, FP32 master weights and wgrad
  • ☐ Sensitive modules at BF16/FP32: embeddings, output head, MoE gating, normalization, attention
  • ☐ Fine-grained: NC = 128 for activations, 128×128 for weight blocks
  • ☐ Online α: computed from current tensor, not historical max
  • ☐ Accumulation: promote to FP32 every 128 elements during GEMM
  • ☐ Format: E4M3 for both forward and backward (not E5M2)
  • ☐ Dequantization: apply block scale factors on CUDA cores after Tensor Core GEMM
