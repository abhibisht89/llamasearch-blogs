DECODING DEEPSEEK · CHAPTER 04

The Cache Chronicles

KV Cache, Multi-Query Attention, and Grouped Query Attention — the inference memory problem and the evolution from MHA to MQA to GQA that leads to DeepSeek's latent attention.

11Core Sections
7Interactive Demos
1Playground

During inference, a language model generates one token at a time. At every step it recomputes attention over the entire prefix. The key-value cache eliminates that waste by storing previously computed keys and values. But memory is not free: as context grows, the KV cache can consume hundreds of gigabytes. This chapter derives the cache from first principles, quantifies its cost, and walks through Multi-Query Attention and Grouped Query Attention — the progression that leads to DeepSeek's multi-head latent attention.

00

The Inference Pipeline

Every conversation with a large language model happens during inference, not pre-training. When you ask an assistant to make a travel plan for Italy, the model is not learning from your query. It uses a pre-trained, frozen network to predict one new token at a time. The key-value cache applies only during this inference stage.

Pre-training vs. Inference

Pre-training: Train on massive text corpora. All parameters learned via gradient descent.
↓
Inference: Use the frozen model to answer questions, one token per forward pass.

If a model has 175 billion parameters, all are fixed during inference. The only thing that changes is the input sequence, which grows by one token after each generation step.

Why context size affects API pricing: OpenAI charges $30 per million tokens for GPT-4 (8K context) but $60 per million tokens for GPT-4-32K — exactly 2× the price for 4× the context. The KV cache is one major reason.

Token-by-Token Generation

Although interfaces make responses appear instantly, the model generates text one token at a time. With GPT-2 and the prompt "The next day is bright":

  • Input: The next day is bright → output: and
  • Input grows → output: sunny, then ., etc.

Prerequisites

This chapter assumes familiarity with self-attention, causal masking, and multi-head attention from Chapters 02 and 03. If you can compute Q, K, V matrices, apply softmax with a causal mask, and explain why multi-head attention captures multiple perspectives, you are ready.

The Road to Multi-Head Latent Attention

DeepSeek-V3's multi-head latent attention (MLA) sits at the end of a long research thread on inference efficiency. This chapter follows that path:

  1. KV Cache — cache keys and values to avoid recomputation (good: linear compute; bad: memory grows with context)
  2. Multi-Query Attention (MQA) — share K/V across all heads (good: N× memory reduction; bad: quality loss)
  3. Grouped Query Attention (GQA) — share K/V within groups (middle ground)
  4. Multi-Head Latent Attention (MLA) — DeepSeek's solution (next chapter)

At DeepSeek scale — 61 layers, 128 heads, 100K context — a naive MHA cache reaches roughly 400 GB. That number motivates every step below.

01

Only the Last Token Matters

The KV cache rests on one fact: next-token prediction uses only the context vector of the last token in the sequence.

Logits shape: (num_tokens × vocab_size)

Key insight: The last logits row depends only on the context vector for the last token. Prefix tokens are needed inside attention to compute that vector, but not afterward for prediction.

Interactive · Logits Matrix Explorer

Only the last row predicts the next token.
If only the last context vector is needed, why pass the entire sequence?

Because the last context vector is computed from the entire prefix via attention. The KV cache optimizes re-processing old tokens, not the initial need to see them.

The Dependency Chain

For input "The next day is", the logits row for "is" depends on:

Context vector for "is" (attention over full prefix)
↓
Feed-forward + residual layers
↓
Final layer norm → output head → logits row

Attention needs all tokens; prediction needs only the last context vector. With vocabulary size 50,000, the logits matrix has shape 4 × 50,000:

Row 0 ("The"): [0.01, -0.3, 0.05, ..., 0.02] ← not used

Row 1 ("next"): [0.02, 0.01, -0.1, ..., 0.04] ← not used

Row 2 ("day"): [-0.1, 0.03, 0.02, ..., 0.01] ← not used

Row 3 ("is"): [0.05, 0.12, 2.31, ..., 0.08] ← argmax → "bright"

Only row 3 is used (argmax → "bright"). Rows 0–2 are discarded. That waste is tolerable in one forward pass; during autoregressive generation, recomputing them every step is not.

02

The Repetition Problem

After predicting "bright," the token is appended and inference runs on "The next day is bright." The entire sequence passes through attention again — including tokens already processed.

Concrete Walkthrough

Step 1 (4 tokens): Q, K, V each 4×4. Attention scores 4×4. Use context vector for "is."

Step 2 (5 tokens): Q, K, V each 5×4. The top-left 4×4 sub-block was already computed. Tokens 1–4 are recomputed identically. Only token 5 ("bright") is new.

Without cache

Recompute Q, K, V, attention scores, and weights for all previous tokens every step. Total compute: O(n²).

With cache

Retrieve cached K/V for old tokens. Only compute Q, K, V for the new token. Per-step: O(n).

Memory analogy: Think of data as houses on land. For every piece of land occupied, you pay rent. More repeated computations mean more data in memory and higher inference cost.

Interactive · Repeated Computation Visualizer

Mathematical Proof of Repetition

Walk through the attention computation with concrete dimensions. Input: "The next day is" — 4 tokens, embedding dimension 8.

Iteration 1 (4 tokens):

  • Input embedding X: 4 × 8
  • WQ, WK, WV: each 8 × 4 (projecting to head dimension 4)
  • Q = XWQ: 4 × 4.   K = XWK: 4 × 4.   V = XWV: 4 × 4
  • Attention scores = QKT: 4 × 4
  • Attention weights (after scale + softmax + causal mask): 4 × 4
  • Context matrix = weights × V: 4 × 4

Row 3 (for "is") predicts "bright." Append "bright."

Iteration 2 (5 tokens):

  • Input embedding X: 5 × 8
  • Q, K, V: each 5 × 4
  • Attention scores: 5 × 5

The top-left 4×4 block of the 5×5 attention scores matrix is identical in content to iteration 1 (same tokens, same weights WQ, WK, WV). Recomputed unnecessarily:

  • Q, K, V for tokens 1-4 (the black boxes)
  • Attention scores for tokens 1-4 attending to tokens 1-4
  • Attention weights for tokens 1-4
  • Context vectors for tokens 1-4

Yet only the context vector for token 5 ("bright") — the last row — is needed. Everything else is wasted work.

Quadratic vs. Linear Complexity

Without caching, total attention compute over generating n tokens is proportional to 1² + 2² + 3² + ... + n² = O(n³) for the full generation — often summarized as quadratic per step, cubic overall. With KV caching, each step only computes attention for one new query against n cached keys: O(n) per step, O(n²) overall. This is the difference between a model that feels instant and one that grinds to a halt on long outputs.

03

The Key-Value Cache

The solution is caching: store previously computed keys and values. Because only the last context vector drives prediction, the cache needs to store only K and V — not Q.

Backtracking

Context("bright") = AttnWeights("bright") × V
↓
AttnWeights ← softmax(Scores("bright"))
↓
Scores("bright") = Q("bright") × KT
↓
K = [cached K1:4; new K("bright")]   V = [cached V1:4; new V("bright")]

Three New Computations Per Token

  1. embed(new) × WQ → query vector for new token
  2. embed(new) × WK → append to keys cache
  3. embed(new) × WV → append to values cache

Why K and V, not Q? Only the new token needs a query vector. Old queries are never reused. The new query attends to all cached keys and values.

KV Cache = stored K1:t and V1:t (not Q)

The Complete Cached Inference Algorithm

Here is the full algorithm for generating one new token with KV cache:

# State: cached_keys, cached_values (per layer, per batch)

def decode_step(new_token_embed, WQ, WK, WV, cached_K, cached_V):

  q_new = new_token_embed @ WQ          # (1, d_k)

  k_new = new_token_embed @ WK          # (1, d_k)

  v_new = new_token_embed @ WV          # (1, d_v)

  K = concat(cached_K, k_new)            # (t+1, d_k)

  V = concat(cached_V, v_new)            # (t+1, d_v)

  scores = q_new @ K.T / sqrt(d_k)       # (1, t+1)

  weights = causal_softmax(scores)       # (1, t+1)

  context = weights @ V                  # (1, d_v)

  cached_K, cached_V = K, V              # update cache

  return context                             # feed to FFN → logits

Three matrix multiplications per token per layer. Everything else is cache lookup and a single attention computation over the growing prefix.

Multi-Layer Caching

In a model with L transformer layers, each layer has its own independent KV cache. Layer 1 caches its K/V after processing the input; layer 2 caches its K/V after receiving layer 1's output, and so on. The total cache size formula multiplies by L because all L layers must store their own keys and values.

For DeepSeek-V3 with L=61 layers, each layer independently stores 128 heads × 128 dimensions × sequence_length cached keys and values. This is why the 400 GB figure is so enormous — it is not one cache, it is 61 caches stacked vertically through the network.

04

The Good Side: Speed

The KV cache's main benefit: as input tokens increase, compute time increases linearly instead of quadratically. Cached K/V eliminates repeated calculations.

GPT-2 Benchmark

Generating 100 new tokens from "The next day is bright" with GPT-2:

SettingTime (100 tokens)Speedup
use_cache=True~2.0 secondsbaseline
use_cache=False~6.77 seconds~3.4× slower

Another run: 52 tokens in 2.5s with cache vs 3.6s without (~1.43× speedup for shorter generation). The advantage grows with sequence length.

Interactive · Inference Speed Comparison

With caching, keys and values are computed once and stored. Every subsequent token reuses them. Inference speeds up dramatically.

Why Caching Speeds Up Inference

The speedup comes from eliminating redundant matrix multiplications. Without cache, generating token t requires computing Q, K, V for all t tokens across all L layers — roughly O(t) matmuls per layer. With cache, only the new token gets fresh Q, K, V projections — O(1) matmuls per layer. The attention computation itself still scales as O(t) per step (the new query attends to t cached keys), but the expensive embedding projections are eliminated for old tokens.

In HuggingFace Transformers, KV caching is enabled by default (use_cache=True in model.generate()). Setting use_cache=False forces recomputation — useful only for debugging or computing gradients during generation.

05

The Dark Side: Memory

Caching means storing data in memory. Every stored parameter occupies space, slows other computations, and costs money. This is the dark side of the KV cache.

The KV Cache Size Formula

For one transformer layer, storing keys and values for all tokens:

KV_cache_bytes = L × B × N × H × S × 2 × 2

Where:

  • L = number of transformer layers
  • B = batch size
  • N = number of attention heads
  • H = head dimension (N × H = total KV dimension per token)
  • S = context length (sequence length)
  • First 2 = keys + values
  • Second 2 = bytes per parameter (FP16 = 2 bytes)

The 30B Model Example (Detailed)

A 30-billion parameter model with these specs during inference:

  • L = 48 transformer layers
  • Context size S = 1024 tokens
  • Total dimension = 7168 (across all heads)
  • Batch size B = 128 (serving 128 concurrent users)

KV cache = 48 × 128 × (7168/128 heads × 128 head_dim) × 1024 × 2 × 2 bytes. With N=56 heads (7168/128):

48 × 128 × 56 × 128 × 1024 × 4 ≈ 180 GB

180 GB of GPU memory consumed just by the cache — before model weights (~60 GB in FP16), activations, or gradients. This is why batch size and context length are hard limits in production serving.

The Red Curve Problem

Plotting model size (x-axis) against memory (y-axis) for GPT-3 variants (Small, Medium, Large, XL):

  • Blue line (model parameters): grows steadily, roughly linearly with model size
  • Red line (KV cache): grows faster — superlinearly — because larger models have more layers AND more heads AND larger head dimensions simultaneously

At sufficient scale, the KV cache exceeds the model weights in memory consumption. This crossover point is where cache optimization becomes mandatory, not optional.

Context length is the killer variable. As S grows, KV cache grows linearly — but at 100K context with 128 heads across 61 layers, you hit 400 GB. DeepSeek's low inference cost exists because they did not use this naive KV cache.

Deriving the Formula Step by Step

Start with one transformer layer and one token position. Each token produces a key vector and a value vector. If we have N attention heads each with dimension H, the key vector for one token across all heads has N×H elements. Same for the value vector.

For S tokens in the sequence: S × (N×H) key elements + S × (N×H) value elements = 2 × S × N × H parameters per layer per batch item.

Multiply by batch size B for batched inference. Multiply by L layers. Multiply by 2 bytes (FP16). This gives:

Size = L × B × N × H × S × 2 (K+V) × 2 (bytes) = L × B × N × H × S × 4 bytes

Why DeepSeek Inference Is Cheap

DeepSeek's API pricing is remarkably low compared to competitors. One reason: they do not use the naive KV cache described here. Their multi-head latent attention compresses the cache dramatically while preserving quality — the problem set out above is exactly what MLA addresses in the next chapter.

06

Multi-Query Attention (MQA)

The simplest fix for the KV cache memory problem: what if all attention heads share the same key and value matrices? This is Multi-Query Attention (MQA), introduced by Noam Shazeer (co-author of "Attention Is All You Need") in the 2019 paper "Fast Transformer Decoding: One Write-Head is All You Need."

Shazeer's paper states: "Multi-query attention is identical to multi-head attention except that the different heads share a single set of keys and values."

Normal MHA vs. MQA

In standard multi-head attention with 4 heads, WK and WV are split per head — each head has different key/value weights (shown as different colors). The keys matrix K and values matrix V differ across heads. During inference, we must cache K and V for every head.

In MQA, head 1's WK and WV are duplicated for heads 2, 3, 4. All heads share identical K and V matrices. We cache keys and values for one head only.

MQA cache size = MHA cache size / N   (N = number of heads)

For DeepSeek with 128 heads: 400 GB → ~3 GB. A factor-of-128 reduction.

Queries remain different per head (Q1, Q2, Q3, Q4 are distinct). Only K and V are shared.

On an A100 GPU: ~19.5 TFLOPS FP32 compute but only ~1.9 TB/s memory bandwidth — memory is 10× slower than compute. MQA reduces memory traffic, which is why it wins on latency despite similar quality.

The MQA Mechanism in Detail

In standard MHA with 4 heads, the trainable weight matrices WK and WV are split along the column dimension:

WK = [WKhead1 | WKhead2 | WKhead3 | WKhead4]

Each split has different values (different colors in diagrams) because each head learns different projections during training.

MQA forces: WKhead1 = WKhead2 = WKhead3 = WKhead4. Same for WV. When you multiply the input embedding by this shared WK, every head gets the same key vector. You compute keys once, then broadcast (copy) to all heads.

Memory Savings Calculation

MHA KV cache per layer: N head-slots × S tokens × H dimensions × 2 (K+V) × 2 bytes.

MQA KV cache per layer: 1 head-slot × S × H × 2 × 2 bytes.

Reduction factor: N.

Hardware: Memory Bandwidth vs. Compute

Shazeer's insight was hardware-aware. On an NVIDIA A100:

  • FP32 compute: ~19.5 TFLOPS
  • Memory bandwidth: ~1.9 TB/s
  • Ratio: compute is ~10× "faster" than memory

Attention during decoding is memory-bound, not compute-bound. You spend most of the time loading K/V from memory, not doing arithmetic. MQA loads one K/V head instead of N — hence the ~8× latency improvement (48 μs → 6 μs per step) despite nearly identical BLEU scores (26.7 vs 26.5).

07

MQA: The Performance Trade-off

Why Multi-Head Attention Exists

Consider: "The artist painted the portrait of a woman with a brush."

Reading 1

The artist painted the portrait using a brush (instrument).

Reading 2

The artist painted the portrait of a woman who had a brush in her hand.

Single-head attention captures one perspective. Multi-head attention was designed so each head captures different perspectives — head 1 might focus on syntax, head 2 on semantics, head 3 on coreference.

What MQA Loses

If K1 = K2 and V1 = V2 across all heads, we restrict the diversity each head can capture. Queries differ, so attention scores differ — but shared K/V limits how different the resulting context vectors can be.

MQA's dark side: severe performance degradation. MQA solves the KV cache memory problem but undermines the purpose of multi-head attention. DeepSeek's models are highly performant — they did not stop at MQA.

Empirical Evidence: GPT-2 vs Falcon

Comparing GPT-2 Medium (355M, standard MHA) vs Falcon-1B (MQA) on prompt "The quick brown fox jumps over the lazy dog":

Falcon is ~2.5× faster — but heatmaps show GPT-2's 16 heads capture visibly different attention patterns. Falcon's 32 heads look similar — diversity is low because K/V are shared.

When MQA Is Acceptable

MQA works well for models where raw speed matters more than maximum quality — early Falcon models, some PaLM variants, and serving scenarios with strict latency SLAs. But frontier models competing on reasoning, code, and long-context tasks need more head diversity than MQA allows.

08

Grouped Query Attention (GQA)

Grouped Query Attention (GQA), from Josh Ainslie et al. (2023, "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints"), sits between MHA and MQA. Instead of all heads sharing one K/V set, heads are organized into groups — heads within a group share K/V; groups differ from each other.

The Grouping Idea

With 4 heads and 2 groups:

  • Group 1: Head 1, Head 2 — same WK, WV, same K, same V
  • Group 2: Head 3, Head 4 — same WK, WV, same K, same V (but different from Group 1)

With 32 heads and 8 groups: each group has 4 heads. The cache holds 8 K/V sets instead of 32 (MHA) or 1 (MQA).

GQA cache size = MHA cache size × (G / N)   where G = number of groups

DeepSeek (128 heads, 8 groups): reduction = 128/8 = 16× (400 GB → ~25 GB), vs MQA's 128× (→ ~3 GB).

Diversity: H3 vs H6 vs H1 vs H2

With 16 heads in 4 groups of 4:

H3 vs H6 (different groups)

Different K/V → capture different perspectives. GQA is better than MQA here.

H1 vs H2 (same group)

Identical K/V → same as MQA within the group. MHA still best here.

GQA vs MQA Memory Trade-off

MQA caches 1 K/V set. GQA caches G sets. So GQA uses G× more memory than MQA, but (N/G)× less than MHA.

For DeepSeek (N=128, G=8): MQA → 3 GB, GQA → 25 GB, MHA → 400 GB. GQA is 8× more memory than MQA but captures 8 distinct K/V representations instead of 1 — a worthwhile trade for quality.

The central question DeepSeek answered: can a model match MHA-level performance at MQA-level memory cost? Their answer — Multi-Head Latent Attention — is the subject of the next chapter.

A common question is: why not just use MQA everywhere if it is 128× cheaper?

Because quality matters. MQA's BLEU drop (26.7 → 26.5) looks small, but on complex reasoning, code generation, and long-context tasks, the loss of head diversity is significant. Production models (LLaMA 3, DeepSeek) chose GQA or better because they need both speed and quality.

CS

Context Length Scaling: Why Long Context Is Expensive

The KV cache grows linearly with context length S. But because S appears in every layer and every head, the effect is multiplicative across the full model.

DeepSeek-V3 (MHA) at S=2,048: 8.2 GB KV cache

DeepSeek-V3 (MHA) at S=8,192: 32.7 GB KV cache

DeepSeek-V3 (MHA) at S=32,768: 131.0 GB KV cache

DeepSeek-V3 (MHA) at S=100,000: 399.8 GB KV cache

DeepSeek-V3 (MHA) at S=131,072: 524.0 GB KV cache

At 128K context, even GQA with 8 groups requires ~25 GB × (128000/100000) ≈ 32 GB just for the cache. This is why long-context models require specialized attention mechanisms — not just bigger GPUs.

A common question is: can we just use CPU memory for the KV cache?

Some systems (vLLM, llama.cpp) offload KV cache to CPU RAM or disk, but this introduces latency from PCIe transfers. GPU memory bandwidth (~1.9 TB/s on A100) is the bottleneck during decode — moving cache to CPU makes inference slower, not faster. The real solution is compressing the cache (GQA, MLA) not just relocating it.
