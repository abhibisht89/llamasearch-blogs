Why Replace the Feed-Forward Network?

Every transformer block contains multi-head attention and a feed-forward neural network (FFN). Attention lets tokens communicate across the sequence. The FFN lets each token independently transform its representation in a higher-dimensional space. Architecturally, the FFN is an expansion–contraction network — sometimes called a compression–expansion network — that maps input dimension d to hidden dimension 4d and back to d.

Input embedding: d_model (e.g. 768)
↓ expansion layer W₁: (768 → 3072)
Hidden layer + activation (SiLU/GELU)
↓ contraction layer W₂: (3072 → 768)
Output: same shape as input (768)

The FFN is indispensable. Remove it and language model quality drops sharply. It is one of the critical components that allows the model to explore a much richer representational space by temporarily expanding the number of dimensions by a huge amount. But the FFN is also where a disproportionate share of parameters lives.

The Expansion-Contraction Pattern in Detail

The name "expansion-contraction" captures the shape of the computation. Input lives in d-dimensional space. The first linear layer expands to rd dimensions — typically r=4, so a 768-dim input becomes 3072-dim. A nonlinear activation (GELU, SiLU/Swish) applies element-wise. The second linear layer contracts back to d dimensions.

Why expand? The higher-dimensional space provides more room for the network to compute complex feature transformations. Think of it as giving the model a larger workspace for each token's "thinking" step. The contraction ensures the output can be added back to the residual stream via skip connection.

In MoE, each expert is its own expansion-contraction network. They share the same architectural pattern but have independent weights — allowing specialization.

Parameter Accounting

For one transformer block with embedding dimension d = 768:

  • Expansion layer weights: 768 × (4 × 768) = 768 × 3072 = 2,359,296
  • Contraction layer weights: (4 × 768) × 768 = 2,359,296
  • Total per block: 4,718,592 ≈ 4.7 million parameters

With 12 transformer blocks, the FFN alone holds roughly 4.7M × 12 ≈ 56 million parameters — about 48–50 million depending on bias terms. In a full model, the FFN can account for roughly two-thirds of total parameters.

FFN_params(block) = 2 × d × 4d = 8d²

This parameter count directly affects training time and inference time. Every token, whether it is a comma or a verb or a proper noun, activates all 4.7M FFN parameters in every layer. Mixture of Experts optimizes this by introducing sparsity: only a subset of expert networks activate per token, reducing both pre-training compute and inference latency.

01

Thirty Years of Expert Councils

Mixture of Experts is not new. When people call MoE a "DeepSeek innovation," they mean DeepSeek built something powerful on top of decades of accumulated research — not that DeepSeek invented the concept. The first paper introducing mixture of experts was published in Neural Computation in 1991: Adaptive Mixtures of Local Experts, with authors including Jordan and Jacobs — researchers connected to Geoffrey Hinton and the backpropagation pioneers.

Adaptive Mixtures of Local Experts (1991)

The 1991 paper did not concern language modeling. It addressed supervised learning and demonstrated MoE on a vowel discrimination task — identifying which vowel sound a waveform represents.

"We present a new supervised learning procedure for systems composed of many separate networks each of which learns to handle a subset of the complete set of training cases… we demonstrate that the learning procedure divides up a vowel discrimination task into appropriate subtasks each of which can be solved by a very simple expert network."

The 1991 architecture already contained every conceptual element still used in modern LLM MoE:

  • Multiple expert networks, each learning a subset of the task
  • A gating network (selector/router) that decides which expert handles each input
  • Sparse activation — based on the input waveform, a specific expert is routed; not all experts fire
  • Experiments with 4 experts, 8 experts, and more

MoE was slowly brought into language modeling through Mistral and other players. DeepSeek's approach mirrors their MLA strategy: borrow what everyone has done, then add novel tricks. DeepSeek-V2 (June 2024) introduced fine-grained expert segmentation and shared expert isolation. DeepSeek-V3 (January 2025) added loss-free load balancing. Those innovations — covered in later chapters — rest entirely on the foundation built here.

1991: Vowel Discrimination

4–8 expert networks. Gating network selects expert per input waveform. Sparse activation proven on supervised task.

2025: DeepSeek-V3

256+ routed experts per layer. Top-6 activation. 671B total, 37B active. Loss-free load balancing.

MoE builds on decades of work — from Jordan and Jacobs (1991) through Shazeer's trillion-parameter formulations to the ST-MoE team's analysis of expert specialization in language models.

Switch Transformer and the Shazeer Connection

Noam Shazeer — co-author of "Attention is All You Need" — later introduced the Switch Transformer (2021), which popularized MoE for trillion-parameter language models. Switch Transformer uses top-1 routing (k=1) for maximum sparsity: each token activates exactly one expert. Modern models including DeepSeek use top-k with k>1 for better quality — activating two or more experts per token provides an ensemble effect that top-1 sacrifices.

The ST-MoE paper (2022) stabilized MoE training with the auxiliary loss formulation covered in Section 07. DeepSeek's loss-free variant (V3) is the next evolution — but the ST-MoE auxiliary loss remains the pedagogical foundation and is still used in many production systems.

Visual Intuition: The Expert Council Metaphor

Each MoE layer is a council of specialists rather than one generalist. The router summons only relevant experts per token — many members exist (high total parameters), but only a few are active per input.

02

Dense vs. Sparse Activation

The word dense is the key to understanding MoE's efficiency gain. In a dense model, every input token passes through all FFN parameters — all layers, all neurons, nothing set to zero. Whichever token arrives at the FFN — "the", a comma, a number — it activates the full ~4.7M parameters in that block.

In a sparse MoE model, only a small subset of experts activates for any given input. With 64 experts and top-k = 2, only 2 of 64 expert networks fire per token. If each expert uses a smaller hidden dimension — say 128 instead of 3072 — the active compute is 128 × 2 = 256 versus 3072, roughly 12× less FFN work per token.

Dense FFN

1 network per layer. 100% parameters active. Every token → full 4M+ params. Higher training & inference cost.

Sparse MoE

N expert networks per layer. Top-k active. Token routes to specialists. Same output dim, fraction of compute.

The sparsity factor measures how many experts fire. With 4 experts and 1 active per token, sparsity = 1/4 = 25%. With 64 experts and 2 active, sparsity = 2/64 ≈ 3.1%. Lower percentage means sparser — fewer experts active, greater compute savings.

Each expert is specialized for certain computations. When a punctuation token arrives, route it to the punctuation expert — not all 4 million parameters. When a verb arrives, route to the verb expert. This specialization is what makes sparse activation both faster and effective.

Sparsity Factor Illustrated

With 4 experts and 1 active per token, the sparsity factor is 1/4 = 25%. Visualize four input tokens entering one transformer block with four experts:

  • Token 1 → Expert 4 only (Experts 1, 2, 3 dark)
  • Token 2 → Expert 2 only
  • Token 3 → Expert 1 only
  • Token 4 → Expert 3 only

Each token touches 25% of available experts. At 64 experts with top-2, sparsity drops to 2/64 ≈ 3.1% — the compute savings become dramatic.

The 64-Expert Arithmetic

Suppose each of 64 experts uses hidden dimension 128 (versus dense 3072):

Active hidden = top_k × expert_hidden = 2 × 128 = 256
Dense hidden = 4 × 768 = 3072 (for d=768)

Ratio: 3072 / 256 = 12× reduction in FFN hidden-layer compute per token. This is the arithmetic that makes MoE attractive at scale — and why DeepSeek, Mistral, and Llama 4 all adopted it.

Pre-training and Inference Benefits

Adding multiple experts allows pre-training with far less compute than a dense model of equivalent total capacity. It also accelerates inference because each token's forward pass touches fewer FFN parameters. Both benefits stem from the same root cause: sparsity.

03

What Do Experts Actually Learn?

A natural question: if experts specialize, specialize in what? The ST-MoE paper (Designing Stable and Transferable Sparse Expert Models, 2022) — one of the most influential MoE papers for language models — answered this with empirical analysis. Table 13 in that paper maps which experts handle which token categories across transformer layers.

Token CategoryExample TokensLayer(s) Routed To
Punctuation, ; . ? !Layer 2
Conjunctions & articlesthe, and, if, butLayers 3, 6
Verbsfalling, identified, struggling, signed, disagreeLayer 1
Visual descriptionsblue, inner, over, open, dark, upperLayer 0
Proper namesMart, Colin, Ken, Sam, AngelLayer 1
Counting & numbersafter, then, 7, 25, 454Layer 1

From this table, a clear picture emerges. Expert networks do not learn random partitions of the vocabulary — they learn semantic and syntactic categories. One expert handles punctuation (comma, semicolon, full stop). Another handles verbs. Another handles numbers. Another handles spatial/color descriptors.

Consider the efficiency argument: if you know one expert processes punctuation, why activate all 4 million FFN parameters for a comma? Activate the smaller specialized network instead. That saves pre-training time and makes inference faster — the core promise of MoE.

Modern LLMs universally adopt MoE at scale. Llama 4 is Meta's first model built on mixture of experts. DeepSeek-V3 uses it. The pattern is clear: specialized experts, sparsely activated, dominate frontier architecture design.

Why Specialization Beats Generalization (For FFN)

Consider processing a comma with a dense FFN. All 4.7M parameters adjust to handle this tiny punctuation mark — including weights specialized (wasted) for verbs, numbers, and names. The dense network cannot selectively deploy only punctuation-relevant weights.

With MoE, the router recognizes the comma-like embedding and routes to the punctuation expert — perhaps 200K parameters instead of 4.7M. The computation is focused. The expert has learned punctuation patterns deeply because it only ever sees punctuation tokens during training (via routing).

ST-MoE Paper Details

Designing Stable and Transferable Sparse Expert Models (2022) established that MoE experts in language models develop interpretable specializations without explicit supervision. The routing mechanism alone — driven by next-token prediction loss — creates emergent modularity. Table 13 maps categories to layers:

Layer 0 handles visual/spatial tokens ("blue", "inner", "upper"). Layer 1 handles verbs, names, and numbers. Layer 2 handles punctuation. Layers 3 and 6 handle conjunctions and articles. This layer-dependent specialization means the model builds a processing pipeline — early layers handle perceptual tokens, middle layers handle syntactic function words, later layers refine semantics.

04

A Token's Journey Through Every Layer

A common misconception: MoE replaces one FFN in one transformer block. The reality spans all layers. Every transformer block contains its own set of experts. A token's routing changes from layer to layer — the expert that handles numbers in layer 1 may differ from the expert handling numbers in layer 2.

Consider the input sequence: "What is 1 + 1?" Focus on the token "1".

  • Token "1" is embedded and passes through Layer 1 MoE → routed to Expert 1 (numbers specialist)
  • Same token in Layer 2 → possibly Expert 3 (different numbers specialist in this layer)
  • Layer 3 → Expert 2. Layer 4 → Expert 1. … through all 12 (or 48, or 96) layers

Routing is not fixed across layers. We do not hard-code "Expert 1 always handles numbers." The model learns layer-specific specializations from data. Expert 3 in layer 2 might handle numbers even if Expert 1 handles numbers in layer 1.

When the model predicts the next token — say "2" — that new token begins its own independent routing journey through all layers, possibly hitting different experts than "1" did.

The key lesson: routing is per-token, per-layer, learned. No hand-coded rules. The model discovers which expert handles which token type at which depth through gradient descent on next-token prediction.

Multiple Experts Per Layer, Every Layer

If the model has 12 transformer blocks and 4 experts per block, there are 12 × 4 = 48 expert networks total (per MoE-enabled layer set). With 64 experts and 96 layers — as in large production models — you have thousands of expert networks, each with millions of parameters, but only top-k × num_moe_layers active per token.

Seven Steps: MoE From Input to Output

A mixture of experts block takes an input embedding matrix and returns an output of the same shape. The seven steps below use four tokens — "the", "next", "day", "is" — with embedding dimension d = 8 (toy size for visualization; production models use d = 768, 4096, or larger), 3 experts, and top-k = 2.

① Input Matrix
4×8
② Expert Outputs
3 × (4×8)
③ Sparsity (top-k=2)
④ Router × Input
⑤ Top-k + Softmax
⑥ Weighted Merge
⑦ Output 4×8

Why Dimension Must Be Preserved

The MoE block sits inside a transformer with residual connections: output = input + MoE(LayerNorm(input)). For the addition to work, MoE output must match input shape exactly. Every expert individually preserves dimension (expansion-contraction FFN). The weighted sum of same-shaped vectors preserves dimension. This is non-negotiable — shape mismatch would break the entire transformer stack.

Computational Savings Analysis

With 3 experts and top-2: each token computes 2 of 3 experts = 66.7% of expert FFN compute. With 64 experts and top-2: 2/64 = 3.1%. The savings scale with number of experts. Production models use large N specifically to maximize this ratio.

However, the router itself adds compute: X·W_r is a (T×d)·(d×N) multiplication. For large N, router cost is non-negligible but still far less than computing all experts.

Step 1 — Input Embedding Matrix

Four tokens arrive at the MoE block after tokenization, embedding lookup, positional encoding, layer normalization, and multi-head attention. The input matrix X has shape (4 × 8): four rows (one per token), eight columns (embedding dimension).

Step 2 — Pass Through All Experts

Each expert E₁, E₂, E₃ is an expansion–contraction FFN that preserves dimension. Passing X through each expert yields three output matrices, each 4 × 8:

  • Expert Output 1: row 1 = "the", row 2 = "next", row 3 = "day", row 4 = "is"
  • Expert Output 2: same token rows, different transformed values
  • Expert Output 3: same structure

Challenge: three 4×8 matrices, but we need one 4×8 output. How do we merge them?

Step 3 — Sparsity Decision (Top-k Selection)

Decide how many experts activate per token. Here: top-k = 2 out of 3 experts. No token passes through all three experts. With 64 experts and k=2, sparsity is extreme: 62 experts idle per token. This decision is also called the load balancing sparsity constraint.

Step 4 — Routing Mechanism

Two questions per token: (1) Which k experts? (2) What weight for each? A trainable routing matrix W_r of shape (8 × 3) answers both:

ExpertSelector = X · W_r   →   shape (4 × 3)

Row i = token i's raw scores for each expert. Column j = expert j's scores across all tokens.

Step 5 — Top-k + Softmax → Expert Selector Weight Matrix

For each row: keep top-2 values, set others to −∞, apply softmax. Result: each row sums to 1, unselected experts get weight 0.

Example expert selector weight matrix (after top-2 + softmax):

TokenE1E2E3
the0.000.600.40
next0.900.000.10
day0.000.400.60
is0.500.000.50

Step 6 — Weighted Merge Per Token

For token "the" (row 1): E2 and E3 active with weights 0.6 and 0.4.

output[the] = 0.6 × ExpertOut2[row1] + 0.4 × ExpertOut3[row1]

For "next": 0.9 × E1[row2] + 0.1 × E3[row2]. Repeat for all tokens → final 4×8 matrix.

Step 4 Detail — Routing Matrix Dimensions

The routing matrix W_r is trainable — its weights learn during backpropagation which experts should handle which token types. Dimensions:

  • Input X: (num_tokens × d) = (4 × 8)
  • Router W_r: (d × num_experts) = (8 × 3)
  • Expert Selector (raw): (4 × 3) — rows are tokens, columns are experts

Each column of the expert selector corresponds to one expert. Each row corresponds to one token. Entry (t, e) = how much token t "wants" expert e before top-k masking.

Step 5 Detail — Softmax With Concrete Numbers

For token "the" (row 1), suppose raw scores after X·W_r are [0.5, 2.1, 1.8]. Top-2: keep E2 (2.1) and E3 (1.8), mask E1 → [−∞, 2.1, 1.8].

Softmax: exp(2.1)=8.166, exp(1.8)=6.050, sum=14.216. Weights: E2=8.166/14.216=0.574≈0.60, E3=6.050/14.216=0.426≈0.40. Row sums to 1.0.

For token "next" (row 2): raw [2.3, 0.1, 1.5]. Top-2: E1 and E3. After softmax: E1=0.90, E3=0.10.

Step 6 Detail — Merge for "next"

Expert selector says: E1 at 90%, E3 at 10%. Go to Expert Output 1 and Expert Output 3. Take row 2 from each (row 2 = "next").

output["next"] = 0.9 × ExpertOut1[2,:] + 0.1 × ExpertOut3[2,:]

Element-wise weighted sum of two 8-dimensional vectors → one 8-dimensional output vector for "next".

Step 7 — Output

Input was 4×8. Output is 4×8. Dimension preserved — identical to dense FFN behavior. The difference: only 2 of 3 experts computed per token.

06

Router Mathematics: Softmax, Top-k, and Gating

The routing mechanism is the brain of MoE. Given token embedding x (a row of the input matrix), the router produces a probability distribution over experts.

Step A — Raw Expert Scores

s = x · W_r + b    where W_r ∈ ℝ^{d × N}, N = number of experts

Vector s has length N — one score per expert before normalization.

Step B — Top-k Selection

Keep the k largest scores; set all others to −∞:

s'_j = s_j if j ∈ TopK(s, k), else −∞

Step C — Softmax Gating

g_j = exp(s'_j) / Σ_i exp(s'_i)

Because exp(−∞) = 0, non-selected experts receive gate weight exactly zero. Selected experts' weights sum to 1 — interpretable as percentages.

Why −∞ Before Softmax?

Two goals simultaneously: (1) unselected experts → weight 0; (2) selected experts → weights sum to 1. Masking with −∞ then softmax achieves both in one operation. This is the same softmax trick used in attention masking.

Concrete Walkthrough: Token "next" (row 2)

Raw scores: [2.1, 0.3, 1.8]. Top-2: keep E1 (2.1) and E3 (1.8), mask E2 → [2.1, −∞, 1.8].

Softmax: exp(2.1)=8.17, exp(1.8)=6.05, sum=14.22 → g = [0.575, 0, 0.425]. After renormalization over selected only: 90% E1, 10% E3 (matching our table).

Complete Gating Equations

For token embedding x ∈ ℝ^d and N experts, the full routing pipeline is:

s = x W_r   (1 × N raw logits)
s' = TopK_mask(s, k)   (non-top-k entries → −∞)
g_j = exp(s'_j) / Σ_i exp(s'_i)   (gate weights, Σg = 1)
y = Σ_j g_j · Expert_j(x)   (weighted expert outputs)

Only experts with g_j > 0 are computed. In practice, frameworks use expert parallelism — different experts live on different GPUs — so routing decisions also determine cross-device communication patterns.

Batch Matrix Form

For a batch of T tokens, all operations vectorize:

G = Softmax(TopK(X W_r, k))   shape (T × N)
Y = Σ_j diag(G[:,j]) · Expert_j(X)   shape (T × d)

This is how production MoE layers process thousands of tokens in parallel while maintaining sparsity per row.

07

Auxiliary Loss: Balancing Expert Importance

Top-k routing alone has no guarantee of balance. Some experts may be chosen constantly while others never activate — leading to inefficient learning and suboptimal performance. We want every expert contributing across the dataset.

During training, the main loss is next-token prediction (cross-entropy). MoE adds an auxiliary loss term that penalizes imbalanced expert selection, pushing the router toward a more uniform distribution of token assignments across experts.

The core problem: without balancing, routing follows a rich-get-richer dynamic. An expert that randomly receives slightly more tokens early in training gets stronger gradients, produces better outputs, and attracts even more tokens — until it monopolizes routing. Auxiliary loss interrupts this cycle by penalizing uneven importance scores before collapse becomes irreversible.

Expert Importance

From the expert selector weight matrix G (shape T × N, T tokens, N experts), each column j holds the probabilities of all tokens routing to expert j. Summing column j gives expert importance for expert j:

Importance_j = Σ_{t=1}^{T} G_{t,j}

Using our 4-token example:

ExpertColumn Sum (Importance)Interpretation
E10 + 0.9 + 0 + 0.5 = 1.4Moderate
E20.6 + 0 + 0.4 + 0 = 1.0Lowest
E30.4 + 0.1 + 0.6 + 0.5 = 1.6Highest — hogging routes

E3 carries the most importance because more tokens route to it with higher aggregate probability. E2 is underutilized. Ideally all three importance values should be roughly equal.

Coefficient of Variation (CV)

Measure spread of importance values relative to their mean:

CV = σ(Importance) / μ(Importance)

With values [1.4, 1.0, 1.6]: μ = 1.333, σ ≈ 0.249, CV ≈ 0.187.

Auxiliary Loss Formula

L_aux = λ · CV² = λ · (σ / μ)²

λ is a hyperparameter controlling auxiliary loss strength. Higher CV → higher penalty → router adjusts to spread tokens more evenly.

L_total = L_LM + L_aux

Reading Columns vs Rows of G

Rows tell you: for this token, which experts and with what weight?

Columns tell you: for this expert, which tokens route to it and with what probability?

Column 1 (E1): [0, 0.9, 0, 0.5] — token 1 ("the") has 0 probability to E1. Token 2 ("next") has 0.9. Token 3 ("day") has 0. Token 4 ("is") has 0.5. Sum = 1.4 = importance of E1.

This dual reading — row-wise for forward pass, column-wise for balancing — is essential for MoE debugging.

Full Auxiliary Loss Derivation

Given expert selector weight matrix G ∈ ℝ^{T×N}:

Step 1: Compute importance per expert: I_j = Σ_t G_{t,j}

Step 2: Compute mean μ_I = (1/N) Σ_j I_j

Step 3: Compute std σ_I = sqrt((1/N) Σ_j (I_j − μ_I)²)

Step 4: CV = σ_I / μ_I

Step 5: L_aux = λ · CV²

Concrete with I = [1.4, 1.0, 1.6]:

  • μ = (1.4 + 1.0 + 1.6) / 3 = 4.0/3 = 1.333
  • Variance = ((1.4−1.333)² + (1.0−1.333)² + (1.6−1.333)²) / 3 = (0.0045 + 0.1109 + 0.0711)/3 = 0.0622
  • σ = √0.0622 = 0.249
  • CV = 0.249 / 1.333 = 0.187
  • L_aux (λ=0.01) = 0.01 × 0.187² = 0.01 × 0.03497 = 0.000350

During training, gradients from L_aux push router weights so importance values converge — E3's dominance (1.6) gets penalized, E2's underuse (1.0) gets boosted.

What Happens to Idle Experts?

If Importance_j ≈ 0, expert j receives no tokens, no gradient signal, and its weights stagnate at initialization. It becomes dead weight — literally. Auxiliary loss exists precisely to prevent this death spiral. Without it, routing collapse is not a risk but an inevitability at scale.

Critical distinction: Equal expert importance does not guarantee uniform token routing. A single token routed with probability 1.0 to E1 gives E1 importance 1.0, same as four tokens each routed with 0.25 to E2 — but completely different load patterns. That is why we need load balancing loss too.

08

Load Balancing Loss: Aligning Importance with Token Count

Auxiliary loss equalizes expert importance (sum of routing probabilities). But equal importance can mask wildly uneven token counts. Consider this pathological case:

E1E2
Token 11.00.0
Token 20.00.25
Token 30.00.25
Token 40.00.25
Importance1.01.0
Tokens dispatched14

Both experts have importance 1.0 — auxiliary loss is happy. But E1 receives 1 token (with certainty 1.0) while E2 receives 4 tokens (each with 0.25). E2 hogs all the limelight. Non-uniform token dispatch causes high memory usage on hot experts and reduced MoE performance.

Two Quantities Per Expert

P_i — probability the router selects expert i (derived from importance, normalized):

P_i = Importance_i / T    (T = number of tokens)

Example: P1 = 1.4/4 = 0.35, P2 = 1.0/4 = 0.25, P3 = 1.6/4 = 0.40. Sum = 1.

f_i — fraction of tokens actually dispatched to expert i (hard assignment: token goes to expert with highest gate weight among selected):

From our weight matrix: "the"→E2, "next"→E1, "day"→E3, "is"→E1 (tie-break E1 over E3 at 0.5). So f1=2/4=0.5, f2=1/4=0.25, f3=1/4=0.25.

Load Balancing Loss

L_load = α · N · Σ_i (f_i · P_i)

α = scaling hyperparameter, N = number of experts. Minimize Σ f_i · P_i.

Why f_i × P_i Works — Two Scenarios

Scenario A (unbalanced): E1 gets all 4 tokens with probability 1.0 each. P1=1, f1=1, P2=0, f2=0 → loss = 1×1 + 0×0 = 1.0.

Scenario B (balanced): Each expert gets 2 tokens. P1=0.5, f1=0.5, P2=0.5, f2=0.5 → loss = 0.5×0.5 + 0.5×0.5 = 0.5.

Lower loss when distribution is uniform. Minimizing pushes both f_i and P_i toward uniformity simultaneously, aligning importance with actual routing.

Concrete calculation with α=0.01, N=3:

L_load = 0.01 × 3 × (0.5×0.35 + 0.25×0.25 + 0.25×0.40) = 0.0101

The f_i × P_i Product Explained

Why multiply fraction and probability? Compare a collapsed routing pattern against a balanced one:

Case A: f_1=1.0, f_2=0.0, P_1=1.0, P_2=0.0 (all hard-routed tokens to E1). Product sum = 1.0×1.0 + 0.0×0.0 = 1.0.

Case B: f_1=0.5, f_2=0.5, P_1=0.5, P_2=0.5. Product sum = 0.25 + 0.25 = 0.5. But Case A (collapse) gives product 1.0 > Case B 0.5. Minimization prefers Case B.

The product is small when both f_i and P_i are small together (uniform spread) and large when one expert dominates both metrics simultaneously.

Formal Load Balancing Loss

L_load = α · N · Σ_{i=1}^{N} f_i · P_i

With our example: f = [0.5, 0.25, 0.25], P = [0.35, 0.25, 0.40], N = 3, α = 0.01:

L_load = 0.01 × 3 × (0.5×0.35 + 0.25×0.25 + 0.25×0.40) = 0.03 × 0.3375 = 0.0101

Why Minimizing Σ f_i · P_i Works

The product f_i · P_i is minimized when both factors are small and uniform. If one expert dominates (f_1→1, P_1→1), the product approaches 1.0 — maximum loss. If all experts share load equally (f_i→1/N, P_i→1/N), each product is 1/N² and the sum is N·(1/N²)=1/N — much smaller for large N.

Additionally, alignment matters: if P_i is high (router prefers expert i) but f_i is low (few tokens actually go there), the product is moderate but the mismatch hurts model quality. Minimizing the product encourages P_i and f_i to move together — experts with high preference also receive proportionally more tokens.

This increases training stability and leads to more efficient, balanced use of the MoE architecture across all GPUs in a distributed training run.

Remember: Auxiliary loss (Step 8) balances importance. Load balancing loss (Step 9) balances token dispatch. Both are needed because equal importance does not imply equal token counts — the canonical counterexample is E1 with importance 1.0 from a single token at p=1.0, versus E2 with importance 1.0 from four tokens at p=0.25 each. DeepSeek-V3's loss-free balancing (Chapter 09) solves both problems architecturally, but the mathematical understanding from this chapter remains essential.

Capacity Factor: Capping Expert Workload

Even with load balancing loss, one expert can still receive disproportionate tokens during a batch. Expert capacity is a hard guardrail limiting how many tokens any single expert processes.

Capacity = (tokens_per_batch × top_k) / (N_experts × capacity_factor)

With capacity_factor = 1.0, each expert handles exactly its fair share. With 1000 tokens/batch, top_k=2, 4 experts: capacity = (1000 × 2) / (4 × 1) = 500 tokens max per expert.

Why top_k in numerator? Each token is dispatched to k experts, so total expert-assignments = tokens × k.

  • capacity_factor = 1.0: strict fair split; excess tokens dropped or rerouted
  • capacity_factor > 1.0 (typ. 1.125–2.0): experts can exceed fair share — handles natural imbalance
  • capacity_factor < 1.0: stricter cap; some tokens dropped (undesirable — DeepSeek-V3 dropped zero tokens)
  • capacity_factor > 2.0: one expert can hog everything — defeats the purpose

Without capacity: all four tokens "the, next, day, is" could route to E1. With capacity=2: E1 accepts at most 2 tokens; overflow reroutes to E2 or E3.

Capacity Factor Edge Cases

capacity_factor = 1.0: Strictest fair share. With 1000 tokens, top_k=2, 4 experts: capacity = 2000/4 = 500 tokens per expert maximum. No expert exceeds fair share.

capacity_factor = 1.25: Each expert can handle 25% more than fair share. Common in production. Allows natural routing variance without drops.

capacity_factor = 2.0: Upper practical bound. One expert could take 2× fair share — risks imbalance but prevents token drops.

capacity_factor > 2.0: Defeats purpose. One expert can hog all tokens — reintroduces collapse.

capacity_factor < 1.0: Stricter than fair share. Excess tokens dropped or rerouted — hurts training quality. DeepSeek-V3 explicitly avoided dropping any tokens.

Tokens Per Batch Calculation

tokens_per_batch = batch_size × sequence_length × top_k

The top_k multiplier counts that each token generates k expert assignments. A batch of 32 sequences of length 512 with top_k=2: tokens_per_batch = 32 × 512 × 2 = 32,768 expert-token assignments to distribute across experts.

10

Expert Collapse: When the Council Fails

Expert collapse (also called routing collapse) occurs when the router sends nearly all tokens to one or a few experts while others sit completely idle. The idle experts receive no gradients, learn nothing, and waste their parameter budget.

How Collapse Happens

  1. Rich-get-richer routing: Expert E3 gets slightly more tokens early in training → stronger gradients → router learns to prefer E3 → even more tokens → collapse
  2. No balancing loss: Pure top-k + LM loss has no incentive for uniform routing
  3. High capacity factor: Allows one expert to absorb unlimited tokens
  4. Small batch sizes: Statistical noise in f_i estimates per step

Symptoms

  • Expert utilization histogram: one bar at 90%+, others near 0%
  • Validation perplexity plateaus below dense-model equivalent despite more total params
  • GPU memory hotspots on specific expert shards during distributed training

Remedies (This Chapter's Toolkit)

Auxiliary Loss

Penalizes unequal expert importance via CV². Soft pressure toward uniform P_i.

Load Balancing Loss

Penalizes Σ f_i·P_i. Hard alignment of token counts with importance.

Capacity Factor

Hard cap on tokens per expert per batch. Physical overflow prevention.

Loss-Free Balancing (V3)

DeepSeek-V3's innovation — covered in Chapter 09. Removes auxiliary loss entirely.

Interactive · Expert Utilization Chart

Expert Collapse: A Concrete Scenario

Imagine training begins. Router weights are random. By chance, Expert 3 gets slightly higher scores for common tokens ("the", "a", "is"). More tokens route to E3 → E3 gets more gradient updates → E3's FFN improves → router learns to prefer E3 even more.

After 10,000 steps: E3 handles 85% of tokens. Experts 1, 2, 4–64 are idle. Effective model capacity = 1 expert, not 64. Training loss plateaus. Inference shows no speedup over dense because one expert is overloaded while others waste memory.

This is expert collapse — the MoE equivalent of dead neurons, but at module scale. Auxiliary loss, load balancing loss, and capacity factor are the three guardrails against it.

If an expert receives zero tokens, it sits idle, receives no gradient updates, and effectively ceases to exist. With 64 experts and 50 collapsed, you are running a 14-expert model while paying for 64 — the worst of both worlds.

11

671 Billion Total, 37 Billion Active

DeepSeek-V3 is the canonical example of MoE at frontier scale. The model stores 671 billion parameters total but activates only about 37 billion per token — roughly 5.5% of weights compute on any single forward pass.

As introduced in Chapter 1, DeepSeek uses 671B total parameters but activates only ~37B per token. A router in each MoE layer selects top-k experts per token; unselected experts remain in memory but are not computed, yielding inference cost comparable to a ~37B dense model.

Interactive · Total vs Active Parameters

Why 671B Total but Only 37B Active?

DeepSeek-V3 stores every expert's weights in memory — all 671 billion parameters exist on disk and in GPU HBM during inference. But for each token's forward pass, the router selects top-k experts per MoE layer. Unselected experts are not computed.

Arithmetic intuition: if the model has ~256 routed experts per MoE layer with top-6 activation, each layer activates 6/256 ≈ 2.3% of its expert FFN parameters. Aggregated across all MoE layers plus attention/embedding params (which are always active), total active ≈ 37B out of 671B ≈ 5.5%.

MoE Advantages Summary

  • 5–7× speedup in training and inference vs equivalent dense model (typical with 32–128 experts)
  • Larger capacity without proportional compute — store 671B, compute ~37B
  • Reduced memory footprint for compute — activation memory scales with active experts, not total
  • Specialization — experts develop interpretable skills (punctuation, numbers, etc.)
  • Scalability — add experts to increase capacity with sublinear compute increase

MoE gives a 5–7× training speedup and similar inference speedup versus an equivalent dense model with the same total parameter count. DeepSeek-V3, Llama 4, Mixtral — all exploit this ratio.

APPENDIX

Complete MoE Reference: Steps 1–10

This appendix consolidates the entire MoE pipeline — from input embedding to balancing losses — as a single reference you can return to while implementing MoE from scratch.

Steps 1–7: Forward Pass

Step 1 — Input: Token embeddings X ∈ ℝ^{T×d} after attention sub-layer. T tokens, d dimensions.

Step 2 — Expert Forward: For each expert i ∈ {1..N}: O_i = Expert_i(X) ∈ ℝ^{T×d}. Each expert is a standard 2-layer FFN with expansion ratio 4 (or smaller in fine-grained designs).

Step 3 — Sparsity: Choose top-k experts per token. Only k of N experts will contribute.

Step 4 — Router: S = X · W_r where W_r ∈ ℝ^{d×N}. S ∈ ℝ^{T×N} is the expert selector matrix (raw logits).

Step 5 — Top-k + Softmax: For each row of S, keep top-k values, mask rest with −∞, apply softmax → G (expert selector weight matrix). G_{t,j} = probability token t uses expert j.

Step 6 — Weighted Merge: Y_t = Σ_j G_{t,j} · O_j[t,:]. Only k terms non-zero per row.

Step 7 — Output: Y ∈ ℝ^{T×d}, same shape as input. Feed to next sub-layer (residual + dropout).

Steps 8–10: Balancing (Training Only)

Step 8 — Auxiliary Loss: I_j = Σ_t G_{t,j}. CV = σ(I)/μ(I). L_aux = λ·CV². Added to LM loss.

Step 9 — Load Balancing: P_i = I_i/T. f_i = (hard-routed token count to expert i)/T. L_load = α·N·Σ f_i·P_i.

Step 10 — Capacity: cap = (T·k)/(N·CF). Drop or reroute tokens exceeding cap per expert per batch.

PyTorch-Style Pseudocode

class MoELayer(nn.Module): def __init__(self, d_model, num_experts, top_k): self.experts = nn.ModuleList([FFN(d_model) for _ in range(num_experts)]) self.router = nn.Linear(d_model, num_experts, bias=False) self.top_k = top_k def forward(self, x): # x: (T, d) logits = self.router(x) # (T, N) topk_vals, topk_idx = torch.topk(logits, self.top_k, dim=-1) gates = torch.full_like(logits, float('-inf')) gates.scatter_(-1, topk_idx, topk_vals) gates = F.softmax(gates, dim=-1) # (T, N), rows sum to 1 output = torch.zeros_like(x) for i, expert in enumerate(self.experts): mask = gates[:, i] > 0 if mask.any(): output[mask] += gates[mask, i:i+1] * expert(x[mask]) return output, gates # gates used for aux/load loss

Batch Processing: Four Tokens Simultaneously

In practice, all four tokens ("the", "next", "day", "is") are processed in parallel as rows of the input matrix X ∈ ℝ^{4×8}. The router produces S = X·W_r ∈ ℝ^{4×3} — all four tokens scored simultaneously. Top-k and softmax apply row-wise. Each expert receives a subset of tokens (those that selected it), processes them in batch, and returns outputs. The merge reweights and sums per token.

This batched sparse computation is what makes MoE efficient on GPUs — tokens that share the same active expert are grouped together, minimizing kernel launches.

Training vs Inference

Training

All experts receive gradient updates (even those not selected for a given batch — they simply get zero gradient for that step). Balancing losses active. Capacity factor may drop overflow tokens. Router weights learn.

Inference

Only top-k experts computed per token. No balancing losses. No capacity drops (DeepSeek-V3). Router frozen. Maximum sparsity benefit realized.

IMPLEMENTATION

Implementation Notes and Common Pitfalls

Router Initialization

Router weights W_r are typically initialized with small random values (Xavier/Kaiming). If initialized too large, softmax saturates early — one expert wins everything from step 0, triggering immediate collapse. Some implementations add noise to router logits during early training (router z-loss or jitter) to maintain exploration.

Expert Parallelism vs Tensor Parallelism

MoE introduces a third parallelism dimension beyond data parallel (split batch) and tensor parallel (split layers):

  • Expert parallelism: Different experts on different devices. Requires all-to-all token communication each MoE layer.
  • Tensor parallelism within expert: Split individual expert FFN across devices. Used when single expert is too large for one GPU.
  • Data parallelism: Same as dense models — replicate model, split batch.

DeepSeek-V3 training uses a combination of all three across their GPU cluster. Load balancing directly affects expert parallelism efficiency.

Top-k vs Top-1 Trade-off

SettingSparsityQualityUsed By
top-1Maximum (1/N)Lower — no expert ensembleSwitch Transformer
top-2High (2/N)Good balanceMixtral, many models
top-6Moderate (6/N)Higher qualityDeepSeek-V3
top-8Lower (8/N)Diminishing returnsSome experimental models

Higher k improves quality (ensemble of experts) but reduces sparsity benefit. DeepSeek-V3 uses top-6 as their quality-efficiency sweet spot with 256 routed experts.

Common Pitfalls

Pitfall 1: Forgetting multi-layer routing. Drawing MoE for one layer only. Always visualize all L layers with independent routing.

Pitfall 2: Confusing importance with load. Equal column sums do not mean equal token counts. Always check both I_j and f_j.

Pitfall 3: Ignoring router cost. Router is O(T·d·N). For N=256, d=7168, this is non-trivial. Still cheaper than all experts.

Pitfall 4: No balancing losses. Training without L_aux and L_load virtually guarantees collapse by step ~1000.

Pitfall 5: Capacity factor too high. CF > 2.0 re-enables collapse despite balancing losses.

Pitfall 6: Evaluating total params as compute cost. 671B total ≠ 671B compute. Always report active params separately.

Debugging MoE Training

Monitor these metrics every N steps during MoE training:

  1. Expert utilization histogram: Should be roughly flat. Spikes indicate collapse.
  2. CV of importance: Should decrease over training. Target CV < 0.1.
  3. Fraction of dead experts: Experts with zero tokens in last K batches. Target: 0.
  4. Load loss (L_load): Should decrease and stabilize.
  5. Router entropy: Average −Σ G log G per token. Too low = deterministic collapse.
  6. Capacity overflow rate: Fraction of tokens dropped due to capacity. Target: 0 (DeepSeek-V3).

With proper balancing, MoE training is stable and produces models that match or exceed dense-model quality at the same active parameter count — while enabling total parameter counts that dense models cannot afford to compute.

Expert Parallelism Communication Pattern

When experts are distributed across GPUs, each MoE forward pass triggers:

  1. Router compute (local): Each GPU computes router scores for its tokens
  2. Dispatch (all-to-all): Tokens are sent to GPUs hosting their selected experts
  3. Expert compute (local): Each GPU runs its experts on received tokens
  4. Combine (all-to-all): Expert outputs return to originating GPUs, weighted by gate values

Load imbalance directly increases all-to-all communication wait time — hot GPUs finish last. This is why load balancing is both a machine learning concern and a systems engineering concern.

Google's Switch Transformer (Fedus et al., 2021) scaled MoE to trillion-parameter models with top-1 routing and capacity factor 1.25. DEEP DIVE

Mathematical Deep Dive: Every Formula Derived

1. Dense FFN Parameter Count

A 2-layer FFN with expansion ratio r (typically r=4):

W_1 ∈ ℝ^{d × rd},   W_2 ∈ ℝ^{rd × d}
params = d·rd + rd·d = 2rd²

For d=768, r=4: params = 2 × 4 × 768² = 2 × 4 × 589,824 = 4,718,592.

2. MoE Expert Parameter Count

With N experts, each with expansion ratio r_e (may be smaller than dense r):

params_MoE = N × 2r_e d²

Active per token: k × 2r_e d². Condition for compute savings: k/N < 1 (always true) AND r_e ≤ r.

3. Router Logits

s_t = x_t W_r,   x_t ∈ ℝ^d,   W_r ∈ ℝ^{d×N},   s_t ∈ ℝ^N

For batch of T tokens: S = X W_r where X ∈ ℝ^{T×d}.

4. Top-k Masking

Define mask m_t ∈ {0,1}^N where m_t[j]=1 iff s_t[j] is among the k largest:

s'_t[j] = s_t[j] · m_t[j] + (−∞) · (1 − m_t[j])

5. Softmax Gating

G_{t,j} = exp(s'_t[j]) / Σ_i exp(s'_t[i])

Properties: G_{t,j} ∈ [0,1], Σ_j G_{t,j} = 1, G_{t,j}=0 when m_t[j]=0.

6. MoE Output

y_t = Σ_{j=1}^{N} G_{t,j} · Expert_j(x_t)

Only k terms in the sum are non-zero. Each Expert_j is a full FFN: Expert_j(x) = W_2^j · σ(W_1^j · x).

7. Expert Importance

I_j = Σ_{t=1}^{T} G_{t,j}

Column sum of gate matrix. Measures total routing probability mass assigned to expert j across the batch/sequence.

8. Coefficient of Variation

μ_I = (1/N) Σ_j I_j
σ_I = sqrt((1/N) Σ_j (I_j − μ_I)²)
CV = σ_I / μ_I
L_aux = λ · CV²

9. Router Selection Probability

P_i = I_i / T

Normalized importance — probability the router "prefers" expert i averaged across tokens.

10. Hard Assignment Fraction

f_i = (1/T) |{t : argmax_j G_{t,j} = i among active}|

Fraction of tokens where expert i receives the highest gate weight. Computed via hard assignment for load tracking.

11. Load Balancing Loss

L_load = α · N · Σ_{i=1}^{N} f_i · P_i

Minimized when both f and P are uniform. Product f_i·P_i is large when one expert dominates both metrics.

12. Expert Capacity

C = floor(T · k / (N · CF))

Maximum tokens expert i can accept in this batch. Tokens beyond C are dropped or rerouted to next-best expert.

13. Total Training Loss

L_total = L_LM + L_aux + L_load

L_LM is standard cross-entropy next-token prediction. λ and α are hyperparameters typically in range [0.001, 0.1].

14. Active Parameter Fraction (DeepSeek-V3)

active_ratio ≈ (k/N) × (N_moe_layers / L_total) × (r_e/r) + (non_MoE_params / total_params)

Non-MoE params (attention with MLA, embeddings, output head) are always active. MoE FFN params are sparsely active. Combined: ~37B / 671B ≈ 5.5%.

These fourteen formulas are the complete mathematical toolkit for understanding vanilla MoE. DeepSeek's subsequent innovations modify routing (loss-free balancing), expert structure (fine-grained segmentation), and architecture (shared experts) — but every modification builds on this base.

Numerical Example: Load Balancing Two Scenarios

Scenario 1 — Collapsed (E1 hogs everything):

4 tokens, 2 experts. E1 gets all tokens with gate weight 1.0 each. E2 gets nothing.

  • Importance: I_1 = 4.0, I_2 = 0.0
  • P_1 = 4/4 = 1.0, P_2 = 0/4 = 0.0
  • f_1 = 4/4 = 1.0, f_2 = 0/4 = 0.0
  • Σ f_i·P_i = 1.0×1.0 + 0.0×0.0 = 1.0
  • L_load = 0.01 × 2 × 1.0 = 0.02

Scenario 2 — Balanced:

E1 and E2 each get 2 tokens. Gate weights 0.6/0.4 split per token.

  • Importance: I_1 = 2.0, I_2 = 2.0
  • P_1 = 0.5, P_2 = 0.5
  • f_1 = 0.5, f_2 = 0.5
  • Σ f_i·P_i = 0.5×0.5 + 0.5×0.5 = 0.5
  • L_load = 0.01 × 2 × 0.5 = 0.01

Balanced scenario has half the load loss. Gradient descent on L_load pushes the router toward Scenario 2.

Expert Collapse: Formal Definition

Let u_i = I_i / Σ_j I_j be the utilization fraction of expert i. Expert collapse occurs when:

max_i(u_i) > 1 − ε for small ε (e.g., ε = 0.1)

At collapse, one expert handles >90% of routing probability mass. Remaining experts are effectively dead. The model degenerates to a dense model with wasted parameter overhead from idle experts.

Distributed Training Considerations

In production, experts are sharded across GPUs (expert parallelism). Each GPU holds 1 or more experts. When a token routes to expert j on GPU k, an all-to-all communication sends the token's embedding to GPU k and returns the result.

Load imbalance is not just a training quality issue — it is a systems issue. If E3 on GPU 2 receives 80% of tokens, GPU 2 becomes a bottleneck while other GPUs idle. Load balancing loss improves both model quality and hardware utilization.

Capacity factor provides a hard systems-level backstop: even if routing is skewed, no single GPU's experts accept more than C tokens per batch, preventing memory overflow on hot shards.
