Where We Left Off — and What DeepSeek Changed

Mixture of Experts replaces the single feed-forward network in each transformer block with a council of expert networks and a trainable router. For every token, the router selects only top-k experts — not all of them. This sparsity is the entire point: you store many experts but activate only a fraction, improving both pre-training efficiency and inference efficiency.

Building on the seven-step MoE pipeline from Chapter 08, DeepSeek introduces three key modifications.

Without load balancing, one expert hogs all tokens — expert collapse. Chapter 08 introduced three guardrails:

  • Auxiliary loss — penalizes coefficient of variation (CV²) of expert importance
  • Load balancing loss — L_load = α · N · Σ f_i · P_i, aligning token fractions f_i with probability fractions P_i
  • Capacity factor — hard cap on tokens per expert per batch

The fundamental trade-off: Both auxiliary and load balancing losses are added to the language modeling loss. They mean fundamentally different things — next-token prediction vs. expert utilization — yet their gradients flow together through backpropagation. If the scaling factor λ is too small, experts collapse. If λ is too large, language modeling quality degrades. Balancing experts effectively without compromising training quality was an open problem — until DeepSeek solved it architecturally.

DeepSeek did not invent MoE. They noticed limitations everyone else had observed — the λ trade-off, knowledge hybridity, knowledge redundancy — and built targeted architectural fixes. That pattern mirrors their MLA work: stand on existing research, then add one precise innovation that changes the game.

The router weight matrix W_r has shape (num_experts, n_embed) = (3, 8). Each row is one expert's "preference direction" in embedding space. The dot product of a token embedding with each row produces that token's affinity score for each expert — higher score means stronger match.

The Balancing Losses — Why They Hurt

Chapter 08 defined two soft balancing losses added to L_LM:

L_total = L_LM + λ_1 · CV²(importance) + λ_2 · α · N · Σ f_i · P_i

Where f_i is the fraction of tokens hard-routed to expert i, and P_i is the fraction of total routing probability mass assigned to expert i. Minimizing Σ f_i · P_i encourages proportional dispatch: experts with higher importance (more probability mass) receive proportionally more tokens.

The problem is tuning λ. Consider two failure modes:

  • λ too small: Load balancing term is negligible. Expert 3 receives 80% of tokens; Experts 1 and 2 idle. MoE degenerates toward a dense model with one active expert — wasting the other 62 experts' capacity.
  • λ too large: The optimizer prioritizes uniform routing over next-token prediction. Perplexity rises. You get balanced but dumb experts — each handles equal tokens but none specialize.

DeepSeek's insight: stop fighting this trade-off in loss space. Move load balancing to a control mechanism (bias terms) that operates outside the gradient path of L_LM. The model learns language; the controller distributes work.

Innovation 1: Auxiliary-Loss-Free Load Balancing

The load balancing loss from Chapter 08 works — it maintains balance. But it interferes with language modeling because both losses pull the model in different directions. DeepSeek's response: remove the loss entirely and enforce balance through a dynamic bias term b_i per expert, updated each training step without contributing gradients to the main loss.

L_total = L_LM   (no load balancing term)

The DeepSeek-V3 technical report states: "To achieve a better trade-off between load balance and model performance, we pioneer an auxiliary-loss-free load balancing strategy to ensure load balance." The mechanism is Equation 16 — compact on paper, clearest with a concrete example.

The λ Dilemma — Expanded

Consider training a 16-expert MoE on a language modeling task. You monitor two metrics: validation perplexity (lower = better language model) and expert utilization entropy (higher = more balanced routing).

With λ = 0.001 (weak balancing): perplexity = 15.2 (good), but Expert 7 receives 45% of all tokens while Experts 3, 11, 14 receive <2% each. Three experts are effectively dead — 3/16 = 19% of your expert capacity is wasted storage.

With λ = 0.1 (strong balancing): all experts receive 5–8% of tokens (good balance), but perplexity rises to 17.8. The model routes tokens uniformly but loses the specialization that makes MoE powerful — every expert becomes a generalist.

With λ = 0.01 (middle ground): perplexity = 15.8, utilization entropy moderate. Better, but still a visible perplexity hit compared to λ = 0. You are always paying something for balance when balancing lives in the loss function.

DeepSeek's bias mechanism removes this payment entirely. Perplexity tracks the λ = 0 curve (no balancing loss interference) while utilization tracks the λ = 0.1 curve (effective balance). That is the headline result.

The Concrete Example: 4 Tokens, 3 Experts, Top-2

Take 4 tokens routed through 3 experts with top-k = 2. After routing, the expert selector weight matrix (post-softmax) looks like this — each row is one token, each column one expert:

TokenExpert 1Expert 2Expert 3Selected
Token 1—0.60.4E2, E3
Token 20.5—0.5E1, E3
Token 3—0.70.3E2, E3
Token 40.5—0.5E1, E3

Step 1 — Count tokens routed to each expert:

  • Expert 1: Token 2, Token 4 → 2 tokens
  • Expert 2: Token 1, Token 3 → 2 tokens
  • Expert 3: Token 1, Token 2, Token 3, Token 4 → 4 tokens

Total routed assignments = 2 + 2 + 4 = 8 (each token hits 2 experts).

Step 2 — Average token load per expert:

avg_load = 8 / 3 = 2.67 tokens per expert

Step 3 — Load violation (positive = underloaded, negative = overloaded):

v_i = avg_load − tokens_routed_to_expert_i
  • Expert 1: 2.67 − 2 = +0.67 (underloaded)
  • Expert 2: 2.67 − 2 = +0.67 (underloaded)
  • Expert 3: 2.67 − 4 = −1.33 (overloaded)

Step 4 — Update bias terms. Initialize b_i = 0 for all experts. After each step:

b_i ← b_i + γ · sign(v_i)

where γ is the bias update speed (a small hyperparameter). If underloaded (v_i > 0): increase bias. If overloaded (v_i < 0): decrease bias.

  • Expert 1: b_1 ← b_1 + γ (underloaded → boost routing probability)
  • Expert 2: b_2 ← b_2 + γ (underloaded → boost routing probability)
  • Expert 3: b_3 ← b_3 − γ (overloaded → reduce routing probability)

Step 5 — Apply bias to routing scores, not gating weights. This is the critical subtlety from the V3 paper: the bias is added to affinity scores before top-K selection, but the gating value multiplied with the FFN output still comes from the original score s_{i,t} — not s_{i,t} + b_i.

TopK selection uses: s_{i,t} + b_i   |   Gating weight uses: s_{i,t} (original)

Before bias adjustment, raw logits might look like:

E1E2E3
Token 10.10.80.5
Token 20.60.20.7
Token 30.00.90.3
Token 40.50.10.6

After bias (b_1 = +γ, b_2 = +γ, b_3 = −γ): Expert 1 and 2 values increase across all rows; Expert 3 values decrease. Next iteration, the router is more likely to send tokens to E1 and E2, less likely to overload E3. Over many steps, loads converge toward balance — without any auxiliary loss gradient touching the model weights.

DeepSeek demonstrated that auxiliary-loss-free load balancing achieves both better performance and better load balance compared with traditional load balancing — uncompromised language modeling loss plus evenly utilized experts.

If there is no loss term, how does the model "learn" to balance?

It does not learn balance through gradients — balance is enforced externally by updating b_i each step based on observed token counts. The router's weight matrix W_r still learns via L_LM; the bias terms are non-differentiable control knobs, like a thermostat adjusting temperature without retraining the furnace. This decouples "what tokens mean" (language modeling) from "how work is distributed" (load balancing).

DeepSeek-V3 Equation 16 — Full Specification

The V3 paper defines routing with bias as:

g′_{i,t} = s_{i,t} if (s_{i,t} + b_i) ∈ TopK({s_{j,t} + b_j}, K_r), else 0

Three subtle points easy to miss when reading the paper cold:

  1. Bias affects selection, not weight. Top-K uses s_{i,t} + b_i. But the gating value g_{i,t} multiplied with FFN output comes from normalized s_{i,t} — the original affinity, not biased.
  2. Bias updates are per training step, not per batch element. After processing the full batch, count tokens per expert, compute violations, update all b_i once.
  3. γ (bias update speed) is a hyperparameter. Too large → oscillation. Too small → slow convergence to balance. DeepSeek uses small γ so adjustment is gradual.

DeepSeek-V3 also adds a complementary sequence-wise auxiliary loss with extremely small α — not for global balance (bias handles that) but to prevent pathological imbalance within a single sequence. This is a safety net, not the primary mechanism.

Complementary Sequence-Wise Balance Loss (V3)

Equations 17–20 in the V3 paper define a lightweight fallback:

L_Bal = α · Σ_i f_i · P_i

where f_i is the fraction of tokens in the sequence routed to expert i (hard indicator), and P_i is the mean normalized affinity. The balance factor α is assigned an extremely small value in V3 — deliberately negligible compared to L_LM. It prevents the edge case where one sequence sends all tokens to one expert, without reintroducing the full λ trade-off globally.

Think of it as three layers of balancing:

  1. Primary: Bias terms b_i — global, loss-free, per training step
  2. Secondary: Sequence-wise L_Bal — tiny α, within-sequence safety net
  3. Legacy (not used in V3 primary): Full auxiliary + load balancing loss from GShard/ST-MoE era

Sigmoid vs Softmax Routing (V2 → V3 Change)

DeepSeek-V2 used softmax over all routed expert affinities for gating values. V3 switches to sigmoid affinity scores with normalization only among selected top-K experts:

V2: s_i = softmax(u · e_i)  |  V3: s_i = σ(u · e_i), then normalize top-K

Sigmoid scores are independent per expert — expert 5's score does not affect expert 12's score before top-K selection. This decouples expert affinity estimation from competition among non-selected experts, which can improve routing stability with hundreds of fine-grained experts.

Innovation 2: Shared Experts

DeepSeek-MoE identified two structural problems with conventional MoE before proposing fixes. The second problem — knowledge redundancy — is what shared experts solve.

Problem: Knowledge Redundancy

Tokens assigned to different experts often require common knowledge — general syntax, basic facts, shared linguistic patterns. Multiple routed experts independently learn the same information in their parameters. That redundancy wastes capacity and prevents true specialization.

Solution: Shared Experts

Divide experts into two groups: routed experts (sparse, top-k selected) and shared experts (always active for every token). Common knowledge lives in shared experts; routed experts focus on specialized tasks.

The DeepSeek-MoE paper frames the goal as "Towards Ultimate Expert Specialization." Shared experts are the architectural mechanism for isolating redundant knowledge so routed experts can specialize.

Routed vs. Shared: The Key Distinction

PropertyRouted ExpertsShared Experts
ActivationSparse — top-k per tokenDense — all fire on every token
RoutingRouter decides which onesNo routing — always on
Knowledge roleSpecialized (arithmetic, code, etc.)Common / redundant baseline
DeepSeek-MoE config63 routed, top-7 activated1 shared expert always active

Shared experts function like an ER department — always active for every token, handling common patterns that all inputs need, while routed experts specialize.

The final MoE output combines both paths:

h_t = u_t + Σ FFN_i^(shared)(u_t) + Σ g_{i,t} · FFN_i^(routed)(u_t)

Shared expert outputs and weighted routed expert outputs are added together (with residual connection on u_t). No extra routing weights for shared experts — they always contribute their full output.

Weighted Summation Detail

Suppose 1 shared expert and top-7 routed experts activate for token t. The computation is:

  1. Compute shared_out = FFN_shared(u_t) — full forward pass, no gating
  2. Router produces g_{i,t} for i ∈ top-7 routed experts (normalized sigmoid scores)
  3. Compute routed_out = Σ_{i∈top-7} g_{i,t} · FFN_i^(routed)(u_t)
  4. Final: h_t = u_t + shared_out + routed_out

With 1 shared + 7 routed experts, 8 FFN forward passes execute per token (not 64). The other 56 routed experts are idle — that sparsity is where the compute savings come from. The shared expert adds one unavoidable dense pass, but eliminates the need for each routed expert to also learn common knowledge.

Why One Shared Expert Suffices

DeepSeek-MoE ablations use exactly 1 shared expert. More shared experts add dense compute without proportional benefit — the common knowledge base is largely unified (general syntax, basic facts, shared linguistic patterns). One well-trained shared expert captures this; additional shared experts would mostly duplicate each other — recreating the redundancy problem at the shared level.

Innovation 3: Fine-Grained Expert Segmentation

The first problem DeepSeek-MoE identified is knowledge hybridity. Conventional MoE uses a limited number of experts — often 8 to 16. With so few slots and massive training data, each expert gets tokens covering diverse knowledge domains. One expert might handle math, poetry, code, and medical text simultaneously. It assembles vastly different knowledge types in its parameters — knowledge that is hard to utilize simultaneously.

The paper states: "tokens assigned to a specific expert will be likely to cover diverse knowledge. Consequently, the designated expert will intend to assemble vastly different types of knowledge in its parameters which are hard to be utilized simultaneously."

The Fix: Split Large Experts into Smaller Ones

Fine-grained expert segmentation takes each large expert FFN and splits it into m smaller experts by reducing the hidden dimension by factor 1/m. If you had 4 large experts, you now have 4×m smaller ones — but total parameters and compute stay the same because each smaller expert has proportionally fewer dimensions.

N_experts: N → m·N   |   hidden_dim: d_ff → d_ff / m   |   total params: unchanged

Example: 4 conventional experts with hidden dim 4096 become 16 fine-grained experts with hidden dim 1024 each. Same total capacity, four times the routing slots — allowing each expert to specialize in a narrower knowledge slice.

Parameter Math — Concrete Numbers

One expert FFN with n_embed = 2048 and expansion ratio 4:

  • W_1: 2048 × 8192 = 16,777,216 params
  • W_2: 8192 × 2048 = 16,777,216 params
  • Total per expert: 33,554,432 ≈ 33.5M params

Conventional MoE with 4 such experts: 4 × 33.5M = 134M expert params.

Fine-grained with m=4: 16 experts, each with hidden dim 8192/4 = 2048:

  • W_1 per small expert: 2048 × 2048 = 4,194,304
  • W_2 per small expert: 2048 × 2048 = 4,194,304
  • Total per small expert: 8,388,608 ≈ 8.4M
  • 16 experts: 16 × 8.4M = 134M expert params — identical

Evolution Diagram — Conventional → Fine-Grained → +Shared

The DeepSeek-MoE paper shows three stages left to right:

  1. Conventional top-2 MoE: Few large experts, top-2 routing. Baseline.
  2. + Fine-grained segmentation: Same param budget, many small experts. Solves hybridity.
  3. + Shared expert: Add always-on expert alongside fine-grained routed pool. Solves redundancy.

DeepSeek-V3 production config: N_s = 1 shared expert, N_r = 256 routed experts, K_r = 8 activated per token — scaling the segmentation idea to hundreds of specialists while keeping one common-knowledge expert always active.

Which innovation solves which problem?

Shared experts → knowledge redundancy. Common info centralized; routed experts don't duplicate it.
Fine-grained segmentation → knowledge hybridity. More experts with narrower domains; no single expert forced to learn everything.
Loss-free balancing → the λ trade-off. Expert utilization without degrading L_LM.
These are orthogonal fixes — V3 uses all three simultaneously.

04

Device-Level Load Balancing

Expert-level balance is necessary but not sufficient at scale. In production training, experts are sharded across GPUs, nodes, and datacenter racks via expert parallelism (EP). Each GPU holds a subset of experts. When a token routes to expert 47 on GPU 3, that requires cross-device communication — an all-to-all dispatch of token activations to the GPUs that own the selected experts.

DeepSeek-V3's technical report is explicit: "An unbalanced expert load will lead to routing collapse and diminish computational efficiency in scenarios with expert parallelism." If all tokens route to experts on GPU 0, the other GPUs idle. Device-level imbalance wastes expensive H800/H100 compute and creates pipeline bubbles.

Node-Limited (Device-Limited) Routing

DeepSeek-V2 introduced device-limited routing; V3 carries it forward as node-limited routing. The constraint: each token is sent to at most M nodes (not all nodes in the cluster). Node selection works by summing the highest K_r/M affinity scores among experts on each node, then picking the top-M nodes by that aggregate score.

Each token → at most M nodes  |  Node score = Σ top(K_r/M) affinities on that node

Why this matters: with 256 experts spread across 32 nodes, unconstrained routing could dispatch a single token's top-6 experts to 6 different nodes — six cross-node all-to-all transfers. Node-limited routing caps that at M nodes (e.g., M=4), bounding communication volume. Under this constraint, DeepSeek's DualPipe pipeline parallelism can nearly achieve full computation-communication overlap — the compute-to-communication ratio improves from a problematic ~1:1 toward efficient pipelined training.

Expert Parallel Load Balancer (EPLB)

At inference time, DeepSeek released EPLB (Expert Parallel Load Balancer) — a system for rebalancing expert-to-GPU mappings when load skew persists across devices. Two strategies:

  • Hierarchical load balancing — when node count divides expert group count: first pack expert groups evenly across nodes, then replicate heavy experts within each node, then pack replicas to individual GPUs. Exploits group-limited routing to keep same-group experts on the same node, reducing inter-node traffic.
  • Global load balancing — replicate experts globally regardless of groups, pack replicas to GPUs. Used at larger EP sizes during decoding.

EPLB uses redundant experts — duplicating heavily loaded experts so multiple GPUs can serve the same logical expert, evening device load without changing model semantics.

Training at scale: DeepSeek-V3 trained on 2048 NVIDIA H800 GPUs using FP8 mixed precision, expert parallelism, pipeline parallelism (DualPipe), and these routing constraints — completing 14.8T token pre-training in 2.788M GPU hours with no irrecoverable loss spikes.

DualPipe and Communication Overlap

Cross-node expert parallelism creates a compute-to-communication ratio of roughly 1:1 — half the time spent moving token activations between GPUs, half spent computing. DeepSeek's DualPipe pipeline parallelism algorithm overlaps forward and backward computation-communication phases, reducing pipeline bubbles. Combined with node-limited routing (capping tokens to M nodes), the system approaches full compute-communication overlap.

EPLB — Expert Parallel Load Balancer

DeepSeek open-sourced EPLB for inference-time rebalancing. When expert load skews across GPUs during deployment:

  1. Monitor token counts per expert over a sliding window (default 1000 steps)
  2. Identify overloaded experts and create redundant copies
  3. Repack expert-to-GPU mappings every N steps (default 3000)
  4. Hierarchical policy: pack expert groups to nodes first (exploiting group-limited routing), then replicate within nodes, then assign to GPUs

For DeepSeek-V3, adding one redundant expert per EP rank costs approximately 2.4 GB of weight transfer — a one-time repacking cost that prevents sustained GPU idle time.

balancedness = avg_tokens_per_expert / max_tokens_per_expert → 1.0 = perfect balance

Expert Parallelism — How Experts Map to Hardware

In a 256-expert MoE layer with 64 GPUs (expert parallel size 64), each GPU owns 4 experts. When a batch of tokens arrives:

  1. Router runs on all GPUs (replicated) — produces gate weights for every token
  2. All-to-all dispatch — tokens are sent to the GPUs owning their selected experts
  3. Expert compute — each GPU runs its local experts on received tokens
  4. All-to-all combine — expert outputs routed back to origin GPUs
  5. Weighted sum — each token accumulates gated expert outputs

Steps 2 and 4 are pure communication — no matrix multiplies. If routing is imbalanced, some GPUs receive many tokens (compute-bound) while others receive few (idle). Device-level balancing ensures step 3 utilizes all GPUs evenly.

Group-Limited Routing and Node Affinity

DeepSeek-V3 groups experts and constrains routing so tokens prefer experts within selected node groups. When the number of server nodes divides the number of expert groups, hierarchical EPLB can place entire expert groups on the same node — keeping intra-node NVLink bandwidth (900 GB/s) instead of inter-node InfiniBand (200 GB/s). The node-limited routing constraint (at most M nodes per token) makes this placement strategy effective.

Is device-level balancing the same as expert-level balancing?

No. Expert-level balancing (bias terms) ensures each expert receives roughly equal tokens globally. Device-level balancing ensures each GPU/node receives roughly equal compute work. An expert-level balanced model can still be device-unbalanced if overloaded experts cluster on the same GPU. EPLB and node-limited routing address the hardware mapping layer on top of expert-level fairness.

Token-by-Token MoE Merge — Full Walkthrough

The merge step combines sparse expert outputs before the residual add. Below, each of four tokens passes through the sparse MoE merge (Steps 6–7) with the concrete routing weights from Section 01.

Token 1 → Experts 2 and 3 (weights 0.6, 0.4)

Input vector x_1 (shape 8). Router selected Expert 2 (weight 0.6) and Expert 3 (weight 0.4).

out_1 = 0.6 · Expert_2(x_1) + 0.4 · Expert_3(x_1)

Expert_2 applies its 8→32→8 FFN to x_1, producing a (8,) vector. Same for Expert_3. The two outputs are scaled and added element-wise. Result: out_1 has shape (8,) — same as input.

Token 2 → Experts 1 and 3 (weights 0.5, 0.5)

out_2 = 0.5 · Expert_1(x_2) + 0.5 · Expert_3(x_2)

Note Expert 3 handles both Token 1 and Token 2 — but with different input vectors (x_1 vs x_2) and potentially different weights (0.4 vs 0.5).

Token 3 → Experts 2 and 3 (weights 0.7, 0.3)

out_3 = 0.7 · Expert_2(x_3) + 0.3 · Expert_3(x_3)

Token 4 → Experts 1 and 2 (weights 0.55, 0.45)

out_4 = 0.55 · Expert_1(x_4) + 0.45 · Expert_2(x_4)

Stacking: output matrix = [out_1; out_2; out_3; out_4] with shape (4, 8). Same as input (4, 8). The entire MoE layer is a drop-in FFN replacement.

Expert-Loop Implementation — Why It's Faster

Token-centric (slow, pedagogical):

for t in range(num_tokens): out[t] = sum(gates[t,j] * experts[j](x[t]) for j in topk[t])

Expert-centric (fast, production):

for j in range(num_experts): weight = gates[:, :, j].unsqueeze(-1) # (B, T, 1) out += weight * experts[j](x) # expert j processes ALL tokens at once

When gates[t, j] = 0, that token contributes nothing from expert j — but the expert still runs on all tokens (wasted compute for unselected pairs). Production systems use expert capacity and sparse dispatch to skip zero-weight pairs entirely.

Noisy Top-K — When and Why

Gaussian noise on logits before top-K: noisy = logits + ε, ε ~ N(0, σ²). With σ = 0.1, a token that always routes to Expert 0 might occasionally route to Expert 1 instead — spreading load stochastically. This complements bias-term balancing (deterministic) with exploration (stochastic). Switch Transformer and early MoE systems used similar noise; DeepSeek-V3 relies primarily on bias terms but noise remains useful in smaller-scale experiments.

Building MoE from Scratch — The Expert Module

The following implements the full MoE stack in PyTorch — no external MoE libraries, only torch and torch.nn. The FFN in each transformer block is replaced with a sparse MoE module, trained on Shakespeare character-level data.

Architecture target: standard transformer block where the second sub-layer (after layer norm) is SparseMoE instead of a dense FFN. Input arrives as (batch, seq_len, n_embed) — e.g. (1, 4, 8) for a toy example with 4 tokens and embedding dim 8.

Step 1: The Expert Class

Each expert is a standard expansion–contraction FFN: Linear(n_embed → 4·n_embed) → ReLU → Linear(4·n_embed → n_embed) → Dropout. Production LLMs use SiLU/GELU; ReLU keeps the tutorial readable.

class Expert(nn.Module): def __init__(self, n_embed, dropout=0.1): super().__init__() self.net = nn.Sequential( nn.Linear(n_embed, 4 * n_embed), # expansion nn.ReLU(), nn.Linear(4 * n_embed, n_embed), # contraction nn.Dropout(dropout), ) def forward(self, x): return self.net(x)

Three experts with n_embed=8 means three independent networks, each mapping 8 → 32 → 8. Creating nn.ModuleList([Expert(8) for _ in range(3)]) gives us the expert pool.

Shape preservation: For input x of shape (B, T, C), each expert returns (B, T, C). The MoE layer output must match input shape so the residual connection x + MoE(LN(x)) works unchanged.

Inside One Expert — Matrix Dimensions

With n_embed = 8, a single token x_t has shape (8,). The expert computes:

  • Expansion: h = ReLU(W_1 · x_t + b_1) where W_1 is (32, 8), h is (32,)
  • Contraction: y_t = W_2 · h + b_2 where W_2 is (8, 32), y_t is (8,)

Parameter count per expert: (8×32 + 32) + (32×8 + 8) = 264 + 264 = 528 params. Three experts = 1,584 params — tiny, but the pattern scales: at n_embed=4096, each expert holds ~67M params.

Dropout Placement

Dropout sits after the contraction layer, before the residual add. During training, random elements of the expert output are zeroed — regularization. During inference, dropout is disabled. Both the attention module and MoE module embed their own dropout; the transformer block itself does not add another dropout layer on top.

07

The Router — Top-K Gating with Softmax

The router is a single linear layer: nn.Linear(n_embed, num_experts, bias=False). Input (B, T, C) is multiplied by weight (num_experts, C) to produce logits (B, T, num_experts) — the expert selector matrix.

Top-K Selection

With num_experts=3 and top_k=2, torch.topk(logits, k=2, dim=-1) selects the two largest logit values and their indices per token row — identifying which two experts handle each token.

Softmax Masking

After top-K, unselected experts must be zeroed before softmax so weights sum to 1 across only the selected experts:

  1. Initialize gates matrix as −∞ everywhere
  2. Scatter top-K logit values into their index positions
  3. Apply softmax → selected experts get positive weights summing to 1; others get 0

class TopKRouter(nn.Module): def __init__(self, n_embed, num_experts, top_k): super().__init__() self.top_k = top_k self.gate = nn.Linear(n_embed, num_experts, bias=False) def forward(self, x): logits = self.gate(x) # (B, T, num_experts) topk_logits, topk_indices = torch.topk(logits, self.top_k, dim=-1) gates = torch.full_like(logits, float('-inf')) gates.scatter_(-1, topk_indices, topk_logits) return F.softmax(gates, dim=-1)

Why −∞ Before Softmax?

Softmax over [0.8, 0.3, −∞] gives [0.62, 0.38, 0.0] — the third expert contributes nothing. Without −∞ masking, softmax would spread probability across all three experts, violating the top-K sparsity constraint. The scatter operation writes top-K raw logits into their positions; everything else stays at −∞.

Numerical Walkthrough — One Token Row

Raw logits for Token 0: [0.8, 0.3, −0.5]. Top-2 selects indices 0 and 1 (values 0.8 and 0.3).

After masking: [0.8, 0.3, −∞]. Softmax: exp(0.8)/(exp(0.8)+exp(0.3)) = 0.62 for E0, 0.38 for E1, 0.0 for E2.

Interpretation: Token 0 sends 62% of its weighted sum through Expert 0, 38% through Expert 1. Expert 2 is not computed at all (gates[..., 2] = 0, so 0 × Expert_2(x) = 0 regardless).

Noisy Top-K Router

An optional variant adds Gaussian noise to logits before top-K: noisy_logits = logits + torch.randn_like(logits) * noise_std. The rest is identical. Noise introduces controlled chaos — preventing the router from always favoring the same experts, an additional load balancing heuristic complementary to bias terms.

class NoisyTopKRouter(nn.Module): def __init__(self, n_embed, num_experts, top_k, noise_std=0.1): super().__init__() self.top_k = top_k self.noise_std = noise_std self.gate = nn.Linear(n_embed, num_experts, bias=False) def forward(self, x): logits = self.gate(x) if self.training and self.noise_std > 0: logits = logits + torch.randn_like(logits) * self.noise_std topk_logits, topk_indices = torch.topk(logits, self.top_k, dim=-1) gates = torch.full_like(logits, float('-inf')) gates.scatter_(-1, topk_indices, topk_logits) return F.softmax(gates, dim=-1)

Noise is applied only during training (self.training check). At inference, routing is deterministic — same input always routes to same experts. Training noise acts as exploration; inference exploits learned routing preferences.

Sparse MoE — Merging Expert Outputs

Given gate weights G of shape (B, T, E) and E expert networks, the output is a weighted sum of expert outputs. Conceptually, for each token t: out_t = Σ_j G[t,j] · Expert_j(x_t).

Production code loops over experts (not tokens) for efficiency — each expert processes all tokens routed to it in one batched forward pass, enabling expert parallelism:

class SparseMoE(nn.Module): def __init__(self, n_embed, num_experts, top_k, dropout=0.1): super().__init__() self.router = TopKRouter(n_embed, num_experts, top_k) self.experts = nn.ModuleList([Expert(n_embed, dropout) for _ in range(num_experts)]) def forward(self, x): gates = self.router(x) # (B, T, E) out = torch.zeros_like(x) for i, expert in enumerate(self.experts): weight = gates[..., i].unsqueeze(-1) # (B, T, 1) out += weight * expert(x) return out

For token 1 routed to experts 2 and 3 with weights 0.6 and 0.4: take Expert_2(x_1) × 0.6 + Expert_3(x_1) × 0.4. Accumulate across all experts. Tokens not routed to expert i contribute 0 because gates[..., i] = 0.

Interactive · MoE Weighted Merge Visualizer

Token 1 → Expert 2 (60%) + Expert 3 (40%). Adjust weights and see the merge.

Why loop over experts instead of tokens?

Token-centric loops are easier to explain but slower — each iteration processes one token through one expert. Expert-centric loops batch all tokens assigned to expert i into one forward pass. In distributed training, each GPU owns specific experts; the expert loop maps naturally to "process my experts, send results back." Same math, better compute layout.

Counting Tokens for Bias Updates

To integrate loss-free balancing into the SparseMoE training loop, count hard-routed tokens per expert after each forward pass:

def count_expert_tokens(gates, top_k): # gates: (B, T, E) after softmax num_experts = gates.size(-1) counts = torch.zeros(num_experts) for e in range(num_experts): counts[e] = (gates[..., e] > 0).sum().item() return counts # After optimizer.step(): counts = count_expert_tokens(gates, top_k) router.update_bias(counts, gamma=0.01)

This closes the loop: forward pass produces gates → count tokens → update biases → next forward pass uses updated biases in routing. No backward pass through bias updates.

Character Tokenization Pipeline

Shakespeare input.txt → raw text → character list → integer encoding:

chars = sorted(list(set(text))) vocab_size = len(chars) stoi = {ch: i for i, ch in enumerate(chars)} itos = {i: ch for i, ch in enumerate(chars)} encode = lambda s: [stoi[c] for c in s] decode = lambda l: ''.join([itos[i] for i in l]) data = torch.tensor(encode(text), dtype=torch.long)

Batch Construction — Next-Character Prediction

For each batch: sample random starting positions, extract block_size consecutive characters as input x, and x shifted by 1 as target y. If x = [t_0, t_1, t_2, t_3], then y = [t_1, t_2, t_3, t_4]. The model predicts y from x — standard autoregressive language modeling.

def get_batch(split): data = train_data if split == 'train' else val_data ix = torch.randint(len(data) - block_size, (batch_size,)) x = torch.stack([data[i:i+block_size] for i in ix]) y = torch.stack([data[i+1:i+block_size+1] for i in ix]) return x.to(device), y.to(device)

Full Language Model Class

class MoELanguageModel(nn.Module): def __init__(self, vocab_size, n_embed, n_head, n_layer, num_experts, top_k, block_size): super().__init__() self.block_size = block_size self.token_emb = nn.Embedding(vocab_size, n_embed) self.pos_emb = nn.Embedding(block_size, n_embed) self.blocks = nn.ModuleList([ MoEBlock(n_embed, n_head, num_experts, top_k) for _ in range(n_layer) ]) self.ln_f = nn.LayerNorm(n_embed) self.lm_head = nn.Linear(n_embed, vocab_size) def forward(self, idx, targets=None): B, T = idx.shape tok = self.token_emb(idx) pos = self.pos_emb(torch.arange(T, device=idx.device)) x = tok + pos for block in self.blocks: x = block(x) x = self.ln_f(x) logits = self.lm_head(x) loss = None if targets is not None: loss = F.cross_entropy(logits.view(-1, logits.size(-1)), targets.view(-1)) return logits, loss def generate(self, idx, max_new_tokens): for _ in range(max_new_tokens): idx_cond = idx[:, -self.block_size:] logits, _ = self(idx_cond) probs = F.softmax(logits[:, -1, :], dim=-1) next_id = torch.multinomial(probs, num_samples=1) idx = torch.cat([idx, next_id], dim=1) return idx

(Expert, NoisyTopKRouter, SparseMoE, MoEBlock, MoELanguageModel from above) # Hyperparameters vocab_size = len(chars) n_embed, n_head, n_layer = 128, 4, 4 num_experts, top_k = 8, 2 block_size, batch_size = 32, 16 max_iters, lr = 5000, 3e-4 device = 'cuda' if torch.cuda.is_available() else 'cpu' model = MoELanguageModel(vocab_size, n_embed, n_head, n_layer, num_experts, top_k, block_size) model.to(device) optimizer = AdamW(model.parameters(), lr=lr) for iter in range(max_iters): xb, yb = get_batch('train') logits, loss = model(xb, yb) optimizer.zero_grad(set_to_none=True) loss.backward() optimizer.step() if iter % 100 == 0: print(f'iter {iter}: loss {loss.item():.4f}') # Inference context = torch.zeros((1, 1), dtype=torch.long, device=device) print(decode(model.generate(context, max_new_tokens=200)[0].tolist()))

Did DeepSeek invent Mixture of Experts?

No. MoE dates to 1991 (Jordan & Jacobs). Shazeer's Switch Transformer scaled it to trillion-parameter LMs. DeepSeek's contribution is surgical: they identified three specific failure modes — the balancing loss trade-off, knowledge redundancy, knowledge hybridity — and built precise architectural fixes. Then they proved them in the DeepSeek-MoE paper with ablations showing shared experts and fine-grained segmentation each measurably improve benchmarks, and V3 showed loss-free balancing beats traditional auxiliary losses on both quality and balance.

Up next: Multi-Token Prediction — extending the prediction target to multiple future tokens per position, another DeepSeek-V3 training innovation that densifies learning signals and enables speculative decoding at inference time.
