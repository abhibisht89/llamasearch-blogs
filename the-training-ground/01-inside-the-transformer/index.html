01 · OVERVIEW

What this tutorial covers

In the Life of a Prompt blog, we traced a prompt through the vLLM inference engine — tokenization, KV cache, paged attention, and continuous batching. We treated the transformer model itself as a black box.

Now we open that black box.

This tutorial follows Aleksa Gordić's excellent visual deep-dive into a modern dense transformer, using the architecture of Rnj 1.5 (built at Ashish Vaswani's AI Lab, Essential AI Labs) as a running example. Rnj 1.5 is a long-context model that extends from 32k to 160k tokens, scoring 79% on RULER at a 128k context window.

We will trace a single token through every component of the forward pass:

Running example

Throughout this tutorial, we use:

  • Batch size = 1
  • Sequence length = 16 (two documents packed together)
  • Model dimension = 4,096
  • Transformer layers = 32
  • Attention heads = 32 (Q), with GQA for K/V
  • Data type = bf16
02 · TOKENIZATION

From raw text to integer sequences

Every forward pass begins here. The tokenizer is a black-box component that takes raw text and maps it to a sequence of integers, where each integer represents a sub-word token from a fixed vocabulary.

In practice, modern tokenizers are "trained" on a large corpus using algorithms like BPE (Byte Pair Encoding). The algorithm learns a vocabulary by repeatedly merging frequent character or byte sequences. Good tokenizer design has measurable impact — for example, representing digits as individual tokens helps with numerical reasoning.

Figure 1: Tokenization stage — two documents are tokenized into sequences of integers, then packed into a single sequence. Alongside the tokens, we construct input positions (for positional embeddings) and a segmentation mask (for attention masking).

Notice three key things in this diagram:

1

Document packing

Two separate documents are packed into a single sequence. This is an efficiency trick — instead of padding short documents to the max length, we concatenate them. This maximizes GPU utilization during training.

2

Input positions reset per document

Each document gets its own position indices starting from 0. This is critical for positional embeddings — we don't want the model to think document 2 starts at position 10.

3

Segmentation mask

A mask that tells the attention mechanism which tokens belong to the same document. Without this, tokens from document 1 could attend to tokens from document 2, which would corrupt training.

Key insight: In practice, all of this preprocessing happens before training starts. A Spark data pipeline tokenizes and packs documents into chunks, and the data loader feeds these preprocessed structures directly into the training loop. The model never sees raw strings.

Special tokens: Tokens like <FIM_PRE>, <FIM_SUF>, <FIM_MID> don't appear naturally during tokenization. They are injected during training for capabilities like Fill-in-the-Middle (FIM). During FIM training, a document is split into prefix, middle, and suffix, then rearranged as: <FIM_PRE> prefix <FIM_SUF> suffix <FIM_MID> middle. This teaches the model to complete gaps — the exact capability used by code autocomplete in IDEs.

03 · EMBEDDING

From integers to high-dimensional vectors

The next step converts our sequence of integers into vectors that the transformer can actually process. This is done by indexing into an embedding table.

Think of the embedding table as the vocabulary of the LLM. It's a giant matrix of shape (vocab_size × model_dim). Each row corresponds to one token ID, and that row is the token's learned representation — a 4,096-dimensional vector in bf16.

Figure 2: Embedding stage — each token ID is used to look up its corresponding row in the embedding table, producing a sequence of 16 vectors, each 4,096-dimensional in bf16.

After this step, our input has been transformed from a sequence of 16 integers into a (1 × 16 × 4096) tensor of bf16 vectors. These vectors are now ready to flow through the transformer layers.

A common question is: why 4,096 dimensions? Isn't that a lot?

Higher dimensions give the model more "space" to encode nuanced relationships between tokens. The choice of dimension is a trade-off: too small and the model can't represent complex patterns, too large and you waste compute. 4,096 is a common sweet spot for models in the 1-8B parameter range. Larger models like LLaMA 70B use 8,192 dimensions.

04 · THE TRANSFORMER BLOCK

The repeating unit — 32 times

Now we enter the core of the transformer. The model has 32 transformer layers, and the input vectors pass through each one sequentially. You can think of this as a for loop, but each layer has its own learnable weights.

Every transformer block has the same high-level structure:

Figure 3: The full forward pass through a transformer block. Four RMSNorm submodules, one MLP, one attention module, two residual connections, and two sum operations.

Let's unpack what this diagram is showing:

1

Residual connections (the highway)

The input vectors are copied and added back after each sub-layer (attention and MLP). This means information can "skip" a layer entirely if the layer's output is close to zero. Residual connections are the single most important architectural trick that enables deep networks — without them, gradients vanish and training collapses.

2

RMSNorm before each sub-layer

Normalization stabilizes training by keeping vector magnitudes in check. Rnj 1.5 uses pre-norm (normalize before the sub-layer, not after). There are also post-attention and post-MLP norms.

3

All submodules operate on individual vectors, except attention

RMSNorm and MLP process each vector independently — they don't look at other positions. Attention is the only component that mixes information between positions. This is why attention is special.

Key insight: The transformer block can be summarized as: normalize → attend (mix across positions) → normalize → transform (process each position independently) → add residuals. This pattern repeats 32 times, with each layer refining the representations further.

Now let's dive into each component, from simplest to most complex.

05 · RMSNORM

Root Mean Square Layer Normalization

RMSNorm is the simplest component in the transformer block. Its job is to normalize the magnitude of each vector so that training remains stable. Without normalization, vector magnitudes can explode or vanish across layers, making optimization impossible.

RMSNorm operates on individual vectors — it doesn't look at other positions in the sequence. For a single 4,096-dimensional bf16 vector, here's what happens:

Figure 5: RMSNorm — takes a single 4,096-dim bf16 vector, normalizes it using the root mean square, then scales by a learned parameter γ. Output has the same shape and dtype.

The operation in three steps:

1

Compute RMS

Calculate the root mean square of all 4,096 elements. This is a single scalar value that represents the "average magnitude" of the vector.

2

Normalize

Divide every element by the RMS value. After this, the vector has unit RMS — its magnitude is controlled.

3

Scale

Multiply element-wise by a learned parameter vector γ (same dimension as the input). This lets the model learn the "right" scale for each dimension after normalization.

How is RMSNorm different from LayerNorm?

LayerNorm computes both the mean and variance, then normalizes using both. RMSNorm skips the mean computation entirely — it only divides by the root mean square. This makes it faster (one less reduction operation) while being empirically just as effective. Most modern transformers (LLaMA, Mistral, Gemma, DeepSeek) use RMSNorm over LayerNorm.

06 · GeGLU MLP

The gated feedforward network

The MLP (Multi-Layer Perceptron) is a pointwise feedforward network that processes each vector independently. Its job is to learn complex non-linear relationships between features within each position.

Rnj 1.5 uses a GeGLU (GELU-Gated Linear Unit) variant. The gating mechanism uses GELU activation and takes the form:

where ⊙ is element-wise multiplication.

Figure 6: GeGLU MLP — the input vector is projected through two parallel paths (W0 and W1), one of which passes through GELU. The results are element-wise multiplied (gating), then projected back down by W2.

Let's break down what's happening step by step:

1

Up-projection (expand)

The 4,096-dim input is projected to a higher dimension (typically 4× larger, so ~16,384) through two separate weight matrices W0 and W1. This expansion gives the model more room to represent features.

2

Gating with GELU

One path goes through GELU activation, producing values that can be positive, slightly negative, or near-zero. This is multiplied element-wise with the other path, effectively "gating" which features pass through. Think of it as a learned filter that selectively amplifies or suppresses different features.

3

Down-projection (compress)

W2 projects the result back to 4,096 dimensions. The output has the same shape as the input — ready for the residual connection.

Key insight: The gating mechanism is what makes GeGLU more powerful than a standard MLP. With a vanilla MLP (just W2 × ReLU(W1 × x)), every feature goes through the same activation. With gating, the model can learn to selectively route information — some features get amplified, others get suppressed, all based on the input itself.

Why does the MLP expand to 4× the model dimension and then compress back?

The expansion creates a higher-dimensional "workspace" where the model can learn more complex feature interactions. The compression back to the original dimension ensures the output is compatible with the residual connection. This expand-then-compress pattern (also called a "bottleneck in reverse") is universal across transformer architectures. The 4× ratio is a common default, but some models use different ratios.

07 · MULTI-HEAD ATTENTION

The only component that mixes information across positions

This is the most important and most complex component. Attention is the only mechanism in the transformer that allows tokens at different positions to exchange information. Without attention, each position would be processed in total isolation.

Rnj 1.5 uses GQA (Grouped Query Attention) — a variant where the number of Key/Value heads is reduced compared to Query heads. Multiple query heads share the same key-value pair, saving memory and compute without sacrificing much quality.

Figure 7: Multi-Head Attention — each vector is independently projected into Query, Key, and Value vectors. After reshaping into heads, QK normalization, and YaRN positional embeddings, core attention mixes information across positions. A final linear projection produces the output.

The high-level flow of attention:

Project into Q, K, V

Each input vector (4,096-dim) is independently projected into Query, Key, and Value vectors through learned weight matrices. These projections are the "questions" (Q), "labels" (K), and "content" (V) of each position.

Reshape into heads

The vectors are split into multiple attention heads. Each head operates on a lower-dimensional slice of the full vector, allowing the model to attend to different aspects of the input simultaneously.

QK normalization

Queries and keys are normalized to prevent attention scores from becoming too large, which would cause softmax to produce near-one-hot distributions (losing nuance).

YaRN positional embeddings

Rotary positional embeddings inject position information through rotation. This is how the model knows where each token is in the sequence.

Core attention

The actual mixing: Q × KT → attention scores → mask → softmax → multiply by V → context vectors.

Output projection

A final linear layer combines all heads back into a single 4,096-dim vector.

Let's now dive into the two most interesting parts: YaRN positional embeddings and core attention.

08 · YaRN — POSITIONAL EMBEDDINGS

Teaching the model where tokens live

Here's a fundamental problem: attention computes Q × KT — a dot product between queries and keys. But dot products are permutation-invariant. If you shuffle the order of tokens, the dot products don't change. The model would have no idea that "the cat sat on the mat" is different from "mat the on sat cat the."

Figure 8: The WHY behind positional embeddings — without positional information, the attention mechanism treats all orderings of tokens as identical. The model would be unable to understand word order.

This is why we need positional embeddings. They inject position information directly into the query and key vectors, so the dot product becomes position-aware.

How RoPE works

RoPE (Rotary Position Embeddings) is the foundational technique. Instead of adding position vectors (like the original Transformer), RoPE rotates pairs of dimensions by angles that depend on position. Different pairs rotate at different frequencies — some fast, some slow.

Figure 9: YaRN frequency table — each pair of dimensions is assigned a rotation frequency. Lower-frequency pairs encode coarse position (long-range), higher-frequency pairs encode fine position (local).

Here is a visualization showing how different YaRN frequencies behave across positions. Notice the dramatic range — the slowest frequency completes one full cycle every 1.088 million positions:

Figure 10: YaRN frequencies — high-frequency dimensions capture fine-grained local position, while low-frequency dimensions provide a "global clock" that spans millions of positions.

YaRN: Extending RoPE for longer contexts

YaRN (Yet another RoPE extensioN) modifies RoPE in a clever way to enable better extrapolation to longer context lengths. The key insight is that not all frequency bands need the same treatment when extending context:

  • High-frequency dimensions (local patterns) — keep unchanged
  • Low-frequency dimensions (global position) — scale down the frequencies
  • Mid-frequency dimensions — interpolate between the two strategies

Here is how positional embeddings are actually injected during the forward pass:

Figure 11: YaRN forward pass — for each token position, we compute rotation angles (cos θ, sin θ) and apply pairwise coordinate rotations to the query and key vectors. The rotation is applied to pairs of dimensions (x0, x1), (x2, x3), etc.

How rotation encodes relative position

The beautiful property of RoPE is that when you compute Q × KT, the rotations combine in a way that depends only on the relative distance between the two positions, not their absolute positions. This is exactly what we want — the model should care about "how far apart are these two tokens," not "what is the exact position number."

Figure 12: How RoPE encodes relative positional information — when query at position m and key at position n are dot-producted, the rotation angles cancel except for the difference (m - n). The attention score depends only on relative distance.

Key insight: RoPE/YaRN achieves something elegant — it injects absolute position information into queries and keys through rotation, but the resulting attention scores depend only on relative positions. You get the best of both worlds: position-awareness without absolute position dependence.

Why do we need YaRN if RoPE already works?

RoPE works great within the training context length, but performance degrades when you try to use the model on sequences longer than it was trained on. YaRN modifies the frequency bands to enable better extrapolation — Rnj 1.5 extends from 32k to 160k tokens using this technique, achieving 79% on RULER at 128k context.

09 · CORE ATTENTION & MASKING

Computing attention scores and applying masks

Now we arrive at the heart of the transformer — the actual attention computation. In practice, this uses FlashAttention for efficiency, but let's walk through vanilla attention to understand the logic.

Computing the attention matrix

For each attention head, we compute the (seqlen × seqlen) matrix of attention scores:

Figure 13: Computing the attention score matrix — each cell (i, j) represents how much token i should attend to token j. This is the Q × KT operation, producing a 16×16 matrix for our 16-token sequence.

At this point, every token can attend to every other token. But this creates two problems:

  1. Cross-document attention: Tokens from document 1 can attend to tokens from document 2 (and vice versa). This would contaminate training.
  2. Future token attention: Token at position i can attend to token at position i+1. This breaks causality — during generation, the model shouldn't be able to "see the future."

The solution is masking:

Figure 14: Attention masking & value vector aggregation — the causal mask (lower triangle) prevents attending to future tokens. The segmentation mask prevents attending across documents. After masking, softmax is applied row-wise, and the result is multiplied by V to produce context vectors.

Hybrid attention: block-local + global

Here is where Rnj 1.5 gets interesting. For longer sequences (imagine 32,768 tokens instead of 16), a full causal mask would be enormous and computationally expensive. Rnj 1.5 uses hybrid attention — most layers use block-local attention (each token only attends to a local window of ~4,096 tokens), while a few layers use global attention (full causal mask).

Figure 15: Hybrid attention for a 32,768-token sequence — the block-local mask (left) restricts attention to a window of 4,096, while the global mask (right) allows full causal attention. Rnj 1.5 uses 24 block-local layers and 8 global layers.

Here's another way to visualize the hybrid layout, focusing on two specific token positions:

Figure 16: Hybrid attention layout — tokens at positions 9,000 and 10,000 can only attend within a 4,096-token window in block-local layers (most layers), but can attend all the way back to position 0 in the 8 global layers.

Key insight: Hybrid attention is a cost-quality trade-off. Full global attention is O(n²) in sequence length — prohibitively expensive for 160k tokens. By making most layers block-local (O(n × window_size)) and only a few layers global, Rnj 1.5 achieves long-context capability at a fraction of the cost. The global layers provide the "long-range wires" that connect distant parts of the sequence.

Why not make all layers global?

For a 160k sequence, a full causal attention matrix would be 160k × 160k = 25.6 billion cells per head, per layer, per forward pass. That's computationally infeasible. Block-local attention reduces this dramatically — each token only attends to ~4,096 positions. The 8 global layers (out of 32) provide enough long-range connectivity for tasks like needle-in-a-haystack retrieval, while the 24 local layers handle the heavy lifting of local language understanding.

10 · FROM LOGITS TO OUTPUT & TRANSFORMER MATH

The final projection and the numbers that matter

After passing through all 32 transformer blocks, the output vectors are projected into a 128,256-dimensional space — one dimension per vocabulary token — via a final matrix multiplication. These raw scores are called logits.

Figure 4: The output stage — vectors exit the final transformer block, pass through a final RMSNorm, then are projected to vocabulary size (128,256). Softmax converts logits into probabilities. During inference, we sample. During training, we compute cross-entropy loss.

During inference, we sample from this probability distribution (using temperature, top-p, etc.) to select the next token. During training, we compute the cross-entropy loss between the predicted distribution and the actual next token, then backpropagate.

KV cache: the inference memory tax

As we covered in Life of a Prompt, during inference the model generates one token at a time. Recomputing keys and values for all previous tokens at every step would be wasteful. Instead, we store them in a KV cache.

Figure 17: KV cache storage requirements — the amount of memory needed scales with sequence length, number of layers, number of KV heads, head dimension, and data type. For large models with long contexts, this can easily consume tens of gigabytes.

Counting parameters

How many learnable parameters does the model have? We just need to account for all weight matrices:

Figure 18: Parameter count calculation — the 3 matrices inside the MLP and 4 matrices inside attention account for nearly all parameters. Everything else (normalization, embeddings) is relatively small.

Quick mental math: For a rough parameter count, you only need to account for the 3 MLP matrices (W0, W1, W2) and 4 attention matrices (Q, K, V, O projections) per layer. Everything else is negligible.

FLOPs per token

How much compute does each token require? This is critical for planning how many GPUs you need and how long training will take.

Figure 19: FLOPs per token — the famous 6N approximation. For a model with N parameters, each token requires approximately 6N FLOPs (2N for the forward pass, 4N for the backward pass). This holds when sequence length is much smaller than the model dimension.

Cluster sizing: from FLOPs to GPU-hours

Once you know the FLOPs per token, you can calculate how many GPUs you need and how long training takes. This is the practical calculation every AI lab does before starting a training run:

CLOSING · THE COMPLETE PICTURE

The life of a token, end to end

Let's retrace the full journey one final time:

1

Tokenize

Raw text → integer token IDs via BPE tokenizer. Documents packed, positions and segmentation masks constructed.

2

Embed

Token IDs → 4,096-dim bf16 vectors via embedding table lookup.

3

32× Transformer blocks

Each block: RMSNorm → Multi-Head Attention (GQA + YaRN + hybrid masking) → RMSNorm → GeGLU MLP. Residual connections throughout.

4

Project to vocabulary

Final RMSNorm → linear projection to 128,256 dims → softmax → probabilities.

5

Output

Sample (inference) or compute loss and backpropagate (training).

Connecting the dots: In Life of a Prompt, we traced a prompt through the inference engine — the wrapper that manages tokenization, batching, KV cache, and memory. In this blog, we opened the transformer itself — the actual model that those infrastructure pieces serve. Together, they form the complete picture: the engine manages how tokens flow, and the transformer determines what happens to them.
