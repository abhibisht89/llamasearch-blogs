Why LLMs need retrieval

A neural language model assigns high probability to plausible token sequences learned from its training mixture. At inference, you build a prompt and the model continues token by token so that the completion reads coherently with the prefix. That coherence is not a guarantee of factual alignment with the world. If weights were frozen years ago, questions about events that unfolded afterward may be answered poorly or not at all unless you supply fresh evidence in context or update the model. A model whose pretraining snapshot ends in 2018, for example, should not be trusted to know the detailed timeline of the COVID-19 pandemic unless you retrieve contemporaneous text or otherwise ground it.

Knowledge cutoff and static weights. Whatever was absent or rare in pretraining may be missing or wrong at query time. A model cannot “look up” new facts unless you give it text in the context window or change the weights (fine-tuning, continued pretraining, adapters).

Hallucination here means confident text that is not justified by reliable evidence. Without grounding—retrieved passages, tool outputs, or curated context—the model may invent plausible-sounding details. Supplying explicit context in the prompt (question answering with a provided paragraph) is one fix; Retrieval-Augmented Generation (RAG) automates finding that paragraph from a large corpus.

Prompt-only QA scales poorly when the answer might live anywhere in a large document set: stuffing everything into the window is slow, expensive, and may exceed context limits. RAG selects a small set of chunks likely to contain the answer, then asks the generator to read those chunks.

Concretely, a language model is a probabilistic model that assigns probabilities to sequences of tokens. In practice it lets you answer questions such as: what is the probability that the word China follows the prefix “Shanghai is a city in”? We usually train a neural network to predict those next-token distributions. A network trained on a very large text corpus is what people call a large language model.

Training corpora are often huge collections of documents: all of Wikipedia, millions of web pages, thousands of books—because we want the model to internalize as much distributional knowledge as possible. If a model saw only English at scale, you should not expect it to fluently generate Japanese or French; new languages and new facts generally require fine-tuning or context injection.

Decoder-only vs encoder-only (typical naming). Many open “LLaMA-style” stacks are decoder-only Transformers: roughly the decoder stack of the original Transformer (without cross-attention to another encoder), plus a linear layer and softmax for next-token prediction. BERT-style models are encoder-only: they use the encoder stack and task-specific heads (often a linear layer on top) for classification, span prediction, or similar. For retrieval-augmented generation, a decoder (or an instruction-tuned decoder) usually produces the final answer; encoders or bi-encoders often score or embed evidence.

At inference you build a prompt and the model extends it token by token so that each continuation stays coherent with the prefix—much like finishing a joke after “You are what you eat…” so the punchline reads naturally with what came before. That coherence is about plausibility under the training distribution, not a guarantee that every fact is current.

Parameter count and fine-tuning limits. Model families are released at multiple sizes for a reason: a 7B checkpoint can hold useful knowledge, but a 70B checkpoint can represent substantially more. Capacity is not infinite; you cannot assume “any” document collection fits in the weights. Fine-tuning is also not strictly additive: if you start from an English-heavy model and heavily adapt it to another language or domain, you may see forgetting of behaviors or facts from the original distribution unless you mitigate it (regularization, replay, careful mixing, adapters, etc.).

Retrieval-augmented generation has been used in production settings where freshness matters—for example, systems that ground answers in large, continually updated text streams (social posts, news, tickets) instead of relying solely on weights frozen at training time.

You can sometimes elicit a new formatting rule with instructions plus in-context examples (few-shot prompting). The same pattern supports question answering with a provided passage: prepend an instruction (“answer using only the context”), paste the evidence, then ask the question. If the fact never appeared in pretraining but appears in the context, the model can still answer—provided the span is actually present and the prompt is followed.

Prompting is powerful, but large pasted contexts cost tokens every query and still hit window limits. Fine-tuning can bake domain knowledge into weights so a short question alone often suffices; many deployments combine both—a little fine-tuning for style or tool use, plus a vector index for facts that change often.

Worked QA-with-context example (parameter count). Suppose the context contains the sentence: “After announcing X, we prototyped and trained the prototype LLM with 33 billion parameters.” Question: “How many parameters does Grok-0 have?” A model that was never updated with that product name in weights can still answer 33 billion by conditioning on the supplied passage—exactly the behavior RAG automates at scale by retrieving the right passage for you.

01

Embeddings and semantic similarity

An embedding maps a discrete object (token, sentence, image patch, product) to a fixed-length real vector. The hope—especially for text—is that semantic nearness in meaning becomes geometric nearness in vector space: related concepts point in similar directions; unrelated concepts form wider angles. Pure keyword matching misses that: “parameters” and “weights” share no characters yet mean the same thing—dense retrieval matches intent, not surface strings.

The distributional hypothesis motivates this: words that share contexts tend to share meaning (“teacher” and “professor” co-occur with school-like words); conversely, words that keep showing up in the same kinds of surroundings—school, university, exam, lecture, course, and so on—tend to be close in meaning. Shared meaning predicts contextual overlap. Transformer self-attention uses token embeddings plus position information so each position’s representation mixes information from the whole span—contextualized token vectors, not static type IDs alone.

To build intuition in two dimensions, take the words cherry, digital, and information. In the original Transformer, token vectors often live in a much higher dimensionality (commonly on the order of 512 in the “vanilla” encoder/decoder stacks); BERT-Base uses 768 for each token vector. If you project mentally down to a plane, you hope that digital and information point in nearly the same direction—a small angle between them—while cherry points somewhere else, giving a larger angle to digital. Add tomato: you might draw it nearly collinear with cherry (a “vertical” family of directions in the sketch) so that cherry–tomato is a small angle again. Cosine similarity is the standard way to turn those directions into a single score: a smaller angle yields a higher cosine; a larger angle yields a lower cosine.

Self-attention scores each position against every other position in the same sequence, using both the token embedding (lexical meaning) and the positional encoding (where the token sits). Nearby tokens are not forced to behave like distant ones: distance in the sequence is part of the representation. The mechanism rewrites each token’s vector so that it reflects not only the word type but also the sentence-wide context it participates in.

Cosine similarity:  cos(θ) = (a · b) / (||a|| ||b||)  ∈ [−1, 1]

Cosine similarity measures the angle between vectors (length-normalized dot product). For normalized embeddings, higher cosine means smaller angle—often used as a proxy for semantic similarity in retrieval. Raw dot product depends on magnitude; cosine cancels length so you measure direction only—vectors (1,1) and (100,100) both score 1.0.

02

From BERT token outputs to a sentence vector

BERT-style encoders output one contextual vector per input token—a T × d matrix for sentence length T (see Chapter 03 for the encoder stack, MLM objective, and token-level shapes). For retrieval you collapse that matrix to one sentence embedding, typically by mean pooling across tokens (alternatives include max pooling or the [CLS] vector).

Why naive pooling is weak for retrieval. Off-the-shelf BERT was trained for masked-token prediction, not to make pooled vectors comparable under cosine distance. Similar sentences can sit farther apart than you want unless the encoder is adapted for semantic similarity—exactly what Sentence-BERT-style fine-tuning addresses in the next section.

For retrieval, you compare a query sentence to a candidate sentence that paraphrases it—e.g. asking “how many parameters are in Grok-0?” versus a passage that spells the name slightly differently. The encoder must be aligned to your similarity metric. Chunks longer than the encoder limit (typically 512 tokens) must be split or windowed before embedding.

03

Sentence-BERT: Siamese bi-encoders

The line of work is published under the title Sentence-BERT: Sentence Embeddings using Siamese BERT-Networks. The core idea: start from pretrained BERT, attach a pooling step, and fine-tune so that the resulting sentence vectors behave well under a similarity function you care about—most often cosine similarity, though the same framework can target other metrics (including distances related to Euclidean geometry in embedding space).

Sentence-BERT (sentence embeddings from Siamese BERT networks) fine-tunes a shared BERT trunk so that pooled sentence vectors align with a chosen similarity—typically cosine similarity—on pairs or triplets of sentences with known semantic relationships.

Architecturally, diagrams show two branches; in code there is one set of weights. Sentence A and sentence B are encoded sequentially (or batched) through the same network; each side is pooled (mean, max, or [CLS]) to a vector; cosine (or another metric) scores the pair; loss (e.g. regression to a target similarity, contrastive loss, triplet loss) backpropagates through the shared encoder.

Sentence A

“My father plays with me at the park.”

Sentence B

“I play with my dad at the park.”

Encode A and B separately. Suppose A becomes 10 tokens and B becomes 8 after WordPiece-style splitting; BERT still returns one contextual vector per token. Apply pooling (typically mean pooling) on each side to obtain two vectors u and v in ℝ768 for BERT-Base. Compute cosine similarity between u and v. Because you are training for retrieval, you also choose a target similarity: for a near-duplicate paraphrase pair like the example above, you may supervise toward a cosine close to 1 (small angle). The loss compares predicted similarity to the target; gradients update the shared encoder weights so that paraphrases move together in vector space.

Pooling choices

The Sentence-BERT paper compared mean pooling, max pooling, and the [CLS] vector. In their experiments, mean pooling was strong and is widely used in production pipelines; [CLS] did not consistently beat mean pooling for sentence embeddings in that setting.

Optional projection layers can map 768-dimensional BERT vectors down to 512 (or lower) for storage and faster distance computations, trading a bit of expressivity for index size and throughput.

What “Siamese” means. Diagrams draw two branches with identical architecture. In a correct implementation there is still only one encoder: you run sentence A through it, then sentence B through it (or batch both), compute the similarity on the two pooled outputs, and backpropagate once. The two branches are the same network with shared weights, not two independent copies that could drift apart.

The [CLS] token is the first input token in BERT and has a final-layer representation that, because of self-attention, can aggregate information from the entire sequence. Sentence-BERT’s authors nevertheless report that mean pooling outperformed both max pooling and relying on [CLS] for sentence embeddings in their experiments—so mean pooling is the usual default in production pipelines, with optional projection afterward (e.g. 768 → 512).

Deep Dive — Bonus Q&A
Bonus Question

Sentence-BERT is trained on sentence pairs — but where do those labeled pairs come from? What kind of training data does it need?

Common sources include NLI datasets (Natural Language Inference) like SNLI and MultiNLI, where sentence pairs are labeled as entailment, contradiction, or neutral. Paraphrase datasets (like QQP — Quora Question Pairs) also work. The key is having pairs with known semantic relationships. Training can use contrastive loss (push similar pairs close, dissimilar apart) or regression loss (predict a continuous similarity score). Data quality directly determines embedding quality.

Bonus Question

Can you use a decoder-only model (like LLaMA) as a bi-encoder instead of BERT?

Yes, but it requires care. Decoder-only models use causal attention (each token only sees previous tokens), so the last token's hidden state is typically used as the sentence embedding (since it has seen the entire input). Some recent work fine-tunes decoder models for embedding tasks and achieves competitive results. However, BERT-style bidirectional encoders are still preferred for embeddings because every token attends to every other token, giving richer sentence representations.

04

Bi-encoder vs cross-encoder

A bi-encoder (dual encoder) embeds query and document independently, then scores with a cheap vector operation—dot product or cosine. Encoding each document once and reusing its vector makes large-corpus search feasible with an index (hash tables, trees, or graphs like HNSW).

A cross-encoder concatenates query and candidate text into a single transformer forward pass (e.g. [CLS] query [SEP] passage) and uses a classification head for relevance. Every query–document pair needs its own pass—accurate but too slow for million-document search. Production stacks use a bi-encoder for recall (embed documents once offline; at query time one encoder pass plus cheap dot products) and a cross-encoder to rerank top-k. If the bi-encoder misses a relevant document in stage 1, the cross-encoder never sees it—the recall ceiling problem—so stage 1 often retrieves a generous top-k. Adding a new document requires encoding only that document and inserting its vector into the index.

At query time against a million indexed vectors, each comparison is a cheap dot product—no neural network per candidate. At billion scale even that becomes heavy; approximate nearest neighbor indexes such as HNSW (next sections) trade a little recall for large speedups.

Bi-encoder

  • Encode docs once; query encoding + index lookup at search time
  • Great for first-stage recall over large corpora
  • Weaker if shallow pooling misses subtle query–passage interactions

Cross-encoder

  • Joint attention between query and passage
  • Strong precision on a short candidate list
  • Impractical as exhaustive first-stage scorer over huge sets

05

Vector databases and k nearest neighbors

A vector database stores embedding vectors of fixed dimension d and answers similarity queries: return the vectors closest to a query embedding under cosine distance, Euclidean distance, or inner product (depending on index and normalization). Internally, many systems implement this as a variant of k nearest neighbors (kNN)—exact or approximate—specialized for high-dimensional dense vectors. Besides RAG, the same pattern powers duplicate detection, music or image similarity, and product recommendations.

Exact kNN compares the query to every stored vector: complexity on the order of O(N · d) per query for N vectors—simple and precise, but slow at web scale when N reaches millions or billions.

Picture a query like “how many parameters are in Grok-0?” against an index of N = 1,000,000 sentence embeddings. A naïve pipeline computes a similarity score between the query vector and each of the million candidates—imagine scores such as 0.3, 0.1, 0.2, and so on—then sorts by descending similarity (or ascending distance, depending on the metric), and keeps the top-k rows. With BERT-Base–sized vectors, d = 768, the dominant cost is proportional to N × d. A million vectors is already heavy; live text corpora (web-scale pages, large social streams) can sit in the billions of vectors, which makes exact linear scans prohibitive without enormous hardware.

Beyond RAG, the same vector-search pattern appears whenever you need “items like this one”: music similarity (embed songs, then retrieve nearest neighbors), image similarity (embed images, retrieve visually or semantically related results—the same geometric story as text), and product recommendations (embed catalog entries or sessions). The database abstraction hides whether the backend is exact kNN or an approximate index.

Recall (retrieval sense). Suppose the true set of relevant neighbors for your query is R and the algorithm returns set S. A common metric is |R ∩ S| / |R|—what fraction of the true relevant items you actually retrieved. Approximate methods trade a little recall for large speedups.

Concrete recall sketch (top-3). Suppose the three genuinely best matches for your query are unique items {a, b, c}. If an approximate search returns only {a, b}, you recovered 2 of 3 true positives, so recall is 2⁄3 ≈ 66.7%. In production you monitor this kind of metric (often alongside latency and MRR/nDCG) when you dial up the “approximation aggressiveness” of an ANN index.

Precision vs speed trade. Exact kNN is slow because it compares the query to every vector, but it is fully precise under the chosen distance: no candidate is skipped. Approximate nearest-neighbor (ANN) methods deliberately skip many comparisons to answer fast; the risk is missing some of the true top-k neighbors unless you add redundancy (wider beams, multiple entry points, larger candidate lists, etc.).

Naïve exhaustive kNN

Score the query against all N vectors (cost ~N · d), sort, take top-k. Always finds the true top-k under the metric—maximum precision for the ranking rule, minimum speed at large N.

ANN (e.g. graph indexes)

Navigate a sparse graph of neighbors; visit only a subset of nodes per query. Much faster at billion-scale N, but recall can fall below 100% unless you tune entry points, degree, and candidate list sizes.

Deep Dive — Bonus Q&A
Bonus Question

If approximate search can miss the true top-k, how do you know if your ANN index is good enough for production?

You benchmark against exact kNN on a held-out query set. Run exact search to find the true top-k, then run your ANN index on the same queries and measure recall@k (what fraction of the true top-k did the ANN find?). Production systems typically target 95–99% recall. You also monitor latency and MRR (Mean Reciprocal Rank) to balance speed vs. accuracy.

Bonus Question

Besides HNSW, what are other common ANN algorithms, and when would you use them instead?

IVF (Inverted File Index) partitions vectors into clusters and only searches nearby clusters — good for very large datasets with GPU acceleration. Product Quantization (PQ) compresses vectors to reduce memory, useful when you have billions of vectors but limited RAM. LSH (Locality-Sensitive Hashing) uses hash functions to bucket similar vectors. HNSW tends to win on recall vs. latency tradeoff but uses more memory than quantization-based methods.

06

HNSW: hierarchical navigable small world graphs

HNSW—hierarchical navigable small world—is a widely deployed approximate nearest neighbor (ANN) index. Public documentation for several engines (for example Qdrant, an open-source vector database) describes HNSW as the vector index in use; reported engineering discussions around large social text systems have pointed to such stacks for real-time retrieval over huge posting volumes. The naming is deliberate: the algorithm merges a navigable small-world graph idea with a hierarchy reminiscent of a skip list.

The small-world intuition is older than modern embeddings. In the 1960s, Stanley Milgram’s small-world experiment asked people in Nebraska and Kansas to forward a letter toward a specific target in Boston without mailing it directly: participants had to pass it to someone they knew personally, chosen to move the letter closer to the unknown recipient. Many chains completed in about five or six steps, motivating the popular phrase “six degrees of separation.” Later, Facebook reported (circa 2016) that among roughly 1.59 billion active users the average distance was about 3.5 hops—again illustrating how sparse local links can still yield short paths through a giant graph. HNSW exploits the same structural idea in embedding space: each vector is a node, and each node keeps a small set of neighbors so total edge count stays manageable, yet greedy routing still finds near points quickly.

Algorithmically, HNSW builds a multi-layer graph: sparse upper layers for long-range jumps, denser lower layers for local refinement—directly analogous to the level structure of a skip list, but with edges defined by proximity in vector space rather than sorted keys.

Navigable Small World (NSW)—an earlier approximate-nearest-neighbor graph method—search starts from an entry node, greedily moves to the neighbor most similar to the query until no neighbor improves the score—a local optimum. Hierarchical NSW (HNSW) layers multiple NSW-like graphs of increasing density so search can “zoom” from coarse to fine. Repeating from several random entry points and merging candidate lists improves recall. Insertion links a new point to its approximate top neighbors found by the same search procedure.

NSW-style walkthrough (toy graph)

Imagine only 15 nodes, each the embedding of a sentence: some discuss the Transformer, others discuss diagnosing cancer with AI, and so on. Edges connect “close” vectors; think of a cap such as up to six neighbors per node as a mnemonic echo of the six-degrees story—real implementations pick degrees from parameters, but the principle is bounded degree.

Query: “How many encoder layers are in the Transformer model?” Pick a random entry node (say node 5). Measure similarity between the query and node 5, then compare to the similarities for node 5’s neighbors—perhaps nodes 7 and 2. If node 2 beats node 5, move to node 2. Repeat: compare the current node against its friends—perhaps node 3 now looks best, so you move again. Stop when no neighbor of the current node beats the current node itself: e.g. node 4 might be locally best among its connections to nodes 0, 8, and 6 even if the global best lies elsewhere. You then rank all visited nodes by similarity and keep top-k. Run the whole procedure again from different random starts, merge candidates, sort again, and keep the best k overall—boosting recall compared with a single greedy path.

Insertion: to add a new vector, treat it like a query, run the same greedy multi-start search, take the approximate nearest neighbors you encounter, and link the new node to those neighbors (subject to degree limits and heuristics in the concrete library).

Skip lists: logarithmic search before the hierarchy

A skip list maintains a sorted sequence using multiple linked levels. The bottom level contains all elements; higher levels contain fewer elements, so the top level is sparse. Average search and insertion are O(log N) in well-tuned implementations.

Find 9. Start at the head of the top level. If the next pointer would overshoot (e.g. you see 5 then end-of-level), drop down a level. Compare forward until you would pass the target (seeing 17 when searching for 9 means go down again). Continue until you can step directly onto 9.

Find 12. Repeat from the top: walk forward while keys stay ≤ 12, drop when the next key would be too large, until you reach 12 on the bottom chain. HNSW reuses this “start coarse, then refine” feeling: upper graph layers are sparse (long jumps across the space), lower layers are dense (local refinement).

HNSW combines that graph idea with the hierarchy: search begins at the top sparse layer, descends layer by layer, performing greedy improvement within each level before dropping down—balancing global navigation and fine local search. Implementations expose parameters (e.g. maximum degree, construction/search depth) that trade memory, build time, latency, and recall.

Hierarchical search pattern. Choose a random entry point on the top layer. Greedily walk to the neighbor most aligned with the query; when nothing improves, move down one layer and repeat the greedy improvement. After reaching the bottom layer, you settle at a local optimum (no friend of the current node beats it). As with plain NSW, you typically rerun from multiple entry points, pool the visited candidates, sort by your similarity or distance, and return top-k.

07

The RAG pipeline: retrieve, augment, generate

Retrieval-augmented generation is still prompt engineering at the generator: you are not necessarily changing the base LM’s weights for every document update. Instead you add a retrieval stage that maps a natural-language query to a small set of text chunks pulled from PDFs, HTML pages, tickets, wikis, or other stores. Those chunks become the context block inside a fixed template (“You are an assistant; answer using the following context…”), followed by the user question. The LM answers by reading the retrieved text—much like the manual copy-paste QA pattern, but automated.

A concrete mental checklist: start from the query (e.g. “How many parameters are in Grok-0?”). Split your knowledge sources into sentences or other small passages. Embed each passage with the same sentence encoder you will use at query time—e.g. a Sentence-BERT-style model that outputs a fixed-size vector such as 768 floats per sentence. Store those vectors in a vector database together with pointers back to the original strings. Embed the query, run a similarity search (cosine if vectors are compared by angle; Euclidean distance on normalized vectors is monotonically related to cosine in many setups; some stacks use inner product on deliberately scaled embeddings). Take top-k hits, map them back to text, paste into the prompt, and generate. Libraries such as LlamaIndex and LangChain orchestrate these steps—chunking policies, embedding providers, index types, and rerankers—even though the underlying geometry is unchanged.

End-to-end RAG for question answering typically runs as follows:

  1. Ingest & chunk: Split documents (PDFs, HTML, tickets, code) into passages—sentences, paragraphs, or fixed token windows with optional overlap.
  2. Embed: Map each chunk to a vector with a sentence encoder (e.g. Sentence-BERT family).
  3. Index: Store vectors in a vector database with an ANN index (often HNSW or other graph/quantization methods).
  4. Query: Embed the user question with the same model; retrieve top-k chunks by similarity.
  5. Augment: Fill a prompt template: system instruction + retrieved passages + user question.
  6. Generate: A decoder-only or instruction-tuned LM produces the answer conditioned on that prompt.

Demo: pipeline pulse

Chunking strategies

  • Sentence-level: Simple, aligns with sentence encoders; may fragment tables or lists.
  • Paragraph / section: Preserves local discourse; variable length may exceed encoder limits.
  • Fixed token windows: Stable memory usage; use stride/overlap to avoid cutting answers at boundaries.
  • Structure-aware: Split on headings, code blocks, or records when the source has explicit structure.

RAG versus fine-tuning

  

    Fine-tuning bakes knowledge and style into weights. It can yield very high quality on a narrow domain
    when data is clean and you can afford training. Downsides include compute cost, need for labeled or curated data,
    and catastrophic forgetting risk: aggressive adaptation to a new locale or language may erode
    behavior on the original distribution—knowledge updates are not automatically additive.
  

  

    RAG leaves the base model frozen (or lightly adapted) and injects facts via context. Updating the
    knowledge base is often as simple as re-embedding new documents—no full retrain. The cost shifts to retrieval quality,
    chunking, and prompt design. Large retrieved context increases tokens per query; hybrid stacks use RAG plus a small
    amount of fine-tuning for tone or tool use.
  

  

    

      Hybrid deployments. You are not forced to pick exactly one strategy. A common pattern is to
      fine-tune for a few epochs on domain instructions or style, then attach a vector database
      that continuously ingests new web or enterprise documents so factual answers can track sources that change daily. The
      fine-tuned head improves formatting and tool use; the index carries volatile knowledge.
