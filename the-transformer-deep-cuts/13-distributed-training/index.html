Distributed Training with DDP

Train language models when one cuda:0 is not enough: process groups and ranks, DistributedDataParallel, bucketed all-reduce with backward overlap, no_sync for gradient accumulation, torchrun across nodes, and the operational details that keep multi-GPU and multi-machine runs stable.

00

Why go distributed?

Large NLP workloads hit three walls: memory (activations and parameters for a single forward pass), throughput (tokens or samples per second on one device), and dataset size (iterating billions of tokens on one worker is slow). Vertical scaling buys a bigger GPU or more HBM; horizontal scaling adds devices and synchronizes them so they behave like one logical trainer.

Training on web-scale corpora with multi-billion-parameter models often exceeds one GPU’s memory, forces tiny per-device batches, and can stretch wall-clock time to impractical lengths—motivating distributed setups even when a single-device prototype works.

Vertical scaling

You keep one machine (for example one GPU with 4 GB of memory) and upgrade hardware: buy a bigger GPU or more RAM. The same program that ran on the small machine usually runs on the big one with little or no code change; you may only tune hyperparameters such as batch size.

Horizontal scaling

You move from one machine to several machines, each with one or more GPUs, interconnected so they can run parallel training and exchange gradients. This path needs some code change, but with PyTorch’s DistributedDataParallel the change stays small compared to rewriting the model.

This chapter focuses on data parallelism: each rank holds a full copy of the model, sees a disjoint shard of the batch, and participates in gradient all_reduce so every replica applies the same update. That pattern assumes the model fits on one GPU—when it does not, you layer model parallelism (tensor or pipeline) on top.

Throughout the data-parallel story below, the working assumption is the same as in large-scale practice for many teams: the model is complex but still fits on one GPU, while the training data is what makes single-machine training too slow. Data parallelism and model parallelism can be combined into a hybrid when both memory and data scale bite at once.

Takeaway: DDP is the default PyTorch path for “same model everywhere, split the data.” The hard parts are correct sampler setup, launcher env vars, and not double-counting batch size when you tune learning_rate.

When to reach for DDP first

If nvidia-smi shows headroom on memory but you are CPU-bound on the dataloader, fix the pipeline (num_workers, pin_memory, storage) before multiplying GPUs. If memory is the binding constraint and a single forward pass does not fit, DDP alone will not help—you need smaller batches, activation checkpointing, or model-parallel sharding.

Once each replica fits comfortably, adding ranks increases throughput roughly with world_size until communication or disk I/O dominates. Measuring tokens/s/GPU and comparing to single-GPU baseline tells you whether scaling is healthy.

  • Symptom: loss diverges after multi-GPU — check loss division vs accum_steps, LR scaling, and that every rank trains (no empty shards).
  • Symptom: hang at startup — verify MASTER_ADDR reachability, port not blocked, and identical code versions on all nodes.
  • Symptom: duplicate logs × WORLD_SIZE — gate prints with rank == 0 or structured loggers that aggregate.
  • Symptom: OOM only in DDP — per-rank batch may equal single-GPU batch; cut micro_batch or raise accum_steps.
01

Data parallel vs model parallel

Data parallel

Replicas share weights; each forward/backward uses different examples. Gradients are reduced across ranks before optimizer.step().

Model parallel

Layers or tensor shards live on different devices; activations cross links every step. Often combined with data parallel “groups” of shards.

Hybrid stacks (e.g. tensor parallel inside a node, data parallel across nodes) are how frontier models train; here we nail the data-parallel contract: world_size processes, each with rank in [0, world_size), and collectives defined over that process group.

Data parallelism in one sentence: if the full model fits on one GPU, you replicate it across servers (each with one or more GPUs). Every GPU runs forward and backward on a different subset of the data in parallel, and the processes synchronize gradients during backprop so all replicas stay identical. Model parallelism is what you use when the model does not fit: you split the network into smaller pieces (layers or shards). Each GPU owns part of the forward and backward graph for gradient descent, rather than a full copy of the model.

Neural networks refresher: from SGD to gradient accumulation

DistributedDataParallel assumes you already understand how a single-GPU loop moves .grad into optimizer.step(). The bridge to multi-GPU is the same idea as gradient accumulation on one device: several backward passes add into .grad before a single step. Walking a tiny regression model makes that mechanism obvious.

A linear model for house prices

Suppose you want to predict house price from two inputs: X₁ = number of bedrooms, X₂ = number of bathrooms. You believe the relationship is approximately linear, so the prediction is

ŷ = X₁·W₁ + X₂·W₂ + B

Training uses stochastic gradient descent to find W₁, W₂, and B that minimize the mean squared error between actual price and ŷ. In other words, you minimize loss with respect to those parameters.

Training loop without gradient accumulation

For each training item you compute ŷ = X₁*W₁ + X₂*W₂ + B, then the loss, then loss.backward(). Backprop computes ∂L/∂W₁, ∂L/∂W₂, ∂L/∂B (and internal intermediate nodes in the graph). Calling optimizer.step() applies the usual SGD rule—written explicitly here without momentum for clarity:

Wnew = Wold − η · ∇W

The update uses a minus sign because the gradient points in the direction of steepest increase of the loss; to minimize loss you step in the opposite direction.

After the step, optimizer.zero_grad() clears gradients on every parameter (and the recorded intermediates) so the next item does not mix stale derivatives. On a conceptual level, optimizer.step() is the moment parameters actually move; loss.backward() only fills .grad.

Concrete numbers on one computation graph

PyTorch builds a computation graph: inputs multiply by weights, the two products add with the bias to form ŷ, ŷ is compared to the target to produce the loss, and backprop applies the chain rule. For the gradient with respect to W₁, you need ∂L/∂ŷ, then ∂ŷ/∂Z₁ (where Z₁ is the contribution from the first input branch), then ∂Z₁/∂W₁—and similarly for the other weights.

Take a first training example with X₁ = 6, X₂ = 2, and target = 15. Suppose weights were initialized to W₁ = 0.773, W₂ = 0.321, and B = 0.067 (typical random-style initialization). Forward pass combines these into ŷ and a scalar loss; loss.backward() populates ∂L/∂W₁, ∂L/∂W₂, ∂L/∂B. A second example uses X₁ = 5, X₂ = 2, target = 12, producing another forward pass, another backward, and another parameter update after step() and zero_grad().

With batch size one, every data item triggers a full backward → step → zero_grad cycle. Geometrically: each backward gives a direction in weight-space; step moves the weights opposite that direction; zero_grad clears the arrow before the next item paints a new one.

Gradient accumulation: sum gradients before stepping

With accumulation you still run forward and loss.backward() every item, but you do not call optimizer.step() (or zero_grad()) after every item. Suppose you accumulate over two consecutive examples. After the first backward, gradients sit on the parameters; you skip step and zero. On the second example, another backward() adds to the existing .grad tensors instead of replacing them—that is the accumulation.

Only after the second backward do you call optimizer.step() once, using the sum of the two per-example gradients, then zero_grad(). The effective update direction is the combined signal from both examples. Gradient accumulation is not DDP-specific—it also simulates a larger batch on a single GPU when memory is tight.

02

Process group, backend, and environment

Call torch.distributed.init_process_group once per process after parsing arguments. The backend is usually "nccl" for CUDA GPUs. The launcher sets RANK (global), LOCAL_RANK (on this host), WORLD_SIZE, and often MASTER_ADDR / MASTER_PORT for the rendezvous server.

Use torch.cuda.set_device(local_rank) before building tensors so each process pins to its GPU. After training, destroy_process_group() releases resources cleanly—omitting this in notebooks or repeated runs can leave NCCL in a bad state.

Common pitfall: Hard-coding device = "cuda:0" in a multi-process script. Always derive the device from LOCAL_RANK (or int(os.environ["LOCAL_RANK"])).

15

The DDP loop: broadcast, local backward, reduce, and all-reduce

At job start, model weights are created on one GPU and copied to every other process with a broadcast. After that, every rank holds the same initial parameters. Each rank then runs forward and backward on its own data shard; loss.backward() produces a local gradient that generally differs across ranks because the minibatches differ. Those local gradients may themselves already be the sum of several micro-batches if you accumulate on device before synchronizing.

The synchronization story matches what you would do by hand: each rank sends its gradient vector toward a designated accumulator (often described as rank 0 in diagrams), the partial vectors are summed—that reduction step is called reduce—and the total is then broadcast back so every rank receives the same combined gradient. Everyone applies optimizer.step() with that shared gradient, so all replicas stay bitwise aligned before the next round of minibatches. After the step, gradients are zeroed and the cycle repeats.

In optimized libraries the pair “reduce then broadcast” is almost always implemented as one fused collective, all-reduce, which is faster than executing the two phases separately even though you can reason about it logically as reduce followed by broadcast.

In a toy picture with a single scalar weight, you might broadcast an initial value such as 0.1 to every rank, let each rank train on different data so local gradients differ, sum those contributions on the root, broadcast the sum, and run the optimizer so every copy ends the step with the same updated weight—as it must, or the replicas would diverge.

Point-to-point vs collective communication

Point-to-point communication is the familiar client–server pattern: one sender, one receiver per message. Collective communication names patterns where one process must talk to many others at once—the canonical deep-learning case is broadcasting initial weights to every rank, then having every rank participate in a gradient reduction.

Here is a file-sharing analogy with explicit timings. You must send a 5 MB file to seven friends. Your uplink is 1 MB/s. Sending sequentially—friend 1, then 2, through 7—takes 5 s per friend, hence 7 × 5 s = 35 s total. You might try to “multicast” in parallel, but if the uplink cap stays 1 MB/s, the capacity splits across seven simultaneous transfers: roughly 1/7 MB/s per friend (~143 KB/s each), and the wall-clock time to finish all seven is still on the order of 35 s because the pipe is saturated either way.

Collective broadcast uses a divide-and-conquer tree on the interconnect: you send first to a middle partner (say rank 4); now ranks 0 and 4 both hold the payload and can transmit concurrently to ranks 2 and 6; then ranks 0, 2, 4, 6 fan out again. In the same toy accounting, that tree schedule finishes in about 15 s instead of 35 s—not because the wire got faster, but because idle links disappear and each hop carries the full 5 MB at 1 MB/s without serializing seven separate root uploads. Real GPU clusters use the same idea: exploit bisection bandwidth and topology so weight broadcast is not a naive loop.

Reduce in logarithmic depth

For gradient summation, imagine every rank starts with its own tensor. Pairs exchange: rank 7 sends to 6, 5 to 4, and so on, each receiver adding the incoming gradient to its own. The next phase combines those partial sums (for example 6→4 and 2→0), then a final hop merges the last two partial totals on the root. In the eight-rank story you need only three stages to aggregate everything on one rank. It can be proved that, with this style of halving, communication time scales logarithmically in the number of ranks—exactly the signature you expect from divide-and-conquer reductions.

NCCL and rank IDs

NVIDIA’s collective library NCCL (often pronounced “nickel”) assigns each participating GPU process a numeric rank. That rank is what launchers such as torchrun wire into RANK and LOCAL_RANK environment variables. NCCL chooses algorithms (ring, tree, hybrid) based on message sizes and hardware; you rarely implement the tree yourself, but the latency model you carry in your head should stay logarithmic for large clusters.

When a process dies: checkpointing instead of cold restart

If a node disappears mid-run—say two GPUs out of four vanish because one machine died—the blunt fix is to reboot the whole job from scratch. That throws away every hour of optimization because you would re-draw fresh random weights and broadcast them again. The better production pattern is checkpointing: periodically write state_dict, optimizer state, epoch counters, and any custom scalars you need to a location every rank can read—typically shared storage—then resume from the latest checkpoint after a failure.

On restart, the “who initializes weights?” step should load from checkpoint instead of reinitializing randomly. PyTorch may pick any process as the source of truth for bootstrapping; documentation stresses that rank is not guaranteed stable across restarts—the process that was global rank 0 before the crash might not be rank 0 next time—so every node should run the same code paths and every node needs access to the shared checkpoint volume.

Never let all ranks write the same checkpoint filename blindly: they will stomp each other’s files. Gate saves on global rank 0 (or an equivalent “main process” flag). On resume, still load the tensors on every rank before wrapping with DDP, and keep auxiliary metadata—Weights & Biases run IDs, random seeds, step counters—inside the checkpoint so training continues coherently.

Annotated walkthroughs: sampler, scaler, checkpoint

Click underlined line numbers to reveal notes. These patterns repeat in almost every DDP training script: partition indices with DistributedSampler, optionally scale loss for mixed precision with torch.cuda.amp.GradScaler, and restrict filesystem writes to dist.get_rank() == 0.

Typical imports for this stack are torch.distributed, torch.nn.parallel.DistributedDataParallel, torch.utils.data.distributed.DistributedSampler, plus init_process_group and destroy_process_group. The call that actually unblocks torchrun when all machines have joined is init_process_group(backend="nccl") (for CUDA). After training finishes, destroy_process_group() tears down the process group cleanly.

LOCAL_RANK indexes the GPU on this host (for torch.cuda.set_device and per-machine UI). RANK is the global process ID across the whole job—use it when exactly one process should log, checkpoint, or initialize W&B.

Because DistributedDataParallel with the NCCL backend targets CUDA, many training scripts disable the CPU training branch entirely when distributed mode is on: the performance model and supported features differ, and you avoid accidentally constructing tensors on the wrong device.

When the model is wrapped, external code must reach the underlying module through model.module—for example model.module.encode(...) instead of model.encode(...) if encode is a custom method on your class. The forward path you registered with nn.Module still runs through the wrapper, but arbitrary methods do not.

Services such as Weights & Biases should be initialized on global rank 0 only. If every rank tried to stream metrics simultaneously, runs would corrupt each other. The same rank gating applies to human-readable tqdm bars when multiple GPUs share one terminal: show one bar per machine (local rank 0) or only on rank 0, depending on how noisy you can tolerate the logs.

Validation without stalling every GPU

A simple pattern runs evaluation only on global rank 0. That is easy to code, but it implies every other rank sits in a barrier while rank 0 completes validation—acceptable for small models, expensive when validation is heavy. An alternative is asynchronous validation: a separate CPU or GPU worker (or a dedicated job) watches the checkpoint directory, loads the latest state_dict, and evaluates while training ranks keep stepping without waiting on metrics. The trade-off is operational complexity versus higher utilization.

Integration template (checklist)

  1. Read LOCAL_RANK and RANK from the environment; call torch.cuda.set_device(local_rank).
  2. init_process_group(backend="nccl") before building tensors on the wrong GPU.
  3. On global rank 0 only, initialize side services (W&B, custom loggers).
  4. Build DataLoader with DistributedSampler, shuffle=False on the loader, and sampler.set_epoch(epoch) each epoch.
  5. Construct the model, optionally load checkpoint before the DDP wrap.
  6. Wrap with DDP(model, device_ids=[local_rank]); use model.module for non-forward helpers.
  7. Training loop unchanged except for no_sync windows when accumulating.
  8. Save checkpoints on global rank 0; store every scalar needed to resume (epoch, step, run IDs).
  9. destroy_process_group() when finished.
05

Effective batch size and learning-rate scaling

If each GPU runs micro_batch examples per forward, you accumulate accum_steps times before step, and you have world_size ranks, then the optimizer sees gradients averaged over a logical batch of size micro_batch × accum_steps × world_size—provided you normalized loss consistently (often loss / accum_steps per micro-batch).

Beff = micro_batch × accum_steps × world_size

A common heuristic is linear LR scaling: multiply base LR by B_eff / B_ref when you scale batch size, sometimes with a warmup phase to avoid early instability. Square-root scaling is another family of rules; always validate on your task.

Keep loss scaling consistent

If you average micro-batch loss with loss / accum_steps, the sum over micro-batches matches the gradient of the large batch. DDP averages gradients across ranks, so do not also divide by world_size in loss unless your framework expects it.

LR warmup intuition

Early steps have noisy estimates at large B_eff. Warmup ramps lr from a small value across hundreds or thousands of steps; cosine or linear decay afterward is common in LM pretraining recipes.

In [1]
1micro, acc, ws = 4, 8, 32
2Beff = micro * acc * ws
3base_lr, Bref = 3e-4, 256
4lr = base_lr * (Beff / Bref)
Out [1]
Beff = 1024
scaled lr ≈ 0.0012  (illustrative linear rule)

DDP internals: hooks, buckets, all-reduce

During backward, DDP registers gradient hooks on parameters. When a bucket’s gradients are ready, NCCL runs an all-reduce so every rank receives the sum (or average, depending on configuration) of that bucket. Overlap means the next backward compute can proceed while the network transfers an earlier bucket—hiding latency.

Synchronization is tied to loss.backward(): each rank finishes the local backward for its shard, produces ∂L/∂(parameters), and participates in the collective so every rank receives the same aggregated gradient before optimizer.step() applies the shared update with the local optimizer’s learning rate.

Without overlap, the timeline is painful: forward, backward, then a stretch where GPUs are mostly waiting on the network to reduce and broadcast gradients—compute sits idle. PyTorch instead exploits the layer-wise structure of backprop. You need ∂L/∂W for upper parameters only after you have traversed deeper into the graph, but early parameters’ gradients become known as soon as their subgraph is finished. The implementation can therefore start an all-reduce on an early bucket while backward is still computing later layers. As each additional bucket’s gradients materialize, launch the next reduction. By the time the final backward operations complete, much of the communication has already been overlapped with compute, shrinking end-to-end step time.

Rather than all-reducing one parameter at a time, DDP packs many gradients into buckets. When bucket k is full, it ships in one collective and the reduced values return together. PyTorch’s documentation recommends on the order of 25 MB per bucket: buckets that are too small multiply fixed per-message overhead; buckets that are too large delay the first network activity and under-utilize the link while later gradients are still being computed. Profiling with your real model width usually beats guessing.

Default bucket sizes are tuned for typical CNNs and Transformers; you can adjust bucket_cap_mb when profiling shows too many tiny messages or poor overlap. The exact schedule is implementation detail; the mental model is “streaming reductions as .grad appears.”

Gradient hooks fire per parameter or group; DDP coalesces into buckets to amortize kernel launch and NIC overhead. That is why naive “all-reduce full model after backward” is slower than DDP’s pipelined approach.

With gradient accumulation under DDP, wrap non-final micro-batches in model.no_sync() so gradients accumulate locally; on the last micro-batch, exit no_sync so the backward all-reduces, then call optimizer.step().

torchrun, rendezvous, and multi-node launch

torchrun replaces older python -m torch.distributed.launch patterns. Key flags: --nproc_per_node (often GPUs per machine), --nnodes (machine count), --node_rank (this host’s index), --rdzv_backend (for elastic jobs; static clusters often use classic MASTER_ADDR / MASTER_PORT), --rdzv_endpoint when using the rendezvous store.

  1. Pick a reachable MASTER_ADDR (head-node private IP) and free MASTER_PORT.
  2. Run the same command on every node, changing only --node_rank.
  3. Ensure WORLD_SIZE equals nnodes × nproc_per_node (usually set by the launcher).

Cloud operations: AWS-style clusters and a Paperspace walkthrough

Production teams routinely split work between “heavy cloud” (AWS, GCP, Azure) with enterprise networking and “fast path” GPU clouds that minimize clicks for experiments. Both deserve the same distributed-training discipline: private connectivity between nodes, a shared or synchronized checkpoint location, and identical container images or virtualenvs on every rank.

Paperspace: minimal-friction multi-node GPU lab

AWS can do everything, but standing up security groups, VPC wiring, and storage mounts takes time; it is easy to get lost in console steps before you ever launch torchrun. Paperspace is useful when the goal is to see distributed training work end-to-end without first becoming a cloud network engineer—though real products eventually move toward infrastructure-as-code (Docker, Kubernetes) for repeatability.

A concrete layout that matches a four-GPU, two-machine job: create a private network (call it something like distributed-training) and keep every resource in the same region (for example New York 2). Provision two machines from an ML-ready image such as ML-in-a-Box, each with two GPUs—the transcript example used Multi-GPU P4000 ×2 per host—50 GB boot disks, dynamic public IPs so you can SSH in, and both interfaces attached to the private network. Add a network drive (the smallest commonly offered size is around 250 GB) also attached to that network, named for example model-training-250, to hold checkpoints both nodes can read.

Per-machine cost in that tier is often on the order of ~$1/hour; one end-to-end experiment that runs many epochs landed around $5 total in the source walkthrough—your spend will vary with runtime and list prices, but the takeaway is that a short distributed rehearsal can stay inexpensive if you tear the cluster down afterward.

On each host: update packages, install net-tools if you need ifconfig (some images occasionally hit packaging glitches such as Seahorse prompts during apt operations—follow the distro’s workaround if apt stalls). Note the machine’s private IP on the subnet, mount the network share with the vendor-supplied mount command (substitute the drive’s address, username, and password; replace any escaped characters in pasted URLs with normal slashes as the shell expects), clone the training repository (for example a project named along the lines of pytorch Transformer distributed), and pip install -r requirements.txt. Install and log in to Weights & Biases if you want centralized curves—remember only global rank 0 should initialize the run so metrics do not collide.

PyTorch NCCL initialization frequently requires mutual hostname resolution. If ranks cannot find each other by name, add lines to /etc/hosts on both machines mapping the other host’s private IP to its hostname (for example cuda-zero and cuda-one in a two-node demo). Symmetric entries matter: a missing mapping on one side leaves processes waiting at the rendezvous barrier.

Pick one machine as the master for MASTER_ADDR (often the first box you created). In production you might front the master with a floating IP or DNS name that can be repointed if that host dies; in a minimal tutorial you often hard-code the master’s private IP for clarity. The launch command is the same script on every node; torchrun (the supported entry point—older docs sometimes wrote torch run as two words) supplies RANK, LOCAL_RANK, and WORLD_SIZE. You pass --nnodes (number of machines), --nproc_per_node (GPUs per machine), a per-cluster unique job identifier where the launcher expects it, --master_addr pointing at the master’s address, and NCCL as the backend for CUDA. Arguments after the training script path are forwarded to your Python entrypoint—for instance --batch_size 8 and a --model_folder pointing at the mounted shared path so checkpoints land on the network drive.

When one SSH session fires the command before the other, the first process blocks until peers join—exactly the rendezvous handshake. If training starts but then stalls, double-check /etc/hosts on every node and verify both sides use the same ports and codebase revision.

In a four-GPU job (two hosts × two GPUs), each process may iterate roughly 910 minibatches per epoch for a fixed dataset while a progress bar shows only one stream per machine for readability. Across four ranks the dataset is partitioned four ways; the global number of optimizer steps per epoch is governed by that per-rank count times the number of ranks—not “910×2” from glancing at two terminals. The important invariant is that every rank steps through its shard without overlap and all-reduce keeps weights identical.

Failover rehearsal: kill the master node mid-run. After NCCL tears the job down, relaunch the same torchrun line. With checkpoints written each epoch to shared storage from global rank 0, reload should skip finished epochs—for example resuming at epoch 1 after epoch 0 completed—because the loader reads the latest state_dict and auxiliary counters from disk. Save anything else you need to reconstruct training—global step, RNG state, W&B run id—inside that checkpoint bundle.

Hand-provisioned VMs (Paperspace-style)

Fast to click together for learning and prototypes; you SSH in, edit /etc/hosts, mount a share, and run torchrun twice. Good when you are not ready for Kubernetes but need real multi-node NCCL behavior.

Orchestrated containers (Docker / k8s)

Same training code, but images and env vars are declared once; scaling out repeats automatically. This is what you want for teams and for production, at the cost of up-front platform work.

AWS checklist (enterprise defaults)

On EC2, prefer instances in the same placement group and enable EFA when available for lower latency between nodes. Mount FSx for Lustre or EFS if many ranks read the same dataset; local NVMe instance store is fastest for ephemeral staging.

Image-wise, match driver, CUDA, and PyTorch wheels to the GPU generation (A100, H100, L4, …). Container images from NVIDIA NGC or PyTorch official bundles reduce “works on my laptop” drift. For cost, use spot with checkpointing—but expect preemption; barrier hangs if one rank vanishes without teardown.

Security: Do not expose MASTER_PORT on a public interface. Keep training traffic on private subnets; use Security Group rules source-restricted to the cluster SG.

Cost and resume strategy

Billing is usually proportional to GPU-hours × instance_type price. Checkpoint to durable object storage (S3, GCS) from rank 0 on a fixed interval so spot interruptions only lose partial work. Document the exact torchrun line and container digest alongside each checkpoint for reproducibility.

For multi-region redundancy, avoid splitting one training job across regions—latency kills collectives. Instead replicate finished checkpoints for inference or fine-tuning elsewhere.

Data-parallel shard map (per step)

Conceptually, global batch indices are partitioned across ranks so each forward uses disjoint examples. The demo below mirrors how you sanity-check batch_size settings against world_size.

In real code, batch_size in DataLoader is the per-process count. Global examples per optimizer step equal that times world_size when you step every batch. With gradient accumulation, multiply further by accum_steps before the next optimizer.step().

Sanity check: Sum of per-rank samples across one step should match your intended global batch. Off-by-one errors in custom samplers often show up as slightly different len(loader) per rank—use drop_last=True or pad consistently.
