Flash Attention: First Principles to a Triton Kernel

Standard attention materializes S and P in HBM; fused attention keeps only tile-sized score blocks in SRAM while streaming K and V. Running row max m and denominator mass ℓ implement online softmax; saving m, ℓ (LSE form) enables a tiled backward that matches forward numerics without a dense N×N activation tensor.

00

What Flash Attention optimizes

Multi-head attention projects inputs into queries Q, keys K, and values V, splits head dimensions, then applies the same core map to each head. Linear projections and the output projection are dense matrix multiplies—already heavily optimized by vendor libraries.

The expensive, memory-hungry piece is the scaled dot-product block inside each head:

Attention(Q, K, V) = softmax(QK⊤ / √dk) V

Shapes (per head, batch omitted): Q and K are N×d, V is N×d, where N is sequence length. The product QK⊤ is N×N. Everything below focuses on computing that map with minimal traffic to off-chip memory and without writing the full attention matrix to DRAM.

Multi-head layout—WQ, WK, WV projections, head split, and WO merge—is covered in Chapter 01. Those linear maps are already fast; FlashAttention targets the per-head map softmax(QK⊤/√d) V when N is large.

Outside the fused kernel

Linear maps WQ, WK, WV, WO; head split/merge; anything that stays a single large GEMM per op.

Inside Flash-style attention

The N×N score path: QK⊤, stable softmax over full rows, and the weighted sum into O—all without materializing full S and P in HBM.

01

The standard (materialized) bottleneck

A straightforward implementation matches the math as three explicit stages:

  1. Form scores S = QK⊤ / √dk (N×N).
  2. Apply row-wise softmax to obtain probabilities P (again N×N).
  3. Multiply O = PV (N×d output).

Even if peak FLOPs are plentiful, each stage reads and writes large tensors resident in high-bandwidth memory (HBM). The attention maps S and P dominate memory: storing one N×N tensor in FP16 is 2N² bytes; two such tensors double that. For long contexts, bandwidth—not raw arithmetic—often limits throughput.

Takeaway: reducing round-trips to HBM matters as much as reducing FLOPs. The goal is to compute O while keeping S and P ephemeral in fast on-chip memory.

Why this shows up in the FlashAttention setting: on many datacenter GPUs the largest, “farthest” pool is HBM-style global memory—for example on an NVIDIA A100-class part you often think in terms of on the order of 40 GB of device memory. A much smaller, much faster on-chip space (shared memory / SRAM in kernel parlance) sits next to the math units. If an implementation repeatedly reads and writes a full N×N score map in global memory, the step becomes I/O-bound: time is dominated by moving bytes, not by issuing FLOPs. The engineering response is tiling: stream only blocks of Q, K, V into fast memory, fuse matmul + mask + softmax + accumulation, and avoid ever allocating the dense attention matrix in HBM.

This mirrors the math: scores is (N, N) in HBM, then softmax, then attn @ v. Autograd retains activations proportional to that map unless you swap in a custom torch.autograd.Function with a fused forward and backward.

GPU memory hierarchy: HBM vs on-chip SRAM

A GPU exposes a large, relatively slow HBM (off-package DRAM) and much smaller, much faster on-chip memory (often called shared memory or SRAM in kernel discussions). A thread block can reuse data in on-chip memory at orders-of-magnitude higher effective bandwidth than re-reading from HBM.

CPU-style control

Few, sophisticated cores; branch prediction and large caches; optimized to hide latency across many unrelated programs (browser, media, filesystem). Workloads are often I/O-bound at the system level.

GPU-style throughput

Thousands of simpler cores and a thin control plane per SM; die area favors arithmetic. The machine is built to apply the same instruction stream to massive data—SIMT / “single instruction, multiple thread.”

CUDA vs GPU hardware: the GPU is the chip you buy; CUDA is NVIDIA’s programming stack for it (other vendors have their own). A kernel is the device-side function the host launches; you choose a grid of thread blocks. A contiguous group of 32 threads is a warp: they share a control unit and execute in lockstep, which is why divergent if branches inside a warp cause control divergence (some threads idle while others execute the taken path). Triton keeps the same mental model but names launch units programs and generates the low-level mapping for you.

If an algorithm repeatedly streams through N×N tensors in HBM, the kernel becomes IO-bound: execution time tracks bytes moved, not FLOPs issued. Flash-style attention instead loads blocks of Q, K, V, performs the matmul, softmax, and accumulation while those blocks still live in fast memory, then discards the score tile—never allocating the full N×N tensor in HBM.

Roofline intuition

Arithmetic intensity is FLOPs per byte moved from HBM. When intensity falls below the GPU’s ridge point, kernels are memory-bound: more FLOPs do not shorten runtime. Materialized N×N attention maps tank intensity because each score is written then read again for softmax and PV.

03

Tiling: block matrix multiply as the organizing idea

Matrix multiplication can be decomposed into block matrix multiplication: the same dot-product structure applies when each “scalar” is a submatrix, as long as inner dimensions align. That lets one output tile depend on a strip of Q, a strip of K⊤, and a running reduction—exactly the structure needed to map work to thread blocks and to cap working set size.

For attention, choose blocks of queries (rows of Q) and blocks of keys (columns of K⊤). A tile of scores has size Bq×Bk. Keeping BqBk small enough to fit in SRAM is the mechanical requirement; choosing Bq, Bk to saturate memory pipelines is the art.

Block matrix multiply as parallelization: partition A and B into compatible sub-blocks; each output block is a small matrix multiply instead of one scalar per core. For attention-shaped blocking, take per-head Q, K, V as 8×128, partition Q by row groups and K⊤ by column groups so each blocked score entry is a 2×2 tile—same algebra as standard matmul, only the atomic units are tiles.

Row softmax needs statistics over the entire row, not per tile. The online algorithm in the next section rescales partial sums by exp(mold − mnew) whenever a later tile finds a larger score, so tiled passes still match global softmax.

Numerically stable softmax

Row softmax is Pi,j = exp(Si,j) / Σk exp(Si,k). Subtracting the row maximum mi = maxk Si,k inside the exponentials does not change P but prevents overflow:

Pi,j = exp(Si,j − mi) / Σk exp(Si,k − mi)

Numerical instability and the standard fix: for a row vector x, the literal softmax divides exp(xj) by Σk exp(xk). If components are large—say x1=100, x2=200, x3=300—individual exponentials overflow finite fp16/fp32 ranges. In code, that is what people mean by numerical instability: the true mathematical quantity exists, but the fixed-bit representation cannot hold intermediate values. Multiply numerator and denominator by the same positive constant c; algebraically nothing changes. Write c = exp(−k) and absorb shifts into exponents so each term becomes exp(xj − k). Choosing k = maxj xj forces every exponent to be ≤ 0: the largest entry hits exp(0)=1, every other entry lies in (0,1), and the sum stays representable.

Three sequential passes over a row: (1) scan for the row maximum m; (2) accumulate ℓ = Σk exp(xk − m); (3) write exp(xj − m)/ℓ. Steps must run in order—you cannot form ℓ before you know m, and you cannot normalize before ℓ exists.

Worked micro-example: take the row [3, 2, 5, 1]. The maximum is 5. The stable denominator mass is ℓ = e3−5 + e2−5 + e5−5 + e1−5 = e−2 + e−3 + 1 + e−4. Each output entry is exp(xj − 5) / ℓ. The same numbers appear if you first compute max, then build ℓ, then divide—three passes over the row.

Online softmax (two-pass viewpoint): initialize m ← −∞, ℓ ← 0. Process elements (or tile maxima) left to right. When the running maximum jumps from m to m′, rescale everything accumulated so far:

ℓnew = em − mnew ℓ + em′ − mnew ℓ′,  mnew = max(m, m′)

On the toy vector, after seeing [3,2] the running max is 3 and ℓ matches using 3 as the reference. When 5 arrives, m becomes 5; multiplying the old ℓ by exp(3 − 5) reweights the earlier terms so their exponentials are expressed relative to the new global max—exactly the same algebra as replacing −3 by −5 inside e3−· and e2−·. When the max does not change, the correction factor is exp(0)=1: no update needed.

Proof sketch (induction): show that after processing any prefix of the row, the pair (m, ℓ) matches the two-pass algorithm on that prefix—base case a single element; inductive step adds the next coordinate by applying the merge above. At termination, m is the true row max and ℓ is the sum of exponentials relative to that max, so dividing yields softmax.

Softmax* (“unnormalized softmax”) in tiled attention: define softmax*(x)j = exp(xj − max x) without dividing by ℓ. Tile-wise application uses only the tile max—convenient for parallelism but wrong for global rows until you merge statistics. The running output accumulator O is therefore built from softmax* weights, then row-rescaled whenever m increases; a final division by the fully merged ℓ restores true probabilities. In block form with two query rows, premultiplying the partial output block by diag(exp(mprev − mnew)) (per-row scalars on the diagonal) applies the same correction as the scalar algorithm, before adding the new tile’s contribution.

A literal three-pass algorithm (max, then sum of exponentials, then normalize) visits each row multiple times. For fused attention the deeper issue is global row statistics: if you only see one tile of columns at a time, you do not know the final mi until you have scanned the whole row—unless you update statistics online as new tiles arrive.

Online softmax: streaming max and normalizer

Process partial rows in order. Maintain running maximum m and running sum of scaled exponentials ℓ (the denominator contribution). When a new chunk arrives with its own m′ and ℓ′, merge:

mnew = max(m, m′),  ℓnew = em − mnewℓ + em′ − mnewℓ′

The running output accumulator O (weighted sum of value blocks) must be rescaled when m increases: earlier chunks assumed a smaller max; their unnormalized weights must be down-weighted by exp(mold − mnew) before adding contributions from the new chunk.

Merge (m, ℓ) and rescale O

For chunk scores with tile max m' and sum of exponentials ℓ' (after subtracting m'), merge into global m, ℓ. When m increases, scale the prior output accumulator by exp(m_old - m_new) before adding the new weighted V block so O stays consistent with full softmax.

online_softmax.pyL1–22
1def merge_chunk(m, l, O, scores, Vj):
2    m_new_tile = tl.max(scores, axis=-1)  # per query row in tile
3    p_sum = tl.sum(tl.exp(scores - m_new_tile), axis=-1)
4    m_new = tl.maximum(m, m_new_tile)
5    l_new = tl.exp(m - m_new) * l + tl.exp(m_new_tile - m_new) * p_sum
6    alpha = tl.exp(m - m_new)
7    O = O * alpha[..., None]  # rescale prior value accumulation
8    P = tl.exp(scores - m_new[..., None])
9    O += tl.dot(P, Vj)  # weighted values (still unnormalized)
10    return m_new, l_new, O

Flash Attention: fused forward pass

Outer loop: blocks of queries (rows). Inner loop: blocks of keys/values (columns). For each query block, initialize m = −∞, ℓ = 0, O = 0. For each K/V tile:

  1. Load Q tile, K tile; compute S = QK⊤ (tile) with scale 1/√dk.
  2. Apply causal mask inside the tile if needed (mask before softmax so the normalizer ignores forbidden positions).
  3. Compute tile maxima and unnormalized exponentials; merge (m, ℓ) with the running state.
  4. Rescale previous O; add contribution from current tile’s P̃V with correct relative scaling.

A useful notational trick is “softmax without final division” on a tile—then fixup global normalization through (m, ℓ) and the rescaling of O. Block-wise partial softmaxs that use only local maxima are wrong unless merged with this correction—this is exactly what the online statistics repair.

Alignment with the FlashAttention-2 forward picture: partition queries into blocks of height BR (rows per query tile) and keys/values into blocks of width BC. Outer loop over query tiles can launch independent programs—one output tile depends on its query block and all key/value strips. Inner loop walks those strips: form the BR×BC score tile, take tile row maxima, merge into running (m, ℓ) with the exponential correction, rescale the running weighted value sum O, then add P̃ V for this strip. While looping you are effectively applying softmax* per tile; the closing step divides each row of the finished tile by its final ℓ, equivalent to multiplying by diag(ℓ)−1 on the left of the 2×d (or BR×d) output block—row-wise normalization without ever storing a dense N×N probability matrix.

FlashAttention (v1) framing

Introduces IO-aware tiling and online softmax so attention stays in SRAM-sized chunks; establishes the baseline fused forward/backward narrative and memory savings versus materialized S,P.

FlashAttention-2 refinements

Reorders work for better warps/SM utilization, tweaks block sizes and parallelism, and presents the forward loop with explicit BR, BC blocking—the algorithmic core matches v1’s math, but the schedule is closer to what high-throughput kernels ship on modern hardware.

Autotuning is hardware-specific; avoiding materialized N×N maps in HBM is the algorithmic win.

Autotune configs: Triton’s @triton.autotune sweeps choices of BLOCK_Q, BLOCK_KV, num_warps, and related knobs. Hardware-dependent SRAM budgets, occupancy, and memory coalescing mean the winner is not knowable portably from Python alone—kernels are benchmarked for each (head_dim, sequence length) regime and the fastest variant cached. Software pipelining (exposed as num_stages in many examples) overlaps asynchronous loads, tensor-core math, and stores so the memory subsystem stays busy while ALUs work—same idea as pipeline parallelism across layers on different GPUs, where micro-batches keep every stage utilized, at the cost of prologue/epilogue fill and extra on-chip buffering. More stages raise SRAM footprint; long inner loops amortize that overhead.

Row-major strides: a 2×3 matrix is stored as one contiguous run: row 0’s three elements, then row 1’s three. If the base address of element (0,0) is 100 and each entry is two bytes (e.g. fp16), addresses advance 100, 102, 104 along the last dimension (stride 1 in elements), while stepping to the next row jumps three elements (stride equal to row length). Triton pointer arithmetic uses the same recipe; “transpose” of a tile is often a stride change, not a data movement.

CUDA launch mapping (same logic in Triton with different syntax): thread index i = block_id × block_size + thread_id maps a one-dimensional launch to vector elements. For 34 elements CUDA may round up to a multiple of the warp width (32), spawning 64 threads—hence the ubiquitous guard if (i < n). Two-dimensional tiles use row = block_y × block_rows + thread_y and col = block_x × block_cols + thread_x, with similar bounds checks when dimensions are not exact multiples of the tile. Pointers passed to kernels are base addresses; strides (row-major by default in this narrative) tell you how to step from logical (r,c) to a flat offset.

Backward pass and IO complexity

Gradients

Training requires derivatives through the attention map. For a custom fused op, frameworks invoke a user-defined backward that matches the forward’s numerics. Structurally: dV = P⊤dO, dP = dO V⊤, then dS from softmax (depends on P and dP), then dQ, dK from dS.

For O = P V, treat it like Y = X W: with upstream gradient dO, the right multiply gives dV = P⊤ dO (paper-style dV), and the left multiply gives dP = dO V⊤. Row-wise, oi = Σj Pij vj matches the FlashAttention appendix notation where each vj is a row of V.

The FlashAttention paper states the softmax Jacobian in the compact outer-product form: treating y = softmax(x) as a column vector, the Jacobian is expressed with diag(y) − y y⊤—a diagonal minus rank-one term. When you contract it with an upstream vector in the layout the derivation uses, you obtain the familiar row operations on dP that reduce to elementwise structure involving P and a scalar statistic per row (often written with a dot product di between pieces of dO and O in the tiled backward).

Forward kernels often store log-sum-exp–style statistics (your running m and ℓ) per row to reconstruct softmax probabilities during the backward pass, or recompute attention scores S from reloaded Q, K tiles to trade extra compute for less HBM traffic—consistent with the same tiling schedule as forward.

Why recomputation beats storing S: materializing and reloading a dense N×N map for every head and batch—e.g. thousands of tokens in each direction—blows HBM traffic and capacity. If moving that tensor is already the bottleneck, recomputing score tiles inside SRAM during the backward pass is cheaper than writing them out and reading them back. That is the same memory-bounded logic as the forward pass, only applied to the reverse program.

Loop structure in practice: the paper’s backward can be written with nested loops over query and key blocks; a literal translation may write dQ to HBM every inner step. Implementations (including common Triton reference implementations) often split work: one phase fixes a K/V tile and sweeps all Q tiles to accumulate dK and dV with a single HBM write per K/V block; another fixes Q and sweeps K/V to build dQ. A preprocess pass can form per-row scalars di from O and dO so both phases reuse them. Causal models must reapply masking in backward so masked positions stay inactive—same predicate as forward, typically q_idx ≥ k_idx for autoregressive attention.

Full backward derivations are in the FlashAttention paper appendix (section B.2), starting from dV = P⊤dO, dP = dO V⊤, and the softmax Jacobian. Tiled code applies the same math on SRAM-resident blocks, reconstructing P from stored LSE stats and recomputed scores where needed.

IO analysis (informal)

Let M denote on-chip memory usable for a tile. A standard implementation reads/writes Θ(N²) attention entries in HBM. A tiled fused implementation aims for Θ(N²d² / M) HBM traffic (up to constants from block sizes and recomputation), i.e. each element of the score matrix is “touched” in fast memory rather than resident in HBM. When N grows, that difference shows up as higher effective TFLOPs/s on memory-bound regimes.

08 · LSE

Log-sum-exp storage

Per query row lse = m + log(ℓ) ties together the running max and denominator from online softmax. Storing lse (scalar per row per head) is far smaller than materializing P, and stabilizes backward softmax derivatives.

lsei = maxj Si,j + log ∑j exp(Si,j − maxj Si,j)

Some implementations store a compact per-row tensor historically called M in tutorials: it packs the row max and log denominator so that exp(Sij − Mi) reproduces probabilities without keeping P. The buffer written as Lse in the kernels above is that statistic in log-sum-exp form—one scalar per query position per head instead of N probabilities per row.
