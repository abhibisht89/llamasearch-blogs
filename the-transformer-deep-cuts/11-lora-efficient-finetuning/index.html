LoRA: Low-Rank Adaptation

Freeze pretrained weights W, add a tiny trainable update ΔW ≈ B A, and fine-tune only B and A. LoRA (Low-Rank Adaptation of Large Language Models) was introduced by researchers at Microsoft and has become a standard tool in the parameter-efficient fine-tuning (PEFT) toolbox. Although the name emphasizes language models, the same idea applies to any architecture built from linear maps—including a small convolution-free classifier—when you want specialization without rewriting the full weight tensor. This chapter connects memory, optimizer state, and checkpoint economics to a minimal PyTorch implementation, a digit-classifier demo, and weight merging at inference.

00

Full fine-tuning: memory, Adam states, and checkpoints

Before we name the fix, recall the object we are adapting. A feedforward stack maps an input (a scalar or a vector of features) through one or more hidden layers. Each hidden layer is usually stored as a weight matrix plus a bias; pictorial diagrams draw “neurons,” but numerically it is matrix multiplication and addition all the way to the output. Supervised training compares that output to a target, forms a loss, and runs backpropagation so that every learnable entry in every layer—including both the weight matrix and the bias vector—receives a gradient step.

Fine-tuning adapts a pretrained model to new data the original run never saw—for example specializing a general coding assistant on a particular SQL dialect. Full fine-tuning updates every weight; that is where the costs below bite.

Full fine-tuning loads every parameter of a pretrained network into device memory, runs forward and backward through the whole stack, and updates all weights. For a large transformer that already strains VRAM at inference, training typically needs activations, gradients, and optimizer bookkeeping on top of the parameters themselves.

With torch.optim.Adam or AdamW, each trained tensor carries running estimates: per-parameter exp_avg and exp_avg_sq (first and second moment), effectively two extra full-sized tensors alongside weight and bias. Saving a checkpoint that includes optimizer.state_dict() therefore balloons compared to weights alone.

Checkpoint rotation multiplies disk use: each epoch or step interval may write a full model copy. If you maintain separate adaptations for two domains (for example SQL versus another DSL), naive full fine-tuning stores entire duplicate weight tensors per task. Swapping tasks means unloading one multi-gigabyte checkpoint and loading another.

Full fine-tuning

Train every layer’s weight matrix and bias. Pay for full forward and backward through the frozen-in-name-only stack. Each checkpoint stores the whole tensor soup; with Adam, you also persist optimizer statistics per trained scalar. Switching from “SQL specialist” to “JavaScript specialist” means replacing all weight matrices of the model—expensive I/O and memory churn.

LoRA-style adaptation

Mark the pretrained W tensors read-only: no gradients, no optimizer rows for them. Learn a thin pair B and A whose product has the same shape as the slice of W you would have edited. Backprop touches only those factors. On disk you keep one shared backbone; each specialty ships as a small adapter. Hot-swapping tasks reduces to loading the adapter pair instead of the entire network.

Takeaway: Parameter-efficient fine-tuning (PEFT) targets the bottleneck: fewer trainable tensors, smaller optimizer states, smaller artifacts to store and hot-swap — without assuming you can afford full-model copies per specialization.

LoRA is one PEFT method that keeps the base W fixed and learns a low-rank correction ΔW so backward passes and checkpoints focus on thin matrices B and A. The bet is that many entries in dense W are redundant for the adaptation you care about—a low-rank ΔW targets the subspace that actually needs to move (Section 01 makes that precise).

Bonus Question

If Adam creates 3x memory overhead, does mixed-precision training (FP16/BF16) change that story?

Mixed precision stores master weights in FP32 but forward/backward in FP16. The optimizer states (moments) still live in FP32, so Adam's 2x overhead remains on the full-precision copy. You save on activations and gradients (halved), but the optimizer state stays the dominant cost — which is exactly what LoRA targets.

Bonus Question

If you fine-tune the same base model for 5 different tasks, how does disk usage compare between full fine-tuning and LoRA?

Full fine-tuning: 5 complete model copies on disk. For a 7B model at FP16 that's ~14 GB × 5 = 70 GB. LoRA: 1 shared base (14 GB) + 5 tiny adapter files (often 10–50 MB each). Total ~14.25 GB — roughly 5x less disk usage.

01

The low-rank hypothesis for adaptation

Large weight matrices often lie near a lower-dimensional subspace: many columns (or rows) are approximately linear combinations of a few independent directions. The rank of a matrix is the count of linearly independent column vectors: no column in a basis set can be reproduced as a linear combination of the others. Equivalently, rank measures how many degrees of freedom are genuinely new; every remaining column is redundant in the linear-algebraic sense because you can synthesize it from the basis directions.

Prior work argued that very large pretrained models can still be optimized in far fewer dimensions than their parameter count suggests—they exhibit a small intrinsic dimension for certain learning problems. Building on that intuition, Hu, Shen, Wallis, Allen-Zhu, Li, Wang, Wang, and Chen articulate the central LoRA hypothesis about adaptation itself. In their words: “We hypothesize that the change in weights during model adaptation also has a low ‘intrinsic rank’.” (LoRA: Low-Rank Adaptation of Large Language Models, 2021.) That is the bridge from “nice geometry in pretrained weights” to “fine-tuning updates live in a thin subspace.”

The motivating hypothesis for LoRA is that the update needed during fine-tuning — how much W would move if you trained it — is itself low rank or well approximated by a low-rank matrix, even when W is full sized. That is an empirical inductive bias, not a theorem for every task, but it matches the observation that small r often works in practice.

To sharpen intuition, imagine a square matrix written down as 1000×1000—a million entries—but suppose its true rank is only 10. Then all columns already lie in a 10-dimensional span; a rank-10 factorization (conceptually, “wide times tall”) can capture everything linearly determined by W even though the literal grid is huge. The same rank-reduction viewpoint appears in classical compression algorithms: you keep a few dominant modes and discard directions that cost storage but carry almost no independent information.

Classical tools such as SVD factor a matrix into orthogonal directions and singular values; truncating to the top r singular triplets gives the best rank-r approximation in Frobenius norm. LoRA does not compute SVD online; it learns any low-rank factors B and A by gradient descent, which is cheaper and task-specific.

Deep Dive — Bonus Q&A
Bonus Question

Is the low-rank hypothesis always true? When might it fail?

It's an empirical bet, not a theorem. It tends to hold when the new task is "close" to pretraining distribution — a dialect shift, style change, or domain specialization. It can fail when the adaptation requires fundamentally new capabilities the pretrained model never learned, where the needed ΔW might genuinely be high-rank. In those cases, increasing r or doing full fine-tuning may be necessary.

Bonus Question

What is the difference between "intrinsic dimension" and "rank" in this context?

Rank is a linear-algebra property of a specific matrix — how many independent columns it has. Intrinsic dimension is a property of the optimization landscape — how many dimensions you actually need to traverse to find a good solution. A model may have billions of parameters but an intrinsic dimension of a few thousand, meaning most of parameter space is redundant for the task.

02

Decomposition: W, B, A, and shapes d×r, r×k

Consider a linear map with pretrained weights W ∈ ℝ^{d×k} (output dimension d, input k, matching nn.Linear(k, d)’s weight.shape == (d, k)). LoRA injects

h = W x + b  →  h = (W + ΔW) x + b, ΔW = (α/r) · B A

with B ∈ ℝ^{d×r} and A ∈ ℝ^{r×k}. Matrix multiply B A has inner dimension r, so the product has shape (d, k) like W—the inner dimensions r cancel in the product, exactly like stacking two thin rectangles to match a fat one. When r ≪ min(d, k), storing and differentiating B and A is far cheaper than a dense ΔW. You may choose r = 1 as an extreme sanity check: then B is d×1 and A is 1×k, an outer-product-style update with only d + k trainable scalars.

In implementation you freeze the pretrained W: tell PyTorch W.requires_grad = False so the optimizer never allocates moments for it and autograd never writes into it. You then add the low-rank branch to the frozen map: the layer still computes an output with the same shape as before, compares it to the target, forms the loss, and backpropagates—but gradients flow only into B and A. The original weights stay bit-identical unless you explicitly merge adapters into them later.

ΔW = B A (sometimes scaled as (α/r)·B A)  effective linear map: x ↦ (W + ΔW) x + b

Forward in two equivalent views

Either form the full delta once, or apply A then B to x (cheaper when batch features are smaller than materializing d×k). For a batch X with shape (N, k), the low-rank path is X @ A.T @ B.T after aligning dimensions with nn.Linear.

During backprop, how do gradients flow through B and A? Does W receive any gradients?

W receives zero gradients — requires_grad=False means autograd skips it entirely. For the LoRA branch, the chain rule flows through: loss → output → B.T → A.T. Both B and A get gradient tensors, but they're tiny (d×r and r×k), so backprop is much cheaper than updating the full d×k weight.

02b

Worked warmup: SVD, rank two, and matching outputs with fewer scalars

Before touching a training loop, it helps to see low rank on a matrix you control. Import torch and numpy, then build a 10×10 matrix W that is artificially rank-deficient with true rank 2. The grid still stores 10×10 = 100 numbers, but numpy.linalg.matrix_rank(W) reports 2: only two columns are linearly independent; every other column is a linear combination of those two directions.

Singular value decomposition (SVD) factors W = U Σ Vᵀ into three matrices. For a rank-r matrix, only the first r singular triplets carry nonzero singular values; the rest are numerically redundant. Truncating to the leading r columns of U and V and the top r×r block of Σ yields a low-rank factorization analogous to LoRA’s B and A: in the demo skeleton you form a B of shape 10×2 and an A of shape 2×10 so that B @ A is again 10×10.

Draw a random input vector x and bias b. Compare two forwards in parallel:

  1. Original path: y = W @ x + b using the full 10×10 storage.
  2. Factored path: y′ = (B @ A) @ x + b, matching the LoRA-style order “low-rank map then add bias.”

For the constructed rank-two W, y and y′ agree for the same x and b even though the factorized side stores only 10·2 + 2·10 = 40 entries in B and A combined versus 100 entries in W. That is the numerical content of “capture most of the linear map with fewer parameters.”

Caution: This construction is not a general proof that every weight matrix in a trained network is exactly low rank. The demo matrix was built to be rank deficient. Real checkpoints are messier; LoRA’s bet is that the adaptation you need is still well modeled by a low-rank update even when the frozen W is full numerical rank.

Bridge to LoRA: SVD finds an optimal fixed factorization for a given W. Training-time LoRA learns B and A with gradients instead of recomputing an expensive decomposition on every step—task-specific, online, and cheap relative to updating all of W.

Deep Dive — Bonus Q&A
Bonus Question

Why doesn't LoRA just use SVD to decompose the pretrained W directly?

SVD finds the best approximation of the existing W, but LoRA isn't trying to compress W — it's trying to learn a task-specific update ΔW. The optimal low-rank update for SQL fine-tuning is completely different from the dominant singular vectors of W. Learning B and A by gradient descent finds the update that minimizes task loss, not the update that best reconstructs the original matrix.

Bonus Question

If the pretrained W is full numerical rank, does that contradict the low-rank hypothesis?

No — the hypothesis is about the update ΔW, not about W itself. A full-rank pretrained W can still require only a low-rank adjustment for a new task. Think of it as: W already encodes broad knowledge across many directions; the fine-tuning nudge only needs to move a few of those directions.

03

Parameter count: millions versus thousands

For d = 1000, k = 5000, a dense W holds d·k = 5_000_000 scalars. With r = 1, matrices B and A contribute d·r + r·k = 1000 + 5000 = 6000 trainable scalars — on the order of 0.1% of the dense layer.

At r = 5 the LoRA pair has 5·(d+k) = 5·6000 = 30_000 parameters for that layer, still far below five million—under one percent of the five million dense entries. Across many layers, total trainable LoRA counts stay manageable while the frozen backbone stays shared.

Beyond the arithmetic, the savings show up everywhere gradients touch storage: fewer trainable tensors mean smaller optimizer state if you use adaptive methods; faster backpropagation because you skip gradient evaluation for the frozen bulk; smaller checkpoints when you snapshot only adapters; and cheaper task switching—imagine one base model for SQL assistance and another head for JavaScript code generation. You reload only the thin B and A pairs per specialty while the untouched W stays identical to the shared pretrained checkpoint.

|ΔW| = d × k parameters if you trained a full residual weight matrix.

|B| + |A| = d·r + r·k = r·(d+k) — linear in r, not in d·k.

Bonus Question

The parameter savings are clear, but how do Adam optimizer state savings compound on top?

With full fine-tuning of a 5M-parameter layer, Adam allocates 10M extra floats (two moments). With LoRA at r=1 (6K params), Adam allocates only 12K extra floats. The total memory saving is not just 5M → 6K on weights — it's 15M → 18K when you include optimizer state. That's an 833x reduction per layer.

04

Initialization, scaling α/r, and biases

The LoRA paper specifies initialization explicitly: B starts at zeros and A is drawn from a random Gaussian (or another small-variance random scheme). That pairing matters. At optimization step zero, B A = 0 regardless of the draw in A, so the forward map is identical to the frozen pretrained linear until training moves B away from zero. Many codebases use Kaiming-style uniform init for A as a convenient default—functionally it plays the same role as Gaussian noise at small scale. Alternative inits exist in follow-up work, but zero-B plus random A is the canonical starting point.

The scalar α is introduced in §4.1 of the paper as a scaling hyperparameter separate from r. Intuitively, you might sweep r to trade capacity for cost; α lets you rescale the adapter’s magnitude without changing how wide the bottleneck is. The effective low-rank contribution is (α/r) · B A: when you increase r, dividing by r prevents the branch from blowing up merely because you added columns. In code, store self.scale = alpha / r and multiply the low-rank branch output by that constant.

Published LoRA recipes typically adapt weight matrices only, not biases: b stays frozen or pretrained. You can extend the idea, but the default keeps the parameter count and interface simple.

Deep Dive — Bonus Q&A
Bonus Question

What would happen if both B and A were initialized to zeros?

Training would be stuck. If B=0 and A=0, then the forward output is zero. The gradient with respect to B depends on A (and vice versa) — both are zero, so the gradient is zero too. No parameter ever moves. You need at least one of them to be nonzero to break symmetry and let gradients flow.

Bonus Question

Could you swap the convention — initialize B randomly and A to zeros?

Yes, mathematically it works the same: 0 @ random = 0 at init, and gradients will flow once A starts moving. The paper chose zero-B/random-A as convention, but the key property is just that the product starts at zero so the pretrained model behavior is preserved at step 0.

05

Which layers to adapt?

You do not need a separate B and A for every weight matrix in the pretrained stack. LoRA is deliberately modular: pick the projections that carry the adaptation signal you care about—often attention and MLP linears in transformers—and leave the rest frozen without adapters. That choice is a knob between capacity, training time, and disk footprint.

In transformers, attention projections W_q, W_k, W_v, W_o and MLP matrices W_in, W_out are common targets. You rarely need LoRA on every linear in a giant stack: ablations in the literature often show strong results with adapters only on attention outputs and feed-forward layers.

For the educational MNIST classifier below, we attach LoRA to each nn.Linear in a deep MLP to make parameter deltas visible. In production LLM fine-tunes, configuration flags such as target_modules=["q_proj","v_proj"] (names vary by hub) restrict where LoRALayer hooks run.

Rule of thumb: More modules → more capacity and trainable parameters; fewer modules → faster training and smaller adapter files. Validate on a dev set rather than assuming “all layers” is optimal.

Deep Dive — Bonus Q&A
Bonus Question

At step 1, B is all zeros so ΔW = 0. How does the very first gradient update break out of this?

Even though B = 0, the gradient of the loss with respect to B is not zero — it depends on A (which is random) and the input x. Specifically, ∂loss/∂B = scale · (∂loss/∂h) · (x @ A.T).T. Since A is nonzero, the gradient for B is nonzero, and B moves away from zero on the very first step.

LoRALayer: trainable A and B

Module responsibilities

LoRALayer owns lora_A and lora_B as nn.Parameter tensors with shapes (r, in_features) and (out_features, r). Method delta_weight() returns scale * B @ A for merging. forward(x) applies the branch without materializing full ΔW when possible—the two-step matmul keeps activations at width r instead of forming a full d×k delta.

Bonus Question

Why are lora_A and lora_B stored as raw nn.Parameter tensors instead of using nn.Linear layers?

Using nn.Linear would add unnecessary bias vectors and the overhead of an extra module. LoRA's branch is pure matrix multiplication — no bias, no activation. Raw nn.Parameter gives you exactly the tensor you need, registered in .parameters() and state_dict() automatically, with no extra baggage.

08

LinearWithLoRA: enable, disable, merge

Wrapping keeps a reference to the original nn.Linear. Training uses base(x) + lora(x) when enabled is true. For ablations or serving the untouched base, set enabled=False so only base runs — no need to reload checkpoints.

Merging

merge() adds delta_weight() into linear.weight.data and can zero or detach LoRA parameters afterward. After merge, one F.linear (or nn.Linear forward) suffices, which reduces Python overhead and kernel launches in tight inference loops.

Deep Dive — Bonus Q&A
Bonus Question

Can you "unmerge" — subtract the LoRA delta back out of W after merging?

Only if you saved B and A before zeroing them. If you kept a copy, you can compute W -= scale * B @ A to recover the original. Some libraries support this with a merge() / unmerge() pair. But if you zeroed B and A without saving, the merge is irreversible.

Bonus Question

What would go wrong if you merged ΔW into W during training instead of after?

If you bake scale * B @ A into W mid-training, then W is no longer frozen — its values changed. But requires_grad is still False on W, so the merged portion stops receiving gradients. Meanwhile B and A keep training and add another delta on top. You'd effectively double-count the adaptation and break the clean separation between frozen base and trainable adapter.

08b

Optional pattern: torch.nn.utils.parametrize and effective weights

Another clean way to inject LoRA—especially when you want the rest of the module graph untouched—is PyTorch’s parametrization API (torch.nn.utils.parametrize). Register a function on linear.weight. On every forward that reads the parameter, PyTorch calls your registered callable with the stored base tensor and returns the effective weight used in matmuls.

Concretely, when LoRA is enabled, the callable returns W + scale * (B @ A)—exactly the paper’s “replace X Wᵀ with X (W + ΔW)ᵀ” story, with ΔW identified as the learned low-rank term. When LoRA is disabled, the same hook can pass through the untouched W so the module behaves like the original pretrained linear without unloading checkpoints. The rest of nn.Linear still performs F.linear(x, weight, bias); only the tensor named weight is virtualized.

Why bother? Parametrization keeps a single code path through standard layers while making “what is weight?” explicit. Toggling an enabled flag then flips between base-only and base-plus-adapter semantics—useful for A/B tests that must reproduce pretrained metrics bit-for-bit when adapters are off.

The algebra matches LinearWithLoRA; a wrapper composes base(x) + lora(x), while parametrization redefines the tensor that base already multiplies. Merge-to-base for deployment works the same once you materialize W ← W + scale·B A.

Deep Dive — Bonus Q&A
Bonus Question

When would you prefer the parametrization approach over the LinearWithLoRA wrapper?

Parametrization shines when you want drop-in compatibility with existing code that reads module.weight directly. The rest of the model sees a normal nn.Linear with a "virtualized" weight — no wrapper, no changed forward signature. It's also cleaner for bit-exact A/B testing: toggling the enabled flag makes .weight return exactly the original tensor, not just skip a branch.

Training loop: MNIST MLP with LoRA-only gradients

The full LoRA paper fine-tunes billion-scale language models; reproducing that here would be infeasible on modest hardware. The same mechanism nonetheless shows up on a toy task: a deliberately oversized multilayer perceptron on MNIST so the parameter accounting is dramatic. Call the architecture what you like in your own notebooks—the design goal is educational: three nn.Linear stages with a ReLU nonlinearity between them (rectified linear units are the standard choice for such demos), ending in a 10-way logits head for digits 0…9.

The pattern mirrors domain-specific fine-tuning: pretrain the MLP on all digits (in the reference run, a single epoch of ordinary supervised training is enough to reach high overall accuracy), then clone the pretrained tensors if you want an immutable reference for later assertions. Evaluate per-digit behavior: overall accuracy looks strong, yet digit 9 lags—exactly the kind of skew that motivates a targeted adaptation pass. LoRA in the wild targets subtler gaps; here the digit imbalance makes the effect visible in a few hundred steps.

After pretraining, freeze every parameter that is not LoRA: set requires_grad = False on base weights and biases. Only the adapter factors train. Fine-tune on batches that contain only images labeled 9 for a short run—on the order of 100 parameter updates—so you nudge the decision boundary without relearning the entire dataset. Expect digit-9 quality to improve at some cost to other digits: specialization from narrow data is the point.

Bonus Question

After LoRA fine-tuning on digit 9, why might accuracy on other digits drop slightly?

The low-rank update shifts the decision boundary to better classify 9s, but that shift can encroach on nearby digit regions (e.g., 4 or 7 which share visual features with 9). This is the classic specialization vs. generalization tradeoff — the narrower your fine-tuning data, the more you risk slight regression on unrelated classes.

10

Inference-time merging and other PEFT methods

At evaluation time you can treat adapters as a switch: with LoRA enabled, reads of the effective weight include scale · B A, so the network reflects the specialized fine-tune (digit 9 improving in the MNIST story). With LoRA disabled, the same code path should drop the low-rank term and reproduce the exact pretrained confusion counts—down to matching how often digit 0 and digit 9 were wrong before adaptation—because the frozen W never changed on disk; only the side matrices moved.

After training, merge() folds (α/r) B A into linear.weight. Serving frameworks can then ignore LoRA modules entirely. If you need both base and several specialties, keep weights separate on disk: ship one frozen .bin plus small adapter.safetensors per task, and merge or compose at load time.

Beyond LoRA, common PEFT families include adapters (bottleneck MLPs inserted between sublayers), prefix tuning (learned prefix key/value vectors prepended to attention), and IA³ (elementwise rescaling vectors applied to activations, often with very few parameters per module). LoRA’s sweet spot is simplicity and direct matrix form sharing the same interface as dense linear layers.

Deep Dive — Bonus Q&A
Bonus Question

Can you combine multiple PEFT methods on the same model — e.g., LoRA + prefix tuning?

Yes — they target different parts of the computation. LoRA modifies weight matrices; prefix tuning prepends learned tokens to attention context. Combining them can sometimes outperform either alone, though the gains are task-dependent and add complexity to the training and serving pipeline.

Bonus Question

What is QLoRA and how does it push efficiency even further than standard LoRA?

QLoRA quantizes the frozen base weights to 4-bit (using NF4 data type) while keeping LoRA adapters in FP16/BF16. This slashes the memory for the frozen backbone by ~4x on top of LoRA's optimizer savings. A 65B model that would need ~130 GB in FP16 can fine-tune on a single 48 GB GPU with QLoRA.
