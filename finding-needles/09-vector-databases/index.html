Vector Databases — Architecture, Indexing & Operations

Libraries like FAISS solve approximate nearest neighbor (ANN) search in memory—but production retrieval also needs durability, CRUD, metadata filters, replication, and access control. A vector database wraps ANN algorithms in storage-engine semantics borrowed from search indexes and OLTP systems: write-ahead logs, segment files, background merges, and query planners that combine vector similarity with structured predicates and sometimes full-text signals. The sections cover architecture, filtering, hybrid ranking, scaling, and vendor trade-offs.

§0 Why not just FAISS?

FAISS (and similar libraries) are ANN engines: they expose index structures and batch search kernels optimized for GPU or CPU throughput. What they are not, by themselves, is a database. A database is a long-lived service contract: you insert and delete rows, expect crash recovery, enforce who may read what, and compose queries that mix similarity with business attributes. An in-process FAISS index is typically ephemeral unless you build your own persistence, snapshotting, and multi-tenant isolation around it.

FAISS-class library
  • Fast k-NN kernels and composite indexes (IVF, HNSW, PQ, …).
  • You manage process lifecycle, memory maps, versioning, and backup.
  • Filtering beyond bitmasks often requires custom integration.
Vector database product
  • WAL + segments for durability; scheduled compaction.
  • CRUD, metadata indexes, optional RBAC and quotas.
  • Operational tooling: replication, metrics, multi-region options.

Concretely, teams outgrow “raw FAISS in a sidecar” when they need persistence across deploys, online updates without rebuilding a monolithic index from scratch, metadata filtering that is selective (e.g., “same tenant, last 30 days, in stock”), high availability via replicas, and governance (encryption, audit trails, network policies). Vector databases implement those cross-cutting concerns and expose a stable API—REST, gRPC, GraphQL, or SQL—while delegating the innermost neighbor search to algorithms you could also call from a library.

None of this implies you must adopt a dedicated vector database. If your corpus is modest, your team already runs PostgreSQL, and latency targets are forgiving, pgvector can be the right trade.

§1 Vector database architecture

Vector databases use the WAL → memtable → segment → merge pattern from Chapter 1: writes append to a log, accumulate in a mutable memtable, flush to immutable on-disk segments (each with its own ANN structure), and merge in the background to limit read amplification.

Write path (simplified): vector + metadata → WAL append → memtable insert → (flush) → new segment file
Read path: query → parallel ANN over {memtable ∪ segments} → merge top-k → optional filter / rerank

Queries scan the memtable plus relevant segments and merge partial top-k results with a heap—the same multi-segment pattern as text search engines.

Operational levers

  • Flush interval / memtable size trades write latency variance against how “hot” the mutable path is.
  • Compaction throughput caps prevent background merges from starving foreground queries on shared disks.
  • Segment-level caches keep hot posting lists or graph layers in memory—critical when working sets exceed RAM.

§2 Metadata filtering

Vectors encode semantics, but applications almost always need structured predicates too: category = electronics, price < 500, created_at ≥ '2025-01-01', tenant_id = UUID, or tags CONTAINS 'safety'. Pure k-NN on the full corpus ignores those constraints unless you embed them into the vector (usually a bad idea: brittle, hard to maintain, and wasteful of dimensions). Instead, the engine must intersect similarity search with metadata evaluation— and the order in which you do that changes both latency and recall behavior.

Pre-filtering applies predicates first, then runs ANN on the eligible subset. Results respect constraints by construction, but if the filter is highly selective, the remaining set may be so small that graph navigation or cluster probing becomes inefficient—or the filtered subset is too sparse for the index structure you built globally. Post-filtering runs ANN on the whole index (or a coarse bucket), then discards neighbors that fail the predicate. That keeps index navigation fast but risks returning fewer than k matches: your top-50 approximate neighbors might include only three that pass a tight filter. Hybrid strategies interleave predicate checks with graph or cluster expansion— for example, oversampling k′ ≫ k during ANN and trimming, or maintaining metadata-aware posting lists alongside vector postings.

Post-filter risk: requested k, delivered k′ < k → caller must detect shortfall, increase ef_search / oversample, or fall back to brute force on the filtered set.
Structured metadata is not “nice to have.” It is how you enforce multi-tenancy, time windows, catalog facets, and compliance constraints. When evaluating vendors, ask not only QPS on unfiltered benchmarks but how selective filters interact with their index layout (bitmap indexes, inverted side indexes, zonemaps, etc.).

§3 Hybrid queries (vector + full-text)

Semantic similarity excels at paraphrase and concept drift, but some intents hinge on exact lexical identity: model numbers (iPhone 15 Pro Max), legal citations, SKUs, rare proper nouns, or safety-critical strings where approximate matching is unacceptable. Production systems therefore combine dense retrieval (vectors) with sparse retrieval (BM25, DFR, or learned sparse models) or with structured keyword indexes inside the same platform.

Architecturally, you either maintain separate indexes and fuse ranked lists at query time, or build a unified index that stores multiple signal types with a single query planner. Separate indexes are flexible—each side can evolve independently—but fusion requires careful normalization because scores live on incomparable scales. RRF fusion (detailed in Chapter 12) merges rank lists without raw scores; alternatives include weighted linear combinations after score calibration, or learned fusion models trained on click or human relevance data.

RRF(d) = Σi 1 / (krrf + ranki(d)) — see Chapter 12 for derivation and tuning.

Products such as Weaviate and Qdrant expose hybrid search primitives in their APIs; teams using Elasticsearch with dense_vector fields implement the same pattern with multi-stage queries and normalized scores. The design question is not “vector or text” but how to allocate latency budget between candidate generation, fusion, and cross-encoder reranking.

§4 Scaling patterns

Beyond single-node tuning, growth forces sharding and replication. Sharding partitions vectors (and their metadata) across machines—commonly by hashing an id, by range on a key, or by embedding-derived partitions. A query router broadcasts k-NN to every shard (for recall) or uses a routing shortcut if metadata narrows tenants, then merges partial top-k. Replication adds read copies for throughput and fault tolerance; consistent routing and stale-read policies matter when segments compact asynchronously.

Quantization at the storage layer reduces bytes per vector: PQ (product quantization), SQ (scalar quantization to int8/fp16), or binary sketches for maximum compression at the expense of accuracy. These are not mutually exclusive with library-level PQ; the database chooses representations that integrate with filtering and replication. Tiered storage places hot segments in memory or local NVMe, warm data on attached SSD, and cold archives in object storage—with background migration policies driven by access frequency and cost curves.

Dynamic updates without full rebuilds

Immutable segments mean inserts land in the memtable or fresh small segments; deletes often become tombstones until compaction removes them. Some engines maintain a separate delta HNSW graph for recent writes while serving reads from frozen graphs—queries merge both views. The exact mechanics vary by product, but the user-facing goal is the same: sustain reasonable p99 latency while the corpus churns, without nightly full reindexes except as a safety valve.

§5 The vector database landscape

The space spans managed SaaS, Kubernetes-friendly open source, and “no new infra” extensions. None win on every axis; the right choice depends on scale, team skills, filtering complexity, and whether you already anchor data in Postgres.

Pinecone

Fully managed with low-friction onboarding. Strong for getting started quickly; vendor lock-in and pricing at very large scale may matter.

Weaviate

Open-source with GraphQL APIs and modular extensions (vectorizers, rerankers, multi-modal paths). Flexible schema; good when multiple retrieval modalities share one service.

Qdrant

Open-source Rust engine emphasizing speed and expressive filtering. Strong filtered ANN latency; REST/gRPC APIs.

Milvus / Zilliz

Open-source for large-scale cloud-native deployments; Zilliz offers managed hosting. Targets billion-vector footprints with GPU paths in the ecosystem.

Chroma

Lightweight embedding store with embedded and client-server modes. Fast prototyping and Python-native ergonomics.

pgvector

PostgreSQL extension for vectors in SQL. Transactional unity with relational data; at scale and strict latency targets, purpose-built engines may pull ahead.

§6 Choosing the right vector database

Start from measurable constraints: maximum corpus cardinality, embedding dimension, tail latency budget, update rate, filter selectivity, tenancy model, and whether vectors must live in the same transaction as relational updates. Those inputs narrow the field faster than brand affinity.

Scale bands (rules of thumb)

  • < ~100k vectors: pgvector or Chroma often suffice if filters map cleanly to SQL or lightweight Python services.
  • 100k – 10M: Qdrant and Weaviate are common self-hosted sweet spots; managed layers compete on ops savings.
  • > 10M toward billions: Milvus/Zilliz or mature managed offerings (Pinecone tiers, vendor clouds) dominate discussions—sharding and compaction stories matter more.

Operations preference splits teams cleanly: if you lack platform engineers, prioritize managed control planes with backup/restore attestations. If you run Kubernetes already and need cost control, open-source images with Helm charts may win. Integration pulls toward pgvector when embeddings are secondary attributes of entities you already store transactionally, and toward Python-first stacks for Chroma during research spikes.

Heavy filtering (narrow boolean combinations, range stacks on payloads) rewards engines that invest in metadata indexes and query planning—not just raw ANN throughput. Light filtering makes more options viable; the unfair comparison is an unfiltered k-NN benchmark that ignores your real predicates.

Cost scales with stored vectors, replica count, query volume, and egress—plus embedding generation if you self-host models. Watch compaction overhead on write-heavy workloads: you pay for temporary disk amplification during merges. Migration strategies usually dual-write into the new index, backfill historical vectors in batches, verify recall on held-out queries, then cut reads over with feature flags—rolling back if tail latency or filter correctness regresses.
