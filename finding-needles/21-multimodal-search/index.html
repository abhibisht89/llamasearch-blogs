00 · Beyond text — the multimodal web

Human experience is inherently multimodal: we read text, look at images, listen to audio, and watch video. Digital systems that only index plain strings leave enormous signal on the table—layout in a slide deck, color and texture in a product photo, charts that never became clean tables, spoken emphasis in a clip. Modern retrieval therefore increasingly asks: can one modality query another?

A text query like “red summer dress” should rank matching photographs, not titles that happen to contain those tokens. A description of a diagram—“flowchart with three branches about deployment”—should surface the right PDF page even when surrounding text is boilerplate. Both require aligned representations so a query in one modality compares fairly against candidates stored in another.

Alignment is the hard part. Text token sequences and image pixel grids live in different native spaces. Successful multimodal search learns a joint embedding space (or a late interaction mechanism) so that “similar meaning” becomes “similar geometry” for ranking.

Why this matters for search engineers

  • E‑commerce discovery. Text queries against catalog photos; “visual search” from an uploaded reference image.
  • Document and slide retrieval. Finding pages where structure carries meaning—tables, plots, UI mockups—not only paragraphs.
  • Media archives. Cross-modal bridges between transcripts, thumbnails, and full-resolution assets.

The chapter covers CLIP-style alignment, cross-modal retrieval, VLMs, ColPali for visual documents, e-commerce patterns, and a build checklist—ending with a search playground.

01 · CLIP — contrastive language-image pretraining

CLIP (Contrastive Language–Image Pretraining) is the canonical vision–language pair: an image encoder (ViT, ResNet, or similar) and a text encoder map web-scale (image, caption) pairs into one shared embedding space. Training follows the same contrastive / InfoNCE recipe as text embedding models in Chapter 6—in-batch negatives from mismatched image–text pairs, temperature-scaled softmax over the similarity matrix—except both towers are multimodal rather than sentence-only.

What you get at inference

  • Zero-shot classification. Embed class names (“golden retriever”, “dalmatian”) as text prototypes; classify an image by nearest text vector.
  • Cross-modal retrieval. Embed a query sentence and rank images by cosine similarity—or embed an image and rank captions.
  • Feature transfer. The image tower is a strong generic visual backbone for downstream tasks with light fine-tuning.

02 · Cross-modal retrieval

Once both images and texts map to comparable vectors, retrieval becomes a familiar nearest neighbor problem—only the encoder changes with the query modality. Text-to-image: embed the query string with the text tower, compare against a gallery of precomputed image embeddings. Image-to-text: embed the query image, compare against a corpus of text vectors (captions, titles, bullet lists). Image-to-image: use the image tower on both sides for visual similarity, sometimes with additional metadata filters (category, price band, color family).

Text+image-to-image appears in interfaces like “more like this, but in blue.” A common pattern is to form a composite embedding: for example a weighted average of the text vector and the reference image vector after normalization, or a small learned fusion module. Simplicity often wins early: average two L2-normalized vectors and renormalize. The full production path almost always includes batch inference over the catalog, a vector index such as HNSW, and post-processing (business rules, diversity, deduplication, safety filters).

Precompute aggressively. Image embeddings are comparatively expensive; query-time latency improves when the corpus is already embedded and sharded in a datastore that supports high-QPS ANN search.

03 · Vision-language models (VLMs)

CLIP excels at alignment and compact vectors, but it is not, by itself, a conversational reasoner over pixels. Vision-language models extend the idea: architectures such as LLaVA, and proprietary systems like GPT-4V, Claude 3, and Gemini, interleave image understanding with language modeling so the network can describe scenes, answer questions, and follow instructions grounded in what is visible.

Search-relevant uses of VLMs

  • Captioning for lexical retrieval. Generate textual descriptions of images or video keyframes; index those strings with your existing sparse or dense stack.
  • Visual question answering. “What color is the car?” becomes structured metadata extraction when you trust the model’s parse.
  • VLM + RAG pattern. Retrieve candidate images (or pages) with embeddings, then let a VLM read pixels for verification, comparison, or summarization before a text LLM composes the final answer with citations to asset IDs.

The trade-offs are familiar: higher cost per document, latency budgets, and the need for guardrails when generated text becomes part of the index. Hybrid designs often retrieve cheaply with vectors, then verify expensively with a VLM only on the top-k.

04 · ColPali — late interaction for visual documents

      

        Classical document search over PDFs often runs OCR or extracts embedded text, then treats the page like a noisy text file.
        That breaks when the signal is inherently visual: dense tables, compound figures, handwritten annotations, or charts where numbers live in pixels rather than a clean text layer.
        ColPali applies late interaction directly to page images: patch embeddings from a vision backbone score against per-token query embeddings via MaxSim, so layout and non-textual graphics participate in the match—often without reliable OCR.
      

      
ViDoRe and benchmarks

      

        The ViDoRe benchmark family focuses on visual document retrieval tasks where page images are first-class.
        It helps compare models that skip brittle text extraction pipelines against traditional BM25 or dense baselines that only see what OCR recovered.
        In practice, teams may still hybridize: use ColPali-style scoring for candidate generation, then optionally enrich with text-side signals where OCR is reliable.

05 · E‑commerce product discovery

      

        Retail catalogs are image-first: text queries like minimalist wooden desk and uploaded reference photos both need embedding match against product images, usually with category filters so unrelated inventory does not compete.
        CLIP, SigLIP, and OpenCLIP are common encoder choices; prompt tuning and in-domain fine-tuning correct domain shift between web training data and studio catalog photography.

06 · Building a multimodal search system

      

        Moving from a notebook demo to a reliable service means pinning decisions on model choice, data hygiene, indexing mechanics, and query-time composition.
        The list below is a practical ordering many teams follow; it is not a universal law, but it catches the dependencies early.
      

      
    
        
  • Choose an embedding model. Start with a strong general model (CLIP, SigLIP, OpenCLIP) and quantify domain shift on a hand-labeled slice before investing in fine-tuning.
    • 
        
  • Pre-process and embed the corpus. Decide input resolutions, aspect handling (pad vs center crop), and whether to embed multiple crops per image. Batch GPU inference and checkpoint manifests for reproducibility.
    • 
        
  • Index in a vector database. Store SKU / URI / access control metadata alongside vectors; plan for periodic re-embedding when the model version changes.
    • 
        
  • Compose the query pipeline. Accept text, image bytes, or both; normalize exactly as training expects; expose toggles for strict filters vs exploration modes.
    • 
        
  • Post-process. Business-aware reranking, near-duplicate suppression with perceptual hashing, and safety classifiers are standard finishing layers.
    •

        If you take one implementation idea from this page, let it be this: separate embedding generation from serving.
        Treat encoders as versioned batch jobs, treat indexes as replaceable artifacts, and keep query-time code thin—parse inputs, call the index, apply policy layers.
        That separation is how teams swap SigLIP for CLIP, add a ColPali stage for PDFs, or bolt on a VLM reranker without rewriting the entire product surface.
