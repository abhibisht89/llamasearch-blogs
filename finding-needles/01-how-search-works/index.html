00 The Search Problem

Search is easy to describe and hard to do well: a few typed words must surface the most useful matches from a vast collection in milliseconds—a needle-in-a-haystack problem where intent is ambiguous and patience is tiny.

The difficulty is not only size. A query like python threading is short, but it compresses intent: someone may want tutorials, API docs, Stack Overflow threads, or a specific PEP. The same words appear in many documents for different reasons. Conversely, the right answer might use different vocabulary—concurrency instead of threading—so literal word matching is not enough once you care about quality. Even before ranking enters the picture, you must solve a more basic question: which documents even mention the ideas the query might refer to? That is where text processing and inverted indexes come in.

Structured data

Rows and columns with explicit types: IDs, dates, prices. Queries map cleanly to predicates (WHERE price < 100). The engine can index fields directly. Semantics are mostly in the schema.

Unstructured (and semi-structured) text

Natural language, markup, typos, synonyms, multiple languages. Meaning is distributed across tokens and context. You must derive searchable structure via tokenization, normalization, and statistical signals.

Relevance goals differ by domain, but almost every system shares the same backbone: turn text into terms, map terms to documents with an inverted_index, and evaluate queries over posting lists. Ranking layers then reorder candidates using signals beyond yes/no matching.

From card catalogs to inverted files

Card catalogs map from book to metadata; search inverts that direction—each term maps to the documents containing it. That layout, refined since Salton’s SMART and the first web engines, remains the core trick that makes large-scale text lookup tractable.

Takeaway. Search begins by reducing unstructured text to normalized terms, then precomputing a term → document mapping. Everything else—Boolean logic, phrase search, ranking—is layered on that spine.

01 Text Processing Pipeline

Raw text on disk or over the wire is rarely ready to index. It includes capitalization, punctuation, invisible Unicode characters, markup, and morphological variants (jump, jumps, jumped). A text processing pipeline (often called an analyzer in Lucene and Elasticsearch) transforms raw strings into the tokens that the indexer records. The same pipeline (or a compatible one) must run at query time so that query terms land in the same coordinate system as indexed terms.

Tokenization splits character streams into words or word-like units. Simple whitespace splitters break on spaces; language-aware tokenizers handle punctuation attached to words, URLs, hashtags, and CJK scripts without spaces. A bad tokenizer either merges distinct concepts (foo.bar as one token) or shatters meaningful units (splitting product SKUs). Tokenization is therefore both mechanical and product-specific.

Lowercasing folds case so Apple and apple share a term—usually desirable for prose, wrong for proper nouns and some identifiers. Stemming chops suffixes with heuristic rules; the Porter stemmer is a classic English algorithm that normalizes jumped → jump. Lemmatization uses vocabulary and morphology (often with POS tags) to map to dictionary lemmas (better → good), which is linguistically cleaner but slower and language-dependent.

Stop word removal drops extremely frequent terms (the, and, of). Pros: smaller indexes, less noise for Boolean AND. Cons: hurts phrase queries and disambiguation (To be or not to be), and frequency signals for ranking. Many systems keep stop words in a separate field or phase-dependent strategy instead of deleting them outright.

Character filtering strips HTML, zero-width spaces, or control characters. Unicode normalization (e.g., NFC) ensures that different byte sequences that look identical hash and compare identically. Without it, duplicate entries proliferate in the index and queries miss obvious matches.

Analyzers as chains

In Lucene-style systems, an analyzer composes a char_filter → tokenizer → zero or more token_filter stages. Each stage sees a stream of tokens with positions and offsets, which matters for highlighting and phrase queries. Changing one filter can invalidate assumptions elsewhere, so analyzer definitions are versioned carefully in production clusters.

02 The Inverted Index

A forward index stores, for each document, the list of terms it contains—natural for displaying a document, expensive for ad hoc term lookup across the whole corpus. An inverted index flips the direction: for each term, it stores a posting_list of documents where the term appears. Lookup by term becomes an array or tree hop to the list head, hence near O(1) term lookup (plus scanning the list), rather than scanning every document.

Each posting is typically more than a document ID. Common fields include term_frequency within the document and positions (token offsets) for phrase and proximity operators. A minimal posting might be (docId); richer postings enable scoring and positional constraints:

posting ∈ { docId, tf, [pos₁, pos₂, …] }

Building an inverted index (three documents)

After simple lowercasing and splitting on spaces:

D2the lazy dog
D3the quick dog jumps

Scan each document sequentially. For every term, append the document identifier to that term’s posting list. Merge duplicate entries within the same document if you store only presence; aggregate counts if you store tf. The result:

  • the → [D1, D2, D3]
  • quick → [D1, D3]
  • brown → [D1]
  • fox → [D1]
  • lazy → [D2]
  • dog → [D2, D3]
  • jumps → [D3]

03 Boolean Retrieval

In the Boolean model, each query is a combination of literals with AND, OR, and NOT. A document either matches or does not; there is no graded score within the model itself. That simplicity makes Boolean retrieval a building block inside real engines, even when the outer query language adds ranking on top.

Evaluating term1 AND term2 reduces to intersecting two sorted posting lists. Because both lists are sorted by docId, a linear-time merge walk compares heads and advances the smaller ID, emitting matches when IDs are equal. The complexity is O(n + m) for lists of length n and m—far better than scanning the full corpus. OR is a union merge; NOT requires a universe list or skipping against the complement, often implemented with skip pointers or bitsets at scale.

merge_intersect(L₁, L₂): advance pointers; if id₁ = id₂ → output id; else advance min(id₁, id₂)

Limitations: no notion of “better” match—all conjuncts are equal. Frequent terms blow up intermediate lists unless optimized. Users rarely think in pure Boolean form, so interfaces translate natural queries into soft-Boolean or ranked retrieval. Extended Boolean models (e.g., weighted AND, p-norm) blend strict logic with partial satisfaction.

04 Posting List Compression

At web scale, inverted indexes consume terabytes. Posting lists are long integer sequences with skewed distributions: a few terms appear everywhere, most are rare. Compression reduces RAM and disk bandwidth, improving cache efficiency and I/O throughput. The design space trades compression ratio against decode speed—query latency often depends on how fast lists can be decompressed and traversed.

Variable-byte (VByte) encoding represents integers in 7-bit chunks with a high continuation bit. Small IDs use one byte; larger values use more. Decoding is branchy but simple and fast enough for many engines.

Sorted posting lists store monotonically increasing docIds. Delta encoding stores the gaps between successive IDs instead of absolute values. Gaps are smaller on average, so they compress better under VByte or bit packing. After decoding a prefix of gaps, reconstruct absolutes with a running sum.

Δᵢ = docIdᵢ − docIdᵢ₋₁  (with docId₀ = 0);  decode: docIdᵢ = docIdᵢ₋₁ + Δᵢ

Bit-packing exploits known maximum bit widths for blocks of integers (PForDelta, SIMD-friendly layouts). Blocks are decompressed in bulk, trading more complex encoders for higher throughput on modern CPUs.

Example: deltas on a short list

Posting list: [107, 110, 120, 130]. Deltas: [107, 3, 10, 10]. The first gap is large; subsequent gaps shrink when documents cluster in segments—common when crawl order correlates with site structure.

Takeaway. Compression is not archival—it is a latency tool. Choose codecs that align with query patterns: skip-friendly layouts, block decoders, and caching of hot postings dominate engineering decisions.

05 Query Parsing

Users type strings; executors need structured operations. A query parser turns surface syntax into an operator tree (or an intermediate representation) that the retrieval layer understands. Along the way, the query undergoes the same textual analysis as documents so that Foxes matches an index containing fox if that was the analyzed form.

Common query types include:

  • Term single-token lookup in the inverted index.
  • Phrase requires consecutive positions—needs positional postings.
  • Boolean combines subqueries with set logic.
  • Wildcard / n-gram expands to many terms via prefix or n-gram indexes.

A typical parsing pipeline is: tokenize the query string → apply the same analyzer (or a query-time variant) → map tokens to internal nodes → build a tree with operators (must, should, must_not in Elasticsearch parlance mirrors Boolean structure while allowing soft clauses for ranking).

Phrase queries intersect postings on term equality and enforce that positions align (e.g., second term at position p+1 if slop=0). Proximity queries generalize phrase constraints to windows (“within n positions”), useful for legal and patent search where exact order is flexible but closeness matters.

Parse tree sketch

MUST( AND( TERM(quick), TERM(brown) ), SHOULD( TERM(fox) ) )

Real parsers handle precedence, field scoping (title:fox), fuzziness, and boosts. The tree is the contract between the language surface and low-level iterators over postings.

06 The Anatomy of a Search Engine

End-to-end search stacks separate concerns: acquiring data, transforming it, indexing it, serving queries, and learning from signals. While products differ, the pattern is stable: ingestion, indexing, and query serving pipelines connected by segment files or shards.

Major subsystems

  • Crawling / ingestion: fetch or receive documents, extract text, assign IDs, enqueue for indexing.
  • Indexing: analyze text, accumulate postings, flush compressed segments, merge periodically.
  • Query path: parse → plan → open iterators → score → rank → render snippets with highlights.

Where ranking fits: after candidate generation. Inverted indexes answer “who matches?” cheaply; scoring functions (BM25, vector similarity, click models) reorder candidates for presentation. Hybrid systems run lexical and semantic retrievers in parallel, then fuse results. Boolean or weak-AND retrieval produces a set or heap of candidates; ranking consumes features from terms, fields, anchors, freshness, and behavioral data.

Query → Parser → Analyzer → Plan → Posting iterators → Score → Top-K → Snippets
