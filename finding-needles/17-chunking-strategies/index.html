Chunking Strategies
The Highest-Leverage RAG Decision

Chunking is how you cut documents into units before embedding and retrieval. It shapes what your index can “see,” what gets matched to a query, and what evidence the model reads. Fixed-size splits, recursive separators, meaning-based boundaries, structure-aware rules, contextual prefixes, and late chunking each trade implementation cost against boundary quality.

00 · Why chunking matters

In a typical retrieval-augmented generation (RAG) stack, raw documents rarely flow whole into a vector database. They are first transformed into chunks: contiguous spans of text that become rows in your index—each with an embedding vector, optional metadata, and sometimes links back to a parent file or section. That transformation is chunking: the policy that decides where the scissors go.

Chunk boundaries sit upstream of embedding, retrieval, and generation. A weak embedding model on well-chosen chunks can still retrieve useful evidence; a state-of-the-art model on badly fragmented or bloated chunks will confidently surface the wrong paragraphs. The generator only reads what retrieval promotes into the prompt window, so evidence that was never retrieved—or arrives without enough local context—limits answer quality regardless of prompt wording.

The dilemma is structural. If chunks are too small, each vector encodes a narrow slice of meaning: pronouns lose their antecedents, definitions detach from terms, and legal clauses split from the headings that disambiguate them. If chunks are too large, each embedding becomes an average of many topics; similarity search drifts toward “vaguely related” passages, and the model wastes attention on irrelevant sentences bundled into the same hit.

There is no universal best strategy. What works for uniform internal memos may fail for HTML knowledge bases, PDF manuals with two-column layouts, or repositories where the unit of truth is a function body rather than a paragraph. The right approach is the one that aligns chunk boundaries with how your users ask questions and how meaning is organized in the source material.

What “good” looks like

Good chunks are semantically coherent (mostly one topic or task), self-contained enough to answer targeted queries without mandatory off-chunk context, and sized appropriately for your embedding model and retriever. They should also carry metadata when possible—source title, section path, page span, version—so filters and rerankers can exploit structure downstream.

  • Retrieval precision benefits when chunks line up with natural question targets (procedures, definitions, policies, examples).
  • Generator faithfulness benefits when each retrieved block includes the local context the model needs to interpret specialized terms.
  • Operational cost shifts with chunk count: more chunks mean more embeddings, more index storage, and often more candidates to rerank.

01 · Fixed-size chunking

The simplest policy is fixed-size chunking: walk the document in steps of N characters or tokens and cut, optionally sliding the window so neighboring chunks overlap. Libraries and benchmarks often cite token budgets (for example 512 tokens) because embedding models were trained with specific sequence lengths; in product code you might approximate tokens with a byte-pair estimate or count with the same tokenizer your embedder uses.

Overlap (for example 100 tokens shared between consecutive chunks) reduces the chance that a critical sentence sits on a hard boundary with half its content in one chunk and half in another. Overlap is not free: it multiplies storage and indexing work, and highly redundant chunks can skew retrieval if the same fact appears in many near-duplicate vectors.

Pros

Trivial to implement, deterministic, fast on huge files, easy to reason about average chunk length and index size. Ideal for first prototypes and uniform narrative text.

Cons

Ignores grammar and document structure: you can sever sentences, tables, and list items arbitrarily. Boundaries are arbitrary with respect to meaning, so two related facts may land in non-adjacent chunks with no overlap bridge.

When to use: early experimentation, logs or streams with weak structure, or when you must guarantee strict token budgets per index row for compliance or latency reasons. Move to richer strategies when retrieval quality plateaus or when your sources have clear headings, code fences, or markup.

02 · Recursive character splitting

Recursive character splitting is a practical default in many frameworks: try to split on large structural separators first, then recurse with finer separators until pieces fit under a maximum size. A common hierarchy (as in LangChain’s RecursiveCharacterTextSplitter) is: "\n\n" (paragraphs) → "\n" (lines) → ". " (sentence-like breaks) → " " (words) → empty string (characters).

The algorithm prefers to keep paragraphs intact; only when a block still exceeds the limit does it walk down the separator list. The result is usually more readable than raw fixed windows, and chunk boundaries more often fall on natural pauses—though it is still fundamentally a textual heuristic, not a semantic understanding of topic shifts. Recursive splitting is a common default because it improves on blind fixed slicing without an embedding pass at ingest time.

You still choose chunk_size and chunk_overlap in character or token units. Overlap applies when reassembling or when further splitting merges fragments; tune it the same way you would for fixed-size chunking, typically as a fraction of the chunk budget.

03 · Semantic chunking

Semantic chunking aims to cut where the meaning shifts rather than at every N characters. A representative approach—popularized in discussions of Greg Kamradt’s experiments—embeds each sentence (or a short sliding window of sentences), measures similarity between neighbors, and treats sharp drops in cosine similarity as topic boundaries where a new chunk should start.

Variants compare adjacent single sentences, adjacent windows, or cumulative context against the next window; all share the idea that embedding space geometry approximates topical continuity. When similarity falls below a threshold τ, you start a fresh chunk and group subsequent high-similarity sentences together until the next drop.

Pros

Chunks tend to align with subject changes—helpful for long essays, policy compendia, and raw dialogue logs where paragraph breaks are missing or misleading.

Cons

Requires an embedding pass during ingestion (cost and latency). Threshold τ is data-sensitive: too low merges unrelated material; too high fragments coherent sections. Short sentences can produce noisy vectors.

For production, pair semantic boundaries with a maximum chunk size cap so outliers do not create enormous single vectors, and consider normalizing or smoothing similarity scores across a document to reduce single-sentence spikes.

04 · Structure-aware chunking

Structure-aware chunking uses explicit document signals—headings, lists, tables, code fences, page blocks—instead of guessing from whitespace alone. For HTML, splitting on tags like <h1>, <h2>, and <h3> keeps sections intact; for Markdown, lines beginning with # through ###### define a natural outline tree.

PDF sources often need layout analysis (reading order, columns, headers/footers) before structure is trustworthy; many teams run specialized extractors or vision models to recover headings and blocks. For source code, the logical unit is frequently a function, class, or method; tree-sitter or language servers can chunk by AST nodes while preserving syntax validity inside each span.

Pros

Chunks map to how humans navigate the material (chapters, API methods, config keys).

Cons

Section lengths vary wildly—a short README heading may cover one line while another section spans pages—so you may still need secondary splitting inside oversized sections.

05 · Contextual retrieval (Anthropic’s approach)

Even perfect physical boundaries can produce orphaned chunks: a passage that made sense on page seven reads like gibberish without the contract title, product name, or jurisdiction stated only in the introduction. Contextual retrieval addresses this by prepending a short, human-readable contextual prefix to each chunk before embedding (and often before storage), summarizing where the chunk lives in the broader document and what it is about.

A typical prefix might read: “This passage is from a software licensing agreement for Product X; it discusses payment terms and audit rights.” Prefixes are usually generated by an LLM with the full document (or a rolling summary) in view, then cached alongside the chunk text.

Anthropic reported roughly a 49% reduction in failed retrievals when contextualizing chunks in a published enterprise benchmark (exact figures depend on corpus and eval). Prefixes help embeddings capture local wording when the chunk’s role in the document is spelled out explicitly. Costs include extra LLM calls at ingest time and longer strings to embed; mitigations include batching, caching stable documents, and generating concise prefixes with a small, fast model.

06 · Late chunking

Classical pipelines chunk before embedding: each span is encoded in isolation, so cross-chunk context never influences the vector representation. Late chunking flips the order: pass the entire document (or the largest feasible segment that fits the model’s context) through the transformer once, then slice the sequence of token embeddings at your chunk boundaries to produce per-chunk vectors.

Because every token’s representation was computed with global self-attention (within that forward pass), each slice is context-aware of the rest of the document—pronouns, definitions, and section themes leak appropriately into local vectors without concatenating the whole file into every chunk at rest. Jina AI and others have popularized embedding models and documentation oriented toward this workflow; it pairs naturally with long-context encoders. You need a model that exposes token-level outputs and supports long sequences; memory and latency scale with document length, and very long sources may still require hierarchical splitting before each late-chunking pass.

07 · Practical recommendations

Start with recursive character splitting unless you already know your corpus demands structure-first or semantic rules. It is the best “boring default” for mixed prose: cheap, predictable, and kinder to readers than raw fixed windows.

KnobStarting rangeNotes
chunk_size 256–512 tokens (typical) Align with embedder sweet spot; smaller for precise facts, larger for narrative context.
overlap 10–20% of chunk size Reduces edge cuts; watch for duplicate retrieval hits.
Metadata title, path, header, page Enables filtering, parent expansion, and UI source chips.

Always evaluate with real user queries from logs or interviews—not generic “vibes” on a handful of hand-picked questions. Build a small labeled set (query → relevant chunk ids) and measure recall@k, mean reciprocal rank, or task success after generation.

Parent document pattern

A powerful hybrid is parent document retrieval: embed smaller, precise “child” chunks for search, but when a child hits, return a wider parent span (section or page) to the model. You keep retrieval sharp while giving the generator enough surrounding prose to interpret the hit.

Agentic chunking

Some teams use agentic chunking: an LLM or tool-using agent proposes split points, classifies passages, or labels chunks with structured metadata before indexing. Quality can be excellent; cost and nondeterminism rise, so guard with schemas, spot checks, and regression tests on chunk cardinality.
