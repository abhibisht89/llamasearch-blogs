Dense Retrieval — Bi-Encoders for Scalable Search

Dense retrieval maps queries and documents into a shared embedding space so that cosine similarity (or inner product after normalization) proxies semantic nearness. Unlike BM25, which scores overlap of surface forms, a bi-encoder can connect paraphrases, bridge vocabulary mismatch, and reflect task-specific training— at the cost of heavier indexing, opaque failure modes, and the eternal tension between similarity and true relevance.

§0 From lexical to semantic retrieval

BM25 excels at exact term matching (Chapters 2–3) but cannot bridge vocabulary gaps like car/automobile.

Encode the query and each document (or passage) into vectors q, d ∈ ℝd with a neural encoder. Define a score s(q, d) = ⟨q, d⟩ after L2 normalization (equivalently cosine similarity). Retrieval becomes nearest-neighbor search in embedding space rather than inverted-index intersection in term space. The geometry is learned from data; the index structure (HNSW, IVF, product quantization, etc.) is an engineering layer on top.

Dense passage retrieval (DPR, Karpukhin et al., 2020) is the reference point that popularized this recipe for open-domain question answering at scale: two BERT-class encoders, contrastive training with negatives, and a clear empirical story that learned vectors can beat strong lexical baselines when the task rewards paraphrase and indirect evidence. It did not erase BM25; in mature stacks, dense and lexical signals are routinely hybridized—either by fusing scores, running parallel retrievers, or using lexical first stages to feed a reranker. Similarity is computed in embedding space, not term space.

§1 Dense Passage Retrieval (DPR)

The DPR architecture is a two-tower design. A query encoder (a BERT-based transformer) reads the question and outputs a pooled vector; a separate passage encoder (another BERT with its own weights) reads each candidate passage and outputs its own pooled vector. Both outputs are typically L2-normalized so inner product equals cosine similarity, which stabilizes training and plays nicely with standard approximate nearest neighbor libraries.

Why separate encoders? Queries and passages are not drawn from the same distribution of length, style, or information density. A question is short, interrogative, and intentionally under-specified; a Wikipedia paragraph is declarative, self-contained, and packed with redundant supporting phrases. A single shared encoder can work—and many later systems use one model with asymmetric prefixes—but DPR’s hypothesis is that specialization frees each tower to allocate capacity to its side’s quirks. The query tower can emphasize interrogative cues and entity slots; the passage tower can emphasize definitional patterns and supporting facts.

Training follows the contrastive pattern now standard across retrieval. For each gold (query, passage+) pair in a mini-batch, treat all other passages as in-batch negatives. The loss pushes sim(q, p+) above sim(q, pi) for every negative passage pi in that batch. This is mathematically an instance of InfoNCE / softmax cross-entropy over a partition function built from the batch.

DPR also demonstrated the power of BM25 negative sampling beyond random easy negatives: use BM25 to retrieve top passages that are not labeled positive. Those passages are often hard—lexically close or topically adjacent—forcing the dense encoder to learn finer boundaries than random unrelated paragraphs would require. The recipe matters: training with only trivial negatives yields inflated offline metrics and brittle deployment behavior.

Datasets in the original line of work included Natural Questions, TriviaQA, and WebQuestions—supervision comes from question–answer evidence passages mined from web or Wikipedia snapshots. On open-domain QA retrieval, DPR improved over BM25 by substantial margins on recall-oriented metrics, especially when downstream readers are sensitive to whether the true evidence appears anywhere in the top-k candidates.

What DPR does not solve by itself

End-to-end QA also needs reading comprehension, calibration, and often reranking. DPR is a retrieval substrate: it addresses whether the right paragraph is in the candidate set. Domain shift, temporal drift, and adversarial overlap between misleading passages remain active engineering concerns—dense models can be confidently wrong with high similarity.

§2 The bi-encoder architecture

Abstracting away from DPR-specific details, a bi-encoder is any setup where fq(query) and fd(document) produce vectors independently, without cross-attention between the two inputs at encoding time. The towers may share weights (common in symmetric semantic search) or use separate parameters (common in asymmetric QA retrieval). Shared-weight models simplify deployment—one checkpoint, one inference path—but asymmetric pairs often benefit from specialization or from instruction-style prefixes that tell the model which role it is playing.

Offline indexing is the expensive phase: run fd over the entire corpus (often sharded across workers), L2-normalize if needed, and load vectors into a vector database or custom ANN service. For static snapshots this is a batch job; for rapidly changing content you need incremental updates, versioning, and consistency policies just like any search index.

Online querying is comparatively cheap: one forward pass for the query (milliseconds to tens of milliseconds on GPU, depending on width and batching), then a sublinear approximate search returning top-k ids. The asymmetry is strategic—pay once per corpus revision, amortize across unbounded queries.

Bi-encoder
Encode once per item; score with dot product. Complexity at query time is O(1) encoding plus O(log N) or sublinear ANN—not O(N) full attention over the corpus.
Cross-encoder
Concatenate query and document inside one transformer; every layer attends across both. State-of-the-art pairwise relevance for short lists, impractical as exhaustive first-stage retrieval.
Poly-encoder
Multiple representations per candidate (e.g., several summary vectors) to approximate cross-attention fidelity with a few more inner products—middle ground for reranking.
ColBERT-style late interaction
Token-level vectors with deferred interaction—often treated as its own family; richer than single-vector bi-encoders, still more index-friendly than full cross-encoders.

Production pipelines frequently chain them: bi-encoder (or hybrid lexical–dense) for width, cross-encoder or feature-heavy Learning-to-Rank for depth on dozens of candidates.

§3 InfoNCE loss — the training objective

InfoNCE (noise contrastive estimation) is the standard contrastive objective for many retrieval models. For a query embedding q and a positive passage embedding p+ with negatives { pi }, define similarities si = sim(q, pi) (often dot product of normalized vectors). With temperature τ > 0:

L = −log
exp(sim(q, p+) / τ) / Σi exp(sim(q, pi) / τ)

Intuitively, the model is trained to classify which passage in the candidate pool belongs with the query; the softmax sharpens or softens those decisions. The positive index is supervised; every other term in the denominator acts as a negative. When negatives are easy (very low similarity already), gradients shrink—one reason hard negative mining (§4) dominates practical recipes.

Temperature τ rescales logits before the softmax. Small τ makes the distribution peaky—almost one-hot if a positive is clearly best—amplifying gradients for small mistakes but sometimes increasing variance. Large τ smooths the distribution, spreading probability mass and behaving like gentler distillation toward uniform attention over negatives.

In-batch negatives recycle every other passage in the mini-batch as a negative for each query. That yields B − 1 negatives per query for batch size B without extra forward passes. The downside is correlation: negatives are not independent draws from the true corpus distribution. Despite that, the trick scales beautifully on modern accelerators.

Why large batch sizes help: more negatives increase the effective difficulty of the classification problem inside each step, provide richer gradient signal about relative ordering, and better approximate the full corpus partition function—at least in expectation. Memory becomes the bottleneck; tricks include gradient accumulation, cross-device negatives via all-gather of embeddings, and mixed-precision training.

§4 Hard negative mining

Uniform random negatives are often too easy: their embeddings drift far from the query early in training, contributing tiny gradients. The model masters a toy decision boundary that does not resemble deployment, where the user sees a slate of plausibly related snippets scraped from the web, not random noise paragraphs.

BM25 negatives are the classic cheap hard-negative source: retrieve top-k lexical hits that are not labeled relevant. They tend to share vocabulary and surface topic with the query while missing the precise supporting fact—exactly the confusion you want the dense encoder to unlearn.

Cross-encoder negatives push further: take pairs that a strong cross-encoder mis-scores—passages it thinks are relevant but humans mark irrelevant—and use them as hard negatives for the bi-encoder. The teacher is imperfect but often sharper than lexical overlap alone.

In-batch hard negatives select the highest-similarity wrong passage within the current batch as an extra emphasis target, sometimes mixed with random negatives for stability. Curriculum learning varies difficulty over time—start with easier negatives so optimization does not collapse, then ramp hardness as representations stabilize. Across many ablations, the quality and difficulty distribution of negatives often matters as much as architectural width—a mid-sized model with excellent negatives and clean positives routinely beats a giant model fed naive random pairs, because the loss fires where the decision boundary must live.

§5 Similarity vs relevance

Cosine similarity is not relevance. It is a geometric proxy induced by training data and model capacity. Two strings can be close in embedding space because they share syntactic templates, entities, or discourse genre—even when only one document answers the user’s information need.

Canonical pattern: the queries “What is the capital of France?” and “What is the capital of Germany?” embed similarly because they are structurally parallel and differ by a single entity slot. Yet the correct answers are mutually exclusive. A retriever optimized purely for surface similarity might rank cross-country confusers highly unless negatives and task labels teach finer discrimination—or unless a downstream reader resolves the ambiguity.

Relevance is task-specific: legal retrieval, e-commerce search, medical QA, and internal enterprise lookup each define different positive classes. Similarity is geometric: an artifact of the encoder and the distribution it was trained on. Mismatch between the two is why offline embedding benchmarks only partially predict production wins.

Training data construction must encode your notion of relevance—pairs labeled by editors, clicks debiased, hard negatives drawn from confusers your metrics care about. Asymmetric search (question ↔ evidence passage) amplifies the distinction: the query is a short underspecified probe; the document is a self-contained text blob. Prefixing inputs with query: vs passage: (as in E5) explicitly signals roles to a shared encoder.

§6 Modern dense retrieval models

The ecosystem matured rapidly after DPR. Today’s checkpoints differ in pretraining data, instruction tuning, pooling, sequence length, and whether they emit symmetric or asymmetric embeddings. §7 Practical considerations

Embedding dimension vs quality: higher d increases ANN memory and distance-compute cost, often improving recall up to a point of diminishing returns. Matryoshka-trained checkpoints let you truncate prefixes when storage dominates; quantize only after validating acceptable regression on your metric.

Batch size during training: bigger batches mean more in-batch negatives → sharper contrastive signal, assuming learning rate and temperature are retuned. Watch for divergence if hardness ramps too quickly; use gradient clipping and mixed precision carefully when pushing batch size.

Instruction prefixes: for E5-style models, follow the upstream template literally—query: … vs passage: … (or document:). A mismatch at serving time silently drifts the geometry and can slash recall overnight after a deploy typo.

Domain adaptation: if your vocabulary and style diverge from pretraining (internal jargon, biomedical, legal), start with a strong off-the-shelf checkpoint and measure. Fine-tune with curated positives and mined hard negatives when offline metrics justify the data and ops cost; otherwise prefer hybrid lexical–dense retrieval and reranking before touching base weights.

Encode (offline) → Index (ANN + metadata) → Search (query vector + top-k) → Return ids → (optional) rerank / reader

Instrument every stage: embedding drift alerts, index freshness lag, p95 query latency, and recall@k on golden queries. Dense retrieval fails quietly—high similarity with wrong facts—so monitoring needs human spot checks and adversarial query sets, not only aggregate dashboards.
