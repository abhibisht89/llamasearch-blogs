00 · Why graphs?

Dense retrieval with embeddings excels at finding semantically similar text: paragraphs that read alike, paraphrases, and topical neighbors. What it often misses is explicit structure—who bought whom, which product belongs to which line, which paper cites which method—especially when those facts are scattered across many documents.

Consider a question like “Which companies acquired AI startups in 2024?” A vector index may return news articles that mention acquisitions and AI, yet the model still has to reconstruct a precise list from noisy prose. A knowledge graph stores acquisitions as typed edges between company nodes, optionally with a year property, so retrieval can be constrained to paths that actually satisfy the query shape.

Core idea. Graphs capture entities (nodes), relationships (edges), and optional attributes on both. GraphRAG combines that structure with generative models so answers can be grounded in multi-hop facts and community-level themes—not only the nearest embedding neighbors.

Where vectors stop and graphs start

  • Similarity without linkage. Two chunks may both discuss “M&A trends” without ever co-locating the same (acquirer, target, date) triple in one passage.
  • Multi-hop reasoning. Answering “Which investors backed firms later acquired by BigTech?” is naturally expressed as path queries over a graph, not a single cosine match.
  • Global questions. Thematic prompts (“What are the main themes in this corpus?”) benefit from summaries of clusters of related entities—something pure chunk retrieval does not organize for you.

None of this replaces embeddings. The strongest systems often hybridize: graphs for relational scaffolding, vectors for fuzzy language and long-form evidence. Extraction, GraphRAG architecture, SQL grounding, and hybrid routing follow—with an in-browser lab at the end.

01 · Knowledge graph fundamentals

A knowledge graph is a labeled network: nodes represent things in the world (people, organizations, products, concepts), and edges represent how those things connect (acquired_by, located_in, invented, part_of, and so on). Unlike a bag of text chunks, the graph makes relational commitments explicit—useful both for humans auditing data and for algorithms traversing structure. These curated entity–relation graphs differ from a statistically induced semantic knowledge graph, which bridges lexical, semantic, and behavioral spaces—but both move retrieval beyond flat text chunks.

Schema and typing

Real graphs usually enforce a schema: allowed entity types (for example Company, Person, Technology) and relationship types with domain and range constraints (only Company may acquire another Company). Schema reduces ambiguity, improves deduplication, and helps downstream query planners know which indexes and filters apply.

Triples and property graphs

The atomic statement is often written as a triple: (subject, predicate, object)—for example (Google, acquired, DeepMind). In a property graph model (think Neo4j, Apache TinkerPop), nodes and relationships can carry key-value properties such as announced_on, deal_size_usd, or confidence.

02 · Entity and relationship extraction

Most source material arrives as unstructured text. GraphRAG therefore begins with structure induction: algorithms (and often models) that propose entities and relationships with confidence scores. The output is rarely perfect; entity resolution, human review, and constraint checks are normal parts of a mature pipeline.

Named Entity Recognition

NER tags spans as PER, ORG, LOC, MISC, or custom types. Libraries such as spaCy and transformer models on Hugging Face provide strong baselines. NER alone does not give edges—it gives candidate nodes anchored to character offsets in text.

Relationship extraction

Classical approaches combine dependency parsing, syntactic patterns, and supervised classifiers over token pairs. Pattern guards help—for example, ensuring subject and object mentions co-occur within a sentence window. Open Information Extraction (OpenIE) aims for high recall triples without a fixed schema, which is powerful but noisy.

Hearst patterns

Lexico-syntactic templates like “X such as Y” or “Y and other X” cue hypernym / taxonomic relations (Y is a kind of X). They are lightweight, interpretable, and still useful as features or silver-label generators.

LLM-assisted extraction

Prompting a capable LLM with a strict JSON schema can produce entities and typed relations at scale. Guardrails matter: validate JSON, coerce types, reject unknown predicates if you maintain a closed schema, and log provenance (doc id, offsets) for auditability.

Semantic knowledge graphs (SKG). An SKG couples graph structure with semantic representations—entity embeddings, node summaries, or neighborhood encoders—so lexical variation resolves to canonical IDs while supporting soft retrieval alongside exact graph matching. GraphRAG extraction produces a related but typically more typed and curated entity graph from documents.

03 · Microsoft GraphRAG (reference architecture)

The public GraphRAG research implementation popularized a concrete end-to-end pattern: ingest text, extract an entity-relationship graph, detect communities, summarize those communities, and expose multiple retrieval modes over the resulting artifacts. Understanding this flow helps you map ideas to your own tooling even if you reimplement pieces differently.

Pipeline outline

  1. Segment documents into units suitable for extraction (often overlapping windows).
  2. Use an LLM (or hybrid extractors) to propose entities, relationship types, and reified claims.
  3. Build a graph with deduplicated nodes; optionally weight edges by frequency and confidence.
  4. Run community detection—commonly Leiden—to find cohesive clusters at one or more resolutions.
  5. Ask an LLM to write community summaries that compress each cluster into narrative form.
  6. Index both local facts (text units, incident edges) and global summaries for retrieval-time routing.

Search modes (conceptual)

  • Local search. Anchor on specific entities mentioned in the question; gather neighboring nodes and supporting text for fine-grained factual prompts.
  • Global search. Lean on community summaries to answer broad, thematic questions that do not name a single entity.
  • DRIFT-style search. Emphasize following typed relationships across multiple hops—helpful when the evidence path is longer than one adjacency step.

04 · Building a GraphRAG pipeline

      

        Production pipelines glue together ingestion, extraction, graph writes, analytics, and serving. The list below is a practical decomposition you can map to orchestrators (Dagster, Airflow), event buses, or simple batch jobs.
      

      
    
        
  • Document ingestion & splitting. Normalize encodings, deduplicate files, and split into windows with modest overlap so entities that span boundaries still appear whole in at least one chunk.
    • 
        
  • Entity & relationship extraction. Combine NER, parsers, and LLM structured outputs; keep raw mentions for provenance.
    • 
        
  • Entity resolution. Cluster string-variants (“Open AI”, “OpenAI”) to one canonical ID using embeddings, rules, and pairwise classifiers.
    • 
        
  • Graph construction. Load nodes/edges into NetworkX for analysis or into Neo4j for transactional queries and visualization.
    • 
        
  • Community detection. Apply Leiden / Louvain at multiple resolutions to capture both fine and coarse structure.
    • 
        
  • Summary generation. For each community, generate a concise narrative plus bullet claims with citations back to supporting text units.
    • 
        
  • Search indexes. Maintain a vector index over textual units, a keyword/BM25 index if helpful, and graph-native indices for one- and two-hop expansions.
    • 
      

      

        Cost awareness. LLM extraction and hierarchical summarization can dominate spend. Mitigations include smaller models for draft graphs, caching by document version, sampling edges for summarization, and reusing stable community assignments when only a few files change.
      

    


    

      
05 · Structured data retrieval — text-to-SQL

      

        Much of the world’s decisive data already lives in tabular form: relational databases, warehouses, spreadsheets, and metrics APIs.
        For questions that map cleanly to joins, filters, and aggregations, converting natural language to SQL (or a DSL) can outperform vector search because the answer is exact rather than approximate retrieval over prose.
      

      
Typical architecture

      

        A common pattern is: question → schema linking → LLM generates SQL → execute against the database → optionally validate → feed rows (and/or a sub-sampled schema) back to the LLM → final natural language answer.
        Toolkits like LangChain SQL agents and LlamaIndex SQL modules implement variations of this loop with guardrails and retry logic.
      

      
Schema linking

      

        Models hallucinate fewer column names when you inject a curated CREATE TABLE excerpt, sample rows, value distributions, and short column glossaries.
        Some systems learn string matches from past questions or embed column metadata for nearest-neighbor selection before generation.
      

      
Challenges

      
    
        
  • Complex joins. Star schemas and many-to-many bridges confuse naive prompts; provide join paths or a semantic layer (metrics definitions).
    • 
        
  • Ambiguous columns. Multiple date columns named created_at require disambiguation rules or clarifying questions.
    • 
        
  • Safety. Treat generated SQL as untrusted input: use read-only roles, allowlists, timeouts, row limits, and static analysis to mitigate injection and runaway scans.

06 · Hybrid approaches

      

        Graphs and SQL excel when the query shape is relational; dense retrieval excels when the query is exploratory or definitional.
        Most mature assistants compose backends instead of betting everything on one mechanism.
      

      
Complementary roles

      
    
        
  • Graph-first. “Who,” “which entity,” “along which supply chain,” “within which subsidiary” — precise hop constraints and typed paths.
    • 
        
  • Vector-first. “Explain,” “compare tradeoffs,” “summarize criticism,” “what metaphors appear” — language-heavy tasks where similarity is the right prior.
    • 
      

      
Routing

      

        A lightweight query classifier (rules, small model, or LLM tool-choice) can route to subgraph retrieval, SQL execution, BM25 search, or multi-source fusion.
        Confidence thresholds and abstention matter: when routing is uncertain, run multiple backends and merge with a reranker.
      

      
Knowledge-grounded validation

      

        Use graph facts as constraints on generation: retrieve candidate answers from SQL or graph lookup, then ask the model to verbalize only what those tuples support.
        Mismatches between retrieved facts and draft answers become detectable contradictions you can repair or flag.
