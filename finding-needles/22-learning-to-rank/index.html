00 · What is Learning to Rank?

Learning to rank (LTR) is the application of supervised machine learning to the ranking problem: you learn a scoring function f(q, d) (or f(x) when x is a feature vector for a query–document pair) from labeled examples so that documents with higher human-assessed relevance receive higher scores.

The central idea is signal fusion: a retrieval stack may expose lexical scores (BM25, TF-IDF—Chapters 2–3), dense retrieval similarity (Chapters 6–7), click-through rate, freshness, authority, and dozens of other measurements. An LTR model learns how to weight and combine those signals for your traffic, domain, and product goals—far beyond hand-tuned linear blends.

Production search stacks have long used LTR-style reranking: first-stage retrieval stays fast and broad; a second stage applies a learned function to a short candidate list.

Three families of objectives

  • Pointwise — predict an absolute relevance grade or probability for each (query, document) pair in isolation.
  • Pairwise — learn from relative preferences: for the same query, should document A appear above B?
  • Listwise — optimize a metric defined on the entire ranked list (for example nDCG), often via clever gradients.

In code and in search engines, the scoring function is usually a real-valued score; sorting by descending score yields the ranking. Neural rerankers are a modern variant: f may be a deep network over query and document text, but the same training-data story (judgments, features, list metrics) still applies.

ranking_api.py
def rank_documents(query, candidates, model):
    # x_i = feature_vector(query, doc_i) logged at query time
    scores = [model.predict(features(query, d)) for d in candidates]
    return sorted(candidates, key=lambda d: scores[d], reverse=True)

01 · Judgment Lists — The Training Data

Supervised LTR needs labels. A judgment list (or relevance judgments) stores triples (query, document, grade) produced by people or derived from behavioral signals. The grade encodes how useful the document is for that information need on an agreed scale.

Grading scales

  • Binary — 0 (not relevant) / 1 (relevant). Common when the task is coarse filtering.
  • 4-point (0–3) — typical web search: not relevant, relevant, highly relevant, perfect (exact definitions live in your guidelines).
  • 5-point (0–4) — finer granularity for difficult domains (medical, legal) where calibration matters.

A machine-readable row often expands into query_id, document_id, a dense features[] vector (after feature logging), and grade. That row is what training code consumes—whether you use libsvm format, Parquet, or an internal pipeline.

Collecting judgments

Crowdsourcing scales volume but needs tight templates and quality checks. Expert annotators cost more but anchor difficult domains. Click and engagement signals (implicit feedback) can augment or proxy labels when carefully debiased—often covered as a dedicated topic next to explicit judgments.

Quality control includes inter-annotator agreement (for example Cohen’s kappa), adjudication of disagreements, and crystal-clear annotation guidelines with worked examples. Without that, models learn noise.

02 · Feature Engineering

Features are the interface between your search stack and the learner. Good LTR is less about exotic algorithms and more about faithful, leak-free features computed the same way in training logs and at serving time.

Lexical and dense signals

  • Lexical scores (BM25, TF-IDF—Chapters 2–3) per field: title, body, URL, anchors, structured metadata.
  • Dense and late-interaction scores (Chapters 6–7, 11): embedding cosine, ColBERT-style MaxSim, cross-encoder logits.

Document quality and query–document interaction

  • Static quality: PageRank-style link features, site authority, spam scores.
  • Freshness: age of content, recency of last crawl, half-life decay.
  • Interaction features: token overlap counts, longest common subsequence, character edit distance, bigram matches.

Behavioral and structural signals

  • Clicks: CTR, position-aware models, dwell time, bounce proxies (use with care—position and presentation bias dominate).
  • Structure: document length, heading count, number of images, reading level estimates.

Normalization (per-query z-score, min-max, quantile binning) stabilizes tree ensembles and linear models when scales differ wildly. Feature logging means persisting the exact feature vector seen online for each judged pair so offline training matches production.

Below is a toy feature-extraction sketch. Production systems add caching, field-specific analyzers, and alignment with the first-stage retriever.

03 · Pointwise Approach

    

      The pointwise recipe treats each labeled example as an independent supervised learning problem: predict the numeric grade
      (regression) or the label distribution (classification). The loss might be MSE, MAE, or cross-entropy for ordinal buckets.
    

    

      Simplicity is the win: any off-the-shelf learner works. The downside is conceptual: a ranking is a structured object—order matters—while
      pointwise loss only indirectly encourages good ordering. It often works reasonably for binary relevance; with fine-grained grades, mispredictions
      on mid-range labels can scramble ordering among top results.
    

    

      

        

          Training builds design matrix X of shape (N, F) and target vector y of grades.
          At inference, you sort by predicted score. Calibration of probabilities (if you use them) is a separate concern from rank quality.

04 · Pairwise Approach

    

      Pairwise methods learn from ordered pairs under the same query. For documents A and B with grades g_A and g_B,
      if g_A > g_B then the desired ranking places A above B. Many algorithms reduce this to classification on the difference vector
      x_A - x_B: positive label means “A should beat B.”
    

    

      RankSVM (Joachims) is the classic pairwise formulation: a large-margin classifier on difference vectors with a hinge-like loss,
      optionally weighted for higher-grade gaps. Modern tree boosting still exploits the same preference structure inside more flexible split rules.
    

    

      

        

          Pairwise transforms can explode the number of training rows (all comparable pairs per query). Subsampling hard negatives or pairs near decision boundaries
          keeps training tractable without sacrificing much accuracy.
        

      

      

        
pairwise_transform.py

        
def pairwise_rows(X, y):
    # X: (n_docs, F), y: grades for one query
    rows, labels = [], []
    for i in range(len(y)):
        for j in range(len(y)):
            if y[i] == y[j]: continue
            rows.append(X[i] - X[j])
            labels.append(1 if y[i] > y[j] else 0)
    return rows, labels

05 · Listwise — LambdaMART

    

      Listwise methods reason about the entire permutation or set of scores for a query at once. The metric of interest—often
      nDCG, MAP, or a business-weighted variant—is usually non-smooth in the scores, which complicates direct gradient descent.
    

    

      LambdaMART combines gradient boosted trees with lambda gradients: for each document, assemble a pseudo-response that approximates
      how much the list metric would improve if that document’s score nudged up or down relative to others, then fit a regression tree to those lambdas.
      The trick sidesteps differentiating nDCG directly while still optimizing list quality in practice.
    

    
Why LambdaMART dominates production reranking

    
    
      
  • Handles heterogeneous features and feature interactions via tree splits.
    • 
      
  • Trains quickly at moderate data sizes with XGBoost, LightGBM, or CatBoost LTR modes.
    • 
      
  • Interpretable via feature importance and partial dependence—valuable for debugging search.
    • 
    

    

      

        

          Training alternates: compute lambdas from the current scores and the metric’s sensitivities, fit a tree to predict those lambdas,
          update scores with a learning rate (boosting shrinkage), repeat until validation nDCG@k plateaus.
        

      

      

        
lambdamart_loop.txt

        
# conceptual loop
for round in range(num_trees):
    λ = lambda_gradients(scores, grades, metric='ndcg')

06 · End-to-End LTR Pipeline

    

      Shipping LTR is a systems story as much as a modeling story. The steps below mirror what teams run from first prototype to continuous improvement.
    

    
    
      
  1. Collect judgments (explicit labels or carefully debiased behavioral proxies).
    2. 
      
  2. Log features for every judged (query, document) using the same code path as live traffic.
    3. 
      
  3. Transform or pack data — pairwise differences for RankSVM, or raw matrices grouped by qid for boosting.
    4. 
      
  4. Train with query-level splits: hold out entire queries for validation and test so the model generalizes to new intents, not new documents for memorized queries.
    5. 
      
  5. Evaluate offline with nDCG@k, MAP, precision at one for navigational sets, and segment-specific slices.
    6. 
      
  6. Upload the model to your search serving layer (Solr LTR plugin, Elasticsearch learning to rank, OpenSearch plugins, custom rankers).
    7. 
      
  7. Deploy as a reranker: stage-one lexical or dense retrieval recalls hundreds of candidates; stage-two LTR rescores the top K.
    8. 
    

    

      The continuous loop: monitor ranking quality and engagement, refresh judgments, retrain, shadow-test, promote, repeat.
      Drift in queries or corpus without retraining slowly erodes gains.
