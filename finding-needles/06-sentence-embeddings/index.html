Sentence Embeddings — Sentence-BERT & Contrastive Learning

Word-level vectors help with lexical similarity, but search and matching usually need sentence- and passage-level meaning. Averaging word vectors is only a baseline. §0 From words to sentences

Static word embeddings such as those from Word2Vec or GloVe place individual word types into a vector space where cosine similarity correlates with substitutability and topical relatedness. That is already useful for query expansion, soft lexical matching, and feature engineering. Yet the object we usually rank in search is not a single token: it is a span of text—a sentence, a paragraph, a product description, a code comment. The natural question is how to go from word vectors to a single vector that represents a longer unit of meaning.

The simplest widely used baseline is to average (or weighted-average) the embeddings of all content words in the span, optionally dropping stopwords. This trick is surprisingly decent. Averaging cancels some noise, pulls the vector toward a “topic centroid,” and keeps inference trivially cheap. Many production systems have shipped exactly this pattern as v_doc = mean({ v_w : w in document }) because it requires no neural model beyond a lookup table.

Order blindness. A mean treats the bag of words as exchangeable. The classic failure mode is that "dog bites man" and "man bites dog" contain the same multiset of tokens, so any representation that depends only on per-word vectors and permutation-invariant pooling assigns them identical embeddings. Humans read these as very different events; a search engine that conflates them will return the wrong story under a literal bag-of-embeddings model.

The deeper issue is compositionality. Predicate–argument structure, negation, quantifiers, and long-range dependencies all change meaning while reusing the same vocabulary. Pooling static word vectors has no mechanism to privilege which token should dominate when interactions are non-linear. You can patch this with character n-grams (FastText-style), learned idf-style weights, or by moving to contextual word vectors—but the moment you need faithful sentence-level semantics for paraphrase, entailment, or answerability, you typically want a sequence model that reads tokens in order and builds a representation of the whole.

Sentence embeddings are that next step: a function f(text) → ℝd trained so that semantic nearness in language becomes geometric nearness under cosine similarity or Euclidean distance. Fine-tuning BERT-class encoders with contrastive objectives—Sentence-BERT—is the dominant approach; MTEB scores, Matryoshka prefixes, and quantization determine what you can deploy at scale.

§1 Sentence-BERT (SBERT)

BERT and its relatives produce contextual token representations. A naive approach to a sentence vector is to take the final hidden state of the special [CLS] token, or to mean-pool the token vectors of the content subsequence. That already beats static averaging in many semantic tasks because the network can disambiguate "bank" as riverbank versus financial bank using context. The problem is training: vanilla BERT is optimized for masked language modeling and next-sentence prediction—not for making cosine distances between arbitrary sentences correlate with human judgments of similarity.

Sentence-BERT fine-tunes a transformer encoder so its pooled output behaves like a similarity embedding. Architecturally, it uses a Siamese network: two sentences pass through the same BERT weights (parameter sharing), each producing a pooled vector. During training, a loss compares the two outputs; at deployment, you run the encoder once per text chunk, cache vectors in an index, and answer similarity queries with cheap vector math instead of re-running a heavy cross-attention model for every pair.

sentence A → BERT → pool → u   |   sentence B → BERT → pool → v

Pooling strategies matter because BERT’s token sequence includes subword pieces and special tokens. Common choices include:

  • [CLS] pooling: use the top-layer hidden state of the classifier token. Simple, but not always the best semantic summary of the full span.
  • Mean pooling over the token representations of the actual words (masking out padding) is the common default in many sentence-transformers checkpoints.
  • Max pooling over the time dimension takes a coordinate-wise maximum; it can emphasize salient features but is less standard for general sentence similarity.
Bi-encoder (SBERT-style)
Encode A and B independently; score with cos(u, v). Pre-compute corpus vectors once, then answer each query with one forward pass plus vector search.
Cross-encoder
Concatenate A and B with separators; cross-attention reads both sides. More accurate for pairwise scoring, but one heavy forward pass per pair— impractical for exhaustive search over large corpora without a bi-encoder first stage.

Why Siamese weight sharing?

Sharing parameters guarantees that u and v live in the same semantic coordinate system. Two independent encoders could each learn arbitrary rotations of space; similarity would be meaningless without careful alignment. A single encoder ensures that a cached embedding from last week is comparable to one computed today.

§2 Training objectives — contrastive learning

Contrastive learning is the family of losses that reward agreement between positive pairs and penalize confusion with negatives. For embeddings, pull synonyms, paraphrases, and entailed sentences together while pushing unrelated or contradictory neighbors apart. The geometry you get is only as good as your definition of positive and negative, which is why data curation rivals architecture in importance.

Triplet loss is the classic formulation. Given an anchor a, a positive p that should be close, and a negative n that should be farther away, you define a margin m and penalize violations:

L_triplet = max(0, ||a − p||² − ||a − n||² + m)

If a is already closer to p than to n by at least the margin, the loss is zero. Otherwise the model is pushed to shorten ||a − p|| and/or lengthen ||a − n||. In cosine space, variants replace Euclidean distance with angular distance or combine normalization explicitly.

InfoNCE (noise-contrastive estimation; a popular instance is NT-Xent with temperature) turns classification on its head: for each anchor in a mini-batch, treat the paired positive as the correct class among many negatives. The “trick” is to use other in-batch examples as negatives for free. Larger batches yield more negatives and often sharper learning signals—at the cost of memory.

L_InfoNCE = −log exp(sim(a,p)/τ) / (exp(sim(a,p)/τ) + Σk exp(sim(a,nk)/τ))

Multiple Negatives Ranking Loss (MNRL) is the workhorse default in the sentence-transformers ecosystem for retrieval-style training. Given a mini-batch of (query, passage) pairs, each query should rank its paired passage above all other passages in the batch. Like InfoNCE, it exploits in-batch negatives; unlike hand-authored triplets, construction scales to enormous supervised datasets as long as you trust the pairing labels.

Hard negative mining addresses a limitation of uniform random negatives: they are often too easy. If negatives are almost orthogonal already, gradients vanish and the model stops improving at the decision boundary you care about. Strong systems mix mined hard negatives (top results from a baseline retriever that are not actually relevant), sometimes with controlled ratios to avoid collapse where everything is pushed apart infinitely.

Typical training sources include natural language inference corpora such as SNLI and MultiNLI (entailment as a strong positive class), large paraphrase collections, and internal click or human relevance judgments formatted as labeled pairs or triplets. The mapping from business logs to contrastive labels is itself a design problem: clicks are noisy positives; non-clicks are not reliable negatives.

§3 The MTEB benchmark

Massive Text Embedding Benchmark (MTEB) standardizes how embedding models are compared across many task types. Instead of declaring victory on a single semantic textual similarity set, MTEB aggregates performance over a menu of evaluations that stress different capabilities: pairwise similarity, classification, clustering, retrieval, reranking, bitext mining, and more.

Representative task families include:

  • STS — semantic textual similarity: predict relatedness scores for sentence pairs; Spearman correlation to human judgments is a common metric.
  • Classification — embed training examples, train a linear classifier (or kNN) on frozen vectors; measures whether clusters are linearly separable for known labels.
  • Clustering — group embeddings with algorithms like k-means; evaluate with V-measure or similar against gold partitions.
  • Retrieval — given a query embedding, rank a corpus of passages; nDCG, MRR, and Recall@k quantify whether the right items float to the top.
  • Reranking — score candidate lists more finely than pure vector search typically allows; still tests geometry, but often with shorter lists and richer supervision.
  • Pair classification — threshold cosine similarity or train a shallow head to predict duplicate vs not-duplicate.
  • Summarization / long-document tasks — stress pooling and context length behavior when inputs exceed a single sentence.

No single winner is an empirical regularity: a model that dominates short paraphrase similarity might underperform on bitext retrieval or clustering. Latent causes include training data mixture, sequence length limits, pooling choices, and whether the model was instruction-tuned for asymmetric retrieval (query vs document prefixes). MTEB makes those tradeoffs visible instead of collapsing them into one marketing number.

Choosing a model is engineering, not astrology. Increase dimension and width when recall quality is the bottleneck; shrink them when latency, memory, or cost dominate. Always validate on your distribution: a leaderboard aggregate is a prior, not a substitute for measuring end-to-end retrieval on your corpus and query stream.

§4 Matryoshka Representation Learning (MRL)

Classical sentence embeddings pick a fixed width d ∈ {384, 768, 1024, …}. That commitment propagates to vector databases, caching layers, and mobile clients. Often you do not need all dimensions for a first-stage filter, yet training a separate model per width is wasteful. Matryoshka Representation Learning attacks the rigidity directly: train the vector so that any prefix [u₁, …, uk] is itself a useful embedding for smaller k.

The training trick is multi-head supervision. Instead of applying the contrastive or ranking loss only on the full d-dimensional output, apply the same family of losses simultaneously on truncated prefixes—say at k ∈ {64, 128, 256, … , d}—with shared trunk parameters. The network learns to pack the most discriminative information into early coordinates, like progressive JPEG coefficients but for semantics.

Reported benefits include storage efficiency: a 256-dimensional prefix can approach the quality of a full 768-dimensional standard embedding from a non-Matryoshka model, reducing footprint by a multiplicative factor. When combined with scalar or binary quantization, the savings compound: shorter vectors mean fewer bytes per passage even before aggressive compression.

Binary quantization on top. After MRL gives you a short float vector, product quantization or per-dimension binarization can map each dimension to one bit, yielding extremely compact sketches. A 256-float vector at 4 bytes per coordinate is 1 KiB; 256 bits is 32 bytes—a 32× reduction before accounting for metadata. The cost is approximation error; hybrid pipelines use compressed vectors for candidate generation and fall back to higher precision for rescoring.

§5 Scalar and binary quantization for embeddings

Uncompressed float32 storage allocates four bytes per coordinate. A 768-dimensional embedding therefore costs about 768 × 4 = 3072 bytes before compression or alignment overhead. Multiply by a billion documents and you are planning datacenter footprints, not notebook demos.

Scalar quantization maps each float to a lower-bitwidth type. float16 halves storage; bfloat16 trades precision range differently on hardware accelerators. int8 quantization stores one byte per dimension, often with per-vector or per-channel scales and zero-points so that dot products approximate the full-precision inner product. These schemes keep vectors in floating-friendly formats for SIMD while shrinking bandwidth.

Binary quantization goes further: each dimension becomes a single bit (or blocks are encoded with compact codes), reducing inner products to popcount-friendly operations. A 768-dimensional binary sketch uses 768 bits = 96 bytes—about 32× smaller than float32 for the same nominal width. The representational capacity collapses, so recall@k for pure binary distance may dip unless you widen dimensions or add rescoring.

When scalar int8 shines
You want a smaller memory footprint but still need graded similarity for top-k vector search with minimal changes to scoring code beyond scale factors.
When binary sketches shine
You need extreme compression for first-stage hashing or on-device caches, and you can afford a second stage with higher precision or a cross-encoder.

Rescoring pattern: retrieve candidates with quantized inner products or Hamming distance, then re-evaluate the short list with float32 dot products—or even a cross-encoder— to reorder. The expensive operator runs on tens or hundreds of items, not millions.

§6 Fine-tuning your own embedding model

Off-the-shelf checkpoints are trained on web-scale mixtures that may not respect your jargon, SKUs, regulatory language, or code idioms. When in-domain errors cluster systematically— confounding library names, legal clauses, or sensor telemetry labels—it is time to fine-tune rather than endlessly prompt-engineer a frozen encoder.

Data formats mirror the losses above. The minimal supervised unit for ranking losses is a (query, positive passage) pair. Triplets add explicit (query, positive, negative) tuples; negatives may be random in-batch, mined hard negatives, or both. Some teams augment with synthetic pairs from smaller language models with human spot-checking; others distill from a slower teacher cross-encoder that labels hard pairs for the student bi-encoder.

The sentence-transformers training loop, at a high level, is: sample a batch of texts, tokenize with the model’s word-piece vocabulary, run the transformer trunk, pool to vectors, compute a batch-wise contrastive or ranking loss, backpropagate into shared weights, and step the optimizer. Mixed-precision training and gradient accumulation are common when effective batch sizes need to be large for MNRL.

Evaluation during training should track both in-domain retrieval metrics (perhaps on a held-out click log formatted as qrels) and a stable external sentinel such as a small STS subset. Watching only loss curves is risky: contrastive objectives can overfit to batch negatives without improving real recall. Periodic full-index evaluations are expensive but catch regressions early.

Practical knobs

  • Batch size — directly controls how many negatives each query sees in MNRL; often the first lever to pull when learning stalls.
  • Temperature — sharpens softmax contrasts; interacts with batch size and learning rate.
  • Learning rate & schedule — transformer fine-tuning is sensitive; cosine decay with warmup is a frequent default.
  • Hard negatives — add difficulty as the model improves; curriculum schedules can stabilize early training.
