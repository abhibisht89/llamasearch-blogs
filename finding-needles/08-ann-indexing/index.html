ANN Indexing — FAISS, HNSW, IVF & Product Quantization

Modern semantic search stores millions or billions of embedding vectors. Exact k-nearest-neighbor search is linear in corpus size and dimensionality: O(N × d) inner products or distances per query. Approximate nearest neighbor (ANN) methods reshuffle the problem: accept a small miss rate in exchange for orders-of-magnitude higher queries per second and lower memory. This page walks through the ideas that power libraries like FAISS—from hashing and clustering graphs to aggressive vector compression— with interactive sketches you can manipulate.

§0 The nearest-neighbor problem

You are given a query vector q ∈ ℝd and a static collection of N vectors {x1, …, xN}, all in the same space. The task is to return the k vectors whose similarity to q is highest—typically under inner product (for length-normalized embeddings, equivalent to cosine similarity) or L2 distance, depending on convention. In information retrieval, q might encode a user question while each xi encodes a passage; the neighbors are your candidate documents before reranking.

The brute-force algorithm is conceptually perfect: compute the score between q and every database vector, keep the top k with a heap. Its cost is O(N × d) arithmetic per query, plus O(N) memory bandwidth if vectors live in RAM. That is entirely reasonable when N is in the thousands and d is a few hundred—many prototypes and offline evaluations run exactly this way. It collapses when N reaches tens of millions or billions: a single query would touch the entire corpus, blowing latency and power budgets.

Brute force cost per query ≈ N distance computations × d multiply-adds each → scales linearly with corpus size.

Approximate nearest neighbors deliberately relax the guarantee. Instead of promising the mathematically exact top-k, an ANN index returns a list that usually overlaps heavily with the true top-k. Quality is measured by recall@k: the fraction of true top-k neighbors that appear in the approximate result set. A recall@10 of 0.95 means five percent of the time you drop a genuinely relevant item from the initial candidate pool—often acceptable if a later reranker or second-stage retrieval can recover it, or if tail misses are rare enough for the product.

The operating point. Almost every deployment chooses a point on the frontier between recall@k (higher is safer) and queries per second / tail latency (higher is cheaper). More aggressive compression, fewer graph hops, or smaller nprobe in IVF shifts you toward speed; increasing probe counts, ef_search in HNSW, or using Flat sub-indexes inside clusters pulls you back toward accuracy. No single knob is “correct”—only faithful to your SLOs and hardware budget.

Common ANN families include random-projection hashing (LSH), k-means partitioning (IVF), navigable graphs (HNSW), and codebook compression (PQ). Real systems stack these ideas; FAISS exposes them as composable index types and string factories so you can experiment without reimplementing low-level kernels.

§1 Locality-sensitive hashing (LSH)

LSH families map vectors into discrete buckets such that close points collide with higher probability than far points. A classic construction for cosine similarity uses random hyperplanes. Draw a random direction r ∈ ℝd; for any vector x, output one bit according to which side of the hyperplane orthogonal to r the point lies on. Equivalently, take the sign of the dot product: h(x) = sign(r · x) (with a tie-breaking rule). Vectors that are nearly aligned with each other tend to share the same sign pattern across many random r, so they land in the same bucket more often than orthogonal or opposite vectors.

A single hash bit is a coarse partition of space. To tighten the decision boundary, concatenate several independent bits from different random directions into a hash code. Points that match on many bits are candidates for being near neighbors. To improve recall, you maintain multiple hash tables, each built with a different draw of random hyperplanes. A query is hashed under each table; the union of buckets visited forms the candidate set, which is then rescored exactly (or with a cheaper proxy).

Strengths
  • Conceptually simple; no training pass required beyond sampling r.
  • Applies in any dimension; geometry is agnostic aside from dot-product structure.
  • Parallelizes naturally across tables and buckets.
Weaknesses
  • High recall often demands many tables—memory and query-time lists explode.
  • Candidate sets can be noisy; heavy rescoring may eat the savings.
  • For competitive accuracy on dense embeddings, graph and quantization methods often win on the same hardware budget.

§2 Inverted file index (IVF)

IVF borrows the spirit of an inverted index from text search: instead of posting lists per term, you attach vectors to clusters. Train nlist centroids (prototypes) on a representative sample of the corpus—almost always via k-means in embedding space. Each database vector is assigned to its nearest centroid. At query time, you compute distances from q to all centroids (cheap when nlist is thousands, not millions) and only search inside the closest nprobe clusters. Unvisited clusters are ignored, which is where the approximation enters: a true nearest neighbor might live one cluster over if the Voronoi boundary cuts awkwardly.

Building the index is a pipeline: subsample if needed, run k-means to obtain centroids {c1,…,cnlist}, then second-pass assignment of every vector to argminj ‖x − cj‖ (or inner-product equivalent). Some implementations store residuals x − cassign(x) for finer quantization inside the cluster. Searching ranks centroids by distance to q, merges inverted lists for the top-nprobe cells, and runs distance computations only on those vectors.

nprobe = 1 → fastest, lowest recall; nprobe = nlist → degenerates toward exhaustive search over lists (still can skip structure if you visit everything).

The parameter nprobe is the smooth dial on the accuracy–latency curve. Production systems often benchmark recall@k versus p99 latency while sweeping nprobe, then freeze a setting that meets the retrieval stage’s contribution to end-to-end error. When combined with PQ or HNSW inside each cluster, the same outer IVF skeleton still applies: first select cells, then run a specialized inner index.

§3 HNSW — hierarchical navigable small world

HNSW builds a multi-layer graph reminiscent of a skip list. The bottom layer contains every vector as a node, connected to up to M neighbors chosen by a heuristic that balances proximity and graph connectivity. Higher layers subsample nodes; edges at upper layers create long “highway” jumps across the manifold. To insert a new point, the algorithm enters at the top layer, greedily walks toward the new vector’s neighborhood, then descends layer by layer, refining the position until it reaches layer zero and wires local links.

Search mirrors insertion: start from an entry point at the highest layer, repeatedly move to the neighbor that most improves the objective (greedy hill-climbing in the graph), drop down when no local improvement remains, and continue until layer zero. A priority queue of explored candidates widens the search beyond pure greediness: the ef_search parameter controls how many alternative vertices are considered, trading extra work for higher recall. During construction, ef_construction plays an analogous role for link quality. M caps degree, influencing both index size and graph navigability.

Why HNSW is popular. On many embedding workloads it sits near the Pareto frontier of recall@k versus query latency without requiring a separate training clustering phase (though hybrid indexes may still use one). Implementations are mature, CPU-friendly, and well understood—making HNSW the default mental model for “graph ANN” in vector databases and in FAISS when memory allows full-precision graphs.

§4 Product quantization (PQ)

A float32 embedding of dimension d = 768 costs 768 × 4 = 3072 bytes before metadata. Multiply by a billion vectors and you are in terabytes of RAM. Product quantization attacks this by factoring the vector into m contiguous subvectors—commonly m = 8 blocks of 768 / 8 = 96 dimensions each. Each block is compared independently to a small codebook of k centroids learned by k-means on that subspace. The index of the nearest centroid requires only log₂(k) bits; with k = 256, that is exactly one byte per subspace, hence 8 bytes total for the whole vector’s quantized signature instead of three kilobytes.

Distance between a database code and a query is approximated by table lookups. In asymmetric distance computation (ADC), the query stays in full precision (or a higher bit width). For each subspace, you precompute the distance from the corresponding query slice to every centroid in that subspace’s codebook—O(m × k × d/m) = O(m k d/m) per query setup—then sum the distances indicated by each stored code. Database vectors never need to be fully decompressed for scoring against that query.

Storage per vector ≈ m × ⌈log₂ k⌉ bits (plus index overhead). Example: m=8, k=256 → 8 bytes + tables.

§5 Composite indexes

Production indexes rarely use a single trick in isolation. IVFPQ is the canonical large-scale recipe: IVF reduces the number of vectors examined by partitioning, while PQ compresses residuals (or full vectors) inside each posting list so distance computations are cheap and memory footprint stays bounded. At search time you decode only the buckets you probe—amortizing the cost of wide codebooks.

IVF + HNSW combinations appear when centroid assignment itself becomes expensive at very large nlist: a secondary HNSW (or other ANN) on centroids accelerates the routing stage, so the query quickly finds which clusters merit a deep search. IVF + scalar quantization (SQ) trades off higher per-dimension bitrate than PQ but simpler decode paths—sometimes a win when dimensions are moderate and CPUs dislike random lookup patterns.

FAISS exposes many of these compositions via index factory strings. Examples: "IVF4096,PQ32" for an IVF with 4096 lists and a 32-byte (or subcode) PQ configuration as specified by the factory parser; "HNSW32" for an HNSW graph with parameter M=32 in the usual naming; "IVF1024,SQ8" for IVF buckets with 8-bit scalar-quantized vectors. Exact string grammar evolves with versions—treat the factory as a concise shorthand, not a substitute for reading the release notes when upgrading.

Quick heuristic (starting point only):
• N < 10⁴ → IndexFlatIP / IndexFlatL2 (exact, simplest).
• 10⁴ – 10⁶ → IVF + Flat or HNSW if memory allows.
• 10⁶ – 10⁸ → IVFPQ, IVFSQ, or product variants + careful nprobe tuning.
• > 10⁸ → sharding, distributed FAISS, or a hosted vector database with replication and I/O-aware placement.
Always validate on your embedding model and query distribution—geometry and noise differ across domains.

§6 FAISS in practice

Facebook AI Similarity Search (FAISS) is a library of highly optimized CPU and GPU kernels for clustering, quantization, and graph search. It is not a database—no transactions, no multi-tenant access control—but an engine you embed in an indexer service. The conceptual lifecycle is: index.train() on a training matrix (centroids, codebooks, or graph statistics depending on index type), index.add() to ingest database vectors in batches, and index.search() to retrieve neighbors for query matrices.

faiss-gpu mirrors many index types and can overlap computation across streams when datasets fit device memory. The winning configuration depends on PCIe bandwidth, batch size, and whether queries are synchronous—GPU indices shine on high-throughput, batch-oriented workloads.

§7 Scalar and binary quantization

Scalar quantization (SQ) stores each dimension in a low-bit integer after per-dimension (or per-vector) affine scaling—commonly float32 → int8 using min/max or learned scale/zero-point parameters. It is simpler than PQ structurally because there is no subspace codebook at query time beyond the linear transform, but bitrate per dimension is higher than PQ at comparable distortion when d is large.

Binary quantization collapses each dimension to one bit—often the sign of the coordinate after some centering or rotation. Hamming distance on binary strings is extremely cheap and SIMD-friendly. Accuracy per bit is poor for a single dense embedding, but when models emit Matryoshka-style high-dimensional representations where early dimensions already carry coarse geometry, sign bits can act as a fast filter. A practical pattern is rescoring: use binary codes (or another aggressive index) to generate a shortlist, then reorder those candidates with full precision float inner products.

Pre-launch validation

  • Measure recall@k against a held-out query set with exact Flat labels.
  • Profile tail latency under concurrent queries, not just average QPS.
  • Version embedding model and index together; changing one invalidates the other’s calibration.
  • Plan for incremental adds: some graph indexes prefer batch rebuilds; IVF lists can grow unevenly.
