Agentic Search — LLMs That Search for Themselves

When the model does not merely answer from memory but actively retrieves, rewrites, and re-queries until evidence is sufficient, search becomes a closed loop inside the model’s reasoning process.

Chapter 25 · Finding Needles

00 · The Paradigm Shift

Classic search is linear: a person types a query, the system returns a ranked list, and the person reads and synthesizes. Retrieval and interpretation are separate steps—the engine finds candidates; the human assigns meaning.

Agentic search closes that loop inside the model stack. The model consumes retrieved text, writes follow-up queries, judges result quality, and decides when to stop: query → retrieve → read → decide → (maybe) query again. Agency migrates from the end user to the model, or is shared between them.

In practice the agent chooses what to search, how to read noisy snippets, and when to stop—decisions classical IR systems leave to the caller. A search engine scores documents; an agent must sometimes treat evidence as sufficient, insufficient, or in need of corroboration.

The primary consumer of search APIs may no longer be a human skimming blue links. The same inverted index can serve both audiences, but evaluation metrics diverge: click-through and dwell time versus grounding fidelity, citation coverage, and hallucination rate on multi-hop tasks.

Search for humans versus search for agents

Humans tolerate ambiguous UI copy; agents need explicit structure—source IDs, timestamps, licensing hints, and clear boundaries between quoted evidence and paraphrase. Latency expectations differ too: sub-second feedback for exploratory typing versus multi-second tool rounds when an autonomous job prioritizes answer quality. Oversight moves to policy, logging, and trace review rather than per-query formulation.

Accountability shifts with synthesized answers. Agent prose reads authorial even when derivative, so provenance and replayable traces become requirements for anyone who must explain why a claim appeared—not only for engineers debugging failures.

Throughput scales differently as well. A batch agent may fire thousands of queries per minute on one API key. Rate limits, caching, deduplication, and fair-share scheduling must treat orchestrators as first-class traffic, not only individual keyboard users.

01 · The Tool-Use Paradigm

Modern assistants expose tools to the model: web search, SQL, vector retrieval, HTTP to internal services, or sandboxed code. The weights need not store every fact if the model can invoke the right tool with validated arguments.

The ReAct pattern iterates Reason (trace intent), Act (structured tool call), Observe (ingest tool output), then repeat. Observations differentiate tool use from a single-shot prompt; each one updates context for the next step.

Implementers typically define tools with JSON schemas or vendor-specific descriptors: function name, argument types, and human-readable descriptions the model uses as its “menu.” At runtime, the host application parses model output, validates it against the schema, executes the side effect, and returns a string or structured payload back into the chat. Vendors label this differently—function calling (OpenAI-style), tool use (Anthropic-style), or open pipelines where the model emits code that a runner executes—but the abstract contract is stable: the model proposes; the runtime disposes.

Robust systems cap tool calls per turn, allowlist hosts, redact secrets from observations, and enforce timeouts. Validation layers must treat every tool call as untrusted input—even from the local model.

Two details often decide production success: observation serialization (raw HTML, cleaned text, JSON, or capped windows) and error surfaces (how timeouts and failures are returned to the model). Opaque failures invite hallucinated filler for empty observations.

Open-source stacks sometimes let the model emit executable code instead of rigid function JSON. That increases expressiveness for multi-step data wrangling but complicates sandboxing and determinism. Hybrid designs expose a small set of audited primitives to code (safe query builders, HTTP GET to allowlisted domains) rather than arbitrary system calls. The principle is unchanged: constrain the act channel so the observe channel remains trustworthy.

02 · Multi-Hop Retrieval

Some information needs are single-hop: one well-formed query retrieves a definition, a date, or a canonical name. Others are irreducibly multi-hop: answering requires chaining entities and constraints that no single document states outright. Compare “What is BM25?” with “Compare GDP growth for countries that joined the EU after 2004.” The second forces membership resolution, temporal alignment of statistics, and a fair comparison axis—none of which reliably appear in one snippet.

A common strategy is query decomposition: ask the model to emit a checklist of sub-questions, answer each via retrieval, then synthesize with explicit stitching logic (or another model pass). An alternative is chain-of-search, where each retrieval informs the phrasing of the next query, without a fully enumerated plan up front. Decomposition favors transparency and parallelization; chaining favors adaptability when the space of needed evidence is unknown until partial results arrive.

Without a budget, models spiral—rephrasing endlessly or repeating failed queries. Production stacks use step caps, duplicate-query detection, confidence heuristics, and sufficiency rubrics from a verifier pass. Most deployments rely on simple, auditable rules over learned stopping policies.

Evaluation for multi-hop setups often combines precision of intermediate facts with end-to-end answer correctness. A system can ace the final string while silently baking in a wrong middle hop; trace logging and intermediate supervision catch that failure mode earlier than aggregate accuracy alone.

Parallel decomposition is not always safe. Sub-questions may share hidden dependencies—resolving an entity in hop A changes the interpretation of hop B. Agents mitigate this with sequential gating (run B only after A’s entities are fixed) or with consistency checks that compare merged graphs of entities before synthesis. These checks resemble database normalization for natural language: redundant paths should agree, or the agent should fetch another source rather than averaging contradictions.

When corpora are proprietary, multi-hop retrieval also raises access control issues. Different hops might touch documents with different clearance levels. A responsible orchestrator propagates authorization context into each tool invocation and prunes observations before they ever enter the general context window. Agentic convenience must not become an accidental privilege-escalation path across siloed indexes.

03 · LLM Query Understanding

The retriever rarely sees the user's raw string. An agent runs query understanding first: intent classification, contextual expansion, decomposition into searchable units, and routing to the right index or tool—aligning natural language with how the corpus was chunked, stemmed, or embedded.

Query classification might distinguish navigational, definitional, transactional, or evidence-seeking requests—each implying different retrieval depth and snippet length. Query expansion adds synonyms, entity aliases, or temporal qualifiers inferred from dialogue state. Query decomposition splits a compound request into parallel retrievals that reduce cross-talk in dense vector spaces. Query routing sends legal clauses to a clause index, product specs to a structured catalog, and open-web background to a web search connector.

After retrieval, agents often perform context self-editing: discard redundant passages, down-rank off-topic paragraphs, or quote only spans that survive a salience model. If results are poor, the agent can retry with a narrower technical term, a different language, an explicit site restriction, or a pivot from keyword to vector retrieval. That feedback loop turns search from a single forward pass into a control system regulated by observations.

Query understanding is also where grounding contracts get negotiated. If the user’s utterance is underspecified, the agent might ask a clarifying question—or silently pick a disambiguation path and document it in the trace. Silent disambiguation is faster but riskier; explicit clarification is slower but auditable. Products differ on which default to privilege, and the right choice often depends on domain (medical, legal, and financial settings lean toward explicitness).

Multilingual queries add another layer. The agent may translate for retrieval, retrieve in the source language, or run cross-lingual embeddings. Each strategy changes error modes: translation drift versus tokenization mismatches versus culturally divergent snippets. A mature agentic stack records which path was taken so downstream grading knows whether to trust a translated span literally or only paraphrastically.

04 · Agentic Search Architectures

      

        Industry stacks increasingly expose retrieval surfaces tuned for LLM consumption—context packaged for grounding rather than pages
        optimized for browsing. The pattern is stable: evidence in machine-friendly slices with stable IDs and reproducible fetches.
      

      

        A canonical retrieval-agent loop looks like this: the user asks a question; the agent plans a search strategy (tools, order, stopping criteria); it executes one or more searches; it evaluates sufficiency; if evidence is thin, it refines queries and retrieves again; if evidence is adequate, it synthesizes an answer with explicit citations tying claims to sources. That loop can be monolithic (one model doing all roles) or modular (planner, retriever, grader, writer as separate prompts or services).

05 · Search for Humans vs Search for Agents

      

        Human-facing search optimizes for ten blue links, snippets, and visual diversity. Agent-facing search prefers
        structured payloads—URLs, titles, timestamps, extracted entities, calibrated scores—fields a model can copy or compare without visual
        heuristics.
      

      

        APIs reflect the split: HTML and incremental rendering for people; JSON or protobuf with stable schemas for agents.
        Human SERPs sometimes surface opposing viewpoints; grounding tasks may prefer authoritative redundancy over editorial breadth.

06 · The Future of Search

      

        Research explores end-to-end differentiable retrieval. Differentiable Search Indexes (DSI) and
        generative retrieval (models emitting document identifiers directly) blur the line between weights and indexes;
        updatability and provenance remain open engineering problems.
      

      

        Conversational agents may hide retrieval mechanics behind answers, shifting UX investment toward trace viewers, citation inspectors, and
        governance consoles rather than public SERPs.
      

      

        Continuous learning and privacy-preserving retrieval (federated indexes, on-device search, encrypted matching) add
        policy constraints alongside personalization. Human roles persist in curation, evaluation, and red-teaming—the open question is which loops require
        supervision when generation and retrieval fuse.
      

      

        Traditional search engines may become invisible for task-oriented queries embedded in agents, while discovery-oriented browsing (shopping, local
        exploration) keeps list-based interfaces. The stack splits: interfaces for people, structured APIs for machines, and shared compliance layers
        between them.
