00 · What is RAG?

Retrieval-Augmented Generation (RAG) is a pattern for answering questions with a large language model (LLM) after first retrieving text that is likely relevant to the user’s question. Instead of relying solely on weights learned during training, the model reads fresh, explicit context you inject into the prompt—typically passages from your own documents, help center, or internal wiki.

A plain LLM can sound authoritative while being wrong: it may hallucinate details, rely on stale knowledge frozen at training time, and offer no source attribution tied to your organization’s truth. RAG does not eliminate those risks, but it anchors generation in retrieved evidence rather than parametric memory alone.

The modern formulation traces to Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (2020), which trained a sequence-to-sequence model to condition on retrieved Wikipedia passages. Interest surged in 2023–2024 as chat-style LLM products went mainstream and enterprises demanded answers over private data with clearer provenance and update paths than periodic full retraining.

RAG is not one algorithm; it is an architecture with interchangeable pieces: chunking strategy, embedding model, vector store, prompt template, and the generator model itself. Getting value from RAG is usually less about picking a trendy vector database and more about disciplined pipeline design and measurement.

01 · The RAG architecture

Production RAG systems almost always separate work into two pipelines: ingestion (offline or batch) and query (online, per request).

Ingestion (offline)

documents → load → clean → chunk → embed → store in vector DB (often with metadata and access control).

Query (online)

user question → embed (same model as ingestion) → retrieve top-k → assemble context → LLM → answer (plus optional post-processing).

The default flow is retrieve, read, generate: fetch candidate evidence, place it in the prompt window, then synthesize a response that cites or paraphrases that material. Multi-hop retrieval, tool use, and structured filters extend this pattern but keep the same core shape.

02 · The ingestion pipeline

Document loading is the front door: PDFs, HTML pages, databases, API exports, tickets, wikis, and code repositories all land here. Each format needs reliable text extraction; layout-heavy PDFs and complex tables are notorious weak points without specialized parsers.

After extraction comes cleaning: strip boilerplate, normalize whitespace, optionally deduplicate headers/footers, and preserve structure hints (headings, lists) when your chunker can exploit them. Chunking splits text into retrieval units—size, overlap, and semantic boundaries strongly affect what the retriever can surface (Chapter 17).

Embedding turns each chunk into a vector using a chosen model; batch your calls, handle rate limits, and version the model id alongside stored vectors so re-embedding is reproducible. Vector storage persists vectors plus identifiers; choice of vector DB or search service involves latency, filtering, hybrid support, and ops maturity (Chapter 9).

Rich metadata—updated_at, author, product area, language, access tier—powers filtering, ranking boosts, and UI citations. Deduplication (exact and near-duplicate via embeddings or shingling) keeps indexes from being noisy with repeated policy PDFs or mirrored pages.

Orchestration frameworks such as LlamaIndex, LangChain, and Haystack provide connectors, abstractions, and evaluation hooks. They accelerate prototyping; production teams still own data contracts, evaluation, and failure handling beneath the framework surface.

03 · The query pipeline

At query time, the user’s text is embedded with the same embedding model and dimensionality as ingestion—mixing models without re-embedding yields meaningless similarity scores. Retrieval returns top-k neighbors (plus optional metadata filters), often followed by reranking with a cross-encoder for better precision at small k.

Context assembly formats chunks into a single string or structured message list: numbering sources, injecting titles, and truncating to the model’s context budget. The prompt template typically combines a system instruction, the context block, and the user question; clarity here directly affects faithfulness and refusal behavior.

The LLM generates an answer conditioned on that augmented prompt. Post-processing may extract citations, validate JSON, run a consistency check against retrieved text, or attach confidence signals for the UI.

04 · Prompt engineering for RAG

The system prompt should state the contract explicitly: answer only from provided context, cite source numbers, and refuse when evidence is insufficient. Vague instructions invite the model to fill gaps from parametric memory.

Context formatting benefits from numbered blocks ([1], [2]) and optional metadata lines (title, date) so the model can refer to sources unambiguously. A small set of few-shot examples in the system message—ideal answers given sample contexts—can lock in tone, citation style, and refusal patterns.

Add an explicit abstention rule: if the answer is not supported by the context, respond with a fixed phrase such as “I don’t know based on the provided documents.” Pair that with monitoring to ensure abstention is not overused because retrieval is broken.

For RAG, temperature and top-p are often kept low (roughly 0.1–0.3 for temperature) to reduce creative paraphrase that drifts from evidence; creative writing use cases may differ. Token budget management is non-negotiable: sum system prompt, instructions, retrieved chunks, tools output, and user message against the model’s context window, reserving headroom for the completion.

05 · RAG failure modes

RAG fails in recognizable clusters. Treating them separately helps instrumentation: log retrieval sets, prompt snapshots, and model outputs together so you can tell whether to fix search, chunking, prompting, or the generator.

Retrieval failures

  • Query–document mismatch: lexical or semantic gap so the “right” passage never ranks high.
  • Missing in top-k: answer exists in the corpus but not in the shortlist shown to the model.
  • Bad chunk boundaries: critical fact split across two chunks so neither looks relevant alone.

Generation failures

  • Hallucination with context: model invents details not entailed by passages.
  • Ignoring context: strong parametric answer overrides retrieved evidence.
  • Misreading correct chunks: wrong entity or number picked from valid text.

Integration failures

  • Lost in the middle: very long context reduces attention to mid-document evidence.
  • Contradictions: retrieved chunks disagree; model may pick arbitrarily or blend incorrectly.
  • Dilution: irrelevant chunks consume budget and distract the model.

06 · Guardrails

Input guardrails scan for prompt injection attempts (“ignore previous instructions”), off-topic abuse, and policy violations before expensive retrieval and generation. Output guardrails check for unsupported claims, missing citations when required, PII leakage, and toxic content.

Faithfulness checking asks whether each sentence (or the whole answer) is entailed by the retrieved set—using a smaller model, NLI-style classifiers, or citation-backed verification loops. Safety filters remain important even with good retrieval; grounding reduces but does not remove harmful completions.

Cost guardrails cap tokens per request, cache frequent queries and embeddings, deduplicate retrieval for similar questions, and throttle abusive clients. Monitoring should track retrieval hit rate, citation coverage, human thumbs feedback, latency per stage, and drift when documents or models change.

07 · RAG vs fine-tuning vs long context

RAG keeps knowledge external and refreshable: update documents and embeddings without touching base model weights; citations can point to real sources. Fine-tuning bakes patterns and facts into weights—great for stable domain jargon, formatting, or tone, but brittle for fast-changing corpora unless you retrain often.

Long-context models (very large context windows) invite “stuff everything in the prompt” strategies when corpora are small; latency and cost scale with tokens, and models may still attend unevenly across the window.

When RAG shines

Frequently updated knowledge, need for traceability, cost control via small k, and hybrid filtering over metadata.

When fine-tuning shines

Stable domain knowledge, consistent output schema, style transfer, or teaching specialized reasoning formats.

These approaches are complementary: a fine-tuned or instruction-tuned model can enforce citation and refusal behavior while RAG supplies updatable facts from your corpus.
