Building a WaveNet

From a flat character MLP to a hierarchical, WaveNet-style autoregressive model: more context, progressive fusion, modular torch.nn-like layers, and the shape gymnastics that make it work.

8Interactive Demos
1Playground

This chapter extends the makemore-style character model: you recap the three-character MLP, widen context to eight characters, then replace “squash everything at once” with a binary tree of fusions—FlattenConsecutive, batched linear layers, a fixed BatchNorm1d for 3D tensors, and a Sequential container so logits = model(x) reads like real PyTorch.

00

Recap: flat MLP, three characters → fourth

Earlier chapters built a flat character MLP: three context characters embedded, flattened, then Linear → BatchNorm → tanh → Linear for next-character logits (see Multilayer Perceptrons and BatchNorm). The same sliding-window (X, Y) builder and training loop carry forward here—only block_size and the layer stack change.

Core constraint of the flat design: every bit of context is multiplied by one large weight matrix in the first linear layer. Adding context length grows that matrix quickly; more importantly, the model has no structured way to combine local patterns before mixing everything globally.

Forward path (conceptual)

Integers xb with shape (batch, block_size) become (batch, block_size, n_embed) after Embedding, then (batch, block_size * n_embed) after flatten, then (batch, n_hidden) after the first linear layer.

forward sketchshapes
1xb: (B, T)   # T = block_size, integer token ids
2emb: (B, T, C)   # C = n_embed
3flat: (B, T*C)   # one vector per example
4h: (B, n_hidden)
5logits: (B, vocab_size)

BatchNorm and “state”: running mean and variance update on every forward pass via an exponential moving average, outside the usual gradient update. You must respect training vs eval; you often need running statistics to settle; and because normalization pools over the minibatch, examples are no longer statistically independent inside a step. Stateful layers are powerful—and easy to misuse when the net is left in the wrong mode during validation or sampling.

01

Goal: more context, deeper fusion

Two ambitions drive the redesign. First, use more than three characters of context so predictions can depend on a longer prefix. Second, avoid crushing all positions into one layer immediately—instead, build a deeper network that progressively fuses information: local pairs, then pairs of pairs, and so on, until a single vector is ready for the final prediction.

That inductive bias matches how hierarchical structure appears in sequences: bigrams inform trigrams, which inform longer spans. A single huge linear map from “all embeddings concatenated” can still learn, but it allocates parameters less structurally; the hierarchical layout makes the computation tree explicit.

You can always add more ordinary hidden layers after the giant first projection, but that does not fix the basic issue: all eight (or more) character embeddings are still combined in one shot at the shallowest level. Making that first matrix wider adds neurons; it does not change the fact that the network waits until the bottom of the stack to mix long-range context in a structured way. The WaveNet-style picture instead fuses two at a time, then fuses the resulting pairs, then fuses those groups—so depth buys you a schedule of who talks to whom, not only a deeper sandwich after a single flatten.

You might wonder whether “deeper” always beats “wider.” Not automatically: depth changes how representations compose; width changes how many features exist at each stage. The WaveNet picture motivates depth with locality—each stage mixes only neighboring summaries, so the network must build longer-range structure through repeated fusion rather than one abrupt projection.

02

WaveNet (2016): same autoregressive job, different modality

The WaveNet architecture (van den Oord et al., DeepMind, 2016) models raw audio waveforms autoregressively—P(x_t | x_{<t})—the same next-step objective as character-level name modeling, only the symbols are acoustic samples instead of letters. The published diagram shows a tree-like hierarchy: merge past information in stages rather than one fat input projection. Dilated causal convolutions widen the receptive field exponentially while preserving causality (no peeking at future samples); they are an efficient implementation of repeated local fusion, not a separate conceptual story.

y_t = f(x_{t-L}, …, x_{t-1})  with causal masks so ∂y_t/∂x_s = 0 for s ≥ t

Autoregressive = predict next element from a finite past; “causal” enforces that past-only dependence.

03

Hierarchical structure and dilated convolutions

In a dilated causal stack, each layer can attend to inputs spaced farther apart—dilation inserts gaps between taps of the filter. Stacking layers with dilation 1, 2, 4, 8, … yields a wide receptive field with depth logarithmic in the window size. That is the “scary name” for a simple idea: combine neighbors, then neighbors of neighbors, at increasing distance.

(a *_{d} k)_i = Σ_j a_{i - d·j} · k_j  (causal 1-D, dilation d)

04

From flat MLP to hierarchical fusion

The implementation path is deliberate: keep Embedding and activations familiar, replace full flatten with pairwise grouping, and use the fact that torch.matmul applies the matrix on the last dimension while leaving leading dimensions as batch axes. That lets you fuse all adjacent pairs in parallel across both batch and position.

05

Increasing block_size from 3 to 8

Changing block_size rebuilds the dataset: each example now provides eight context characters and asks for the ninth. Parameter count jumps because the first linear layer’s input dimension scales with block_size * n_embed in the flat layout—even before you switch to hierarchical fusion. On a typical names corpus, bumping context from three to eight characters increases the first-layer fan-in and can add on the order of ~10 000 extra parameters in that matrix alone compared to the three-character setup—before you change hidden width or depth.

On a typical names corpus, the sliding window over words produces on the order of ~182k training tuples when block_size = 3; increasing block_size changes how many partial windows each word contributes, so N moves accordingly (see the MLP chapters for the full (X, Y) builder).

Empirically, simply giving the flat MLP more context often improves validation loss before any architectural fancy footwork: the model has more signal about the prefix. Treat that as a baseline: scaling context is a legitimate win; the hierarchical design is about how you spend parameters and compute on that wider window.

Concrete numbers from a typical run: with three-character context, validation loss might sit around 2.10. After rebuilding the dataset with eight characters but keeping the flat MLP, validation can drop to about 2.02—a clear gain from context alone. Qualitatively, samples usually look more name-like at that point. The hierarchical rebuild is then compared against this stronger baseline, not against the old three-character model.

Row counts move when you change block_size: one representative build produced X.shape[0] == 228 146 for eight-character contexts, while the three-character build on the same corpus sat near 182 000 rows. The relationship is not monotonic in a simple closed form—it depends on word lengths, how start tokens pad short prefixes, and how you count boundary positions—so always print X.shape after rebuilding the dataset rather than assuming.

A useful performance log keeps a few scalars per experiment: block_size, parameter count, best validation loss, and qualitative samples. Without a harness, you still learn—but comparisons across runs stay fuzzy. Later chapters can formalize sweeps; here the focus stays on architecture and tensor shapes.

06

Modular layers: Linear, BatchNorm1d, Tanh, Embedding, FlattenConsecutive, Sequential

Each building block exposes parameters() and a forward method, mirroring torch.nn.Module ergonomics. Linear wraps matmul plus optional bias; BatchNorm1d tracks running mean and variance; Tanh is elementwise; Embedding is a lookup table; FlattenConsecutive reshapes without copying memory.

Sequential is a container: it holds an ordered list of layers and forwards input through each in turn, aggregating parameters from children. Once the model is a Sequential, training and sampling both become logits = model(x)—provided you remember training flags for batch norm.

Gotcha after the refactor: if you rename layers to model but reuse a stale object from before the rebuild, weights may not match the code you are editing—and batch norm may stay in the wrong mode. After any structural change, reconstruct the model and set evaluation flags before trusting loss or samples.

Sequential container

Sequential is a container module: it composes child layers and aggregates their parameters. A plain Python list is not enough—a list does not recurse into children for parameters() or nest cleanly inside other containers.

makemore.pySequential
1class Sequential:
2    def __init__(self, layers):
3        self.layers = layers
4    def __call__(self, x):
5        for layer in self.layers:
6            x = layer(x)
7        return x
8    def parameters(self):
9        return [p for layer in self.layers for p in layer.parameters()]

Initializing a single global torch.Generator (instead of ad-hoc generators inside each layer) keeps seeding predictable while you iterate on the model. The pattern mirrors how small libraries centralize RNG state before scaling up training code.

Pulling the embedding table C and the old manual view into modules is mostly housekeeping: Embedding wraps the integer index lookup; Flatten (or the full-sequence flatten you had before FlattenConsecutive) wraps the reshape that concatenates character vectors along the last axis for free when memory is contiguous. Once those sit in the layer list, the training loop’s forward pass can start from raw xb integers and become a single composed call—same numerics, fewer lines, fewer places to forget a step.

Embedding: table lookup

The embedding matrix has shape (vocab_size, n_embed). Integer indices in x select rows; the output preserves all leading dimensions and appends n_embed. In PyTorch, nn.Embedding wraps the same idea with additional options (padding indices, sparse gradients, etc.).

Linear: last-axis multiply

Weights (fan_in, fan_out) multiply the last dimension of the input. Bias broadcasts over all batch axes. Scaling initialization down on the final logits layer avoids starting confidently wrong when the vocabulary is large.

makemore.pyLinear · forward
1self.out = x @ self.weight + self.bias
2return self.out

BatchNorm quirks (recap): running statistics update outside plain backprop; train vs eval behavior differs; and the layer couples examples within a minibatch to estimate variance. State in modules is powerful—and easy to get wrong when you forget model.eval() or reuse a cell that left training=True.

07

FlattenConsecutive: pack neighbors on the last axis

Given (B, T, C), the old Flatten did view(B, T*C). FlattenConsecutive(n) instead forms (B, T/n, n*C) when n divides T, treating each group of n consecutive positions as a single fat feature vector for the next linear layer.

If T/n == 1, the middle dimension is a spurious 1 and can be squeezed back to (B, n*C) so the API stays compatible with earlier two-dimensional tensors. When block_size was three, the old flatten concatenated all three embeddings at once—equivalent to FlattenConsecutive with n == block_size. Naming the general layer FlattenConsecutive avoids confusion with torch.nn.Flatten: PyTorch’s version takes start_dim / end_dim and behaves slightly differently, so the APIs are not drop-in identical.

For debugging shapes, prefer explicit T // n in the view instead of leaning on -1 everywhere: you want a clear error the moment a dimension does not divide evenly, rather than a silent reshape that scrambles time and batch.

Why view matches explicit even/odd stacking

For evenly spaced rows in memory, view(B, T//n, n*C) places the same elements you would get from splitting even and odd indices and cat along the feature axis—without an extra copy. That is the same trick as viewing a length-10 vector as (2,5) versus (5,2): layout determines meaning.

makemore.pyFlattenConsecutive
 1class FlattenConsecutive:
 2    def __init__(self, n):
 3        self.n = n
 4    def __call__(self, x):
 5        B, T, C = x.shape
 6        x = x.view(B, T//self.n, C*self.n)
 7        if x.shape[1] == 1:
 8            x = x.squeeze(1)
 9        return x

Indexing tricks in pure Python preview the same grouping: even positions 0::2 and odd positions 1::2, then concatenating along the feature axis, reproduces the pair packing that view(B, T//2, 2*C) achieves without copies when memory is contiguous.

Same idea as slicing a Python list: take list(range(10)). Indices [0::2] pick 0,2,4,6,8; indices [1::2] pick 1,3,5,7,9. Stack those two halves along the feature axis and you have explicitly separated even and odd time positions. On a contiguous embedding tensor e with shape (B, T, C), the operations e[:, 0::2, :], e[:, 1::2, :], and torch.cat(..., dim=2) build the same (B, T/2, 2C) layout that e.view(B, T//2, 2*C) produces—use the explicit version once to build intuition, then keep the view for speed.

scratch.pyexplicit pairs

2odd  = e[:, 1::2, :]
3explicit = torch.cat([even, odd], dim=2)  # (B, T/2, 2C)
4assert torch.all(explicit == e.view(B, T//2, 2*C))
08

Tree structure: pairs of two, then again, then predict

With block_size = 8 and n = 2 at each stage, tensor time lengths go 8 → 4 → 2 → 1. After each fusion, a linear layer maps 2*channels → hidden, batch norm and nonlinearity stabilize and break symmetry, and the next FlattenConsecutive(2) prepares the following pairwise merge.

A full WaveNet diagram may show more layers and a longer receptive field; the code you build for eight characters is the same black subtree repeated conceptually—convolutions later slide that subtree along positions to reuse intermediate nodes.

Printing type(layer).__name__ and out.shape after each step catches silent broadcasting bugs early. The hierarchical stack looks like this (numbers are representative of the tutorial run, not mandatory):

(B=4, T=8, C=10) → embed → (4, 8, 10) → FlattenConsecutive(2) → (4, 4, 20) → Linear(20, 200): (4, 4, 20) @ W(20×200) + b(200) → (4, 4, 200)

The key linear-algebra fact is that @ always multiplies the last axis of the left tensor with the weight matrix. A “surprise” that often unlocks hierarchical designs: the left operand does not have to be two-dimensional. If it were (4, 5, 80) instead, the same 80×200 weight would emit (4, 5, 200)—every leading dimension is treated as an independent batch axis. That is what lets you fuse four adjacent pairs inside each example in parallel, while still processing a minibatch of examples.

  • ● Embedding → (4, 8, 10)
  • ● FlattenConsecutive(2) → (4, 4, 20)
  • ● Linear (20→200) → (4, 4, 200)
  • ● BatchNorm1d + Tanh → same rank, per-channel stats
  • ● FlattenConsecutive(2) → (4, 2, 400)
  • ● Linear (400→200) → (4, 2, 200)
  • ● BN + Tanh → (4, 2, 200)
  • ● FlattenConsecutive(2) → (4, 400) after squeeze
  • ● Linear → logits (4, vocab_size)

When matching parameter counts between architectures, a hidden width near 68 can land both flat and hierarchical models around ~22k parameters—useful for a controlled comparison. Pushing capacity to ~76k by widening embeddings and hidden layers is where validation loss near 1.99 becomes reachable with longer optimization.

09

Training the deeper hierarchical model

The training loop stays familiar: sample a minibatch of contexts, forward through model, cross-entropy against next characters, backward, optimizer step. Two practical fixes matter enormously when prototyping.

First, smooth the loss curve for plotting: averaging consecutive loss values (for example reshaping the loss history into rows of 1000 and taking row means) removes scratchy variance from small batches. Second, when BatchNorm is in training mode, passing a batch of size one during sampling uses batch statistics with undefined variance—switch to eval mode and use running statistics.

Small minibatches—for example 32 contexts per step—make the instantaneous cross-entropy bounce wildly: a few easy or hard names in a batch swing the scalar up and down. If lossi is a long Python list of per-step losses, convert it with torch.tensor(lossi), then .view(-1, 1000).mean(dim=1) so each plotted point is the mean of 1000 consecutive steps. On a 200k-step run that yields 200 smooth points; the curve then clearly shows the phase where learning-rate decay drains energy from the optimizer and lets the trajectory settle into a late plateau—structure that is almost invisible in the raw trace.

Sampling bug you can actually hit: after refactoring to model(x), if the cell that rebuilds model does not re-run, batch norm may stay in training mode while you sample with a single-row context. Variance over one scalar is ill-defined; NaNs poison everything downstream. Fix: for layer in model.layers: layer.training=False (or equivalent) before evaluation, and give contexts shape (1, T) so the batch dimension exists.

Why BatchNorm “breaks” on a batch of one in training mode: training-mode batch norm estimates variance from the current minibatch. With a single scalar activation (or a degenerate slice), that estimate is not defined in the usual sense—the spread of one number is not a meaningful statistic. Concretely, you can see this in toy code: the variance of the lone value 5 does not behave like a stable population variance. The layer may not always throw a loud error; instead you can get nan values that propagate through tanh and the rest of the forward pass, so loss can look fine during training while sampling returns garbage. The fix is eval mode plus running statistics, not a larger vocabulary.

When training and validation loss track closely, you are often not wildly overfitting yet—there may still be room from capacity and architecture. The opposite pattern (train low, val high) would push you toward regularization or more data; here the story is “underfitting relative to what a bigger net could do.”

Flat MLP vs hierarchical model

When you match parameter counts between a wide flat model and a hierarchical one (for example tuning hidden size so both land near ~22k parameters), validation loss may look nearly identical at first—architecture alone is not a free lunch without tuning. After fixing BatchNorm reduction axes for 3D tensors, you may see a small additional gain because statistics are estimated over batch × time_groups rather than batch alone.

Representative matched-capacity numbers: a flat eight-character model might reach validation loss about 2.027 after a decent training schedule. A first hierarchical cut at the same ~22k parameters (hidden width tuned to match—e.g. 68 hidden units in the tree variant) can land near 2.029—essentially the same score, which is what you expect if the bottleneck is optimization and hyperparameters, not the logo on the diagram. After correcting BatchNorm so time positions contribute to the same running statistics, the hierarchical run might improve to about 2.022. That is a small delta; it may or may not be statistically significant on a single seed, but the direction matches the diagnosis that the buggy norm was maintaining separate statistics per temporal group.

Code quality: Sequential and clean modules

Refactoring scattered forward logic into layers plus a container pays off twice: readability (the model’s story is a list) and correctness (one place to set training=False for every batch norm when evaluating). After the refactor, rebuild the model whenever you change layer definitions—stale objects are a common source of confusing eval bugs.

You might wonder whether explicit view calls are “cheating.” They are not: they document intent and fail fast when shapes disagree. Prefer explicit T // n over excessive negative-one dimensions when you want clearer error messages during prototyping.

Define all layers in one place, sanity-check parameter count (~12k for a tiny flat model, tens of thousands after widening), then share one forward path for training and sampling—the same endgame as production PyTorch code.

Before

Embedding lookup, view, and matmul spelled out in the training loop; easy to mistype a dimension when experimenting.

After

Key takeaway: containers are not “object-oriented ceremony”—they are how frameworks recurse parameters, hook optimizers, and (later) load checkpoints. Your minimal Sequential is the same structural idea as nn.Sequential, just without the extra utilities.

A workflow that shows up constantly in practice: prototype new layers and shape logic in a Jupyter notebook—print shapes after every line, break after the first forward pass, fix bugs in isolation—then, once the tensors line up, copy the vetted code into a real repository and launch longer runs from an editor such as VS Code. The notebook is where you babysit ranks and broadcasting; the repo is where you keep training scripts, configs, and version control. Neither replaces the other.

Mapping to real torch.nn

Your hand-rolled modules correspond closely to PyTorch’s: nn.Linear, nn.BatchNorm1d, nn.Tanh, nn.Embedding, nn.Flatten (different kwargs—hence the custom name), and nn.Sequential. The important API deviation called out in careful implementations is tensor layout: PyTorch BatchNorm1d on 3D inputs assumes (N, C, L) and normalizes over N and L for fixed C. This tutorial’s convention keeps channels last—(N, L, C)—and reduces over leading batch/length dimensions instead. Both are valid; mixing them without translation causes silent shape bugs.

Debugging heuristic: print tensor.shape after every layer when introducing a new layout. Inspect running_mean.shape in batch norm: it should carry one statistic per channel, not per spurious position.

PyTorch nn.BatchNorm1d (3D)

Documented layouts are (N, C) or (N, C, L): the channel axis C sits in the middle. For volumetric 3D inputs, the layer reduces over the batch dimension N and the length dimension L, treating C as the feature vector per position.

This chapter (channels last)

Activations are (N, L, C): time or sequence length L precedes channels. Batch norm must reduce over (0, 1) so each of the C channels gets one running mean—not L separate means per channel slice.

13

Performance, batch-norm fix, and convolutions as a for-loop

Representative numbers from a full notebook-style run: validation loss might move from about 2.10 (three-character context) to about 2.02 after widening context to eight with a flat MLP alone. Matching parameter counts between flat and hierarchical stacks often lands both near 2.03 nats—for example 2.027 vs 2.029 in one log—until batch norm is audited for 3D activations; fixing the reduction axes can nudge the tree model toward about 2.022. Scaling embeddings to 24 and widening hidden layers to roughly 76k parameters can push validation toward about 1.993—crossing below 2.0 is a satisfying milestone even when hyperparameters are not fully grid-searched.

Qualitatively, samples after better validation loss tend to look more name-like—still sometimes novel relative to the training list, but with improved letter statistics and morphology. Numbers alone never tell the whole story; keep a handful of printed samples per checkpoint.

The batch norm bug is instructive: with activations (32, 4, 68), reducing only over batch dimension 0 leaves a 4 in the statistic shape—four separate running means per channel position. Instead, reduce over (0, 1) so each of the 68 channels has one running mean and variance estimated from 32×4 values.

μ, σ² computed over dim ∈ {0} if x.ndim == 2 else dim = (0, 1) for x.shape = (N, L, Clast)

After the fix, a forward probe should show running_mean.shape == torch.Size([1, 1, 68]) for that layer—68 global channel statistics—not [1, 4, 68]. Intuitively, each mean and variance now pools 32 × 4 = 128 scalar activations per channel per step instead of only 32, which stabilizes the estimates and removes the artificial per-position drift.

Scaling the same hierarchical stack by widening embeddings to 24 dimensions and increasing hidden width yields on the order of 76 000 parameters. Training takes noticeably longer, and without a systematic sweep it is easy to feel “in the dark” on learning rate and width choices—but a longer run in that regime can push validation loss to about 1.993, i.e. slightly below the psychologically round 2.0 barrier on the same task.

Fixing reduction dimensions

torch.mean accepts a tuple of dims. For 2D inputs, keep the old behavior (reduce batch). For 3D (N, L, C) with channels last, reduce (0, 1) so statistics are (1, 1, C)—one mean/variance per channel.

Why convolutions are “just a fast for-loop”

Take a concrete name from the corpus—say DeAndre, seven letters plus the usual end token—which generates eight supervised rows in the dataset (eight different contexts that each predict a next character). You can run the hierarchical MLP on each row separately: build a tensor with shape (1, 8) (note the explicit batch dimension of one), forward through model, read logits. If you index a single row with a one-dimensional slice, you must promote it with something like X[[i]] so the batch axis exists—shape (8,) alone will not broadcast through the stack the way batched training does.

Now imagine you want logits at all eight positions for efficiency. A literal for loop in Python performs eight independent forwards. A 1-D convolution implements the same repeated linear filters, but the loop moves into CUDA kernels (or other fused CPU backends): each layer’s affine map becomes a sliding operator over the sequence. The computational graph is unchanged; only the scheduling and memory reuse change. WaveNet diagrams make this vivid: the black subtree is exactly one forward you implemented; the orange outputs along the time axis are what convolutions compute in parallel. Crucially, intermediate nodes in the fusion tree reuse work—a node that is the right child of one local tree is the left child of the next—so separate Python forwards recompute values that a sliding implementation shares for free.

Dilation in the WaveNet paper widens the receptive field per layer without naïvely widening every kernel: you skip inputs according to a schedule (1, 2, 4, 8, …), which is the convolutional view of “reach farther at each depth.” The pairwise tree in this chapter fixes the schedule to halving T at each stage; the underlying “combine neighbors, then neighbors of neighbors” story matches the diagram, even when the efficient implementation is still written as batched matmuls in a notebook.

Not implemented in this chapter: gated activations, residual and skip wiring, and the full WaveNet forward as published. Those additions change optimization dynamics and capacity routing; the tree-shaped fusion scaffold is the prerequisite geometry.

Process notes (how deep learning work actually feels)

  • Framework docs are a starting point, not a guarantee—when shapes get weird, trust interactive probes over assumptions.
  • Most “debugging” time is babysitting tensor ranks: promoting dimensions, view/permute, and aligning NCL vs NLC.
  • Prototyping in a notebook then copying validated layers into a repository mirrors how small teams move fast without sacrificing reproducibility.
  • A serious experimental harness (configs, sweeps, paired train/val plots) matters once runs take long enough that guess-and-check becomes expensive. Glancing only at training loss—or tuning without logging hyperparameters alongside curves—is not how most production teams iterate; you want scripts that accept many CLI flags, launch parallel jobs, and archive plots next to the settings that produced them.

On reading framework documentation: large libraries invest heavily in kernels and distributed primitives, but surface-level docs for individual layers are not always kept perfectly aligned with behavior. Shape sections can be incomplete, ambiguous, or occasionally wrong relative to the code. The practical response is the one used throughout this chapter: cross-check against small experiments—print shape, read the running_mean tensor, step through a single batch—rather than trusting a prose table when the loss curve looks fine but samples do not.

Natural continuations from here include true dilated causal conv stacks (so the tree is slid along the sequence the way the WaveNet paper draws it), gated activations, residual and skip connections, classical recurrent nets including LSTM and GRU cells, and eventually Transformers—each a different way to route context, with complementary inductive biases and engineering trade-offs.

Stepping back, the cumulative modules in this series are effectively a miniature reimplementation of torch.nn on top of torch.Tensor: you have seen how Module-like objects nest, how containers aggregate parameters, and why stateful layers demand discipline. That mental model is the real “unlock” for reading production PyTorch—whether you keep training in notebooks or move entirely to scripts.

Finally, 1-D convolution is the efficient way to slide the same fusion tree across all positions in a sequence, reusing shared nodes (the right child of one window is the left child of the next). The model’s math does not change; the loop moves from Python into optimized kernels.

Shape recipes & sanity checks

    
Use this as a fast lookup when something “almost works.” Each item is a symptom → fix pair distilled from the chapter.

    

      
Embedding output rank

      
Expect (B, T, C). If you see (B, C), you indexed wrong or squeezed time prematurely.

    

    

      
After FlattenConsecutive(2)

      
From (B, T, C) to (B, T/2, 2C) when T is even. Odd T needs padding or a different tree.

    

    

      
Linear after hierarchical flatten

      
Weight shape (2*C_in, H) for pairwise fusion stages; multiply on the last axis only.

    

    

      
BatchNorm running mean shape

      
Should collapse batch+time into statistics: (1,1,C) for 3D NLC tensors—not (1,L,C).

    

    

      
Sampling NaNs

      
Set training=False on norm layers; ensure context has batch dimension (1, T).

    

    

      
Logits shape vs targets

      
cross_entropy wants (N, V) logits and (N,) integer targets; flatten extra dims first if needed.

    

    

      
Parameter explosion

      
First flat linear scales as O(T·C·H). Hierarchical stages spread cost across layers but still grow with H and C.

    

    

      
View vs copy

      
view requires contiguous memory; use contiguous().view after transposes.

    

    

      
Squeeze surprises

      
squeeze() without dim removes all size-1 axes—dangerous if batch size is 1. Prefer squeeze(1).

    

    

      
Dilation vs pairwise tree

      
Both widen context exponentially with depth; dilation schedules skips in convolution; the tree uses fixed halving in time length.

Track both train and validation curves, repeat seeds or use a proper experiment harness, and treat leaderboard decimals with skepticism until you have a distribution of outcomes.

    

    

      
Pushing the ~1.993 validation score without new ideas: the reported ~76k-parameter run was not heavily tuned: channel counts, fusion widths, and optimizers were chosen by hand. It is plausible that a wider flat MLP with enough tuning could match or beat the hierarchical net—embarrassing for the fancy diagram, instructive for you as a practitioner. Reasonable projects include reallocating channel budgets across layers, reading the original WaveNet paper for the gated/residual blocks, adjusting initialization and learning-rate schedules, and building a small sweep harness so you are no longer guessing in the dark.

    

    
Hierarchical models do not always beat flat ones at equal parameter count: allocation of width per stage, regularization, and optimizer settings dominate. The hierarchy buys a prior; tuning still decides the score.
