Recap: the bigram model

Chapter 2 built a character-level bigram model using both a count table and a neural equivalent. The bigram's key limitation: it only looks at one character of context.

01

Why the table explodes

If context is a single character, there are 27 possible histories. If you use two characters, there are 27² = 729 rows. For three characters, 27³ = 19,683. Each extra character in the context multiplies the number of distinct histories by the alphabet size.

|\text{rows}| = V^{\text{block\_size}}   (here V = 27)

Most rows get few or zero counts — sparse, unreliable estimates — while memory and lookup cost grow exponentially in context length. You need a model that shares statistical strength across similar histories instead of storing a separate count for every exact string.

02

Neural probabilistic language model

Bengio et al. (2003) popularized the neural probabilistic language model: map each token to a learned embedding, concatenate a fixed context, pass through a tanh hidden layer, then softmax over the vocabulary — lookup → concat → tanh MLP → softmax. Training maximizes log-likelihood; parameters include C, hidden weights, and output weights.

Generalization: if the exact context never appeared in training, similar contexts can still yield reasonable predictions because similar tokens pull similar embeddings during training — e.g. interchangeable function words or related content words need not each have isolated rows of a giant count table.

In their word-level setup the vocabulary has roughly 17,000 types. Each word id is an integer in 0 … 16,999. A shared lookup matrix C has shape 17,000 × 30 in their illustrative setting: every word is a point in a 30-dimensional space. At initialization those points are random, but under training they move. Words with similar meaning or distribution (including synonyms) tend to drift near each other; unrelated words drift elsewhere.

Consider predicting the blank in “a dog was running in a ___.” If that exact prefix never appeared in training, a count table has little to say — but a neural model can still behave sensibly when similar prefixes did appear: interchangeable words like a and the land in nearby embedding regions, and related nouns like cat and dog share structure that transfers through C and the hidden layer.

Their diagram fixes three previous words to predict the fourth. After embedding, the input layer has 3 × 30 = 90 scalar activations (three word vectors laid side by side). The same matrix C is reused for every position — always index into one shared embedding table. The hidden layer width is a hyperparameter; 100 hidden units is a concrete example size. Those 100 units are fully connected to all 90 inputs (fully connected layer, then nonlinearity). The output layer has 17,000 logits (one per word), each connected to every hidden unit — that is where most of the parameters live when the vocabulary is large. A softmax sits on top: exponentiate logits, normalize so each row sums to 1, yielding a proper distribution over next words. During training the true next word index selects the corresponding probability; optimization increases that probability jointly over C, hidden weights, and output weights via backpropagation.

Word-level (Bengio et al., illustrative)

|V| ≈ 17,000, n_emb = 30, three context words → 90 inputs to the first linear layer; hidden size e.g. 100; output 17,000 logits + softmax.

Character-level (this chapter)

V = 27, small n_emb (e.g. 2 for plots, 10 when serious), block_size characters concatenated → block_size × n_emb inputs; hidden and output sized to 27 next-character logits.

Takeaway: character-level names use the same pipeline with V = 27 and smaller dimensions — the pattern scales across vocabulary sizes.

03

Embedding lookup: the C matrix

Let C ∈ ℝ^{V × n_emb}. Each integer token id 0 … V−1 selects one row of C. A batch of ids indexes C in parallel — in PyTorch, C[x] with integer tensor x gathers rows.

e_i = C[i, :]   (row i)

This is equivalent to one-hot multiplying C: if h is one-hot for id i, then h @ C = C[i]. The embedding layer is a linear layer with no bias and no nonlinearity; integer indexing is the fast implementation.

Indexing and shapes

Single id, list of ids, or a 2D tensor of ids all work. For input X of shape (N, block_size), C[X] has shape (N, block_size, n_emb) — one embedding vector per position per example.

2D embedding space (trained sketch)

With n_emb = 2 you can plot each character. After training, vowels often cluster; rare or special symbols (q, .) can sit apart — structure emerges from the loss.

Indexing is not limited to a single id: a list of rows (e.g. 5, 6, 7), a 1D integer tensor, or repeated indices (the same row retrieved twice) all work. For a 2D tensor of ids X with shape (32, 3), the expression C[X] returns shape (32, 3, n_emb): every integer slot is replaced by its row of C. You can spot-check element-wise equality, e.g. C[X][13, 2] versus C[X[13, 2]], to convince yourself that advanced indexing is doing what you expect.

F.one_hot returns integer dtypes; C is float. Matrix multiply refuses to mix them until you use .float() on the one-hot. Once cast, multiply h @ C masks every row of C except the one where the one-hot is 1 — identical to C[i]. The embedding layer is exactly a linear layer with weight matrix C, no bias, no nonlinearity; integer indexing is simply the fast path.

PyTorch stores tensor data in a contiguous 1D storage; shape, stride, and storage_offset describe how that storage is interpreted as a multidimensional array. A view that preserves total element count (e.g. reshaping 18 elements as 2×9, 9×2, or 3×3×2) typically relabels the same memory without copying. By contrast, naive torch.cat along an axis that is not already laid out that way allocates new storage and copies — fine for clarity, worse for memory traffic.

On a tiny development slice, a randomly initialized net often lands near negative log-likelihood ≈ 17 on a batch of classification targets — far from a trained model, but a useful sanity check before scaling to the full corpus. With n_emb = 2, block_size = 3, n_hidden = 100, and 27 output classes, parameter count is on the order of 3,400 scalars — embeddings plus two weight matrices and biases.

Fused ops and backward: treating “softmax + log + gather” as one kernel is not only faster on the forward pass; the backward can simplify analytically (compare implementing tanh in Micrograd: the forward is messy, the local gradient collapses to a compact 1 − tanh² expression). F.cross_entropy bundles logits→loss so autograd sees one stable, efficient primitive.

04

Context window: block_size

block_size is how many previous characters feed the prediction (after . padding at the start). For each name, you slide a window: context is the last block_size symbols (padded), target is the current character. Changing block_size changes how much history the net sees and the size of the flattened input block_size * n_emb.

The full name corpus yields roughly 228,000 training examples at character granularity.

05

MLP architecture

Pipeline: embedding C[X] → concatenate / view to a vector of length block_size * n_emb → hidden tanh(x @ W1 + b1) → logits h @ W2 + b2 → softmax for probabilities over the next character.

Concrete shape story when block_size = 3 and n_emb = 2: embeddings have shape (N, 3, 2). You cannot multiply that directly by W1 shaped (6, 100) — you need a (N, 6) layout. One route is torch.cat(torch.unbind(emb, dim=1), dim=1), which generalizes to any block_size without hard-coding three slices. Another is emb.view(N, -1) or view(-1, block_size * n_emb), which stacks the three 2-vectors into one row of six entries per example — the same concatenation, but usually without an extra memory allocation when the underlying tensor is already contiguous in the right order.

After emb_flat @ W1 + b1, tanh squashes activations into (−1, 1). For a batch of 32 examples and 100 hidden units, hidden activations have shape 32 × 100. The bias vector has length 100; broadcasting expands it to every row so the same bias is added to each example — verify alignment (rightmost dimensions match or are 1) whenever you add.

The output layer maps 100 hidden units to 27 logits per row; biases length 27. Manual softmax: exponentiate logits to get nonnegative “counts,” divide by the row sum so each row sums to 1. On an untrained net some assigned probabilities look plausible (e.g. ~0.2 on one position) while others are tiny (e.g. ~0.07) — that spread collapses only after optimization.

\text{logits} = W_2^\top \tanh(W_1^\top \text{emb\_flat} + b_1) + b_2

Building the training dataset X, Y

For each word wrapped as .name., maintain a running context of length block_size, initially all padding (0). For each new character, append (context, char) as one training pair: input row is the integer ids of the context, label is the id of the current character. Then shift the window.

Rolling context

The sliding window is the same idea as n-gram datasets, but you store indices for a neural net instead of keys into a count table. For debugging, loop over the first few words only; switch to the full list for real training (~228k examples for the standard name corpus).

Forward pass in code

After emb = C[X], reshape with view(N, -1) or view(-1, block_size * n_emb). Hidden preactivation emb_flat @ W1 + b1 uses broadcasting on b1. Apply torch.tanh. Output layer produces logits of shape (N, 27) — raw scores, not yet probabilities.

view vs cat

view (when contiguous) reinterprets the same storage — cheap. Naive torch.cat along the embedding axis can allocate new memory. For variable block_size, torch.cat(torch.unbind(emb, dim=1), dim=1) matches view logically but prefer view when layout allows.

08

Cross-entropy loss

For each example, you want high probability on the true class Y[i]. The average negative log probability is the cross-entropy between a one-hot target and the softmax of logits. A manual construction: build probs with softmax along the class dimension, then index each row i at column Y[i] — in code, pair torch.arange(0, N) (or an equivalent row index) with Y to gather the assigned probability per example, take log, negate, and mean. PyTorch F.cross_entropy(logits, Y) implements the same scalar in one call — fused, gradient-friendly, and numerically stable (log-sum-exp shift trick internally; avoids exp overflow on large logits).

\mathcal{L} = -\frac{1}{N}\sum_i \log \frac{e^{z_{i,y_i}}}{\sum_j e^{z_{i,j}}}

Implementing “softmax, then log, then pick the label column, then mean” as separate tensor ops materializes intermediate tensors and is easy to get slightly wrong. F.cross_entropy(logits, Y) is the standard shortcut: same scalar loss, but forward and backward are fused and tuned.

Numerical stability: suppose logits are [-2, 3, -3, 0, 5]. Exponentiating and normalizing yields a perfectly fine probability vector. If one logit becomes very negative (e.g. -100), exp underflows toward zero — still safe. If a logit becomes very positive (e.g. +100), exp(100) overflows finite floating-point range and you get inf / nan in the softmax pipeline.

Softmax is invariant to adding the same constant to every logit: subtracting max(logits) sends the largest entry to 0 and shifts the rest negative, so exponentials stay bounded. PyTorch applies that (log-sum-exp) trick inside cross_entropy. You can verify in a scratch cell: add +1, +2, or -3 to all logits — the normalized probabilities do not change, even though raw exponentials would differ.

\text{softmax}(z)_i = \frac{e^{z_i - \max_j z_j}}{\sum_k e^{z_k - \max_j z_j}}

09

Minibatches and gradient descent

Full-batch gradient descent on ~228k examples per step is slow. Instead draw a random subset of indices ix = torch.randint(0, N, (batch_size,)), slice Xb = X[ix], Yb = Y[ix], and step on stochastic estimates of the gradient. Noisier per step, but many more steps per second — usually a better tradeoff.

Why it works

The minibatch gradient is an unbiased estimate of the true gradient in expectation. Smaller batches add variance but enable vastly more updates; learning rate and batch size are coupled hyperparameters.

train.py L80–95 / 200 
80ix = torch.randint(0, X.shape[0], (batch_size,), generator=g)
81Xb, Yb = X[ix], Y[ix]
82# forward → loss → zero_grad → backward → SGD update

Full-batch gradient descent on roughly 228,000 rows per step is expensive: each update touches the entire dataset. Minibatch SGD uses an unbiased estimate of the gradient from a handful of rows (e.g. batch size 32). The direction is noisier, but you can afford vastly more steps per wall-clock second. In practice an approximate gradient with many updates usually beats an exact gradient with few.

Each minibatch is a different random subset, so logged loss jitters step to step — plotting loss.item() per step often shows a thick band of noise. For a cleaner picture, periodically evaluate F.cross_entropy on the entire X_train, Y_train (or dev) under no_grad(), or plot log10(loss) to compress the vertical scale after the initial steep drop.

10

Learning rate finding

Pick a range in log space: exponents from -3 to 0 give learning rates from 0.001 to 1. Run many steps, increasing lr each step (or follow a schedule), record (lr, loss), and plot. You want a region where loss decreases smoothly; too low barely moves, too high oscillates or explodes.

LR finder curve (schematic)

Typical shape: flat left (LR too small), valley (good), spike right (instability). Drag the marker to read off a reasonable exponent.

-1.0

Around 10⁻¹ often lands in a usable band for this small MLP; always verify on your split.

When a learning rate is too small (e.g. exponents around -3), loss barely moves — optimization is timid. When it is too large (e.g. toward 10⁰ = 1), the curve becomes unstable: loss spikes and oscillates. A practical bracket for this architecture often lies between 0.001 and 1 on a log scale.

A systematic sweep: reset weights, define lre as 1000 values stepping linearly in exponent space from −3 to 0, set lr = 10**lre so the actual learning rates are exponentially spaced between 0.001 and 1. Run one (or a few) optimization steps per candidate lr, append (lr, loss) or (lre, loss), then plot. The good zone is the valley before the spike; for this problem that often lands near exponent −1, i.e. lr ≈ 0.1.

After the sweep: fix lr = 0.1 (or your valley pick), train for many steps, then apply learning-rate decay: multiply lr by 1/10 (e.g. from 0.1 to 0.01) for a late-stage fine-tune when the loss curve plateaus. Production schedules are smoother (cosine, warmup, etc.), but the “train fast, then slow down” pattern is the same idea.

11

Train / validation / test split

Reporting loss on the same examples you optimize invites overfitting: capacity grows, training loss can approach zero while held-out text looks worse. The usual protocol uses three splits:

  • Train (~80%) — update weights with gradient descent.
  • Validation / dev (~10%) — tune hyperparameters (embedding dim, hidden width, block_size, lr, batch size, regularization).
  • Test (~10%) — final score, touched rarely; each peek teaches you something and risks adapting to the test set by accident.

Shuffle words before slicing so splits are as exchangeable as your data allows. Build (X, Y) per split with the same build_dataset(words_slice) helper.

With about 32,000 words, taking n1 = int(0.8 * n) and n2 = int(0.9 * n) yields on the order of 25,000 training words, 3,000 development words, and the remainder (~4,000) for test — exact integers depend on n. Character-level tensors X_tr, Y_tr contain every sliding-window example produced from training words only, disjoint from dev/test word lists, so optimization never sees dev rows.

If n = len(words), use n1 = int(0.8*n), n2 = int(0.9*n). Train on words[:n1], validate on words[n1:n2], hold out words[n2:] for a single final evaluation.

During training, log noisy minibatch loss and periodically evaluate full F.cross_entropy on X_tr, Y_tr and X_dev, Y_dev under torch.no_grad().

Underfitting

Train and dev track together and stay high — increase capacity, train longer, or tune lr. Example: both near 2.3 on names while dev rows were never in the optimizer.

Train drops while dev stalls or rises — regularize, shrink the net, or gather more data. Example: train ~2.16 vs dev ~2.19 as curves slowly separate late in training.

Representative training dynamics on the full training split (exact numbers vary with seed and step counts): minibatch loss may hover near 2.5 while a full pass reports ~2.7 early on; continued optimization might show full-train values stepping down through 2.6, 2.57, 2.53. The important comparison: a smoothed bigram baseline in the same setup achieved about 2.45 nats per character — so a shallow MLP with three characters of context can beat that baseline on training loss when everything is wired correctly.

Do not celebrate training loss alone. As capacity grows (hundreds → thousands → millions of parameters), the network can memorize training strings: training NLL approaches zero while samples degenerate into training excerpts and held-out NLL blows up. Track dev loss and touch test rarely.

When train and dev curves sit on top of each other and both are still relatively high, you are more likely underfitting than overfitting — the model lacks capacity or has not trained long enough. In one run with a small net after splits, both train and dev sat near 2.3 with dev examples never optimized directly — evidence the model had not yet saturated capacity on names.

Hyperparameter tuning

Knobs not updated by backprop — n_emb, n_hidden, block_size, batch size, lr schedule — are hyperparameters. Tune them on dev; report test loss once.

Bottleneck: if a wider hidden layer barely helps, try larger n_emb — n_emb=2 may cram too much into the plane for tanh to exploit.

Hyperparameters include hidden width, embedding width, context length, batch size, learning rate, weight decay (optional here), and training duration. Weights are updated on the training split; hyperparameters are chosen by whichever settings improve dev loss. Test loss is read once, after tuning — peek at test too often and you implicitly tune to it.

Concrete sweep from the reference run: starting from an underfitting regime with n_hidden = 100, bumping the hidden layer to 300 pushes parameter count to about 10,000. Early dev loss can stall around 2.5 while the larger net is still converging; training longer, raising batch size to reduce gradient noise, or halving the learning rate can help. In one sequence, halving lr moved dev toward 2.32, then further optimization reached about 2.23 train and 2.24 dev — still not a dramatic win, which suggests the two-dimensional embeddings were the limiting factor: every letter must share the plane, so vowels get squeezed next to consonants and rare letters fight for space.

Before leaving n_emb = 2, plot the rows of C as (x, y) coordinates. After training you often see vowels clustered — the model treats them as interchangeable in many contexts — while q and the period token sit far away as exceptions. That structure is not random; it is what the objective induces. Once you increase n_emb beyond two you lose an easy scatter plot but gain room to separate characters.

A stronger configuration: n_emb = 10, n_hidden = 200, still block_size = 3, so the hidden layer sees 3 × 10 = 30 inputs. Parameter count lands near 11,000. Train with lr = 0.1, then decay to 0.01 for another long run; full-training loss may reach ~2.30 with dev around 2.38 mid-training, then after decay train ~2.17 and dev ~2.20 as the curves begin to separate slightly — a hint of emerging overcapacity. Pushing further might reach train 2.16 and dev 2.19. A heavier schedule used 200,000 steps total: 100,000 at lr = 0.1 followed by 100,000 at lr = 0.01, with best validation loss around 2.17 — a reference point when sweeping block_size, widths, batch size, and schedules more systematically.

Production contrast: at scale, jobs run for hours or days offline with logged experiments and systematic hyperparameter search. The process — dev-driven model selection, rare test evaluation — stays the same.

Sampling from the trained model

Start from a context of . tokens, forward to logits, F.softmax(..., dim=-1), then torch.multinomial. Append sampled id, shift window, stop at . (id 0).

At generation time the batch dimension is usually 1: X has shape (1, block_size) even though training saw N × block_size. Embed with the same C, apply view(1, -1), run the hidden layer and logits head. F.softmax applies the same stabilized softmax as inside cross_entropy; torch.multinomial(probs, 1, generator=g) draws the next integer id. Loop until the sampled id is 0 (the end token), decoding ids back to characters for display. Drawing a batch of 20 independent names is a good qualitative sanity check after each serious training run.

Bigram vs MLP

On the same corpus, a tuned bigram often sits near NLL ≈ 2.45 per character (exact value depends on smoothing and split). A trained MLP with block_size=3 can reach validation NLL in the low 2.2s — lower is better under the same metric.

Anchor numbers from a single reference training path (your splits and seeds will shift them slightly): initial random loss on classification ~17 nats on a small batch; full-dataset training loss stepping through 2.7 → 2.6 → 2.57 → 2.53 before aggressive optimization; minibatch-only readings near 2.5 while full-data loss is higher; after on the order of 20,000 steps at lr ≈ 0.1, ballpark 2.48 then 2.46; after one 10× decay, training loss near 2.3 beating the 2.45 bigram; with splits, small-net train and dev both ~2.3 (underfitting); widening hidden units without fixing embeddings can leave dev near 2.5 until learning rate and noise issues are addressed; with n_emb=10, n_hidden=200, and decay, dev can approach 2.17–2.20 while train creeps slightly lower — the regime where the MLP clearly wins on held-out names.

E pluribus unum — scaling context

Counting uses many isolated rows (pluribus histories). A neural LM uses one shared parameterization (unum): the same C, W1, W2 handle every context. Longer block_size feeds more history through fixed matrices instead of multiplying table rows by V per extra symbol.

Later RNNs and Transformers extend the same principle; the MLP is the first step where a fixed-width vector summarizes bounded context via padding and learned projection.

The Bengio et al. paper adds regularizers and architectural variants beyond this minimal implementation; those refinements can push validation loss below the ~2.17 reference point.
