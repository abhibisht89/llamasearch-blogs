00

Goal: reproduce GPT-2 124M

GPT-2 shipped in 2019 as a family of models (124M → 1.5B parameters). This chapter targets the 124M member: 12 layers, 768 channels, 12 heads, context 1024, vocabulary 50257 (Chapter 8). The objective is twofold: implement a GPT module that can load OpenAI’s public weights bit-for-bit (via Hugging Face’s PyTorch port), then train from random init until validation metrics meet or exceed that reference.

Loading someone else’s checkpoint calibrates the implementation: if architecture, tensor layouts, and naming match the reference, you know you are searching in the right model class. Anything you train is a sibling of the released model, not an accidental cousin.

GPT-2 paper + weights

Public state_dict, TensorFlow inference code, relatively sparse training detail.

GPT-3 paper

No public weights, but concrete optimization hyperparameters (Adam β, warmup tokens, cosine decay, weight decay, clipping) that transfer well to GPT-2–sized models.

The public GPT-2 release is a miniseries of four checkpoints (124M through 1.5B parameters) so that scaling curves can be drawn: model size on the horizontal axis, downstream metrics (translation, summarization, QA, and so on) on the vertical axis. The paper’s parameter-count table has a known summation error; authoritative counts are in the openai/gpt2 GitHub release. Later work on compute-optimal scaling (notably Hoffmann et al., Training Compute-Optimal Large Language Models — “Chinchilla”) revisits how much data you should pair with a given parameter count; the recipe below follows historical GPT-2/3 training rather than re-deriving those tradeoffs.

Compute snapshot: What was a heavy industrial run in 2019 is now roughly ~1–2 GPU-hours on a modern datacenter card for a single epoch over a 10B-token educational subset — on the order of tens of dollars of cloud spend, not thousands.

Concrete anchor numbers from end-to-end reproductions: about one hour wall time for 10B tokens on fast 8×A100-class boxes at ~1.5M tokens/s aggregate, with single-GPU cloud rental often landing near ~10 USD for that scale; an overnight 40B-token run (~four epochs over a 10B pack) is on the order of ~8 hours.

Parameter count breakdown (124M class)

Toggle categories. Numbers follow weight tying: token embedding and LM head share one large matrix (~38.6M params), so the naive sum of “embedding + head” double-counts unless you tie.

Loading OpenAI’s GPT-2 weights (Hugging Face)

The original OpenAI release is TensorFlow-first. For PyTorch work, transformers provides GPT2LMHeadModel.from_pretrained("gpt2") — where "gpt2" is the 124M checkpoint ("gpt2-xl" is the 1.5B tier).

Inspect state_dict(): keys like transformer.wte.weight (token embeddings, shape [50257, 768]) and transformer.wpe.weight (position embeddings, [1024, 768]). Every other key is a block weight, bias, or LayerNorm parameter inside transformer.h.*.

Unlike the original Transformer, which used fixed sinusoidal position encodings, GPT-2 learns wpe end-to-end. If you visualize the table, each row is a position 0 … 1023; many channels look roughly sinusoidal after training — the network rediscovers frequency-like structure even though nothing enforces it. Jagged or noisy rows can indicate under-training (early optimization is pure noise), though smoothness is not strictly required by the mathematics.

For generation parity with Hugging Face defaults, top-k filtering with k = 50 is the usual starting point: keep only the 50 largest probabilities, renormalize, then sample. That keeps the model from drifting into ultra-rare tokens. Small mismatches against the Pipeline API can still appear because the pipeline stacks additional heuristics; bitwise-identical logits between your port and GPT2LMHeadModel are the real correctness check.

Many modules behave identically in train vs. eval here, but keeping eval() for inference is still good hygiene — PyTorch internals may branch on mode in subtle ways.

Architecture: decoder-only GPT-2

Using the GPT architecture from Chapter 7 — decoder-only Transformer with pre-LayerNorm blocks, causal self-attention, and an MLP per block — this section pins down the GPT-2 124M hyperparameters below.

GELU in GPT-2: PyTorch exposes both exact GELU and gelu_tanh “approximate” forms. The approximation exists for historical reasons (exact GELU used a slow error function on older TensorFlow stacks). For a faithful GPT-2 reproduction, keep the approximate variant the checkpoint expects; for new work, exact GELU is usually fine. GELU avoids the exactly-flat negative tail of ReLU that causes dead neurons (zero gradient regions).

Building GPT from scratch in PyTorch

Mirroring Hugging Face’s module tree makes weight porting mechanical: transformer.wte, transformer.wpe, transformer.h as ModuleList, transformer.ln_f, and lm_head without bias (bias False).

Inside each block, Hugging Face’s c_attn fuses query/key/value into one linear for kernel efficiency; the same math as a separate multi-head module can be recovered with careful view/transpose gymnastics so tensor names still line up for load_state_dict. A compact reference implementation is on the order of <100 lines versus multi-thousand-line framework code — useful when you want the entire training surface area in one screen.

Weight initialization & residual scaling

OpenAI’s released code uses Gaussian init with std=0.02 for most weights, zeros for biases where applicable — close to Xavier/Glorot scale for these widths (1/√768 ≈ 0.036, 1/√1600 = 0.025, etc.). Their reference also uses 0.02 for token embeddings and a slightly different scale for positional embeddings in places; mirroring the repository beats guessing from the paper text.

The residual-scaling story is quantitative. Imagine a residual stream of dimension 768 initialized at zero. Add N independent mean-zero updates with unit variance. The post-sum standard deviation grows like √N — e.g. N = 100 pushes the scale toward 10. GPT-2 therefore scales down the projections that inject into the residual by 1/√(2·n_layer): two sublayers per block (attention + MLP) each add to the residual, so the effective count of additive contributors tracks 2·n_layer.

The GPT-2 paper adds a depth-aware scaling for residual branches: multiply projecting layers inside residual paths by 1/√(2·n_layer) because each block contributes two residuals (attention + MLP).

std_residual = 0.02 / √(2 · n_layer)

Residual scaling: If you summed N independent zero-mean updates with unit variance, variance grows like N. Scaling each contribution by 1/√N keeps activation scale stable through depth.

_init_weights hook

Use module.apply(_init_weights). Linear layers: normal with base 0.02, scaled down when isinstance(module, CausalSelfAttention | MLP) projection outputs feed the residual stream.

Porting weights & weight tying

Hugging Face’s tensors sometimes need transpose versus naive PyTorch Linear layouts inherited from TensorFlow. Maintain a small allowlist of keys to transpose when copying.

Weight tying: in GPT-2, the token embedding matrix and the LM head matrix are the same storage — check data_ptr() equality. After copying weights, enforce lm_head.weight = transformer.wte.weight so training matches the architecture.

The Transformer paper states the design explicitly: “In our model, we share the same weight matrix between the two embedding layers and the pre-softmax linear transformation, similar to [30].” Intuition: if two surface forms are semantically nearby, they should sit close together in input embedding space and invite similar output logits. Tying enforces that symmetry instead of learning two unrelated linear maps. OpenAI’s TensorFlow reference forwards wte twice — bottom for embeddings, top for logits — so gradients from the classifier and from the embedding pathway sum into one shared tensor.

\text{Shared rows} \approx 50257 \times 768 \;\Rightarrow\; \sim 3.86\times 10^{7}\ \text{parameters saved }(\approx 30\text{–}35\%\ \text{of }124\text{M})

Why tie?

Inductive bias that “input token space” and “output logit space” should align; also saves ~38M parameters — a large fraction of 124M.

If you forget

You train extra capacity at the classifier, diverge from the reference parameterization, and can hurt sample efficiency.

FineWeb-Edu instead of WebText

Original GPT-2 trained on WebText (Reddit-outbound links) — not redistributable. Modern reproductions use open mixtures: Common Crawl derivatives (C4, RefinedWeb), books, GitHub, Wikipedia, etc.

FineWeb-Edu filters massive web crawl toward educational text; a sample-10BT shard pack is a practical single-epoch target on one machine. Documents are separated with the GPT-2 end-of-text token id 50256.

Quality > scale (per token): Narrower, cleaner English educational prose can match older models trained on noisier, broader data — but comparisons across datasets are never perfectly “fair”; treat downstream evals as sanity checks, not court verdicts.

GPT-2’s WebText was never redistributed; the paper describes scraping outbound Reddit links (roughly 45 million URLs, on the order of ~40 GB of text). Community reconstructions such as OpenWebText attempt the same recipe. GPT-3’s mixture (Common Crawl–derived mass, books, Wikipedia, etc.) is likewise not a public download — Common Crawl alone is extremely noisy (ads, tables, tickers), so modern practice leans on curated mixtures (C4, RefinedWeb, RedPajama / SlimPajama-style packs).

FineWeb targets high-quality Common Crawl at huge scale (on the order of 15 trillion filtered tokens in the full build). FineWeb-Edu applies an additional educational filter — Hugging Face documents on the order of ~1.3T “educational” and ~5.4T “highly educational” tokens in the full Edu release; the public pipeline uses a large LLM judge (e.g. Llama-3 scale) to score educational value. We use the sample-10BT shard pack here: 100 shards × 100M tokens each, with shard 0000 reserved for validation. Preprocessing (download + pretokenization) is often ~30 minutes of wall time on a capable box, depending on bandwidth and CPU parallelism.

DataLoader: token shards & streaming chunks

Text is pre-tokenized with the GPT-2 BPE tokenizer from Chapter 8 (50257 IDs). Pre-tokenize once into uint16 numpy shards (~100M tokens each). At runtime, maintain (shard_idx, pos), fetch windows of length B*T+1, split into inputs and targets shifted by one.

For distributed training, stride the global pointer by world_size so each rank consumes disjoint token streams; advance by B*T*world_size per global step.

Documents are separated with the GPT-2 end-of-text token 50256 (Chapter 8). Shards are commonly stored as uint16 numpy arrays because every legal GPT-2 token id fits in 16 bits.

On TinyShakespeare, loss can fall toward ~6.6 instead of zero because most of the 50257 vocabulary never appears in a 1M-character slice. The optimizer can crush logits for absent tokens (drive unused columns toward large negative values), harvesting “easy” loss reductions without fully solving next-token prediction on frequent bytes — a useful debugging reminder that low loss can hide narrow coverage.

Training loop infrastructure

A minimal loop: optimizer.zero_grad(set_to_none=True) → forward+loss under autocast → loss.backward() → clip_grad_norm_ → optimizer.step(). Log running train loss, periodically evaluate validation loss, sample text, and run benchmarks.

loss.backward() accumulates into .grad fields (+=), so forgetting zero_grad poisons the step. loss.item() moves a scalar from device to host for logging. Device mismatches often come from tensors created on CPU (e.g. token buffers) — reassign buf = buf.to(device) because .to returns a new tensor rather than mutating in place.

For timing GPU work, wrap measurements with torch.cuda.synchronize() (when using CUDA) so you do not stop the stopwatch while kernels are still queued.

Mixed precision: bfloat16 + torch.autocast

TF32 speeds matmuls while tensors still “look like” float32. bf16 autocast runs large ops in bfloat16 while keeping sensitive reductions (softmax, LayerNorm, loss) in higher precision where PyTorch chooses to.

Unlike classic float16, bf16 shares the fp32 exponent width — often no gradient scaler required. Wrap only forward + loss in autocast; leave backward and optimizer steps in default precision.

Memory bandwidth: Many Transformer training steps are memory-bound. Halving activation footprint can beat naïve FLOP arithmetic on paper.

On an NVIDIA A100, marketing sheets quote on the order of ~19.5 TFLOPS of dense FP32 tensor-core throughput versus much larger peak rates for TF32/BF16/FP16 — often quoted ~8× speedups moving from FP32 matmuls to TF32 internals while still storing FP32 tensors in PyTorch. Real training gains are usually smaller than the peak ratio (commonly ~3× in practice on GPT-2–shaped models) because the system is memory-bandwidth limited: tensor cores sit idle waiting on HBM traffic. High-bandwidth memory is on the order of ~2 TB/s class on modern cards — enormous, yet still the bottleneck for elementwise-heavy schedules.

Empirical timing ladder (single-GPU, B=16, T=1024, TinyShakespeare-scale overfit loop — your absolute ms will vary): ~1000 ms per step naive FP32 → ~300 ms after enabling TF32 matmuls → ~300 ms with BF16 autocast (already near bandwidth-bound) → ~129 ms after torch.compile → ~95–96 ms after fused attention. Throughput moves from on the order of ~50k tokens/s in the TF32/BF16 band up to ~125k+ tokens/s once compile + FlashAttention-class kernels land.

torch.compile for throughput

model = torch.compile(model) traces the forward graph, removes much Python per-op overhead, and enables kernel fusion (fewer HBM round-trips). First iterations pay compile cost; steady-state step time often drops sharply.

Caveat: compiled graphs can interact badly with some dynamic evaluation paths (sampling, certain custom eval loops). It is reasonable to disable compile selectively while those issues are debugged.

PyTorch’s own guidance: speedups come primarily from reducing Python overhead and reducing GPU read/write traffic. A concrete micro-example is GELU: an eager schedule may launch separate kernels for cube, scale, add, tanh — each round-tripping through global memory. A compiled graph can fuse those elementwise ops so one chunk of activations stays on-chip through the full nonlinearity, then writes once.

At the hardware cartoon level: CPUs talk to DRAM; GPUs add high-bandwidth memory (HBM) and hundreds of streaming multiprocessors (SMs) with on-chip L1/L2/registers. Data streams from HBM → chip for math → back to HBM; kernel fusion minimizes those hops.

+

Faster steps, better GPU utilization on A100/H100-class hardware.

−

Longer startup; occasional hard-to-read errors in dynamic control flow.

Flash Attention via scaled_dot_product_attention

Vanilla attention materializes a large [B,H,T,T] score matrix in HBM. FlashAttention reorders the computation using online softmax tricks so that full matrices need not be stored — often faster despite more FLOPs because memory traffic dominates.

In PyTorch 2.x, torch.nn.functional.scaled_dot_product_attention dispatches to fused backends (including flash) when shapes and hardware allow.

Why compile isn’t enough: Flash attention is an algorithmic rewrite, not something a generic compiler reliably discovers from four separate kernels (matmul → mask → softmax → matmul).

FlashAttention (Dao et al., 2022; FlashAttention-2 refines the scheduling) replaces the naive attention sequence with a fused kernel that never materializes the full [T×T] score matrix in HBM. For T=1024, a single head at batch one still implies on the order of a million attention weights per head — prohibitive bandwidth-wise if written literally. The trick builds on an online softmax formulation (NVIDIA, 2018) that maintains running statistics so normalization can stream. That earlier work states the hypothesis plainly: “We propose a way to compute the classical softmax with fewer memory accesses and hypothesize that this reduction in memory accesses should improve softmax performance on actual hardware.” FlashAttention can do more FLOPs than the naive decomposed version yet run several times faster because it avoids HBM round-trips — the canonical paper reports large speedups (e.g. ~7.6× in their GPU regime) when memory was the bottleneck.

Vocabulary padding: 50257 → 50304

50257 is prime-ish and awkward for GPU tiling. Rounding up to 50304 (divisible by large powers of two) aligns GEMM shapes with efficient kernels. Extra rows act like never-used tokens; optimization drives their logits down like any out-of-distribution symbol.

50304 = 50257 + 47 \quad\text{“dummy” tokens; } 50304 \bmod 64 = 0

Trade-off: Slightly more FLOPs and memory in the embedding / head — often still a net win when kernels avoid slow tail tiles.

CUDA kernels tile work into multiples of 16 / 32 / 64. “Ugly” dimensions force boundary micro-kernels that process ragged tails slowly. Padding vocabulary to 50304 (highly composite — divisible by 64, 128, etc.) aligns the huge embedding / LM-head GEMMs with fast tiles. Empirically, expect a few percent shaved off step time once everything else is optimized; on some PyTorch stacks the win can be much larger (~30% class improvements have been observed when tail tiles were especially painful) — always measure on your build.

Learning rate: linear warmup + cosine decay

Follow GPT-3’s recipe: warm up from a tiny LR to max_lr over a fixed token horizon, then cosine-decay toward min_lr = ratio · max_lr. For a 10B-token run with 2^19 tokens/step, 375e6 warmup tokens ⇒ warmup_steps = 375e6 / 2^19 (≈715).

The GPT-3 paper specifies linear LR warmup over the first 375 million tokens, then cosine decay down to 10% of the peak LR over the first 260 billion tokens, holding the 10% floor while training continues to 300 billion tokens on the largest runs. The training script sets total steps so that warmup_steps = round(375e6 / tokens_per_step) — e.g. tokens_per_step = 2^{19} = 524{,}288 ⇒ 715 warmup steps — and trains for one epoch over a 10B token pack: 10^{10} / 524{,}288 ≈ 19{,}074 optimizer steps (plots may show nearby counts if logging subsamples or if the run uses a slightly different tokens-per-step product). That is not a literal 300B-token GPT-3 schedule; it is the same functional shape with horizons resized to the dataset.

Paper-faithful nuance

GPT-3’s cosine horizon is shorter than the full training length — the LR sits at 0.1 × peak for the tail. Many small-scale reproductions instead cosine all the way to the final step for simplicity.

Practical note

Warmup lengths around 715 steps are mild; some practitioners use far fewer warmup steps at 124M scale without catastrophe. Treat the paper numbers as a strong default, not a uniqueness theorem.

\mathrm{lr}(t) = \begin{cases} \frac{t+1}{W}\,\eta_{\max} & t < W \\ \eta_{\min} + \tfrac12(\eta_{\max}-\eta_{\min})(1+\cos\pi\frac{t-W}{T-W}) & t \ge W \end{cases}

Weight decay & fused AdamW

GPT-3 uses Adam with β₁=0.9, β₂=0.95, ε=1e-8, plus weight decay 0.1 applied to “2D” parameters (weights in matmuls / embeddings), not biases or LayerNorm γ/β.

In modern PyTorch, AdamW (decoupled weight decay) is the standard drop-in: treat it as the variant you want unless you are deliberately reproducing historical L2-on-gradient quirks.

w_{t+1} = w_t - \eta\, \hat m_t / (\sqrt{\hat v_t}+\epsilon) - \lambda \eta\, w_t \quad\text{(decoupled AdamW view)}

When available, fused=True in torch.optim.AdamW batches optimizer kernels — another small but free throughput win on CUDA.

PyTorch historically defaulted fused=False for compatibility; guard with inspect.signature(torch.optim.AdamW) if you support older installs. A fused kernel can shave a few milliseconds per step once the model is already compile- and attention-optimized — in timed runs, dropping from ~93 ms to ~90 ms per step has been observed purely from fused AdamW on GPT-2–shaped workloads.

Typical parameter accounting: on the order of ~50 tensors receive weight decay (matrices + embeddings) while ~98 small tensors (biases, LayerNorm gains) sit in the no-decay group — only ~100k parameters skip decay, the vast majority are regularized.

configure_optimizers pattern

Split parameters into decay vs no-decay groups. Pass weight_decay only on the decay group; keep betas=(0.9,0.95), eps=1e-8 per GPT-3 table.

Gradient accumulation (effective batch size)

GPT-3 reports batch sizes in tokens (~0.5M). If a single forward pass only fits B·T tokens per GPU, accumulate k micro-batches before optimizer.step() so effective tokens per step matches the recipe.

Because CrossEntropyLoss defaults to mean over tokens, divide each micro-batch loss by k before backward so gradients match one large batch.

Toy sanity check (MSE): Four scalar examples with MSELoss(reduction='mean') produce gradients scaled by 1/4. If you instead run four backward passes on single-example means and sum gradients, you have accidentally optimized the sum objective — gradients differ by exactly the missing normalizer. Fix: divide each micro-loss by grad_accum_steps (equivalently multiply the summed loss by 1/k) so that k serial backwards re-create the mean over the large logical batch.

\text{Let } L = \frac{1}{BT}\sum_{i=1}^{BT} \ell_i.\quad \text{Micro-step } j \text{ uses } \tilde{L}_j = \frac{1}{k}\cdot \frac{1}{|\text{micro}|}\sum_{i\in \text{micro}_j} \ell_i \;\Rightarrow\; \sum_{j=1}^{k} \tilde{L}_j \text{ matches the full mean gradient.}

Concrete token accounting for GPT-3-small-style settings: target 2^{19} = 524{,}288 tokens per optimizer step. With B=16, T=1024, each micro-forward processes 16{,}384 tokens, so single-GPU accumulation requires 32 micro-steps before optimizer.step(). At ~100 ms per micro-forward on a tuned A100-class GPU, that is ~3 s per optimizer step — acceptable because you are simulating an enormous logical batch.

Distributed Data Parallel (DDP)

Launch N processes with torchrun --nproc_per_node=N train.py. Each process binds to one GPU via CUDA_VISIBLE_DEVICES / local rank, runs identical code, consumes different data shards, and averages gradients with all_reduce after the last micro-step of accumulation.

Use model = DDP(model, device_ids=[local_rank]); access hyperparameters and optimizer config on model.module. Guard logging so only global rank 0 prints.

Gradient sync timing: Disable cross-rank synchronization on interior accumulation steps; only sync on the final backward of the accumulation cycle — otherwise you waste bandwidth.

Launch with torchrun --standalone --nproc_per_node=8 train.py (adjust for your machine). Environment variables RANK, LOCAL_RANK, WORLD_SIZE tell each process which GPU to bind (cuda:LOCAL_RANK). After wrapping with DDP, use model.module when you need the underlying GPT (e.g. configure_optimizers).

The sanctioned pattern toggles with model.no_sync(): around interior micro-steps; an equivalent implementation sets model.require_backward_grad_sync = (micro_step == grad_accum_steps - 1) so only the final loss.backward() triggers all_reduce. Average the logged train loss across ranks with dist.all_reduce on a tensor holding the running sum.

With 8× GPUs each doing B·T = 16·1024, you inject 131{,}072 tokens per micro-step across the node, shrinking required accumulation from 32 steps to 4 to hit 2^{19} tokens per optimizer step. Call dist.destroy_process_group() on shutdown so processes exit cleanly.

8-GPU and 1-GPU runs do not bitwise-match despite identical hyperparameters because DDP changes how shards straddle epoch boundaries when the global token pointer advances by world_size · B · T. For debugging, shrink the logical batch so both setups run the same number of accumulation steps with aligned boundaries, then compare traces.

Gradient clipping (max_norm=1.0)

After loss.backward(), compute the global L2 norm across all gradients. If it exceeds max_norm, rescale gradients uniformly so the norm equals the cap. This dampens rare explosive minibatches.

\textbf{g} \leftarrow \textbf{g} \cdot \min\left(1,\;\frac{\theta}{\|\textbf{g}\|_2}\right)

Early in GPT-2 training from scratch, total gradient norms in the ~30 range are common, then they settle below 1.0 as the model exits the “everything is wrong” regime. Sporadic spikes usually merit investigation — bad data, too-large LR, or numerical edge cases.

Hellaswag evaluation

Hellaswag is a multiple-choice commonsense completion benchmark. For small LMs, score each option as the average token negative log-likelihood (or sum) under teacher forcing; pick the lowest-loss continuation. Random guessing ≈ 25%.

Each example provides a shared story prefix and four endings. Distractors are not random sentences — they are adversarially sourced (often LM-generated) so that machines find them challenging while humans remain strong. The original paper reports ~95% human accuracy versus roughly ~48% for top models of its era; modern LMs now saturate the set (~96%), so treat it as a smooth, early-signal metric for small models rather than a frontier benchmark.

Scoring pipeline (completion-native): Build a batch of four rows. Row i concatenates the same context tokens with candidate ending i. Lengths differ, so pad to a common T and provide a mask that is zero on padded positions and one on real continuation tokens. Run a forward pass, compute per-token cross-entropy on the continuation slice only, average over valid tokens, then select the argmin. This is intentionally harder than “multiple-choice with all options visible at once” setups, which let the model compare answers in one context — a luxury 124M-scale models cannot exploit.

Open GPT-2 124M lands around ~29–30% under this completion-style scoring — barely above chance, but a useful early signal curve during training.

Reference accuracies (same completion-style harness): GPT-2 124M ≈ 29.5% (often reported as 29.55%); GPT-2 XL reaches roughly ~49%. Eleuther LM Harness numbers can differ if their wrapper uses an easier MC format — always compare protocols, not just headline percentages.

Training curves, validation, & samples

Log train loss every step (or moving average), validation loss every N steps on a held-out shard, Hellaswag every few hundred steps, and text samples with a separate RNG so sampling does not perturb training stochasticity.

A practical logging rhythm from full training stacks: evaluate validation every 100 steps (including step 0) by resetting a dedicated val loader and averaging ~20 fixed batches; run Hellaswag every 250 steps when dynamic compile/sampling bugs are absent; write plain-text logs (train/val/hellaswag) for matplotlib-style postplots.

Interpreting curves: On FineWeb-Edu, a reproduced model’s validation loss can drop below the OpenAI 124M checkpoint evaluated on the same held-out shard even though GPT-2 was trained on WebText — the distributions differ, so this is a sanity check, not a claim of strict superiority. On Hellaswag, a strong FineWeb-Edu run may cross the GPT-2 124M line after ~10B tokens while the original model saw on the order of ~100B tokens — plausible because English-only educational text is information-dense per token, capacity is freed from multilingual/code noise, modern optimizers help, and benchmark contamination cannot be ruled out without a full dedup audit.

Epoch ripples: If loss wiggles with the shard index, suspect insufficient shuffling between epochs (serial shard order + repeated document adjacency). Remedies: permute shards each epoch, shuffle within shards, or add a strided random access path.

Checkpointing: On a cadence of every few thousand steps (e.g. 5,000), persist model.state_dict() from the raw module (not the DDP wrapper) for inference-only resume. Full training resume also needs optimizer.state_dict(), RNG states, and step counters — Adam’s m/v buffers are not optional if you want bitwise training continuity.

GPT-3 scaling table, timing, & compute

GPT-3 documents how max_lr and batch tokens scale with model width/depth. The 124M-scale row pairs a higher LR (~6e-4) with smaller batches than multi-billion models — always cross-check OOM limits on your hardware.

The GPT-3 trainer uses Adam with β₁ = 0.9, β₂ = 0.95, ε = 10^{-8}, global gradient clipping at 1.0, and weight decay 0.1 on matmul/embedding weights (not biases / LN). Data are consumed without replacement until an epoch boundary. The paper also describes a linear batch-size ramp in tokens; many small reproductions skip the ramp because it complicates bookkeeping — the dominant effect is systems throughput early in training when gradients are highly correlated.
