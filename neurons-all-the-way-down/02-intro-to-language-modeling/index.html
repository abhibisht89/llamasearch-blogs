00

What is makemore?

makemore is the small educational repository that accompanies this track: the goal is to spell out every line, like a from-scratch autograd core, but for sequence models. It generates more examples that resemble a dataset you give it. A classic demo uses names.txt: on the order of 32,000 given names (one per line), drawn from public sources such as U.S. government name statistics. After “training” on that list, the model emits new strings that feel name-like but are usually not in the original data — useful if you want fresh, pronounceable labels rather than copying the corpus.

Concrete samples from a trained neural bigram (same family of model built here) can look like dontel, irot, zhendi: they scan as plausible syllables, yet they are not real entries from the list. That is the point — the system is learning local statistics, not memorizing rows.

Under the hood, makemore is a character-level language model. Each line is one training example; inside the line you work with a sequence of characters. The modeling task is to learn P(next character | previous context). In the bigram version, “context” is only the single previous character (plus special tokens for start and end of word).

Character-level

Tokens are letters (here lowercase a–z) plus one special token. Good for short strings like names; composes to full Unicode in production systems.

Bigram constraint

Only one character of memory. Many plausible continuations are ignored; generations can look “locally OK” but globally wrong.

01

Bigrams: sliding pairs in each name

Load the file, split into a Python list with read().splitlines(), then inspect length, min(len(w)), max(len(w)) — shortest names might be length 2, longest on the order of 15 characters. Every name packs many supervised examples: isabella tells you i is plausible after start, s after i, and so on, and that the word ends after the final a.

Consecutive pairs are easy to iterate with zip(w, w[1:]): for emma you get (e,m), (m,m), (m,a) — but that misses “start → first letter” and “last letter → end”. Fix by wrapping each word as ['.'] + list(w) + ['.'] (here . denotes the single special token used for both start and end), then zipping consecutive characters in that augmented list.

Every full name smuggles in many supervised transitions at once. Take isabella: the corpus is telling you that i is plausible right after the start token, that s often follows i, that a follows is, and so on, and finally that end is likely after the last a. One string on disk is a bundle of bigram events; the learner’s job is to aggregate all of them.

Iterate bigrams with zip

zip stops when the shorter iterator ends, so pairing w with w[1:] yields exactly the internal character pairs. Augment with . so the model sees transitions into the first character and out of the last.

02

Counting bigrams: dictionary first

Store counts in a dict b mapping (ch1, ch2) → count, using b[bigram] = b.get(bigram, 0) + 1. Many pairs appear once; frequent pairs (like n before end, or a followed by n) dominate. Sort with sorted(b.items(), key=lambda kv: kv[1]) to see rare vs common transitions.

On a tiny prefix of the corpus you might see tail bigrams that occur exactly once — e.g. qr or dz in the sorted-by-count view — while the head shows mass on endings: n before the stop token appears vastly more often than any quirky consonant cluster. Flipping the sort (largest count first) surfaces the stereotypes English names obey.

For speed and clean indexing, move to a 2D count tensor N: rows = first character, columns = second character. Use torch.tensor(..., dtype=torch.int32) for integer counts. Map characters to indices with s2i: sort the alphabet to get a stable order, assign a→1, …, z→26, and set s2i['.'] = 0 so the special token is row/column 0. That yields 27×27.

Why not 28×28 with separate start and end tokens? A first cut often uses two specials (call them S and E). Then the count matrix has structural zeros: the end token never starts a bigram, and the start token never appears as the second symbol in a real word, so whole rows and columns stay empty. You also get a cramped 2×2 corner where only the transition “start immediately followed by end” could fire — that is the empty-string edge case. Collapsing to a single delimiter . for both boundaries removes the dead bands, frees a row and column for actual letters, and matches how people annotate boundaries in small pedagogical setups. Offset letters by one (a→1, dot stays 0) so the integer 0 is reserved for the special token alone.

When you render N with something like matplotlib, you can annotate each cell with the letter pair and the integer count. Indexing N[i, j] returns a 0-dimensional tensor; call .item() to pull a plain Python int for printing — e.g. a cell might read 149 for how often a particular successor follows a particular predecessor in the full corpus.

To discover the letter inventory programmatically, concatenate the corpus into one string, wrap it with set(...) to drop duplicates, then sorted(...) so indices follow alphabetical order instead of hash order. You should see 26 lowercase letters before you add the special token to the mappings.

04

From counts to probabilities and sampling

Take row ix of N, cast to float, divide by the row sum to get a probability vector that sums to 1. That is the maximum-likelihood estimate:

P(next = j | current = i) = N[i, j] / Σk N[i, k]

Sample the next index with torch.multinomial (pass replacement=True as needed). Use a torch.Generator seeded for reproducibility. Start with ix = 0 (the . token), repeatedly sample next index, append i2s[ix] until you sample . again.

A worked draw from the first row of N (start token) might land on index 13, which maps to m — reasonable, because on the order of 2,500 of the ~32,000 names begin with m, i.e. just under 10% of the corpus. Conditioning on that m, you read row 13 for successor counts, normalize, sample again, and keep chaining until the stop token appears. One concrete trajectory is m → o → r → ., spelling mor before termination.

torch.multinomial is categorical sampling: imagine a roulette wheel cut into 27 slices sized by p. On a toy vector like [0.6, 0.3, 0.1], drawing many times with replacement=True yields roughly 60% zeros, 30% ones, and 10% twos — rare indices still appear, just rarely. Tie that randomness to a torch.Generator (seeded with something you can share) and torch.rand becomes reproducible as well, which matters when you compare runs across machines.

Bigram samples often look wrong: the model may emit a single letter as a “name” because it only knows “after this letter, how likely is end?” — not how long the word should be or what came earlier. From the model’s perspective, a lone h is not “the first letter h”; it is “we are in state h,” and if P(end | h) is nontrivial, stopping immediately is internally consistent. Longer strings can look like garbled but pronounceable shards — think fragments along the lines of yanuo or o’reilly-ish rhythm — because only pairwise glue is enforced.

Compare to a uniform model torch.ones(27)/27: every successor is 1/27 ≈ 3.7%, so the soup of characters has almost no English-name structure. Placing the trained bigram next to that uniform baseline makes it obvious that the empirical transition table is doing real work even when full words still look broken.

Terminology: running the model to produce text is often called decoding, inference, or generation — same iterative loop: sample or argmax the next token, feed it back as context (here, as the sole previous character).

05

Precomputing P and broadcasting row sums

Normalizing inside the sampling loop repeats work. Convert all counts to probabilities up front: P = N.float(), then divide each row by its sum. In PyTorch, N.sum(1) without keepdim gives shape (27) — when dividing (27,27) by (27), broadcasting aligns trailing dimensions and can accidentally normalize columns instead of rows.

Critical: use N.sum(dim=1, keepdim=True) so the divisor has shape (27,1). Then P / row_sums broadcasts the column vector across each row, producing row-normalized probabilities. With a 1D (27) divisor, the same numeric sums become a row vector under broadcasting rules — wrong normalization, subtle bug.

Prefer in-place ops like P /= P.sum(1, keepdim=True) when you want to avoid allocating a fresh tensor. Master broadcasting early: transformer-era code is full of batched matmuls and careful keepdim usage.

torch.sum axes, spelled slowly. On a 27×27 float tensor P, P.sum(0, keepdim=True) collapses rows and leaves a 1×27 row vector — column totals. P.sum(1, keepdim=True) collapses across columns and leaves a 27×1 column vector — one sum per row, which is what you want before dividing to get P(next | current). If you drop keepdim, that column of sums becomes a flat length-27 vector. Under broadcasting rules, a trailing length-27 tensor aligned against a 27×27 grid is interpreted as a row vector replicated down the matrix, which divides each column by the wrong statistic.

Numerical signature of the bug: after a mistaken divide, the first row of P might sum to something like 7 instead of 1, while some column accidentally normalizes to 1. The raw sum values along rows were correct before broadcasting; the silent insertion of a singleton dimension turns your column of row totals into a horizontal template that torch stretches vertically — normalizing the wrong direction.

Sanity check: after correct row normalization, P[0].sum() should be 1.0 (for a row that has any mass), and re-running the sampling loop with the precomputed P should reproduce the same draws as normalizing fresh rows inside the loop — same probabilities, less work per step.

Correct row normalization

keepdim=True preserves a dedicated axis for “per-row total.” Broadcasting stretches that column vector across columns of each row, so every row is divided by its own sum.

06

Likelihood, log-likelihood, and loss

Evaluate the model on the training bigrams. For each pair (ch1, ch2), look up p = P[ix1, ix2]. The likelihood of the full dataset under the model is the product of these probabilities — impractically tiny. Take logs: log-likelihood is the sum of log(p) (monotonic in the product). Flip sign for a loss: negative log-likelihood (NLL) — lower is better. Report the mean NLL per bigram so scale does not grow linearly with dataset size.

ℒ = −(1/N) Σi log P(yi | xi)

With 27 outcomes, uniform guessing gives log(1/27) per step, mean NLL ≈ −log(1/27) ≈ 3.30. Anything below that means the bigram statistics beat chance. A perfect model on the training set would approach 0.

Print individual bigram probabilities for a few training pairs and you will see a spread: many sit near the ~4% uniform guess (because 1/27 ≈ 0.037), while high-confidence transitions climb into the 30–40% range — evidence the table has learned sharp peaks where the data demands them.

log-likelihood = Σ log p(bigrami)   →   report mean NLL = −(1/N) Σ log p(bigrami)

On a tiny slice (say the first handful of names) the summed log-likelihood might land near −38 before you normalize by the number of bigrams; on the full names.txt training aggregate, the mean negative log-likelihood settles near 2.45 for the unsmoothed count model — the single-number quality score to remember.

Scoring an unusual name like andre can yield reasonable average log-probs; some edges such as ej are genuinely rare in this corpus, which drags the per-character average toward a middling log score even when the string “looks” fine to a human.

Append a rare bigram such as jq after andre and if N has a zero count for j→q, the model assigns 0% to that transition, so log(0) = −∞ — infinite loss. That is mathematically honest but numerically unusable.

Model quality metrics

  • ✓ Mean NLL — single summary; comparable across runs.
  • ✓ Per-bigram probs — often a few percent to tens of percent on real pairs.
  • ✗ Raw likelihood — underflows; avoid for computation.

Uniform baseline

If every next character were 1/27, mean NLL ≈ 3.30. Your trained bigram model landing near ~2.4–2.5 on the full name corpus reflects real structure — not human-level fluency, but better than i.i.d. letters.

07

Smoothing: fake counts

Model smoothing adds a small positive count to every entry before normalization — e.g. N += 1 — so no transition has probability zero. Larger additions push the model toward uniform predictions; smaller additions stay close to the empirical bigram table while fixing infinities in the log.

Concrete failure mode: evaluate a plausible-looking string that contains a bigram never seen in training — say jq after andre if your corpus never has j followed by q. The empirical P(q|j) is 0, so log P is −∞ and the reported NLL is unusable. Smoothing assigns a tiny but positive mass everywhere so logs stay finite; the model still “dislikes” rare sequences, but you can compare scores across strings.

Adding a positive constant to every cell before renormalizing is the textbook “pretend we saw each bigram a few extra times.” It behaves like a Dirichlet-style prior, preserves the row-stochastic interpretation of P, and guarantees finite logs — unlike clamping or ad hoc floors, which are harder to reason about and can break the relationship between counts and probabilities.

N′[i,j] = N[i,j] + k   →   P′(j|i) = N′[i,j] / Σj′ N′[i,j′]

As k grows, each row’s distribution approaches uniform: the fake counts dwarf observed counts. As k → 0, you recover the raw empirical table (and any zero stays zero). k = 1 is a common default “add-one” (Laplace) smoothing for discrete tables.

One line of smoothing

Before converting to floats or normalizing, add your fake count tensor-wide. Then rebuild P exactly as before.

Neural formulation: same bigram, different machinery

Build datasets xs (first character index) and ys (next character index) for every bigram in the corpus. A single name like emma yields five examples: (.→e), (e→m), (m→m), (m→a), (a→.). Convert lists to torch.tensor with integer dtype for indices.

API caution: PyTorch exposes torch.tensor and torch.Tensor. Prefer lowercase torch.tensor(data) when you want inferred dtype (integers stay integral). Uppercase Tensor constructors often default to float32. For index tensors, integer dtype matters before one_hot and embedding lookups.

For the five bigrams inside emma, the integer dataset lines up as: when the input index is 0 (the . token), the supervised next index is 5 (the letter e); when the input is 5, the targets want high mass on 13 (m); the two m steps both ask for 13 then 1 (a); the final step from a wants mass on 0 (return to .). Those five rows are the entire mini-batch for that one name before you scale to the full corpus.

One neuron

Matrix-multiplying a 5×27 one-hot block by a 27×1 weight column yields a 5×1 output — one linear neuron evaluated on five examples in parallel. That is already batched w·x.

27 neurons

Swap the column for a 27×27 matrix W. Now the product is 5×27: for each example you emit one logit per possible next character. Row i, column j is the activity of neuron j on example i, implemented as the dot product of example i with column j of W.

Neurons expect continuous inputs — not raw category indices. Use one-hot encoding: a vector of length 27 that is all zeros except a single 1 at the class index. F.one_hot(xs, num_classes=27) returns shape (num_examples, 27); cast to float before matrix multiply (one-hot often comes out int64).

Linear layer, logits, softmax

Initialize W ∈ ℝ^{27×27} (e.g. torch.randn). Multiply one-hot inputs by W to get logits — interpretable as unnormalized log-counts. Exponentiate to get nonnegative “pseudo-counts”, then normalize across the 27 outputs to sum to 1:

softmax(z)i = exp(zi) / Σj exp(zj)

Chaining logits → exp → normalize is the softmax layer. It maps arbitrary real logits to a valid probability vector; every step is differentiable for autograd.

Exponentiation is what turns signed logits into nonnegative “pseudo-counts.” Negative logits map to masses below 1 (for example exp(−1) ≈ 0.338); large positive logits blow up past 1. After the elementwise exponential you can read the tensor as the analogue of the integer count row from the tabular model, except the values are continuous positives.

Key insight: for one-hot input, xenc @ W selects a row of W. That mirrors the count matrix: previous character picks a row; the row defines a distribution over successors. Optimization discovers logits whose softmax matches the empirical bigram table.

Cross-entropy loss and training

For each example, read the predicted probability at the correct next-character index y. The per-example NLL is -log(probs[i, y]). Vectorized: build row indices torch.arange(N), index probs[torch.arange(N), ys], take log, mean, negate — same mean NLL as the counting model at convergence.

cross-entropy = −log pmodel(y_true | x)   (per example; average for batch loss)

Set W.requires_grad_(True). Run loss.backward(), then update W.data -= lr * W.grad (or use an optimizer). Reset gradients with W.grad = None (efficient in PyTorch) before the next step. With ~228k bigrams from 32k names, a moderate learning rate can drop loss toward ~2.45 — matching the count-based solution because the model class is the same.

Before optimization kicks in, a random W might assign only ~1% probability to the true next letter on several emma edges — e.g. e after . — producing a high average NLL around 3.76 for that word. Reseeding torch.randn can land you near 3.37 or worse purely by luck; that manual “resample weights until it feels better” game is instructive but it is not training. The point of gradients is to replace lottery guesses with a systematic descent direction.

After one serious update with learning rate 0.1, the same forward pass might read 3.74, then 3.72 on the next iteration — tiny steps because the problem is smooth and the rate is conservative. When you expand to all 228,000 supervised bigrams, you can crank the step size dramatically (rates on the order of 50 still work on this toy architecture) and watch the mean loss march into the 2.46–2.47 band, essentially reproducing the 2.45 count solution. The explicit counting estimator was already the maximum-likelihood answer; gradient descent is rediscovering the same table because the parametrization is expressive enough.

Micrograd-style regression

Earlier autograd exercises often minimized mean squared error on continuous targets. The forward pass still produced predictions and a scalar loss, backward still filled .grad, and updates still nudged every parameter opposite the gradient.

This chapter’s classification head

Here the targets are class indices, the loss is mean negative log-likelihood / cross-entropy, and the final layer is softmax on logits. Everything else in the training loop — graph construction, zeroing grads, stepping W — mirrors the same mechanical story.

How to read W.grad[i, j]: each entry measures the sensitivity of the loss to an infinitesimal nudge in that weight. A positive partial derivative means increasing that weight slightly would increase the loss, so gradient descent moves opposite the gradient. After backward, the gradient tensor matches W’s shape (27×27) entrywise.

To gather the predicted probability on the true next character for an entire batch, advanced indexing does the bookkeeping: probs[torch.arange(n), ys] pairs row i with label ys[i]. (Historically people reached for torch.arange; avoid confusing it with a legacy range spelling.) The mean of −log of those entries is exactly the vectorized loss you computed example-by-example in the loop.

Vectorized “pluck” of correct probabilities

For batch size n, row i of probs pairs with label ys[i]. Advanced indexing probs[torch.arange(n), ys] gathers those entries in one expression — the same values you would read in a small Python loop over examples.

index_probs.pyL1–5 / —
1ixr = torch.arange(n)
2sel = probs[ixr, ys]
3loss = -sel.log().mean()

Counting vs neural net

Count + normalize

Exact ML estimate for tabular bigrams. No optimization loop. Explodes combinatorially if you condition on many characters — tables become impossibly large.

One-hot × W + softmax

Same capacity here: each previous char picks a row of W. Gradient descent recovers the same probabilities. Scales to rich networks where you cannot store an explicit table.

Sampling from the neural version: encode current index as one-hot, forward through W, softmax, multinomial — you recover the same procedure as indexing a precomputed row of P when the weights match.

4# same row semantics when W is converged

Left: explicit table. Right: same row selected by one-hot multiply; softmax turns logits into probabilities.

Scaling argument: with only one previous character, a full 27×27 table is tractable. Condition on the last 10 characters and the state space has 27¹⁰ rows — impossible to store. Neural nets compress and generalize: you keep a fixed set of parameters and learn a function from context to logits. The training loop (softmax + NLL + backward) stays the same as you swap in deeper networks — only the forward path from characters to logits grows more elaborate, all the way to transformers.

Identical generative process at convergence: the counting matrix stores normalized frequencies directly; the neural matrix W stores logits such that softmax(W[row]) matches those frequencies. Sampling can use either representation — index a row of P or multiply a one-hot row by W and softmax — and you will emit the same stochastic names once optimization finishes, because both code paths implement the same conditional categorical.

Regularization: pulling W toward zero

Adding fake counts in the count world encourages smoother, more uniform rows. In the neural world, a parallel idea is weight decay / L2 penalty: add λ · mean(W²) to the loss. Minimizing it prefers smaller weights; if all logits were 0, softmax is exactly uniform. Picture each weight on a spring anchored at zero — the data term pulls logits apart to match transitions, while the regularizer pulls them back. Crank λ high enough and softmax flattens toward uniform, just like adding enormous fake counts everywhere; both encode a smoothness prior over conditional distributions.

loss_total = NLL + λ · (1/nweights) Σ Wij²

Combined loss in code

Keep the data term as F.cross_entropy (or manual NLL). Add a small multiple of (W**2).mean(). Tune λ on a dev set if you have one; here it is mainly for intuition.
